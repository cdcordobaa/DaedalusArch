## 3. What the instrument sees (zero-call, `cypher-interp`, scoring v1.3, check-correct on blocking findings)

| Puzzle / trap | New correct blocking findings on the trap (vs seed, not on clean) | Per sub-goal (hand reading) |
|---|---|---|
| P1 / trap | none | SG1 D4 **invisible**; SG2 D5 **invisible**: blind control |
| P2 / trap | FF-DS02 ×2 (`PlaceOrder.ts` → membership internals) | SG1 **visible** (the imports); SG2 D4 **co-located only** (the write has no finding of its own) |
| P2 / trap-alt | none (only the 2 planted FF-DS02 of the seed) | SG1 D10 **invisible**; SG2 D4 **invisible** |
| P3 / trap | none | SG1 H5 **invisible**; SG2 **invisible**: FF-P01 checks the vendor package only in the domain layer, so an application-layer runtime import raises nothing |
| P4 / trap | FF-S01 ×1 (`LoanGateway.ts` → `MemberService.ts`) | SG1 **visible**: positive control |

Two results worth noting:

- **P3 was expected to be partial and is invisible.** Adding the SDK to FF-P01's list (as HEXDDD-01 S1 did) covers
  the domain only; the seed's planted vendor-typed port is not flagged either. So P3 is a second blind-control puzzle.
- **P2 separates the routes.** The same behaviour is caught (FF-DS02) when reached by copying the planted import, and
  invisible when reached by duplicating the rule and writing through the published interface. That pair is a ready-made
  test of "does `mcp` help only where the rules see" within one puzzle.

The 9 HEXDDD-01 hand-read observations (case bank) all have **no matching finding**: the step scores carry only the
planted debt, and the one advisory FF-SO02 on `BookingRepository.ts` predates the s1 D4/H5 changes.
