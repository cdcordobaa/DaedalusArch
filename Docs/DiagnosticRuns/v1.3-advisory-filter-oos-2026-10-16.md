## 3. Reading

- **`cv05-no-logic`** removes about a quarter of FF-CV05 rows on both new sets: 0.40 of external FF-CV05 and 0.32 of wild. In the sample, every removal is a type-only file, DTO, port interface, error class, schema or config file, and its reason matches the file. One reason to check: `luizomf-clean-api … create-user-use-case.ts` is read as "type declarations only". In that repository the use-case file is the interface (its implementation lives under `application/`), so the reason is right, but it shows how much the option's effect depends on naming conventions.
- **`c03-core-only`** removes 92% of FF-C03 rows on the external set and 71% on the wild set, close to #139's in-sample 88% (dev, 120 → 14). That supports #139's argument: per-file instability > 0.8 outside the core is expected design. Note the cost: the option keeps FF-C03 only where a domain layer is declared. On the wild set, specs are inferred, so "domain" is ISE's guess.
- **`composition-roots`** almost vanishes on the wild set (5 rows). The name and role patterns match the dev-set and E1 conventions (`container`, `*.module.ts`, …). The large NestJS products in the wild set wire through framework modules that FF-C03 and FF-CV05 rarely flag. This is an honest "does not transfer" for the volume. It does not show the option is wrong.
- **`cv05-rollup`** is the lever that does not transfer. #139's in-sample 0.69–0.78 came from projects with no tests at all: the E1 cells, and dev variants without tests. Only one external repo (`dannielhugo-clean`, FF-CV05 on 68 of 72 files) crosses the 80% share, and no wild repo does, because real projects have tests. So #139's "biggest lever for E1-style output" is specific to agent-generated, untested projects. It is not a general noise fix.
- **`proposed` removes more out of sample on the external set (0.45) than in sample (0.33).** That is not "better". Without relevance labels, more removal can also mean more lost signal; the criterion said so in advance.
- **Blocking identity holds by construction and on data.** No blocking row moved in any of the 156 set × repo cells (90 external, 66 wild).

## 4. Side observation (not part of U1's measure)

While debugging the sample on partial data, one FF-CV05 row was checked **incorrect**: `ext/dannielhugo-clean src/app/deposit/deposit.interactor.ts`. Its test, `deposit.interactor.spec.ts`, sits next to it. The tool's FF-CV05 sees only files in the analysed program, and spec files are typically excluded by the project's tsconfig. So FF-CV05 can report "no test" for a file that has one. The row is not in the final seeded sample (the pool grew when the wild runs finished). The rule's precision on external code deserves its own check-correct pass over all FF-CV05 rows. Not done here.

## 7. Reproduce

```bash
npm ci
# clone each results/v1.3-external/selection.json entry to <clones>/ext__<id> and each v1.3-wild selection entry to
# <clones>/wild__<id> at its sha; node --import tsx scripts/v1.3/wild-run.ts prepare --repos <dir of wild clones by id>
# copy v1.3-wild's selection.json and results/v1.3-wild/repos/<id>/ise-spec.yaml to <wild-specs>/{selection.json,<id>.yaml}
npx tsx bin/firewall.ts evaluate --project <clones>/ext__<id>/<root> --spec results/v1.3-external/specs/<id>.yaml \
  --symbolic-only --format json --engine cypher-interp --advisory-filter <set> > <runs>/ext/<set>/<id>.json
npx tsx bin/firewall.ts evaluate --project <root> --spec <wild-specs>/<id>.yaml --tsconfig <root>/tsconfig.wild.json \
  --symbolic-only --format json --engine cypher-interp > <runs>/wild/none/<id>.json
npx tsx scripts/v1.3/advisory-filter-oos.ts --runs <runs> --clones <clones> --wild-specs <wild-specs>
npx tsx scripts/v1.3/check-correct.ts --jobs <jobs with real paths> --sample results/v1.3-advisory-filter-oos/sample.json --out <dir>
```
