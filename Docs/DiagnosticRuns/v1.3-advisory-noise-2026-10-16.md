# Advisory (WARNING) noise: per-rule table and opt-in precision filters, 2026-10-16

Branch `v1.3-advisory-noise`, from `origin/v1.3` at `2c64d1d5`. **Development-set and E1 work. Descriptive; nothing here is pre-registered or tuned against the hold-out.** Every option below is a **proposal for the author**: it is implemented and measured, it is **OFF by default**, and nothing in the default output changes.

Script: `scripts/v1.3/advisory-noise.ts` (offline: no Neo4j, no model call). Outputs: `results/v1.3-advisory-noise/measure.{json,md}`. Code: `src/advisory-filter/`. Tests: `tests/unit/advisory-filter/advisory-filter.test.ts` (18 tests).

**Summary.**
- **Advisory output is dominated by two rules.** FF-CV05 (test pairing) is 86% of all advisory rows (2,610 of 3,034 across the dev set and E1). FF-C03 (instability) is another 9%. Every FF-CV05 row is *correct*: the file really has no co-located test (1,426/1,426 dev, 1,184/1,184 E1). So the noise is about relevance, not truth.
- **The judge dismissed 191 of the 252 advisory rows it saw.** By rule: FF-C03 116/120, FF-C02 30/30, FF-CV05 42/86, FF-CV03 2/2, FF-P02 1/4. The dismissal reasons fall into five clusters, and four of them can be tested from the source: orchestrators, composition roots, outer adapters and no-logic files.
- **Four options, taken together ("proposed"), remove 163 of the 191 dismissed rows (0.85 [0.80, 0.90]) and 1 of the 61 confirmed rows (0.02 [0.00, 0.09]).** They cut advisory volume by 33% on the dev set (1,606 → 1,082) and 33% on E1 (1,428 → 953). The one confirmed row removed is an FF-C03 row on a file whose real defect stays visible: a blocking FF-S01 row and an advisory FF-P02 row on the same file remain. The proposed set also includes two options with no measured effect (`c04-entry-points`, `so-framework-members`); they change no number here.
- **Blocking results are byte-identical under every option** on all 71 dev variants and all 65 E1 cells. The filter only reads advisory rows; it never touches blocking rules, tiers or Cypher text; and it lists every removed row in the report instead of dropping it.
- **What is left is mostly FF-CV05 on real logic files in projects with no tests at all.** In 62 of 65 E1 cells, FF-CV05 fires on nearly every file. An optional roll-up (one row per untested project) takes E1 from 1,428 to 137 advisory rows. It is a presentation choice, not a precision fix, so it is reported separately.

> **These are in-sample numbers.** I designed the options after reading the judge's dismissals on this same dev set, so the dismissed-removed share is optimistic. The judge's verdicts are one model's single run, not labels. §7 lists what would make this a real estimate.

Reading the table:
- **FF-CV05**: the rule is true and very loud, and the judge dismisses about half of its rows. The dismissed half is files with nothing to test: types, error classes and in-memory pass-throughs.
- **FF-C03**: nearly every row is dismissed. The rule flags *any* file with instability > 0.8, but the Stable Dependencies Principle expects leaves (use cases, adapters, composition roots) to be unstable. The judge confirmed only 4 rows: domain-kind files depending outwards, plus one use case that injects a concrete adapter. The defect behind each of those 4 is also reported by a blocking or a more specific rule.
- **FF-C02**: all 30 dismissed, on two files: a composition root, and a use case whose 12 imports are mostly ports.
- **E1** has no judge labels. Its mix differs from the dev set: more FF-C03 on infrastructure servers and app files, and 51 FF-P02 rows the judge never saw.

## 3. The options

All options live in `src/advisory-filter/advisory-filter.ts`, and every one of them is off by default. Each acts as a post-filter on finished findings:
- it reads only the finding row, the file's own source (one syntactic TypeScript pass, `source-facts.ts`) and the spec's layer model;
- it acts only on rows whose tier is `advisory`: it checks the sealed table for the style, and the report's blocking set when the report has one;
- it acts only on its own rules (`OPTION_RULES`).

No Cypher template, rule tier or blocking rule changes. In the pipeline the filter runs in `AssembleReportCommand`, after the report is built and before scrubbing and schema validation. It is enabled by `firewall evaluate --advisory-filter <list|all|none>` (default `none`) or by `PipelineConfig.advisoryFilter`. Removed rows move to a new optional report field, `advisoryFilter.suppressed`, with the option and the reason; the report schema is amended to allow it. Scores, tiers, functionResults and the verdict are computed before the filter and do not change.

| Option | Rules | Removes a row when … |
|---|---|---|
| `cv05-no-logic` | FF-CV05 | the file has no runtime logic: type declarations only; a barrel; or only enums, constant data and classes whose members are fields plus a constructor of `super(…)` and `this.x = <data>` (DTOs, error subclasses). Path rules: config (`config/`, `*.config.ts`, `env.ts`) and migrations. This extends ADR-026's name-based `DECLARATION_ONLY_GLOBS` with a content check. |
| `cv05-no-branching` | FF-CV05 | the above, **or** the file has no control flow, no callbacks inside function bodies, and no function body longer than two statements (thin delegation) |
| `composition-roots` | FF-C02, C03, C04, CV05 | the file is a composition root: by the APG v2 name patterns (`main`, `container`, `di`, `*.module.ts`, `test*` roots, …), by the `composition-root` layer role, or by structure (no class, no control flow, and it instantiates imported classes from two or more layers) |
| `c03-core-only` | FF-C03 | the file's layer kind is not `domain`. A file with no layer is kept. |
| `c02-abstract-imports` | FF-C02 | the fan-out minus the imports of type-only targets (`import type`, or a target module that declares only types) is ≤ the threshold. Graph count minus abstract targets, so it never recounts more than the graph. |
| `c02-size-scaled` | FF-C02 | fan-out ≤ threshold × max(1, √(files / 40)) |
| `c04-entry-points` | FF-C04 | `main`, `server`, `index`, `cli`, `app`, `bootstrap` or `start` at the source root, a `package.json` `main` / `bin` entry, or a composition root |
| `so-framework-members` | FF-SO01, FF-SO02 | the counts drop to the thresholds or below without accessors, lifecycle hooks and serialisation members, and without Logger / ConfigService / ModuleRef / Reflector injections; generated files are also removed |
| `cv05-rollup` | FF-CV05 | the rule fires on ≥ 80% of the project's source files (and ≥ 5 rows): the first remaining row stands for the project, and the others are listed as rolled up |

Per rule, proposed set (dev | E1): FF-CV05 1,426 → 1,038 | 1,184 → 884; FF-C03 120 → 14 | 159 → 3; FF-C02 30 → 0 | 21 → 2. FF-P02, FF-C06, FF-C01, FF-CV03 and the rest are unchanged.

**Per option.**
- **`cv05-no-logic`** removes every dismissed FF-CV05 row of the "types" and "error subclass" kind (HttpTypes, BusinessError) and no confirmed row. In the E1 audit sample (`measure.md`), all 12 removed rows are type-only ports and repositories, DTO interfaces, error classes or a container. I read each one, and each matches its reason.
- **`cv05-no-branching`** also catches the dismissed in-memory pass-through repository (14 rows). But in E1 it removes domain behaviour too, for example `Task.canMarkDone()` / `withStatus()` and thin controllers. Only one judge prompt supports it.
- **`composition-roots`** catches `container.ts`, `testContainer.ts`, `ServiceFactory.ts` and `app.ts` on the dev set, and wiring modules (`createApp.ts`, `*Module.ts`, `buildControllers.ts`, route-wiring files) on E1. A first version flagged an E1 `http.ts` with request handlers because it instantiates error classes. Requiring "no control flow" fixed that, and the fix is in the measured version.
- **`c03-core-only`** has the largest effect on the noisiest rule. The one confirmed row it removes, `hexagonal/v03 … FindAvailableRoomsService.ts`, is the planted "use case injects concrete adapter" defect. That defect is still reported on the same file by blocking **FF-S01** (to `InMemoryRoomRepository.ts`) and by advisory FF-P02. On the layered style the business layer is kind `domain`, so `OrderService.ts` stays. That is deliberate: the judge confirmed the same file in v02 and v08, where it imports the view and Express.
- **`c02-abstract-imports`** removes `BookRoomService` (12 imports, 5 of them pure port interfaces) and nothing on E1, where the FF-C02 rows are servers and app factories.
- **`c02-size-scaled`, `c04-entry-points`, `so-framework-members`** have no effect here. All dev and E1 projects are under 40 files. The two E1 FF-C04 rows are unused DTO files: real dead code, correctly kept. The five E1 SRP/ISP rows are 11–12-method services and 6–7-method repository interfaces with no framework members. There is no evidence of noise to remove.

**Dismissed rows the proposed set keeps (28):**
- FF-CV05 `InMemoryMemberRepository.ts` ×14: only `cv05-no-branching` removes these.
- FF-C03 `layered OrderService.ts` ×11: these cannot be told apart, at file level, from the confirmed v02/v08 rows on the same file.
- FF-CV03 ×2 (naming) and FF-P02 ×1.

## 5. Recommendation (for the author)

1. **Adopt `cv05-no-logic` and `composition-roots` as opt-in options.** Neither removes a confirmed or manifest-true row. Both extend exemptions that ADR-026 and the APG v2 scope already grant by name (declaration-only files, composition roots), now decided from content and structure. Together they remove 74/191 = 0.39 [0.32, 0.46] of the dismissed rows and no confirmed row, and cut advisory volume by 27% on the dev set (1,606 → 1,172) and 25% on E1 (1,428 → 1,065).
2. **Adopt `c03-core-only` as opt-in, and consider an ADR on FF-C03 itself.** Per-file instability > 0.8 is the expected state of a leaf module, so outside the core the rule mostly reports correct design. The option keeps the reading where SDP actually applies: domain-kind files, which is exactly where the judge confirmed FF-C01 and FF-C03. Re-tiering or retiring the rule needs an ADR and is not proposed here.
3. **`c02-abstract-imports`: optional and low impact.** It is sound (dependencies on ports should not count as coupling to volatile code), but it acts on one dev file and no E1 file.
4. **Do not adopt `cv05-no-branching` yet.** It removes the in-memory pass-through the judge dismissed, but it also removes small domain behaviour that a test should pin.
5. **`cv05-rollup` is the biggest lever for E1-style output, but it is a presentation decision.** The projects have no tests at all, so one row per project carries the same information as hundreds. It rolls up confirmed rows rather than losing them; the suppressed list keeps every file. Whether a report should show "this project has no tests" or one row per untested file is the author's call.
6. **Keep `c02-size-scaled`, `c04-entry-points` and `so-framework-members` in code but off, or drop them.** They do nothing on any set we have. They become testable only on larger real projects (§7).

A default-off v1.3 profile of options 1–2 (plus 3 if wanted) would reduce noise without touching what the tool blocks on.

## 6. Blocking results stay byte-identical

- **By construction**: a row is considered only when its tier is advisory. An option that would match a blocking row keeps it; the unit test runs every option with a blocking tier and expects every row to be kept. Rules, tiers and Cypher are untouched.
- **Checked on data**: for every option and both option sets, on 71 dev variants and 65 E1 cells, the JSON of the blocking rows is identical before and after (`blockingIdentical` in `measure.json`).
- **Report level**: a unit test assembles a v1.3 report with a blocking FF-S01 row and two FF-CV05 rows and applies `cv05-no-logic`. Every report field except `violations` and the new `advisoryFilter` is byte-identical, the blocking rows are identical, and the report validates against the amended schema. With no option the report object is returned unchanged.

## 7. What this does and does not show

- **In-sample.** I wrote the options after reading the judge's dismissals on the same 71 variants, so the 0.85 dismissed-removed share is optimistic. Next steps:
  - run the proposed set on the sealed hold-out set or on the 14 `v1.3-wild` repositories (their stored output has no advisory rows, so this needs a live run);
  - have the author audit the E1 sample in `measure.md`.
- **The judge is not ground truth.** It is one model, one run, filter-and-explain revision v2, and its verdicts on metric rows are unlabelled. FF-CV05 was sampled: 10 prompts covering 86 of 1,426 dev rows.
- **E1 has no judge or relevance labels.** For E1 there are only volumes and a seeded sample of 12 removed rows per option. Its source comes from judge prompts, not the original trees; 6 rows had no source and were kept.
- **No live pipeline run.** Neo4j was not available in this environment. The pipeline wiring (`AssembleReportCommand`, the CLI flag, the schema amendment) is covered by unit tests and by type checking, not by an end-to-end `evaluate`. The measurement applies the same function to stored findings.
- **Rule correctness labels** say that FF-CV05 rows are true (no co-located test). They say nothing about relevance. "Meaningful" labels were never collected (the labeller hit its usage limit; `v1.3-labelling-2026-10-15.md` §3).

## 8. Reproduce

```bash
npm ci
npx tsx scripts/v1.3/advisory-noise.ts            # writes results/v1.3-advisory-noise/measure.{json,md}
npx jest --maxWorkers=2 tests/unit/advisory-filter
# in a live run (Neo4j):
npx tsx bin/firewall.ts evaluate --project <dir> --spec <spec> --format json --advisory-filter cv05-no-logic,composition-roots,c03-core-only
```

Two runs of the script give byte-identical `measure.json`. The full unit suite (`jest --maxWorkers=2 tests/unit`) has the same 8 failing suites (12 tests) with and without this change: `u5b`, `generators`, `mutation/expected` and `replay-no-binary` need files or binaries this environment lacks. All other suites pass.
