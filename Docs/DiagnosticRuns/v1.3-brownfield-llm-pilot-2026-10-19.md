## 5. What this does not show

- **The Claude-vs-Claude shared-prior risk is the main limit, and this pilot makes it worse, not better.** A and B are
  Claude-written readings (V10). The derived specs are Sonnet's readings of the same README. A κ of 0.90 and 27/27
  findings on luizomf may mean "the same vendor reads the same README the same way", not "the declared norm was
  recovered". The design's cross-vendor arm (Gemini, §7) is the named mitigation, and it was not run.
- **Not the graph's value.** G made one graph call per session and cited none. The pilot says nothing about whether
  graph facts help when a model uses them. A frame that requires stat citations would be a different treatment.
- **Not correctness.** A is a reference, not truth. Zeldaplay disagreements with A are not labelled as errors.
- **Not the hard cases.** The pilot pair has no DDD or hexagonal repo, where the miner was weakest. It also exercises no
  function or exclude change.
- **Tiny n.** 2 repos, 3 runs per arm. No interval is meaningful at this size: Wilson intervals are in `score.json` and
  are too narrow, because the units cluster in repos.
- **Absorption (design §3, F6) was not computed.**
- **A deviation from the design argv.** `--safe-mode` was dropped from both arms because it disables every
  `--mcp-config` server: `claude --safe-mode mcp list` reports "No MCP servers configured", and the first G probe saw
  `mcp_servers: []`. To keep what it protected:
  - sessions run from copies of the clones outside the repository, so DaedalusArch's own `CLAUDE.md` cannot load as
    an ancestor (the driver checks there is no ancestor `CLAUDE.md`);
  - `--disable-slash-commands` turns off skills;
  - `--restricted` ignores settings files;
  - the driver stops unless the init event lists exactly the facts server for G and no server for R.
  The sessions also use the real `HOME` (the judge route) instead of the loop's empty `HOME`: the login lives in the
  macOS Keychain, which an empty `HOME` hides.

## 5a. Mechanism check (zero calls; `scripts/v1.3/bf-01-mechanism.ts`, `results/v1.3-brownfield/llm-pilot/mechanism.derived.{json,md}`)

**Question (author, NS-03).** Did G's graph tools replace reading? Where G differs from A, does G follow the actual
import structure while A follows the README's intent?

**Reading behaviour, from the transcripts:**
- No G session used `Read`. Each G session called `folder_dependency_matrix` once, then only `Glob` and `Grep`. G's
  README citations came from `Grep` line hits.
- All 3 luizomf R sessions read `README.md`.
- On zeldaplay, neither arm read any file: both only globbed.
- No session called `query_graph`.

**Method.** For every file under `src/` whose layer kind differs between the session's spec (as written) and A, count
its order violations: its import edges, in either direction, between mapped files that point from an inner layer to an
outer one. The session's map and order are compared with A's map and order, on the spec-free parser graph. The classes:
- **kind label only:** the same layer, a different kind;
- **omission:** A maps the file and the session does not;
- **re-placed, 0 violations under both:** the code allows both placements;
- **code-consistent:** fewer violations than under A, that is, right about the code but different from the intent;
- **plain error:** more violations than under A.

| Repo, arm | Files differing / compared (3 runs) | Kind label only | Omission | Re-placed, 0 violations under both | **Code-consistent** | **Plain error** |
|---|---|---|---|---|---|---|
| luizomf G | 27/375 | 27 | 0 | 0 | **0** | **0** |
| luizomf R | 27/375 | 27 | 0 | 0 | **0** | **0** |
| zeldaplay G | 73/255 | 0 | 55 | 18 | **0** | **0** |
| zeldaplay R | 78/255 | 0 | 36 | 42 | **0** | **0** |

**Result: 0 "right about the code, different from the intent" and 0 plain errors, in both arms.**
- On luizomf every difference is the `main` layer. A gives it `kind: application`; all 6 derived specs leave it at the
  default `infrastructure`. The placement is identical: outermost, the same files.
- On zeldaplay, A's map and every derived map give 0 order violations. The import graph is compatible with both readings,
  so the code cannot side with either. G's distinct pattern is **omission**: 55 file-runs left unmapped (`validators/`,
  `*/models/`, `options/`, config constants), against 36 for R. R instead re-places `models/` and DTOs into `domain`.
- So, on this pair, the hypothesis "G is right about the code where it departs from intent" is **not supported**. There
  is no code-vs-intent drift for G to have found. What is supported is the behaviour: the graph call replaced reading,
  and it cost coverage (omissions), not correctness.
