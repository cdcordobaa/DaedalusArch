# v1.3 brownfield: the deterministic rule miner against the 15 declared external specs (2026-10-18)

> **Exploratory (brownfield track, map part C2 mined; `ops/01-instrument-map.md:175`, `ops/02-defensibility-conditions.md:76`).**
> Zero calls: no model, no API. Engine `cypher-interp` only; Neo4j was never started. Nothing is pre-registered and no
> threshold is claimed. The miner (`src/rule-mining/`) and every existing script it calls were used unchanged.

**Question.** If a brownfield repository had no spec, how much of its hand-written spec would the existing
deterministic miner (`daedalus mine-rules` / `propose_rules`, `Docs/v1.3/rule-mining.md`) recover? It is scored on
four things: the file-to-layer mapping, the rules, the verdict, and the blocking findings. The references are the 15
wave-1 external specs (author A, `results/v1.3-external/specs/`) and the blind second author (B,
`results/v1.3-spec-author-b/specs/`).

**Reading.** The miner gets the *verdict* right for the wrong reasons. It picks the right *kind* of rule (dependency
rules, high precision). But it puts only about half the files where the author put them, and then it reports almost
none of the author's blocking findings. Of the 10 repos where both specs fail, 7 share **no** blocking finding
(`score.json` rows, `a.findings.both`). Most of the gap comes from the layer map, not from the miner (§4.4).

## 2. Method (fixed before scoring; definitions in `scripts/v1.3/brownfield-score.py` docstring)

1. **Checkouts.** The 15 entries of `results/v1.3-external/selection.json`, cloned blobless at their pinned SHAs into
   `tmp/brownfield-clones/<id>` (git-ignored via `tmp/` in `.gitignore`). zeldaplay-api is sparse on `apps/api`. Git hooks
   were disabled, and nothing was installed, built or run from the clones. All 15 `HEAD`s equal the pins
   (`results/v1.3-brownfield/run-provenance.json`). Total size is about 33 MB.
2. **Mining.** `scripts/v1.3/brownfield-mine.ts` takes the same snapshot as `scripts/v1.3/rule-mining-wild.ts`:
   the analysis root's `src/` plus its flattened tsconfig. It then runs `analyseSnapshot` → `proposeFromAnalysis`, the
   default emission with no `--min-confidence`. 13.7 s in total for 15 repos. A second run gave 15/15 byte-identical
   mined specs. Outputs: `results/v1.3-brownfield/mined/<id>.mined.yaml` and `<id>.json` (every rule with every exception).
3. **Evaluation.** `firewall evaluate --symbolic-only --engine cypher-interp --scoring v1.3 --format json` on each
   repo under A, B and the mined spec, one run at a time. That is 45 runs, 179 s, with exit codes 0 or 1 only
   (`results/v1.3-brownfield/evaluate/{a,b,mined}/`, `evaluate/runs.tsv`). **Reproduction check:** at this commit A gives
   283 blocking findings with the same per-repo counts as #133 and K2, and B gives 319.
4. **Mapping.** `scripts/v1.3/spec-author-agreement.ts labels` (unchanged) labels every git-tracked `.ts` file under
   the root with each spec's layer (`results/v1.3-brownfield/labels/`). The universe is files under `src/` that the
   reference spec does not exclude. Layer names differ across styles, so files are compared on the layer **kind**, which
   is the K2 basis when names differ.
   *Recall* = files the reference maps that the mined spec maps to the same kind / files the reference maps.
   *Precision* = the converse over the files the mined spec maps.
5. **Rules.** A rule is a blocking-tier fitness function that the evaluation executed (`tiers.blocking.rules`), matched on
   `functionId`. In 5 repos the mined style differs, and there FF-S01 matches by id while compiling to a different
   template (`dependency-direction` instead of `dependency-direction-graph`). With a strict template match, recall is
   31/87.
6. **Findings.** The edge key of `ops/notes/g08-violation-identity.md` §2.1, with the rule id ignored. An edge is
   (file, target), a package import is (file, package), and a cycle is its node list rotated to the smallest path.
   FF-S01 and FF-S03 on one edge count once, so A has 273 distinct keys rather than 283.
7. **Surfaced.** A declared finding counts as *surfaced* when one of the mined rule's exceptions names the same
   (file, target), or for a cycle, an edge between two of its nodes. This is the §3.2 measure of `Docs/v1.3/rule-mining.md`.
8. **Oracle arm** (isolates the miner from ISE, as in `Docs/v1.3/rule-mining.md` §1.4): it uses the same graph and
   components, mined over A's layer map, kinds, style and exclusions (`brownfield-mine.ts --oracle-specs`, outputs in
   `results/v1.3-brownfield/oracle/`). It is compared with A's allowed layer graph restricted to the layers that hold a
   file.
9. **Intervals.** Wilson 95% per unit; pooled, this treats files, rules and findings as independent, so it is too
   narrow. A repo-cluster percentile bootstrap gives the pooled intervals (10,000 resamples, seed 20261018).

## 4. Findings

### 4.1 Mapping: about half the files land in the author's layer kind

- Pooled recall is 0.473 and precision 0.474, with cluster intervals of about [0.33, 0.64]. κ by kind is 0.43 pooled over
  `src/` (`score.md`). The K2 tool over all tracked files gives κ 0.50 against A and 0.49 against B, with 0/15 and 1/15
  repos at ≥ 0.80 (`results/v1.3-brownfield/agreement-am/agreement.md`, `agreement-bm/agreement.md`).
- **ISE picks the declared style on 10/15** (`mined/mine-runs.json`). All 3 DDD repos are wrong (ddd-forum and
  event-sourcing as clean, finance as nestjs), and so are 2 of 3 hexagonal repos (both as clean). DDD mapping recall is
  144/515. In ddd-forum, 227 of 270 files go to `infrastructure` (`labels/labels-m.json`).
- Mapping agrees with B about as well as with A (recall 0.487, precision 0.474). The miner is not closer to one author
  than to the other.

### 4.2 Rules: the miner picks the right kind of rule but only the dependency kind

- Rule precision is **0.857** (36/42). Every extra mined blocking rule is a cycle, purity or repository rule that A's
  preset also carries in other repos (`FF-S02` 2, `FF-P01` 3, `FF-P03` 1). Recall is **0.414** (36/87).
- Declared blocking rules the mined spec never executes, counted in repos (`score.json`): FF-S04 9/9, FF-P06 9/9,
  FF-P03 8/9, FF-P01 5/12, and every DDD strategic and tactical rule (FF-DS01–02, FF-DT01–04: 3/3 each). This repeats the
  method limit in `Docs/v1.3/rule-mining.md` §3.2 and §7 (N05: non-dependency rules are not mined).
- **Verdict-relevant rules only** (rules with ≥ 1 finding): recall 10/26 (0.385), precision 10/14 (0.714).

### 4.3 Verdict agreement is high, but mostly base rate

- The mined spec matches A on **13/15** (κ 0.66), and B on 12/15 (κ 0.53) (`score.md`; the K2 tool gives the same,
  `agreement-am/agreement.md`). For comparison, two blind authors match on 10/15 (κ 0.21). This run reproduces that
  N02 figure exactly (`agreement-ab/agreement.md`).
- This **does not** make the miner a better spec author than B. A says fail on 11/15, so a constant "fail" would
  already match A on 11/15. The bootstrap interval of the mined–A κ is [0.00, 1.00].
- **The verdicts agree for different findings.** Of the 10 repos where both fail, 7 share no blocking finding. Only
  vivify, nest-products and finance share any (2 each). Counting a fail as concordant only when it shares a finding,
  mined and A agree on 3 + 3 = 6/15.
- The 2 flips: bulletproof-nodejs (A pass → mined fail, 10 FF-S03 skips that the mined layered order forbids) and
  conduit (A fail → mined pass; A's one finding comes from a test file, §2 erratum 3 of
  `Docs/DiagnosticRuns/v1.3-external-set-2026-10-16.md`).

### 4.4 Blocking findings: almost none recovered end to end; with the declared layers, 42% of dependency findings surface

| | Dependency findings of A (distinct keys carrying FF-S01–S04) | All blocking findings of A | Source |
|---|---|---|---|
| Reported by the engine under the mined spec | 4/189 | 6/273 | `score.md` "Pooled" and "Oracle arm" (`dependencyKeysVsA`) |
| Surfaced as a miner exception (ISE layers) | 5/189 | 7/273 | same |
| Surfaced as a miner exception (**oracle**: A's layers) | **80/189** (0.42; Wilson [0.36, 0.50]) | 80/273 (0.29; Wilson [0.24, 0.35], cluster [0.09, 0.38]) | `score.md` "Oracle arm" |

Every surfaced finding is dependency-shaped (80 of 80). Per-rule counts in `score.md` sum to 193 because 4 keys carry two
dependency rules (FF-S01 with FF-S03 or FF-S04). By rule (oracle): FF-S01 53/123, FF-S02 27/61, FF-S04 1/2, FF-S03 0/7.
Every non-dependency rule is 0.

- **Most of the end-to-end loss is the layer map, not the miner.** With the author's layers, dependency findings go
  from 5/189 to 80/189. The oracle allowed layer graph (default "full" emission) has precision 0.802 (69/86) and recall
  0.683 (69/101). The bootstrap intervals are [0.72, 0.89] and [0.55, 0.81], against 100% / 79% on the development set
  (`Docs/v1.3/rule-mining.md` §3.1). Of the oracle's direction rules, 75/80 forbid what A forbids. Rare-edge rules
  manage 2/12 and unobserved rules 25/42, the same ordering as §3.1.
- **When a violation is the team's habit, the miner learns it as a norm.** pvarentsov-clean: A's 18 FF-S01 findings are
  `presentation → infrastructure` imports. Even with A's layers, the miner *allows* that pair because the code uses it
  throughout (oracle `full` graph includes `presentation>infrastructure`; `oracle/pvarentsov-clean.json`), so 0/18
  surface. luizomf (0/9) and event-sourcing (0/20) are the same pattern. This is the closed-world limit
  (`Docs/v1.3/rule-mining.md` §7.1) seen from the other side.
- **The ceiling.** B's specs recover 184/273 = 0.674 of A's findings (Wilson [0.616, 0.727]), with precision 0.630
  (`score.json` `blindAuthorBvsA_findings`). A second human-style author reproduces two thirds of the findings; the
  miner reproduces 2%.

projects ISE's layer map is exact, so the miner's dependency reach (44/45) carried straight through to the engine. On
the external set the layer map is the bottleneck. Where the layers are right, the miner still loses the violations a
team commits systematically.

## 6. What this does not show

- **Not correctness or meaning.** A is a reference, not truth. A and B are both Claude sessions (V10,
  `Docs/DiagnosticRuns/v1.3-spec-author-reliability.md`), and a mined spec that disagrees with A may be as defensible as
  A in places (B disagrees with A on a third of the findings). No finding was labelled.
- **Not the miner at its best.** Default emission, with no `--min-confidence`, no `--style` and no human review. The
  `--style` override (the declared style given to ISE) was not run. It would probably lift the 5 wrong-style repos; that
  is an untested estimate.
- **Not an LLM baseline.** This is the zero-call floor that a derivation pilot would have to beat. It says nothing about
  what an LLM would derive.
- **Not independent units.** Files, rules and findings cluster in repos: 3 repos hold 207 of A's 273 keys (neoteric 71,
  ddd-forum 86, finance 50). The pooled Wilson intervals are too narrow, so use the cluster bootstrap. With n = 15, the
  verdict κ intervals span [0, 1].
- **Kind-level mapping is coarse.** `composition`/`main` count as `application` kind and the clean `presentation` ring
  as its own kind. A mined spec that folds controllers into infrastructure (as B also did) loses mapping recall without
  necessarily changing a rule.
- **Rule matching by id.** Five FF-S01 matches cross templates (§2.5). The mined spec switches off unbacked functions,
  so "executed" is the right basis, but a rule present in both can still mean different layer pairs.
- **APG v2 rules not run.** `component-adp-cycle` and `deep-import-*` in the mined specs validate, but `firewall evaluate`
  does not execute them (`Docs/v1.3/rule-mining.md` §7.7). The miner's component exceptions are counted only in the
  "surfaced" rows.
- **Snapshot scope.** The miner reads `src/` only, so test helpers outside `src/` that A maps are out of its reach. The
  mapping universe is restricted to `src/` for that reason.
- **One instrument commit** (`5856478a`, working tree of `ops/working-surface-2026-10-18`). The scripts added here are
  new (`scripts/v1.3/brownfield-mine.ts`, `scripts/v1.3/brownfield-score.py`) and have no unit tests.
