# v1.3 development set B (devset-b), 2026-10-16

**devset-b is development data written by Claude (an AI model), not a hold-out.** The variants and their manifests
were written by Claude agents on 2026-10-16 from the rule definitions (`Docs/v1.3-reference-notes.md`,
`Docs/v1.3-hexagonal-notes.md`, `Docs/v1.3-ddd-notes.md`, `Docs/v1.3/style-rule-sources.md`, `Docs/v1.3/rule-tiers.md`,
each spec). Those agents did not read the tool's rule implementations or any earlier results. The tool and its
judge-free symbolic rules were also built with Claude, and the authors knew the reference set, so the cases are not
independent of the tool's construction. Read every figure below as a development-set measurement of the tool as it
is on `origin/v1.3` (133c261a). It is not a validity estimate.

**Nothing in the tool was changed.** `git diff origin/v1.3 -- src bin presets` is empty. The only changes are to the
harness: a `--set devset-b` flag on the reference runner and a new scorer. The 71 reference cases
(`tests/fixtures/v1.3-reference`) and `results/v1.3-reference/*` are byte-identical to `origin/v1.3`.

## Why

`Docs/v1.3/validation-protocol.md` asks for at least 20 planted violations per style. The 71-case reference set falls
short of that for every style. Its cells are small (9 to 13 blocking expected findings per style), and its look-alike
and clean negatives are the same cases the fixes were tuned on.

## Layout and commands

- `tests/fixtures/v1.3-devset-b/<style>/`: byte copies of the reference project, spec and expected graph, plus the new
  variants in the same formats and schemas. Each style also has `devset-b.json`, which gives every variant's role
  (`baseline`, `violation`, `look-alike`, `clean`) and the rule it targets. The schema reserves kind `clean` for the
  baseline, so look-alikes are stored as `near-miss` with ids `n2x`-`n3x`, and further clean variants as `near-miss`
  with ids `n6x`. The copied `clean` baseline is in-sample: it is used only as the runner's baseline and is excluded
  from every devset-b count.
- Run: `ue-baseline-live.ts --set devset-b --out results/v1.3-devset-b`, then
  `validate-reference.ts --set devset-b --from-raw results/v1.3-devset-b/raw`, then
  `devset-b-score.ts --base results/v1.3-devset-b`.
- Engine: v1.3 has no `--engine cypher-interp`, so the run used Neo4j 5.26.24 community from the tarball with APOC
  5.26.24 core. Provenance, timings and the order of commits and runs are in
  `results/v1.3-devset-b/run-provenance.json`. Every manifest was committed before the tool ran on its style.

## Definitions

- **found x/n**: expected findings of the rule on violation variants that a tool row matched, out of all of them
  (recall).
- **reports right x/n**: tool rows of the rule that match an expected finding, out of all tool rows of the rule, over
  every devset-b variant (precision).
- **false alarm**: a blocking-rule row on a look-alike or clean variant.
- Intervals are 95% Wilson (z = 1.959964), as in `ue-score.ts`.
- Matching is the runner's (`compare.ts`): rule + file, with the target required to be equal when both sides carry
  one.

Two views:

- **literal**: the runner's matching unchanged. It was the only view declared before the run, so it comes first.
- **cycle-containment**: declared after the literal result was seen. The manifests name a cycle by its smallest file
  and the next one, the reference convention, which was written when every planted cycle had 2 files. The tool's
  FF-S02 row carries the whole cycle path, so a planted 3-file cycle that the tool reports exactly still fails the
  literal file-set key and counts as 1 miss plus 1 extra row. This view keys a cycle row to the expected cycle finding
  whose two files it contains. Nothing else changes between the views.

## How to read this

- **Coverage of the protocol floor.** Every style now has at least 20 planted blocking findings in devset-b (21 to
  25). Per rule the cells are still small: 2 to 9 for most rules, with S01 at 31 pooled. Most per-rule intervals are
  wide (lower bounds 0.34 to 0.78 at 100% observed).
- **Optimism.** Claude wrote the cases from definitions that Claude also implemented, after the tool had already been
  fixed against a reference set written the same way. High recall here mostly shows that the tool handles the
  constructs its authors think of. The ddd author also predicted from the DDD notes that v33 and v34 (FF-DT03: a public
  non-readonly field, and a mutator not named `set...`) might be missed, and both were found. The non-tool evidence
  that counts is still the blind manifests and the sealed hold-out, neither of which this run touched.
- **What it found.** Two tool-side weaknesses, both in FF-P03: same-file local interfaces are accepted as ports, and an
  aliased type-only port import is not resolved. It also found one scoring-convention defect, 3-file cycles under the
  literal cycle key. None of these was fixed here, as this run's brief required.
