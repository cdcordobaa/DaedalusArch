# v1.3 external set, wave 3: 25 more human-written, pre-2023 TypeScript backends, 2026-10-16

Branch `v1.3-external-set-3`, cut from `origin/v1.3-external-set-2` (PR #181) at `b1d05f7a`. This is an exploratory evidence unit, like waves 1 (PR #133) and 2 (PR #181). It adds no AI-DLC workflow and no pre-registration, and `aidlc-docs/` is untouched. **It depends on #133 and #181**: wave 1's outputs are on #133 only, and this branch carries wave 2's commits.

**Why.** Waves 1 and 2 put 35 human-written projects (7 per style) against a corpus otherwise written by Claude-family models. Wave 3 adds 25 more, 5 per style, under the same protocol, so that pooled figures rest on 60 projects (12 per style). It also adds what waves 1 and 2 lacked on this branch: a deterministic correctness check of every blocking finding (PR #167's X1 method), run on wave 3 and, for the first time, on wave 2.

**What this report does not contain:**
- No meaningfulness labels. "Correct" below means the stated import exists and breaks the rule *under the spec*; it says nothing about whether an architect would want the dependency changed.
- No recall. What the tool misses on these projects was not measured.

## 1. Projects

**Selection rule, the same as waves 1 and 2, except one bound:**
1. Public, with a permissive licence in a licence file at the pin (MIT, ISC, BSD, Apache).
2. A TypeScript backend that claims the style in its README, its repository description or its folder structure.
3. Pinned to the last first-parent commit before 2023-01-01 on the default branch. When that commit is a bot commit, the last human commit must predate ChatGPT (2022-11-30) with no `src/` change in between.
4. **18** to 300 non-test, non-`.d.ts` `.ts` files under `src/` of the analysis root (the task set 18; waves 1 and 2 used 15).
5. Not in the Study 1 corpus, not one of the 14 W1 wild repositories (PR #114), not in wave 1 or wave 2, and not named in either wave's rejection list.
6. Made explicit in this wave: not a copy, a course re-implementation or a derivative of a project already used.

The rejections are grouped in `selection.json`.

## 4. Correctness, checked by reading the code (X1, as in PR #167)

**Method, unchanged from #167.** `scripts/v1.3/check-correct.ts` reads each repository's source with the TypeScript compiler API and the project's own `tsconfig.json` (no `node_modules`, as in the evaluation) together with the committed spec, and never the graph. For each finding it confirms that the stated import exists at the stated line, reaches the stated target, and that both ends fall where the spec's globs put them so as to break the rule's condition. It labels each finding `correct`, `incorrect` or `not-checkable`, with evidence. The **negative control** perturbs every finding so its claim is false (line moved to another statement, target swapped, cycle broken) and requires the checker to reject each one.

**Sample: every blocking finding**, not a sample: 211 in wave 3, and 342 in wave 2 (cloned at wave 2's pins for this purpose). Each wave's 30 seeded advisory findings are checked as a secondary table.

| Wave 2 | 342 | 342 | 0 | 0 | 1.000 [0.989, 1.000] | 485 of 485 rejected (166 line, 172 target, 147 cycle; 29 skipped) |

They include three of the spec-driven groups above: pallavi's `asyncHandler` rows, q00's entity cycles, and meetinger's cross-context imports.

### Incorrect findings: one systematic false positive, in an advisory rule

Every blocking finding is correct. **One advisory finding in wave 2's sample is incorrect**, and it exposes a systematic defect:

- **Example.** felixle-node-core: FF-CV05 reports `src/application/usecases/auth/auth/create-auth-by-email/CreateAuthByEmailHandler.ts` as having no test file. `CreateAuthByEmailHandler.spec.ts` sits next to it.
- **Cause.** The extractor's default exclusions drop `**/*.spec.ts` and `**/*.test.ts` from the graph (`src/apg-extractor/types.ts`, `DEFAULT_EXCLUDE_PATTERNS`). The FF-CV05 template (`src/fitness-compiler/cypher-templates.ts`, `test-file-pairing`) asks whether a `File` node with the `.spec.ts` or `.test.ts` name exists. Under the defaults such a node never exists, so the rule reports every mapped, non-barrel file that has a co-located test.
- **Extent.** I counted FF-CV05 findings whose co-located `<name>.spec.ts` or `<name>.test.ts` exists on disk at the pin:

| Wave | FF-CV05 findings | With a co-located test (false) | Projects affected |
|---|---:|---:|---|
| 1 | 642 | 72 | luizomf-clean-api 45, zeldaplay-api 15, conduit-ports-adapters 7, dannielhugo-clean 3, vivify 1, nest-products-hexagonal 1 |
| 2 | 785 | 66 | felixle-node-core 47, monstarlab-nestjs-starter 16, staart-api 3 |
| 3 | 780 | 16 | nalhin-movies 14, hexagonal-banking 2 |
| **Pooled** | **2,207** | **154 (7.0%)** | 11 of 60 |

  The other 93% are files with no co-located test. Those are "correct" under the template, but only because the template can never see a test. In effect, FF-CV05 under the default exclusions counts mapped files, not untested ones.
- **Impact.** FF-CV05 is advisory in every style, so no verdict and no blocking count changes. It is 62–73% of all advisory findings in every wave, so advisory volume is inflated by a rule that cannot detect what it claims to detect. #167's wave-1 sample did not hit a co-located case, which is why this was not seen before.
- **Not fixed here.** The task forbids tuning rules. A fix would be to let FF-CV05 see test files, either by checking the filesystem or by extracting test files as unmapped nodes; it belongs in a separate change.

**Other advisory results.** Wave 3: 21 correct, 0 incorrect, 9 not-checkable. The checkable ones are FF-CV05 20 and FF-S03 1; the not-checkable ones are metric templates (FF-C03, FF-C04, FF-C05, FF-C06, FF-P02). Wave 2: 15 correct, 1 incorrect (the case above), 14 not-checkable.

## 7. Limitations

- **One model family for selection and specs, as before.** Wave 3's specs were written by five sub-agents, not one context, but all are Claude-family. A blind human spec would remove the residual same-vendor influence, and the checker shares the spec with the tool: a wrong glob gives findings that are "correct under the spec" (pallavi's 22 `asyncHandler` rows are the clearest example).
- **Correct is not meaningful.** Several large groups are plausibly correct but not meaningful to an architect: ORM entities with bidirectional relations as cycles (q00 15, ruslanguns 8), a utility middleware imported by every controller (pallavi 22). Nothing was labelled for meaningfulness.
- **Thinner, less known projects.** Wave 3 has 0 to 79 stars, 18 to 144 files and 3 products. The earlier waves and corpora had used the well-known ones.
- **Weak style claims (3).** q00, twiddlle and canario rest on structure and repository description.
- **Pre-2023 is a proxy, not proof.** 7 last human commits fall after Copilot GA, and four projects have six or fewer commits.
- **Extractor gaps.** msc29's unresolved `domain/*` aliases (half its graph) and the test-file exclusion that breaks FF-CV05. Neither was fixed (no tuning).
- **No `node_modules`**, so package base types are not in the graph.
- **One run per project**; engine parity with Neo4j was not re-checked (no Neo4j by instruction). Wave 2 established 19-of-19 parity for this interpreter.
- **Lint.** `eslint` does not cover `scripts/` in this repository's config (the same holds for wave 2's scripts); `tsc -p tsconfig.scripts.json` is clean and the ported unit test passes (`jest --maxWorkers=2`, 9 of 9).
