# v1.3 floor probe: will Study 2's `none` arm ever break a defining rule?

**2026-10-16. Feasibility probe only.** The agent in every trajectory below is **one Claude session** (the session that
wrote this report), working by hand in a scratch directory. It is not the loop harness, not the loop pilot
(`Docs/v1.3/pilot-outcome-memo.md`) and not Study 2. The sample is 6 tasks × 2 arms × 4–5 steps from one agent, so every
number here is a count, not an estimate. No sealed directory was read; no Cypher template, tier table or spec was changed.

Data: `results/v1.3-floor-probe/` (`summary.json`, `summary.md`, one directory per task with `none/` and `tool/` step
records and snapshots, `correctness/`, `instrument-probe/`, `scripts/`).

| `none`-arm steps after step 1 with a **new** blocking finding (pilot memo §3 identity rule) | **4 / 22**, all layered |
| Rules that fire | Only **FF-S01** dependency-direction (31 instances) and **FF-S03** no-layer-skip (65). Never FF-S02, S04, P01, P03, P06 |
| Correctness of the fired findings | 96 / 96 `correct` (`scripts/v1.3/check-correct.ts`, blocking tier) |

| Tool-arm fix behaviour | 3 fixes, all at step 1 (4, 3, 6 findings), 4–6 files, +2 to +11 LOC; check_diff agreed with the graph on every step; 0 blocking after every fix and at every later step |

## 1. Why this probe

E1 (Study 1): 0 of 65 generated projects broke any rule that v1.3 treats as blocking (`Docs/v1.3/study1-addenda.md`).
The Study 1 spec-level differences lived only in advisory metrics. Study 2's main outcome is blocking violations per
step and their slope (`Docs/v1.3/study2-outline.md` §4). If the `none` arm also never breaks a blocking rule, every arm is
at zero and the contrast measures nothing. Study 2 runs once, so this had to be probed on non-study tasks first.

## 2. Method

### 2.1 Tasks (`results/v1.3-floor-probe/tasks.json`)

| Task | Style | Source | Steps (pressure) |
|---|---|---|---|
| `shelter-adoptions` | hexagonal | pilot task, verbatim | adoptions (first adapter), fostering (cross-module), SMS (second adapter), audit trail (across every layer) |
| `garden-plots` | hexagonal | new | plots + PayBee (first adapter), AquaTick water meters (second inbound adapter), work days (cross-feature reuse), committee dashboard (reporting shortcut), failed-payment hotfix (quick fix) |
| `food-bank` | hexagonal | new | pickups, FreshLink feed (polling adapter), SnapText reminders (new use case + adapter), network CSV report (reporting shortcut), allergen hotfix (quick fix) |
| `market-vendors` | layered | pilot task, verbatim, restyled Clean → Layered | stalls + PayLane, fees and settlement, TillWave poller, audit log and statements |
| `youth-league` | layered | new | teams and fixtures, WeatherNow (first adapter), referees (cross-feature reuse), league tables (reporting shortcut), result-correction hotfix (quick fix) |
| `hive-health` | layered | new | inspections, BuzzScale webhook + TextHive SMS, treatments and harvests (cross-feature reuse), quarterly health report (reporting shortcut), false-swarm hotfix (quick fix) |

The four new tasks follow the pilot rules (`Docs/v1.3/pilot-tasks.md` §1): new domains, plain product language, no
layer, port or pattern named. They were written without reading the sealed list; **before reusing any of them the author
must check them against the sealed Study 2 domains**, as for the pilot tasks.

### 2.2 Prompt frame ("minimal spec level")

The styled loop frame (`scripts/lib/loop/prompts.ts`, `style.ts`): the style sentence plus the preset-derived folder
sentence, and nothing else about the architecture. Hexagonal: "Organise the code following Hexagonal Architecture (ports
and adapters)." + "… exactly five folders: src/domain, src/application, src/adapters/inbound, src/adapters/outbound and
src/config." Layered (no loop style exists for it; written in the same form): "Organise the code following Layered
Architecture (presentation, business and persistence layers)." + "… exactly three folders: src/persistence, src/business
and src/presentation." Evaluator specs: `presets/hexagonal.yaml`, `presets/layered.yaml`, unchanged.

### 2.3 Arms

- **`none`.** Each step implemented by hand as a time-pressed developer, type-checked with the E1 harness options
  (pinned skeleton `typescript 5.9.3`, `express 5.2.1`), and committed. **All six `none` trajectories (28 steps) were
  written before any of them was scored**, so no firewall result reached the `none` arm, including across tasks.
- **Scoring (both arms).** `daedalus-arch evaluate --symbolic-only --engine cypher-interp --scoring v1.3` on every step
  snapshot (`scripts/evalsnap.py`). Blocking = `Docs/v1.3/rule-tiers.md` for the style.
- **`tool`.** After each step: MCP `check_diff` on the step's diff (the `checkDiffTool` handler from `src/mcp-server`)
  and the full evaluation; every blocking finding fixed before the next step; then both re-run (`scripts/toolrec.py`).
  - Hexagonal: the step code is the `none` code (one agent writes the same code twice; re-typing it would only add the
    noise of an agent that now knows the result). Nothing was ever flagged, so nothing was fixed: the tool trajectories
    are replays, scored and checked step by step.
  - Layered: step 1 is the `none` step-1 code, flagged and fixed by hand. Each later step is the `none` step's change
    applied to the **repaired** structure, under the assumption that the developer follows the structure the project
    now has (new record types beside the existing ones in persistence, new wiring in the composition function). The
    transforms are `scripts/xform_*.py`. Under the opposite assumption (old habits return each step) the pre-fix counts
    at steps ≥ 2 would equal the `none` counts and post-fix would still be 0.
- **Correctness.** Every `none`-arm blocking finding (14 layered snapshots) through
  `scripts/v1.3/check-correct.ts --tiers blocking` (`results/v1.3-floor-probe/correctness/`).

### 3.1 Share of `none` steps with a defining violation

14 of 28 steps (50 %): **0 of 14 hexagonal, 14 of 14 layered.** With the pilot memo's identity rule (rule, file,
target; lines ignored), 4 of the 22 later steps add a new blocking finding (market 4, league 2, hive 2 and 3).

### 3.2 Which rules fire

| Rule | Instances (all `none` steps) | Edge |
|---|---|---|
| FF-S01 dependency-direction | 31 | persistence → business (a repository or store imports the entity types from business) |
| FF-S03 no-layer-skip | 31 | **the same 31 upward edges again**: the layered template flags every non-adjacent-downward edge, so an upward import scores twice |
| FF-S03 no-layer-skip | 34 | presentation → persistence (the server file builds repositories and clients) |

All 96 are `correct` under `check-correct.ts`. No P01, P03, P06, S02 or S04 finding in any snapshot, either style.

### 3.3 Which task features induced them

Not the ones designed to. Every violation traces to two choices made at step 1 of each layered task, both ordinary for
a three-folder layout:

1. **Entity types live in `business/`**, and persistence imports them (all three tasks). This is upward in strict
   layering (persistence is the bottom layer).
2. **The composition root is the server file in `presentation/`**, which constructs repositories and API clients
   (league, hive; market used module singletons and has no such edge).

The "new" findings after step 1 are the same two habits replicated: a new persistence file importing business types
(market `transaction.ts` at audit; hive `scale-repository.ts`, `treatment-repository.ts`) or a new client wired in the
server (league WeatherNow and fake mailer; hive TextHive). So **second-adapter and cross-feature steps grow the count,
but only through the step-1 pattern**.

The deliberately tempting steps produced nothing:

- **Reporting endpoints** (garden dashboard, food-bank CSV, league tables, hive quarterly report) were written as one
  more service over the repositories in all four cases. Even had the handler read the store directly, in hexagonal that
  edge (inbound → outbound adapter) is **FF-S03 layer-skip-graph, advisory** (instrument probe, §3.6).
- **Hotfixes under time pressure** (failed payments, allergens, result correction, false swarms) were 7–29 LOC inside
  existing services; none crossed a layer.
- **Across-every-layer steps** (shelter audit trail, market audit log) threaded the actor as a parameter and added a
  unit-of-work port; no request context leaked inward.

### 3.4 Tool-arm fix behaviour

| Task | Step-1 findings | Fix | Files | LOC |
|---|---|---|---|---|
| market-vendors | 4 (2 × S01, 2 × S03) | record interfaces moved to `persistence/models.ts`, re-exported by `business/models.ts` | 4 | 234 → 236 |
| youth-league | 3 (1 × S01, 2 × S03) | same move, plus `business/container.ts` builds services and persistence; the server calls `createServices()` | 5 | 203 → 214 |
| hive-health | 6 (2 × S01, 4 × S03) | same, with an interface-only split (rules and constants stay in business) | 6 | 210 → 219 |

Every fix cleared every finding in one pass and introduced none. `check_diff` reported exactly the graph's blocking
findings on all 31 step and fix diffs. After step 1 the tool arm never saw a blocking finding again (under the §2.3
assumption), so the gate-style repair turn would have been used **once per task, at step 1**.

### 3.5 Advisory counts

Hexagonal: identical in both arms at every step (same code). Layered: the tool arm carries **+1 to +3** more advisory
findings at every step after the fix (final step: market 15 vs 14, league 17 vs 14, hive 18 vs 15), all from the extra
files the fix adds (FF-CV05 test-file pairing, FF-C03 instability). Advisory counts move in the opposite direction to the
blocking counts, so they cannot stand in for the primary outcome.

### 3.6 Instrument probe for hexagonal (synthetic, not counted)

Five shortcut files that the hexagonal steps could have produced, checked with `check_file` and the graph on a copy of
the final garden project (`results/v1.3-floor-probe/instrument-probe/`):

| Shortcut | Graph (v1.3) | `check_file` `blockingVerdict` | `check_file` legacy `verdict` | `check_import` |
|---|---|---|---|---|
| a. dashboard route reads the in-memory repositories (inbound → outbound) | FF-S03, **advisory** | pass | clean | – |
| b. use case imports the concrete fake mailer (application → outbound) | **FF-S01 blocking** | block | **clean** | **allowed / pass** |
| c. domain imports `express` for the request header | **FF-P01 blocking** | block | violations | – |
| d. outbound client with no port, used by nobody | – | pass | clean | – |
| e. inbound handler imports a global from `config/main` | **FF-S01 blocking** | block | **clean** | **allowed** |

So in hexagonal the only blocking-tier shortcuts are a use case reaching a concrete adapter, framework code in the domain,
and adapters reaching the composition root. The reporting shortcut that the task design leaned on is advisory.

### 3.7 Tool defects seen on the way (affect the `daedalus-mcp` arm)

1. **`check_import` does not apply the hexagonal graph rules.** For application → adapters-outbound it returns
   `verdict: allowed`, `blockingVerdict: pass`, `checkedRules: [FF-P01]`; the graph scores the same edge FF-S01 blocking.
   Study 2 prerequisite 3 ("the tool agrees with the graph") fails for this tool on hexagonal.
2. **`check_file` and `check_diff` carry two verdicts that disagree.** The legacy `verdict`, `summary` and `violations`
   come from the old import checker only; `blockingVerdict`, `blockingSummary` and `findings` include the v1.3 rules. Case
   b above reads `verdict: clean` next to `blockingVerdict: block`. The reverse also happens: on the food-bank report step,
   `check_diff` said "1 violation(s) … apply each fix" for an advisory FF-CV03 finding whose suggested fix is to rename
   `NetworkReportService` to `NetworkRepo` (a naming false positive). An agent that reads the first field is misled both
   ways.
3. **FF-S03 double-counts upward edges in layered.** Every upward import is scored by FF-S01 and again by FF-S03
   ("skips layers"). 31 of the 65 FF-S03 instances here are such duplicates. Both are labelled correct under the current
   template semantics, but a count outcome weights a wrong-direction edge twice and a real skip once.

## 4. Conclusion

**Study 2's primary outcome is at real risk of a floor effect.** In this probe, as in E1, an agent given only the style
sentence and the folder layout wrote hexagonal code with no blocking violation at any of 14 steps, including the steps
built to tempt shortcuts. The probe's agent is a strong model that had read the tier table and presets before writing,
so it is if anything biased toward clean code; a weaker or faster agent may erode more. But nothing here suggests that
erosion pressure in plain product language reliably reaches the blocking rules.

Layered escapes the floor, but not in the way Study 2 wants. The violations appear **at step 1**, from layout habits
(entities in business; composition root in presentation), and later steps only replicate them. In the tool arm one
repair at step 1 removed them for good. So in layered:

- the arm contrast would be a **level difference at step 1**, not a difference in erosion slope;
- the count grows with the number of files that copy the pattern, and FF-S03 counts each upward edge twice;
- `gate` would show a large effect that says little about feedback *during growth*.

## 5. Task and outcome designs that avoid the floor

1. **Pick styles whose defining rules conflict with an agent's default layout.** Strict layering (layered) and
   DDD context isolation (FF-DS02, a `shared/` folder outside every context) do; hexagonal and Clean, with the folder
   sentence given, do not. If Study 2 keeps hexagonal, expect zeros there and report it as such.
2. **Aim the pressures at the blocking-tier edges, not at the advisory ones.** In hexagonal that means steps where the
   cheapest path is: a use case calling a concrete adapter (e.g. a fallback that "reuses the existing SMS client from the
   approval"), domain logic that needs request or framework data (the acting user, a header), or a handler that needs a
   global held by the composition root. Reporting endpoints only reach FF-S03, which is advisory in hexagonal; drop them
   as floor-lifters.
3. **Separate step-1 level from erosion.** Report the step-1 blocking count on its own and make the primary outcome
   the **new** blocking identities at steps ≥ 2 (the pilot memo's identity rule), or the slope adjusted for step 1.
   Here that outcome is 4 of 22 later steps, all replications.
4. **Count edges, not rule hits.** Deduplicate FF-S01/FF-S03 on the same edge (or count distinct violating edges per
   KLOC) before any count model; otherwise layered counts are inflated by up to 2× for upward edges.
5. **Fix the MCP tools before the `daedalus-mcp` arm** (§3.7): `check_import` must apply the hexagonal graph rules, and
   `check_file`/`check_diff` should expose one verdict (the v1.3 one) to the agent.
6. **Let the loop pilot decide.** The pilot (Sonnet, Clean / Hexagonal / DDD, `none` and `gate`) has a pre-committed
   erosion criterion (memo §3). If its hexagonal `none` run is also all zeros, redesign or drop the hexagonal tasks
   before Study 2 is registered.

## 6. Limitations

- **n is tiny and the agent is one Claude session.** 28 steps per arm from one agent; no replicate, no second model, no
  harness confinement, no headless CLI. Nothing here is an estimate of a rate.
- **The agent knew the instrument.** It read `rule-tiers.md` and both presets before writing any code, and it designed
  the tasks. The `none` arm was written blind to scores, but not blind to the rules. This most likely biases toward
  clean hexagonal code, i.e. toward the floor.
- **One agent in both arms.** The hexagonal tool arm is a replay; the layered tool arm's later steps are the `none`
  changes transformed onto the repaired structure under a stated assumption (§2.3). Real Study 2 arms are independent
  runs.
- **Variety of habits is the agent's own.** Market used module singletons, league and hive used classes with a server
  composition root; these choices were made before scoring, but they are one developer's habits.
- **Layered has no loop style.** The layered frame here mirrors the styled frame; the harness would need a `layered`
  style and frame to run it.
- Feature completeness was not tested (no acceptance checks), only type-checked.

## 7. Reproduce

```bash
# score one snapshot (needs the pinned skeleton installed; see results/v1.3-floor-probe/scripts/newproj.sh)
python3 results/v1.3-floor-probe/scripts/history.py <project-repo> presets/layered.yaml <outdir> none
# aggregate
python3 results/v1.3-floor-probe/scripts/aggregate.py results/v1.3-floor-probe
# correctness of the none-arm blocking findings
npx tsx scripts/v1.3/check-correct.ts --jobs <jobs.json> --tiers blocking --out <dir>
```

Every step snapshot is under `results/v1.3-floor-probe/<task>/<arm>/snapshots/step-NN/src` (tool arm: post-fix trees;
pre-fix states as `step-NN.pre.diff` against the previous post-fix tree), with its record in `step-NN.json` (`none`) or
`step-NN.{pre,post}.json` (`tool`), including the `check_diff` result for the tool arm.
