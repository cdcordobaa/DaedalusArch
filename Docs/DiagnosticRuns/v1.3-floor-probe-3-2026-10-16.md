# v1.3 floor probe 3: do the rehearsal tasks lift the floor in the `none` arm?

**2026-10-16. Exploratory probe on development tasks; not Study 2.** The loop harness (`scripts/lib/loop`, as the loop
pilot ran it) with the `claude-code-cli` adapter and `claude-sonnet-5-5`, arm `none` only, k = 4 steps, 1 run per task.
The tasks are the dress-rehearsal tasks of PR #201 (`fixtures/v1.3-rehearsal-tasks/`), written under
`Docs/v1.3/study2-task-design.md` so that every later step aims at an edge that is blocking in the task's style. No sealed
directory was read. No rule, tier, template, preset, prompt, frame or spec was changed.

Data: `experiments/v1.3-floor-probe-3/` (`plan.json`, `tasks.json`, and `run-2026-10-16/` with the harness out-root
`outputs/`, `harness.log` and `analysis/`). Scoring script: `scripts/v1.3/floor-probe-3-analyse.ts`.

**Reading.** None of the 8 scored `none`-arm steps had a blocking finding, and both scored tasks stay on the floor.
That is the same result as the loop pilot (0/8 on its Clean and hexagonal tasks). The tasks targeted their blocking
edges deliberately, but the cheap shortcut the design notes predicted was not taken at any pressure point (§2.2). The DDD
task could not be scored, for the same reason as in the pilot. On this evidence, **task design alone does not lift
the floor for this agent in Clean or hexagonal**. The DDD answer is still open, and the code itself (§2.3) gives no sign
that it would differ there. Cost: **3.16 USD** API-equivalent for 12 turns, against a cap of about 8 USD.

### 2.2 Did the agent take the targeted shortcuts? (by-hand reading, not a score)

Folder-level import edges were listed from every snapshot (relative imports only).

| Task, step | Shortcut the design notes predicted | What the agent did |
|---|---|---|
| repair-cafe 1–2 | The finish logic calls the TextLoop / SpareBox client directly (application → outbound) | Both clients sit behind ports in `application/ports.ts`. The only edges into adapters come from `config/main.ts`. Every edge points inward at every step. |
| repair-cafe 3 | Request headers passed into the core rule (domain → framework, application → inbound) | `X-Fixer-Id` and `X-Venue` are read in `adapters/inbound/http-server.ts` and passed in as plain values. The domain imports nothing outside `domain/`. |
| repair-cafe 4 | A mutable on/off flag exported by `config`; the retry timer built with the concrete client | The per-venue switch is a store behind a port (`setSmsEnabled` in the service, the set in `adapters/outbound`). The retry `setTimeout` lives in the application service but calls the port. That is not a dependency edge. |
| school-bus 1–3 | Stores read directly; mailer and push sender imported into the logic; a cycle between feature files | One service file plus `ports.ts`. The only edges are infrastructure → application/domain and application → domain. No application → infrastructure edge, and no cycle. |
| school-bus 4 | A module-level mute map in the outer ring, read by the alert logic | The mute is a ledger entry behind a port (`muteDelays` in the service). The HTTP route only calls the service. |
| vineyard 1–4 | Cellar imports picking's bin type and store (and the reverse for pay); a polling client in the domain; the fix edits a stored weighing from outside the bin | Each context has `acl/`, `api/`, `application/`, `domain/` and `infrastructure/`. The only cross-context imports are `acl → acl`: `cellar/acl/picking-adapter.ts` imports picking's published facade `picking/acl/published-bins.ts`, and `picking/acl/cellar-adapter.ts` imports `cellar/acl/bin-outcomes.ts`. Both are type-only. The WeighWell poller is in `cellar/infrastructure` and `cellar/application`. The domains import only `shared/errors.ts`. |

So the zero is not a measurement artefact. In every targeted spot, the agent chose the port, adapter or ACL route that
the style prescribes. The design notes' assumption that "the shortest path" would be the eroding one did not hold for
this agent. The disciplined path cost it no visible effort (0 type errors, 0.10–0.43 USD per step).

### 2.3 DDD: what can be said without a score

- The tree uses one `domain/` folder per context, with no sub-folder per aggregate. The ISE therefore inferred no
  aggregates (§3.2).
- `src/shared/` (`errors.ts`, `http.ts`, and `http.ts` imports `express`) lies outside both declared contexts. The design
  notes flag a folder outside every context as FF-DS01, with its tier still to be checked. It exists from step 1. So if a
  DDD spec ever scores this tree, a shared-kernel finding would show up as a step-1 level and would not be new at steps
  2–4.
- No edge looks like FF-DS02 (cross-context access outside the public API or ACL). Whether the evaluator counts an
  `acl → acl` facade import as "through the ACL" is a spec question, and this probe did not answer it.

## 3. Tool and design issues found

### 3.1 `ice-rink` cannot run in the loop harness

`scripts/lib/loop/style.ts` frames only `clean`, `hexagonal` and `ddd`, and `styles.json` already records this.
Adding a Layered frame would mean writing new frame wording for Study 2's harness. That is an author decision, so it
was not done here. Layered is also the only style in which the earlier floor probe found blocking findings (14/14 steps,
by hand, `Docs/DiagnosticRuns/v1.3-floor-probe-2026-10-16.md`). The one style likely to escape the floor is therefore
the one the harness cannot yet run.

### 3.2 T1 again: the DDD spec does not freeze (blocking for the DDD answer)

`spec/spec.json` reads `status: failed`, `LOOP_SPEC_FREEZE_FAILED: the constrained spec cannot be compiled: BR-SPEC-10
FF-DT01: aggregates; BR-SPEC-10 FF-DT02: aggregates`. This is the pilot's T1. The harness now rejects the spec at freeze
time, so the run is recorded as unscored instead of failing every evaluation. Two different DDD tasks, in the pilot and
here, produced trees without per-aggregate folders. This is the agent's habit and not chance, so `ise-step1` will
leave Study 2's DDD cells unscored unless the author resolves T1 (pilot report, "Author options"). All four DDD
snapshots are kept in `snapshots.git` and can be scored later without new generation.

### 3.3 New: the in-loop evaluator fails on cypher-interp (blocking for a `gate` arm on cypher-interp)

Every step record carries `evaluationError: PIPELINE_FAILED: No tsconfig.json found at <run>/work/tsconfig.json`, and
the harness log prints `blocking=n/a`. Cause: `src/mcp-server/evaluate-project.ts:122` sends `graphEngine:
'cypher-interp'` to `evaluateInProcess(projectPath, specPath, scoringMode, deps, includeViolations)` and drops
`input.tsconfigPath`. That is the pinned per-run tsconfig the harness passes (`harnessSnapshotTsconfig`, ADR-032). The
work tree has no tsconfig of its own, so the extractor fails. The Neo4j path forwards the tsconfig (line 172), which is
why the pilot, run on Neo4j, was not affected.

- **Effect here: none on the numbers.** The `none` arm does not read the evaluation. The firewall CLI takes `--tsconfig`
  on the interpreter path, and it scored every snapshot. The analysis's `blockingMatch` is false at every step only
  because the step record holds no count to compare against (`recordBlocking: null`).
- **Effect elsewhere.** A `gate` arm run without `NEO4J_URI` would never gate: every step would be "evaluation failed".
  Study 2's harness has to run on Neo4j, or have this one-line forwarding fixed (with a test) before any gate run. It is
  not fixed here, so this PR stays inside its scope.

## 5. Which task features go with violations

Over all four floor studies, the only `none`-arm blocking findings outside E1's zero are these:
1. **Layered style** (FF-S01 and FF-S03, with record types in `business` imported by the stores, and the entry file
   building stores). This is a step-1 level, and later steps copy the habit.
2. **A cross-cutting "across every layer" step** (FF-S02 cycle, floor probe 2 C1).

The following features did **not** produce a violation for either agent in Clean or hexagonal: a core rule that needs
request headers, a time-pressured hotfix with a runtime switch, reuse of an existing sender, a second outbound
provider, a polling inbound adapter, per-user channel choice, and a "reporting shortcut". This probe added the first
four, each aimed at a specific blocking edge, and each was handled with a port.

What these features have in common is a weak signal, from n = 8 steps here and 54 Clean or hexagonal steps over the probes: violations arise when
the **style's own rules are less widely known as conventions** (Layered's no-skip rule is stricter than the common
practice of controllers calling repositories), or when a step makes **two existing modules depend on each other**
(cycles). They do not arise when a step merely offers a shortcut across a boundary that the frame has already named,
because a frame that names the folders and the style already tells a competent agent where each piece goes.

## 6. Honest reading: can task design alone lift the floor?

- **For Clean and hexagonal, with the folder sentence in the frame: on this evidence, no.** These tasks are the most
  deliberate attempt so far, and they gave 0 of 8. Floor probe 2 had already shown that removing the layout sentence
  does not help either: it only moves files out of the instrument's view. With 8 steps from one run, this does not prove
  that the rate is zero. A true rate of 20 % per step would still give 0/8 about 17 % of the time. But it means
  Study 2 cannot count on the rate.
- **Still untested, and the most promising.** (a) Layered, which the harness cannot frame. (b) Steps of the
  "across every layer" or mutual-dependency kind, which k = 4 cut off. (c) DDD, which T1 leaves unscored. If Study 2 keeps
  blocking violations per step as its primary outcome, these three are where the signal might be. Each needs an author
  decision first: a Layered frame, k = 5 or a reordering of steps, and the T1 resolution.
- **Implication for the pilot memo's branch.** For Clean and hexagonal, this probe is a second instance of the memo's
  zero branch, under task design that targeted the blocking edges. The pilot left the decision open only because of
  DDD/T1, and that remains the open item. This probe makes no decision itself (exploratory, not the pilot).

## 8. Limits

- One run per task, one model, one arm, 8 scored steps. Every number is a count.
- k = 4 dropped step 5 of each task, including the steps most like the one known non-layered pressure (§4).
- DDD unscored (T1) and Layered not run, so only two of the four rehearsal styles say anything.
- The rehearsal tasks have not yet passed the author's sealed-list check (fixtures README, "Before any run" §1). This
  probe did not read the sealed list, and nothing here feeds Study 2.
