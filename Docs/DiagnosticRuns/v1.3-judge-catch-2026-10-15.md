Why the reference projects give no positive site:
- **No ORM or injected-repository shape.** The reference projects use in-memory repositories bound through ports. REPO-BYPASS, FAT-CONTROLLER and DUP-RULE therefore find no candidates: no `@InjectRepository`, `Model<>` or `PrismaService`, and no top-level parameter rule in a service method.
- **`type-shape` rejections for PERSIST-IN-DOMAIN and FRAMEWORK-LEAK.** These operators need TypeORM or express types in the project (an import, a `paths` entry or a dependency), and the reference projects have neither. Adding them would mean editing the projects, which this unit forbids. Their twins have no such check, so twins exist where positives do not.
- **Near-miss duplicates.** A near-miss site identical to a clean-project site (same operator, file and site detail) was recorded in the manifest and not applied (`duplicate-not-applied`). The 2 nestjs n02 and n03 FRAMEWORK-LEAKn sites differ from their clean sites, so they were applied.
- **DDD.** `presets/ddd.yaml` declares neither FF-N01 nor FF-N02, so the frozen judge does not run on DDD. The 9 DDD twin copies were seeded and type-checked but not judged (`plan.json` `skipped`).

All 53 applied copies passed `tsc --noEmit` with 0 errors. Diffs are in `results/v1.3-judge-catch/diffs/`.

## 2. Judge runs

**Seeded-unit judging.** Each copy was evaluated through `bin/firewall.ts evaluate` in full mode. The judged set was narrowed to the units holding an edited or created file, for the operator's probed function only. That is FF-N01 (module unit) for REPO-BYPASS and DUP-RULE, and FF-N02 (file unit) for FAT-CONTROLLER, PERSIST-IN-DOMAIN and FRAMEWORK-LEAK. On each unmodified base (the clean control), the judged set was the union of the same units over the rows seeded on it.

The narrowing used the registered variant mechanism, `--judge-baseline-report` (BR-U4-SEL-07). A crafted baseline report carries the copy's own `candidateUnitIds` and `selectedUnitIds` equal to the targets. This departs from the default capped selection (`unitCap` 20). It matches design Option B of `Docs/prereg-drafts/judge-antipattern-test.md` and is what keeps the run inside the budget.

## 3. Results (development set)

Rules (`judge-catch-score.ts`):
- **Catch**: a target unit's majority verdict is `fail`, or in at least 2 valid runs the judge names an edited file with a construct-matching message.
- **Paired catch**: the same unit does not fail on the clean base.

## 5. Verdict against the exit target (catch rate ≥ 0.80)

- **Point estimate: met.** The pooled catch rate is 9/11 = 0.82, and the macro mean over operators is 0.90.
- **Not demonstrated.** The Wilson lower bound is 0.52. Three operators have a single seed.
  - FRAMEWORK-LEAK is at 2/4 = 0.50 [0.15, 0.85], and it is the operator with the most seeds outside the fixture's TypeORM files.
  - All 11 seeds sit on one 8-file fixture, so the seeds are not independent.
- Reading: on this development set the judge separates the repository bypass from its twin (4/4 against 0/4). It misses half the express-request leaks. False fails come from pre-existing ORM entities and one twin template cue.
- Because the reference projects yield no positive site, the 0.80 target cannot be checked with any precision on the v1.3 development set as built. Options for the author (not done here):
  - give the reference projects TypeORM or express types;
  - add hand-written analogues (the reference violation variants already plant some of these defects, for example nestjs v05 and v06 and layered v08);
  - or count E1 or corpus sites under the design draft.
