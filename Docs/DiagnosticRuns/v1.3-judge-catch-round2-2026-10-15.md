## 4. FF-P01 on AP-PERSIST-IN-DOMAIN (round 1's unexpected miss)

**Hypothesis.** `antipattern-nest` maps `typeorm` through tsconfig `paths` to a local stub. If so, the import resolves to a File node, not a Package node, and FF-P01 (which matches `(:File)-[:IMPORTS]->(:Package)`) cannot fire.

**Result: the mechanism is confirmed, but the outcome is not a File edge. The import is dropped entirely.**

Extractor facts (V13 defaults), from `npx tsx scripts/v1.3/judge-catch2-ffp01-repro.ts <scratch>`:

| Project shape | IMPORTS from the domain file | Package nodes | Warning on the file |
|---|---|---|---|
| A `paths: { typeorm: ['vendor/typeorm'] }` → `vendor/typeorm.d.ts` | **none** | none | `EXTRACTOR_008 Import target outside the extracted set: typeorm` |
| B the same alias → `vendor/typeorm.ts` | `File:vendor/typeorm.ts` | none | — |
| C ambient `declare module 'typeorm'` (the v1.3 reference shape) | `Package:typeorm` | `typeorm` | — |
| D `fixtures/unit/antipattern-nest` as committed | **none** | none | `EXTRACTOR_008 … typeorm` (and `@nestjs/typeorm`) |

Mechanism (`src/apg-extractor/import-resolver.ts`, `resolveModuleSilently`):
1. A bare specifier resolves through `paths` to a file under the project root that is not in `node_modules`.
2. `fileResolution` looks the file up as a File node.
3. `**/*.d.ts` is in `DEFAULT_EXCLUDE_PATTERNS`, so the file has no File node, and the result is `no-file-node`.
4. The statement is counted `droppedNoFileNode`. No IMPORTS edge and no Package node are written. Only the `EXTRACTOR_008` warning remains, and it is also in round 1's seeded report.
5. In shape B the alias would give a File edge, which is the original hypothesis, and FF-P01 would still miss it.

**Graph-level confirmation in the live runs.** On the three hand-planted PERSIST-IN-DOMAIN variants, which reach `typeorm` through an ambient `declare module`, FF-P01 fires (S1 3/3). On the fixture, with the same import text, it does not.

**This is a tool defect, not only a fixture artefact** (finding F-P01-ALIAS; not fixed in this unit):
- When the specifier names a package, the right graph fact is a Package node, whatever file the type checker reads.
- Real projects alias packages to local stubs or typings, for example a `paths` entry to `typings/<pkg>.d.ts`, a shim for an untyped package, or a monorepo alias onto a vendored copy.
- Such an import of a forbidden package from a domain file silently evades FF-P01, and also any other package-based rule. Only a non-blocking warning is left.
- Suggested fix, for a later unit: in `resolveModuleSilently`, a bare specifier that resolves to an excluded or declaration file (`no-file-node`) should return `{ kind: 'package', root: packageRootForSpecifier(specifier, ctx.aliasRules) }`. Today it drops the import. Shape B (alias to a `.ts` file) needs a decision: is a `paths` target of a bare package-like specifier a package?
- Consequence for the catch test: round 1's FF-P01 "both-catch control" cannot be read on `antipattern-nest` until this is fixed or the fixture switches to ambient declarations. The hand-planted variants are a working both-catch control: judge 3/3, FF-P01 3/3.
