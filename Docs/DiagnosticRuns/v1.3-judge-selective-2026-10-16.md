# Judge selective prediction: does 3-run unanimity predict a correct verdict? (2026-10-16)

> **DEVELOPMENT-SET NUMBERS.** Every item is a judge-catch item of rounds 1, 2 and DUP v2: the v1.3 reference projects, `antipattern-nest` and the E1 cells. All of it is development data. The TUNE items were used to tune judge v2. CHECK was held out from tuning, but it is still development data, and the judge and the code under test come from the same vendor. No LLM call was made. Every vote comes from committed cassettes and verdict files. This is not a validity claim and not a pre-registration.

Branch `v1.3-judge-selective-prediction`, cut from `origin/v1.3`. Script: `scripts/v1.3/judge-selective.ts`, with tests in `tests/unit/scripts/v1.3/judge-selective.test.ts`. Outputs: `results/v1.3-judge-selective/` (`inventory.json`, `report.json`, `report.md`). The script, the definitions and the decision rule were committed in `742264d5` before any number was computed.

## 1. Question and pre-stated rule

Every judge verdict is the majority of 3 runs. The question is whether a 3/3 verdict is more accurate than a 2/1 verdict. If it is, an agent-facing `review_unit` could tag each verdict `confident` or `uncertain` and abstain on the uncertain ones.

**Decision rule** (backlog N1, fixed before computing). It applies per judge, on the CHECK items, with all classes pooled:
- unanimous-subset accuracy ≥ 0.90;
- its Wilson 95% lower bound ≥ 0.80;
- coverage (the share of items that are unanimous) ≥ 0.60.

If the rule is met, propose a `confidence` field for `review_unit`, OFF by default, and do not implement it. If it is not met, say so in one sentence.

## 2. Data

- **Items and truth labels** come from `results/v1.3-judge-v2/split.json`: 168 items, 105 TUNE and 63 CHECK. The labels are the committed plan kinds and none was changed or invented. A seed should fail. A twin or a clean control should pass.
- **v1 votes** are per run. The round reports keep only each unit's majority, so each item was matched to its cassette triple in `tests/fixtures/judge-cassettes-v13/judge-catch*`. The match uses a fingerprint of the report's unit result:
  - function, unit id or unit file, number of valid runs and majority verdict;
  - the mean confidence of the runs that carry the majority (this is how `src/llm-critic/aggregation.ts` computes it);
  - the population standard deviation of all valid confidences.

  The result: 135 items matched one triple. 29 matched several triples that all have the same vote split; these are byte-identical prompts or look-alikes, and the split is what is used. No item was unresolved. The 4 CHECK `antipattern-nest` entity items take their runs from the current-graph v1 re-judgement (`check-v1-current-graph`), as in the judge v2 report §3.
- **v2.1 votes** come from `results/v1.3-judge-v2/check-v2.1/verdicts.json`: the 63 CHECK items, 3 runs each. The TUNE v2 iterations judged 1 run per unit, so they cannot show agreement and are not used.
- **Consistency check.** The majorities reproduce the judge v2 report's CHECK figures exactly: v1 catches 13/14 and has 2/26 clean false fails; v2.1 catches 14/14 and has 4/26 clean false fails.
- No item had fewer than 3 valid runs.

## 4. Decision

**The rule is not met for either judge, so unanimity is not informative enough to report as confidence:** almost every verdict is unanimous (95%), and the unanimous subset is barely more accurate than all verdicts together: v1 53/60 = 0.883 against 56/63 = 0.889 overall, v2.1 54/60 = 0.900 against 54/63 = 0.857 overall. For v2.1 the gain is the 3 split items, all wrong, and it still leaves the Wilson lower bound under 0.80. No `confidence` field is proposed and no design note was added.

Three reasons explain this:
- **Coverage is too high to separate anything.** 60 of 63 CHECK items are 3/3 under each judge. Only 3 items are split per judge, so the split column has no power: its intervals span 0.00 to 0.56 for v2.1 and 0.44 to 1.00 for v1.
- **The errors are systematic, not stochastic.** Of the unanimous wrong verdicts (v1: 7, v2.1: 6), 4 are the same two `antipattern-nest` entity files, judged on the base and on two PERSIST-IN-DOMAINn twins. 2 are near-duplicate DUP-RULE twins that the judge fails on the twin edit itself (round 2, DUP v2 §4). v1's one missed seed (`AdvanceOrderUseCase.ts`) is 0/3 fail. Every run makes the same mistake, so asking three times cannot reveal it.
- **v2.1 shows one stochastic error class, and abstention catches it.** All 3 of v2.1's split items are wrong. They are the layered `OrderService.ts` false fail (judge v2 report §8): the clean unit counted once per round, plus its same-unit twin. Each is 2/3 fail. Showing only unanimous verdicts would halve v2.1's clean false alarms on CHECK, from 1.5 to 0.8 per 10 clean units, and lose no catch. That is n = 3 on one unit in one style. It is a pointer, not a result.

## 5. What this does not show

- **Development data.** TUNE was used to tune v2. CHECK was held out from tuning, but the authors of v2.0 had read the round reports, which cover both splits. The judge and the code under test come from the same vendor (V10).
- **Items are not independent.** Clusters share units, and the same code is judged on a base and on its twins and in several rounds. One wrong unit (an entity file, `OrderService.ts`) counts 2 to 3 times. The Wilson intervals assume independence, so they are too narrow.
- **3 runs is a coarse agreement measure.** Agreement over 5 or more runs, or the judge's own reported confidence, might separate better. Neither was tested here. No new call was allowed, and confidence calibration was not in the pre-stated analysis.
- **Truth labels are the plan kinds.** Some clean-control failures cite defects that are in the base code (judge v2 report §2). Those count as wrong here. Nothing was relabelled.
- **v2.1 TUNE has 1 run per unit**, so v2.1 is measured on CHECK only (63 items).
- **No construct switch was used.** Status-quo behaviour only.
