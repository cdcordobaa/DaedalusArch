## 8. The new false fail: Layered business layer (kind `domain`) calling its persistence layer

**What happens.** The base layered `OrderService.ts` (`src/business/services/`) is a Fowler Service Layer transaction script. It holds `OrderGateway`, `ProductGateway` and `CustomerGateway` (from `src/persistence`) as constructor fields and calls `findById`, `findBySku`, `updateStock` and `save` on them. v2.1 fails it in 2 of 3 runs, in both rounds and on the PERSIST-IN-DOMAINn twin (whose edit does not touch this behaviour). The judge's citations:
- "This domain-layer class performs persistence I/O …";
- "A domain-layer class takes persistence gateways … as constructor parameters. **The rubric excuses injected repositories only in application files.**"

v1 passes the same three items (on its own v1 prompt, which has the same layer model). In closed layering (presentation → business → persistence, `presets/layered.yaml`), the business layer calling the persistence layer is the design. FF-S01 and FF-S03 encode exactly that edge as allowed.

**Cause: the rubric, triggered by the layer-kind mapping.** Neither alone produces the fail.
1. **Layer-kind mapping (necessary condition).** The layered preset declares `business` with `kind: domain`. The kind enum is `domain | application | infrastructure | presentation`. A layered business layer is both the domain model and the service (application) layer, and it has no kind of its own. So the judge sees "kind: domain" for a file whose role is `business-service`. The mapping is not a bug for the symbolic rules: FF-P01 domain purity and FF-S04 rely on `business` being the core.
2. **v2.1 rubric text (proximate cause).** v2.1 added two clauses that are keyed on layer kind alone:
   - "In a domain file also: … persistence or I/O (queries, database or ORM clients, HTTP or file access)";
   - "Constructor parameters of an **application** file are dependency wiring".

   The first clause turns a call to a lower-layer gateway into persistence I/O. The second exempts only application files, and the judge reads that explicitly as "not for domain files". v1's rubric says "persistence … logic in a domain file", which is looser, and v1 did not read calls through an allowed gateway as such.
3. **The prompt omits what would disambiguate.** `renderLayerModel` prints only name, kind and directories. The prompt carries neither the architecture style (`layered`) nor the layer's allowed dependencies (business → persistence), even though the Neighbourhood shows the edge. The judge has no way to tell "domain reaches infrastructure" (a violation in clean or hexagonal styles) from "business calls the layer below" (the layered design).

So the rubric is what changed, and it is where the fix belongs. Changing the preset's kind would move the symbolic rules, which are frozen and scored.

**Proposed fix for a FUTURE v2.2. Not applied in this run.**
- (a) **Prompt.** Render the style and each layer's allowed dependencies in the layer model, from the spec (for example `- business (kind: domain; may depend on: persistence)` and a `Style: layered (closed)` line). This is spec data that is already parsed. It adds no probe vocabulary (BR-U4-RUB-01 still to be re-checked by the test).
- (b) **Rubric.** Scope the domain I/O clause to *direct* I/O: "a database, ORM, HTTP or file client used in the domain file itself". State that calling an interface or class of a layer that the layer model allows this layer to depend on is not misplaced I/O. Extend the constructor-wiring sentence from "application file" to "any file, for dependencies of a layer it may depend on".
- (c) **Keep** the framework and ORM type, decorator and base class ban for domain files unchanged. Layered v08 (express `Request` in a business service) must still fail, and it is caught on the `Request` alone.
- **Evaluation.** v2.2 needs a **fresh check split**, because CHECK has now been seen and the layered items were found on it. The options are:
  - re-split the not-yet-used items, with a new salt;
  - or, better, new seeds: layered-style business-calls-gateway clean units from new bases, plus a clean or hexagonal domain-calls-repository-implementation seed, so that (b) can be shown not to reopen the real PERSIST-IN-DOMAIN construct.

  TUNE may include the layered base. The new CHECK must include at least one other closed-layering base.

## 9. What this does and does not show

**Shows:**
- On held-out development items, v2.1 catches the construct it was built for: an unused optional `express` `Request` in an application signature, which v1 missed in round 2. It catches it in 3 of 3 runs, paired, without failing that seed's twin.
- v2.1 does not lose any CHECK seed that v1 caught, including the four hand-planted ones.
- v2.1 introduces a reproducible, explainable false fail in layered style. The cause is known (§8).
- On the reference findings, FR-V8 filter-and-explain is conservative: it confirms 65/66 true findings and every blocking-tier finding. Every answer cites existing files and lines.

**Does not show:**
- **That v2.1 is better than v1.** On CHECK the catch difference is one item out of 14, the false-fail differences are 1 to 2 items, and every interval overlaps.
- **Validity.** All items are development data: reference projects, `antipattern-nest` and E1 cells, seeded by the same team. The split is held out from tuning, not independent. There is no pre-registration and no human adjudication of the judge's citations.
- **Generality.** There are 14 CHECK seeds from 7 operator families or hand-planted variants, and one closed-layering base.
- **That FE improves precision.** The scored set has only 2 negatives, and one of them is arguably a true finding scored under another rule. Precision moves by +0.014 with a recall loss of 0.015. The 79% dismissal of unscored metric and convention rows has no labels, so it is neither a precision gain nor a loss.
- **That grounded means right.** The grounding check is syntactic. A fully grounded answer dismissed a planted layer skip.
- **Judge stability across sessions.** The CHECK run spans two CLI sessions on the same model and settings. Variation between sessions, if any, is not separated from variation between runs.
