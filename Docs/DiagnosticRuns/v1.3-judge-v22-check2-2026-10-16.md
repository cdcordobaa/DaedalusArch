- **FF-N02 (the construct v2.2 was written for).** v2.2 removes three of v1's four false fails, unanimously (3/3 runs each: library `LoanHistoryService`, clinic `VisitNotesService`, fleet `MileageService`). It passes every "business service calls an injected gateway, DAO, table or repository" unit. The one v2.2 fail left is fleet `MaintenanceService.ts`. The cause is the delivery-type clause, which v2.2 keeps verbatim: the base's `FleetError` really does carry HTTP status codes (400, 409, 404), and `routes.ts` maps them to the response. So this fail sits in the base, not in the I/O clause. The bases were written by the same team, so this is a construction slip in CHECK-2.
- **FF-N01 (not changed by v2.2, apart from the layer model).** Every layered base has one business service that injects `PrismaService` and calls `prisma.<model>.create/findMany` directly, next to services that go through gateways. Plan §3.1 put that service there on purpose, because `AP-REPO-BYPASS` needs it. Both Claude judges, and Gemini too, fail all six directory units in 3 of 3 runs, citing "skips the module's own persistence abstraction". Plan §7 flagged this grey zone. What it did not foresee is that the FF-N01 directory units would count in D1 and fail all six bases.

D1 is a hard rule, so the outcome stands as NOT CANDIDATE. The FF-N01 failure mode also means that on CHECK-2, FF-N01 does not discriminate (§3).

## 7. Deviations and fixes made during the run

1. **`npm ci` was replaced by a copy of an identical install.** The machine's heavy-command guard refused `npm ci` for more than 30 minutes (memory pressure at "warn", swap above RAM). Another worktree held `node_modules` installed from the byte-identical `package-lock.json` (sha1 `d7fc7c35…`), so it was copied in. No package was resolved differently.
2. **Runner environment fix (`scripts/v1.3/judge-v22-check2-local.sh`).** The runner's minimal `env -i` dropped `USER`, `LOGNAME` and `TMPDIR`. The judge CLI keeps its login in the macOS keychain under the user name, so the init probe failed with `LLM_AUTH` (one ledger entry, no judge call). These three names, plus `__CF_USER_TEXT_ENCODING`, now pass through. They are already in `JUDGE_ENV_ALLOW`, and none of them matches the secret-name pattern, so the scrubbing concern of the runner does not apply.
3. **`record --workers <n>` (`scripts/v1.3/judge-v22-check2.ts`).** The default stays 3. This run used 1, to keep one judge process at a time on a loaded machine. Concurrency changes neither the prompts, the cassette keys nor the verdicts.
4. **Not touched.** The judge texts, the prompts, the split, the decision rule, the frozen hashes and the agy pin.

## 8. What the thesis may claim for SO3

SO3's registered headline is judge-versus-panel agreement on E1 units (`Docs/analysis-plan.md` §3). CHECK-2 does not produce that number, and nothing below replaces it.

**May claim (development data, author-written bases and seeds):**
- On ten fresh bases in five styles, which no judge had seen, the **frozen v1 judge** caught all 40 seeded constructs (40/40, Wilson [0.91, 1.00]). That includes the first judged DDD base (4/4) and the real "domain reaches persistence" constructs on non-layered styles (8/8).
- v1 has a substantial clean-unit false-fail rate: 16/48 = 0.33 [0.22, 0.47]. It is concentrated in layered (11/27) and nestjs (3/5), and in FF-N01 (7/7).
- A rubric revision (v2.2) that gives the judge the style and the allowed dependencies halved the clean false fails (16 → 8) and the twin false fails (12 → 7) without losing a catch. It **failed the pre-fixed adoption rule (D1)**, so it was not adopted. The procedure worked as designed: the rule was fixed before the data and applied unchanged.
- On CHECK-2, FF-N01 did not discriminate: every clean FF-N01 unit failed for both judges. FF-N01 detection results from CHECK-2 should not be reported as evidence.
- *Exploratory only, and only if labelled as such:* a second-vendor rater given the same v2.2 prompt agreed with Claude v2.2 on 134 of 137 units (κ = 0.95).

**May not claim:**
- that v2.2 is better than v1 (it is NOT CANDIDATE, and every interval overlaps);
- any validity of either judge (seeded constructs, no human adjudication of the citations, bases written knowing the construct);
- any SO3 agreement result;
- that a two-vendor ensemble improves the judge (not pre-registered; one run; same prompt);
- generality beyond these ten small bases.

**Next steps, for the author to decide (not done here):**
- **(a)** A v2.3 that addresses FF-N01's mixed-persistence verdict would need a CHECK-3 whose layered bases do not plant a `PrismaService` service in every FF-N01 unit.
