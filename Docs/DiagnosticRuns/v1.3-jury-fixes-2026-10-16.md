## A5: fail-closed verdict

Before: `tiers.blockingNotExecuted` listed a blocking rule that failed to execute (FR-13, for example an `EVAL_002`
transaction timeout), but `tiers.verdict` stayed `pass`. A run whose cycle rule timed out passed.

After (commit "v1.3 A5"):

- `tiered-scoring.ts`: `verdict = fail` if a blocking rule has an applicable violation, else `incomplete` if
  `blockingNotExecuted` is non-empty, else `pass`. `fail` takes precedence. `overallVerdictOf` maps `incomplete` to
  `soft-block` (exit 1) and `fail` to `hard-block`.
- Report schema (embedded `REPORT_SCHEMA` and `schemas/report.schema.json`, kept deep-equal): `tiers.verdict` enum
  gains `incomplete`. A dated `$comment` ("Amended 2026-10-16 … fail-closed") is on the field and in the schema's
  top-level amendment list.
- Architect report: verdict word INCOMPLETE, headline "Incomplete: a defining rule could not run", explanation, and
  amber styling.
- CI gate (`run-check.ts`): engines now return `blockingNotExecuted` with the findings. A blocking rule that failed
  on the **head** commit fails the gate whatever the base did, and the result carries `headBlockingNotExecuted`.
  The field is absent when empty, so the gate's JSON is unchanged otherwise. A failure on the base alone does not
  fail the gate.
- Tests: an `EVAL_002` timeout of FF-S02 gives `incomplete` / `soft-block` and the assembled report validates
  against the schema; `fail` wins over `incomplete`; an advisory rule's timeout leaves `pass`; the gate fails closed
  on a head timeout but not on a base-only one; the architect report renders INCOMPLETE. One existing test asserted
  the old fail-open behaviour (`verdict` `pass` with a not-executed blocking rule) and now asserts `incomplete`. The
  three architect HTML snapshots changed by the two added CSS lines only.
- **Default ON.** The rule was to put it behind an off-by-default option only if it changed a committed reference
  result. It changes none: the 71 reference results are byte-identical, and no committed report under `results/`,
  `experiments/` or `Docs/` has a non-empty `blockingNotExecuted`.
- Type widenings in `scripts/` consumers (`scripts/lib/loop`, `scripts/sdd`): `verdict` types widened from
  `'pass' | 'fail'` to include `incomplete`.

## B1: FF-S02 through the SCC path on large projects

Script: `scripts/v1.3/scc-large-latency.ts`. One extraction per project; the same APG goes to both paths:

- **Cypher**: the compiled FF-S02 template, through `evaluateSymbolic` on the in-process interpreter
  (`MemoryGraphRepository`), the engine the reference results use.
- **SCC**: `findSccViolations` from `scc-cycles.ts`, called directly. `CYCLE_STRATEGY` stays `cypher`.

The SCC was run on two graphs. The *literal* view is FF-S02's view (edge-views.ts). The *union* of both views is what
`buildFileGraph` reads today. They gave identical components on every project. 3 timed runs each; a Cypher run
longer than 60 s was timed once. The interpreter has no query timeout, so each run had a 25-minute wall-clock budget.

Projects: from the committed pins, the three largest wild-set backends (`results/v1.3-wild/selection.json`, with the
ISE-emitted specs committed there and the harness tsconfig regenerated by `wild-run.ts prepare`, byte-identical to
the committed `harness.json`), and bank-server (external wave 2, #181 pin and spec). Data:
`v1.3-jury-fixes-2026-10-16/b1-<id>.json`.

| Project | Files | Extract | FF-S02 Cypher (interp) | FF-S02 SCC | Cypher rows | SCC rows (sizes) | Shared rows | SCC files on a Cypher cycle | Cypher cycles outside one SCC | SCCs with a Cypher cycle |
|---|---:|---:|---:|---:|---|---|---|---|---|---|
| bank-server (external wave 2) | 215 | 1.7 s | 16.0 s | 0.8 ms | 100 (truncated at cap) | 5 (44, 6, 5, 3, 2) | 0 / 100 | 46/60 | 0 | 3/5 |
| podkrepi-api (wild) | 576 | 3.3 s | 994.7 s | 3.2 ms | 100 (truncated at cap) | 6 (34, 4, 2, 2, 2, 2) | 0 / 100 | 29/46 | 0 | 4/6 |
| medplum-server (wild) | 491 | 5.1 s | **> 1,485 s** (not finished) | 2.5 ms | — | 4 (201, 2, 2, 2) | — | — | — | — |
| immich-server (wild) | 458 | 6.9 s | **> 1,485 s** (not finished) | 2.1 ms | — | 3 (94, 6, 5) | — | — | — | — |

**Row-multiset agreement is 0 shared rows everywhere, by contract.** Cypher emits one row per simple cycle of
length 2–10 (closed path), capped at 100 rows plus a sentinel. SCC emits one row per strongly connected component
of 2 or more files, keyed on its smallest member (BR-U3-45). The two row sets cannot coincide unless every SCC is a
single 2-cycle. So agreement is reported at the grains where both answer the same question:

- Every Cypher cycle lies inside exactly one SCC (`cypherCyclesNotInsideOneScc` = 0 everywhere it finished). The
  SCC path never contradicts a Cypher row.
- The SCC path reaches files the Cypher rows do not (14 of 60 on bank-server, 17 of 46 on podkrepi) and SCCs without
  any Cypher row (2 of 5, 2 of 6). In both finished runs this is explained by the 100-row cap: the result is
  truncated, and the rows are ordered by cycle path, so later SCCs never surface.
- On medplum and immich the bounded enumeration of simple cycles inside one large SCC (201 and 94 files) did not
  end within the budget. A 201-file strongly connected component can hold an exponential number of simple cycles of
  length up to 10, and the template enumerates them before the `LIMIT`.

Implications, stated plainly: on large real projects the bounded Cypher cycle rule takes **minutes** on the
interpreter and still stops at 100 rows. The prepared SCC path takes **milliseconds** and reports every cyclic
component. Switching `CYCLE_STRATEGY` is a decision for the latency gate (BR-U3-70) and changes FF-S02's row
contract and counts, so it was not done here. If it is taken, the SCC path should also be made view-aware (literal
view), although on these projects the literal and union views gave the same components.

Details: [`v1.3-barrel-cycle-sensitivity-2026-10-16.md`](v1.3-barrel-cycle-sensitivity-2026-10-16.md).

| | Value |
|---|---|

| Rows that survive the component collapse (barrel rows) | 134 (133) |
| Unbounded SCCs on the rows' edges: file / folder / component | 31 / 14 / 7, of which more than 10 members: 3 / 1 / 0 |
| Unbounded SCCs on the full literal-view graphs: file / folder / component | 42 / 43 / 29, of which more than 10 members: **5** / 6 / **0** |
| File SCCs of more than 10 files | bank-server 44, neoteric-nestjs-auth 22, finance-project-ddd 19, talyssonoc-node-api 13, typeplate 12 |

Also found (not reported in #133/#181):

1. **bank-server's 100 FF-S02 rows are the row cap.** Its committed report carries `EVAL_003` ("truncated at 100
   rows"), so the pooled 208 counts a cap as a count.
2. **7 of the 35 specs do not declare FF-S02.** These are the DDD preset. finance-project-ddd (19-file SCC),
   talyssonoc-node-api (13) and ddd-forum (5 and 4) have cyclic components that no rule looks at.
3. **The length bound hides cycles in one project only.** On neoteric-nestjs-auth (not truncated, longest row 10
   files), 2 of the 27 SCC files are on no reported cycle, so they lie only on cycles longer than 10.

Construct defence (in the B2 doc, with fetched URLs): a barrel is a module. A cycle through it is an evaluation-order
cycle in ESM (TDZ `ReferenceError`, MDN *Cyclic imports*) and a `require` cycle in CommonJS (Node.js *Cycles*: an
"unfinished copy" of `exports`). eslint-plugin-import's `import/no-cycle` counts it, unbounded by default and with no
barrel exception. What remains open is severity, not existence: 26 of the 189 barrel rows are same-folder
self-imports, and 133 couple components.

## B3: dependency-cruiser on this repository's `src/`

Script: `scripts/v1.3/depcruise-self-scc.ts`. dependency-cruiser **18.4.0** with typescript 5.9.3 is the pin in
`experiments/tool-comparison/depcruise`, which #166 used unchanged. Resolution options are graph-fidelity's. Rules:
`no-circular-folder` (`scope: "folder"`) and `no-circular-module`. Data:
`v1.3-jury-fixes-2026-10-16/b3-depcruise-self-scc.json`.

| Tree | Modules | Module cycles | Folder-scope cycles (longest) | Top-level-folder SCC, all imports | Without type-only imports |
|---|---:|---:|---|---|---|
| `b08ec387` (what #155 analysed) | 293 | 5 | 20 (4 folders) | **8 = D1 exactly** | 6 + 2 (`apg-enrich`/`llm-critic` split off) |
| `a39d1ed9` (#155 head, after merging `v1.3`) | 329 | 7 | 153 (9) | 20 (D1 + 12 more) | 6 + 2 + 4 |
| `ae0c8d57` (`v1.3` today) | 329 | 7 | 153 (9) | 20 | 6 + 2 + 4 |

- **Reproduced.** Collapsing dependency-cruiser's module graph to top-level `src/` folders gives the same 8-member
  SCC that #155 found with `component-adp-cycle`: apg-enrich, construct-switches, evaluation-engine,
  fitness-compiler, llm-critic, report, scoring-engine, spec-parser. Two independent extractors agree.
- **Not reproduced as a single finding by the folder rule.** dependency-cruiser's `scope: "folder"` works on each
  file's own directory (`src/apg-enrich/cheap`, `src/shared/types`, …), not on top-level modules. It reports 20 folder
  cycles, the longest 4 folders, touching 7 of the 8 modules plus `shared` sub-folders. `llm-critic` closes its loop
  only through two different `apg-enrich` sub-folders (`ontology` → `llm-critic` → `cheap`), so at leaf grain it
  is in no cycle.
- **Type-only imports matter.** dependency-cruiser counts type-only imports (`tsPreCompilationDeps: true`). Without
  them, `apg-enrich ↔ llm-critic` separates from the other 6.
- **The tangle grew.** On today's `v1.3` the top-level SCC holds 20 folders. One edge that pulls the kernel in is
  `src/shared/types/evaluation.ts → src/fix-hints/types.ts` (a type import, from the fix-hints work), which makes
  `shared` import outward. This is new debt for the dogfood list (D1), not a tool result to explain away.

## Limits

- Latency was measured on a 4-core shared container. The interpreter runs were sequential, but other jobs of this
  session ran during some of them. The load averages are in the run log. Orders of magnitude (ms against minutes)
  are robust; individual seconds are not.
- B1 measured the in-process interpreter, not Neo4j. #155 and the reference results use the interpreter.
- B2's component grain matches spec layers by path only; decorator-only layering falls back to top folders.
- The external-set data (#133, #167, #181) was first read from those PR branches. It reached `v1.3` with merge train
  MT6 during this run, and the inputs are byte-identical. Wave 3 (#232) is not part of the 283 or the 208 figures.
