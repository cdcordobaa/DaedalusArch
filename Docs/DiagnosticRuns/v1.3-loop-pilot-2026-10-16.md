## Tool defect T1: every DDD snapshot unscored (blocking for the decision)

- **What happened.** For both DDD runs (`none` and `gate`), the harness froze a spec from the step-1 tree (`spec/frozen-spec.yaml`, `spec/spec.json` status `frozen`, validator `valid: true`, no warnings). The ISE inferred **no aggregates** from either step-1 tree (`aggregates: []` in `ise-raw.yaml` and in the constrained spec). The frozen spec keeps the preset's FF-DT01 (aggregate-boundary) and FF-DT02 rules. The evaluation pipeline rejects a spec in which these rules have no aggregates: `PIPELINE_FAILED: BR-SPEC-10 FF-DT01: aggregates; BR-SPEC-10 FF-DT02: aggregates`. All 8 DDD step snapshots carry that `evaluationError`. The firewall CLI re-evaluation (`scripts/v1.3/loop-pilot-analyse.ts`) reproduces the same error on every one of them.
- **Why the checks missed it.** The freezer's validation step (`readiness` §3 step 3) and the pipeline's BR-SPEC-10 check disagree. The spec validator accepts an empty aggregate list, but the pipeline does not. The dry run (readiness §5) froze specs from stub trees and evaluated with the stub firewall, so it never sent a frozen DDD spec through the real pipeline.
- **Effect on the gate.** In `relief-volunteers/gate`, the gate was not applied at any step (`repair.skipped: evaluation-failed`; harness summary `gateStepsWithoutEvaluation: 4`). That run is a `gate` run in name only.
- **What is kept.** All DDD commits are in each run's `snapshots.git`, so the runs can be scored later without new generation (readiness §3).
- **Not fixed here.** A fix decides what a DDD spec says when the agent's tree has no aggregate an ISE can see: for example, dropping FF-DT01/FF-DT02, declaring them N/A, or making the freeze fail. That is a construct decision for the author. Memo §6 says any fix is checked on the development set, not on pilot data.
- **Author options.**
  1. Fix the freezer (and test it on the development set). Re-freeze each DDD run's spec from its **same** recorded step-1 commit (the ISE and the constraint step are deterministic), then score the 8 kept snapshots. This makes no model call and gives no new generation. The `gate` DDD run stays unrepaired, so its gate data are lost either way.
  2. Fix the freezer and re-run the two DDD runs from scratch, on a fresh out-root, after a memo revision.
  3. Decide that the pilot stands on two tasks. That would be a memo change, not a reading of this run.
