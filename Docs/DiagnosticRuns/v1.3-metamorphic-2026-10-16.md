> **DEVELOPMENT-SET NUMBERS.** Every figure comes from the 71-case v1.3 reference set (`tests/fixtures/v1.3-reference`, 5 styles). These are the cases the v1.3 changes were made against. Invariance on them is evidence about construct validity and reliability, not a validity estimate. No pre-registration was made. **Nothing was tuned:** no template, tier, preset, manifest or default option was changed.

- **Harness:** `scripts/v1.3/lib/metamorphic.ts` (transformations, comparison keys), `scripts/v1.3/lib/metamorphic-report.ts` (aggregation), `scripts/v1.3/metamorphic-run.ts` (runner). Unit tests: `tests/unit/scripts/v1.3/metamorphic.test.ts` (21 tests).
- **Extractor fix (OFF by default):** `ExtractorOptions.resolvedEdgesInLiteralView`, CLI `evaluate --resolved-edges-in-literal-view` (MT-B1, §4). Unit tests: `tests/unit/apg-extractor/v13-resolved-in-literal.test.ts` (5 tests).
- **Outputs:** `results/v1.3-metamorphic/` (`summary.md`, `summary.json`, `raw/<transform>/<style>/<variant>.json`, `raw/base/...`) and `results/v1.3-metamorphic/mt-b1-on/` (the MT-B1 check). The transformed projects are not committed. They are rebuilt by the runner and deleted after each case.

## 1. Verdict

- **Surface form does not move the verdict.** Six of the nine transformations are invariant on every one of the 71 variants:
  - rename (identifiers and files, the spec following);
  - reorder imports and declarations;
  - reformat;
  - default/named export switch;
  - `import type`;
  - tsconfig path alias.

  So is split (one file into two in the same layer). That makes 7 × 71 = 497 transformed cases, all invariant on (rule, layer pair) and on (rule, file, target).
- **Three transformations change a verdict. Each change was traced to its mechanism:**
  - **barrels** (added: 67/71 invariant; removed: 15/16 applicable);
  - **merging two files** of one layer (58/71).

  Every non-invariant case is classified in §3:
  - **1 tool bug (MT-B1).** A barrel that belongs to no layer hides what it re-exports from the literal-view layer rules (1 case, NestJS). It is fixed behind an OFF option with a unit test. The option cannot become the default: it adds a FF-DS02 false positive on the DDD public-API probe (§4).
  - **3 intended construct choices:**
    - barrel-induced module cycles (4 cases, ADR-V13-01);
    - the DDD public API is a barrel (1 case);
    - a merge that creates a module cycle (13 cases). FF-S02 is a file-level rule.
- **Two probes show where the construct is deliberately name-bound.** They are reported, not counted as transformations of the task:
  - **Opaque names** (61/71). These drop role words such as `Repository` or `.service.ts`, and NestJS file-name layers.
  - **A rename that leaves the DDD spec stale** (68/71). The DDD spec names aggregate roots and inner entities by path and domain events by class name.
- **Barrels and aliases (the 0.926 reading).** On the v1.3 default graph, aliases are invariant: 71/71, including every planted violation. Barrels move the file a finding points at (21 cases are layer-pair-invariant but name the barrel as target). They change a verdict only through the three mechanisms above. The first pass reported 44/71 for aliases. That was a harness confound, not a tool result (§5, H-1).
- **Defaults are byte-identical.** The untransformed cypher-interp run equals the committed Neo4j run `results/v1.3-reference/after-member-facts/raw` on 71/71 variants. The new option is OFF in `V12E_DEFAULT_OPTIONS` and `V13_DEFAULT_OPTIONS`. With the option OFF, extraction is byte-identical (unit test). No Cypher template, tier, preset or manifest was edited.

## 2. Method

### 2.1 Transformations

All transformations keep every directory, so the layer folders the specs map are kept. Each transformed project must pass `tsc` (`typecheckProject`, the project's own tsconfig, no emit). A transformation with several possible shapes (which file to split, which pair to merge, which statement order) yields ordered candidates, and the runner keeps the first candidate that type-checks. 922 of the 923 transformed cases used their first candidate; one merge needed the third. No case was left without a compiling candidate.

| Transformation | What it does | Applicable |
|---|---|---|
| rename | Every top-level declaration of `src/` gets an `Acme` prefix (`ACME_` for constants, `acme…` for camelCase), through the TypeScript language service. Every file except `index.ts` and `main.ts` gets the same prefix (`AcmeOrder.ts`, `acme-orders.service.ts`), so role words and suffixes survive. Every relative specifier is relinked. **The spec follows the rename:** a string in the spec's `architecture` section that names a renamed file or class is replaced (DDD: aggregate roots, inner entities, `domain_event_types`; globs untouched). | 71 |
| reorder | Each file's imports are reversed. Interfaces and type aliases (reversed) come first and function declarations (reversed) last. Classes, variables and enums keep their order, since moving them could use a class before its declaration. | 71 |
| reformat | prettier with settings far from the projects': 4 spaces, no semicolons, double quotes, width 60, no bracket spacing. | 71 |
| barrel-add | Every directory under `src/` without a barrel gets an `index.ts` with one `export * from './x'` per file. Directories with an `export *` name clash are skipped. Every import from outside the directory and its subtree is pointed at the barrel. | 71 |
| barrel-remove | Every `index.ts` that only re-exports is deleted, and each import through it is pointed at the declaring file, name by name, through the type checker. | 16 (all 15 DDD variants, layered n03) |
| default-export | The main export of each file (the class named like the file, else the first exported class, else the first exported function) becomes its default export. Importers switch to a default import. A type-only importer becomes a separate `import type X from`. | 71 |
| import-type | An import declaration whose bindings are all used in type positions becomes `import type`. Under `emitDecoratorMetadata`, a type annotation inside a decorated class counts as a value use, because the compiler emits it as runtime metadata. | 71 |
| path-alias | Adds `baseUrl: "."` and `paths: {"@app/*": ["src/*"]}` to tsconfig.json. Every specifier that leaves its directory (`../`) becomes `@app/…`. NodeNext keeps `.js`. | 71 |
| split | Moves the tail of a file's top-level statements, from an exported declaration on, to a sibling (`ExtraX.ts`, `extra-x.service.ts`). Imports are pruned on both sides through symbols, and importers are repointed name by name. The cut is refused when the two halves would import each other, or when a moved part needs a non-exported name. The new file must get the same layer from the instrument's own assignment. The defining finding's files are tried first. | 71 (13 of 52 violation variants split a file the finding names; the others have no splittable file there) |
| merge | Folds file B into file A of the same directory and the same layer (the instrument's own assignment). Imports are merged, and B's importers are repointed. Pairs with a name clash are refused. The defining finding's files are tried first. Merging the two ends of the defining finding is tried last, because it makes the finding intra-file by construction. | 71 (42 of 52 violation variants merge a file the finding names) |
| *rename-opaque* (probe) | As rename, but with numbered names (`Q001`, `m001.ts`): no role word survives. The spec follows exact paths and class names, not globs. | 71 |
| *rename-spec-stale* (probe) | As rename, but the spec is not updated. | 71 |
| *import-type-drop* (probe) | The reverse of import-type: every `import type` and inline `type` becomes a plain import. | 20 |

### 2.2 Comparison

For each variant and transformation, the runner evaluates both sides with `firewall evaluate --symbolic-only --format json --engine cypher-interp`. Both projects sit in the same work directory, under the OS temporary directory. The comparison uses the v1.3 tiers the CLI reports (`tiers.blocking.rules`).

- **Key.** A blocking row's key is (rule, layer of source, layer of target). Layers come from the instrument's own `annotateNodes`: directory globs first, then file-name patterns. In DDD the key also names the context (`ordering:domain`). A cycle's key is the rule and the set of layers it passes through. Files the transformation renamed, split or merged are mapped to a canonical path before the stricter (rule, file, target) key is built.
- **Defining-rule verdict.**
  - For a violation variant: whether each rule of its expected findings fires, whatever the rule's tier. Three DDD variants plant a rule that is advisory under the DDD tiers.
  - For a clean or near-miss variant: the tool's overall v1.3 verdict.
- **Invariance (the task's definition).** The defining-rule verdict and the set of blocking (rule, layer pair) keys are unchanged.
- **"Files-invariant"** adds that the set of blocking (rule, file, target) keys is unchanged after mapping.
- **Advisory changes** (metrics, fan-in/fan-out) are counted but are not part of invariance.

### 2.3 Base check

The 71 untransformed variants, materialised and evaluated by this runner, have exactly the rows (rule, file, target) of the committed Neo4j run `results/v1.3-reference/after-member-facts/raw` (71/71, `raw/base/*/*.json` field `identicalToCommittedNeo4jRun`). All 71 type-check.

## 4. MT-B1: the fix and its check

**Change.** `ExtractorOptions.resolvedEdgesInLiteralView` is OFF in `V12E_DEFAULT_OPTIONS` and `V13_DEFAULT_OPTIONS`. With `reExportEdges: 'both'`, the option records the resolved occurrence of a name imported through a re-export file without `viaReExport`, so the literal view keeps the edge to the declaring file next to the edge to the barrel.

What the option leaves unchanged:

- the barrel edge and its `reExportHop` mark;
- the resolved view;
- every non-IMPORTS edge.

With `reExportEdges: 'resolved-only'` it has no effect. It reaches the CLI as `firewall evaluate --resolved-edges-in-literal-view` (through `PipelineConfig.resolvedEdgesInLiteralView` and `ExtractCommand`). Files: `src/apg-extractor/{types,import-resolver}.ts`, `src/pipeline/{types,pipeline-factory}.ts`, `src/pipeline/commands/extract-command.ts`, `src/cli/cli.ts`.

**Unit test** (`tests/unit/apg-extractor/v13-resolved-in-literal.test.ts`, on `fixtures/unit/v13-barrels`, 5 tests):

- OFF in both default sets, and OFF extracts the default graph byte for byte;
- ON, the three resolved edges of the order-fulfilment import lose the mark and the hop edge is unchanged;
- ON, the literal view gains the declaring files;
- ON, nothing else changes once the two marks are dropped;
- no effect on the v1.2E graph.

**Check: barrel-add with the option ON**, all 71 variants, both sides with the flag (`results/v1.3-metamorphic/mt-b1-on/`):

| | OFF (default) | ON |
|---|---:|---:|
| invariant | 67/71 | 67/71 |
| defining verdict changed | 1 (nestjs v10) | **0** |
| lost (rule, layer pair) keys | 2 | **0** |
| remaining non-invariant cases | MT-B1 + MT-B2 | MT-B2 only (the 4 barrel cycles) |

**Why the option stays OFF.** On the untransformed set, the option changes one variant: DDD g02, the public-API probe. It adds `FF-DS02 src/billing/api/InvoiceController.ts → src/ordering/application/GetOrderSummary.ts`, a false positive. context-isolation reads the literal view because "whether the import goes through the published barrel is the question" (`edge-views.md`). The resolved edge behind the public barrel must not be in that view.

So MT-B1 cannot be fixed for every literal-view rule at once in the extractor. A complete fix is a per-template view choice: the layer rules see through a barrel outside every layer, and the DDD public-API rules keep the barrel as the boundary. That change lives in the edge-view table of the fitness compiler, which this run does not touch (no template or tier edits). It is left as a recommendation (§7).

## 5. Harness confounds found on the way (not tool results)

The first pass (same code, before these three corrections) is kept out of the results. Its effects are recorded here because two of them look like tool failures.

- **H-1. Work directory under `node_modules`.** The first pass materialised the projects under `node_modules/.cache`, as `validate-reference --check` does for DDD. The extractor treats a resolved file whose path has a `node_modules` segment as an installed package (`import-resolver.ts`, `hasNodeModulesSegment`). Every `@app/*` import therefore became a Package edge (`@app/business`, …), and path-alias scored **44/71**, with 27 defining verdicts lost. Relative imports were unaffected, which is why the base check still passed. Moved to the OS temporary directory, with a `node_modules` link for DDD v04's `class-transformer`: **71/71**. A project checked out under a `node_modules` path is not a normal use, so the behaviour is noted, not fixed.
- **H-2. "Same layer" for merge and split.** The first pass merged within a directory. A NestJS feature folder holds several layers told apart by file-name patterns, so `attendees.controller.ts` folded into `in-memory-attendee.repository.ts` moved code across layers. One FF-S01 infrastructure → application row was gained (nestjs v08). Merge and split now use the instrument's own layer assignment.
- **H-3. A rename must carry the spec.** The DDD spec binds aggregate roots, inner entities and domain-event types by path and name (MT-R2). The rename now updates those strings in the spec's `architecture` section. The stale-spec form is kept as a probe.

## 6. Barrels and aliases

The post-merge review (`Docs/v1.3/post-merge-review-2026-10-16.md`) and the graph-fidelity runs read a below-1 default-graph coverage (0.926 of tsc) as a barrel effect. What the metamorphic run adds:

- **Aliases are a non-issue for verdicts.** Rewriting every cross-directory import to `@app/…` changes no row on any variant, under either key. The extractor resolves `paths` like the compiler. The only alias failure seen was H-1.
- **Barrels are where the default graph and the verdict meet.**
  - **Barrel in a layer folder (the usual case).** The literal view gives the same (rule, layer pair) as the direct import. The finding then names the barrel as its target: 21 files-only cases.
  - **Barrel outside every layer** (feature folders under file-pattern layers, MT-B1). The layer rules go blind.
  - **Barrels in opposite directions** create module cycles (MT-B2, intended).
  - **A barrel that is a declared public API.** It is architecture, not form (MT-B3).

  Only MT-B1 is a defect, and it shows up only where layers are assigned by file name. Real NestJS code is the main case: feature modules with an `index.ts` (cf. `v1.3-wild-2026-10-16.md`, hoppscotch, podkrepi, immich).
- **Implication for coverage figures.** A coverage figure that mixes the literal and resolved edges, or compares the resolved view with tsc, will keep showing a barrel gap. The rules do not read that mixture: each reads one view. The metamorphic result is the more direct check: verdicts are barrel-invariant except for MT-B1, MT-B2 and MT-B3.

## 7. Recommendations (not done here)

1. **MT-B1 proper fix.** Give the layer rules that read the literal view (dependency-direction, no-layer-skip, no-domain-outward-dep, and the hexagonal dependency-direction-graph and layer-skip-graph) a fall-through for a `reExportHop` edge whose barrel has no layer. Keep context-isolation on the plain literal view. This is a change to the edge-view table (`src/fitness-compiler/edge-views.ts`), so it needs an ADR amendment to ADR-V13-01. The OFF option is the measurement tool for it.
2. **FF-S02 and module granularity (MT-B2, MT-M1).** Both are intended, but both can turn a clean or near-miss project to `fail` under a refactoring a developer would call cosmetic: 8 of the 13 MT-M1 cases are clean or near-miss variants. If the thesis claims verdict robustness to refactoring, report FF-S02 under both views, or add a declaration-level cycle variant as an advisory companion.
3. **Name-bound constructs (MT-R1, MT-R2).** Document in the presets that renaming a role-bearing file, or a path the DDD spec names, is a spec change.

## 10. Limits

- **Development set only.** The 71 variants are the cases v1.3 was built against. Hold-out invariance is untested.
- **One shape per transformation.** Each case uses one deterministic shape: first compiling candidate, focus files first. Split reaches the defining finding's file in only 13 of 52 violation variants, because most planted files hold a single exported class. Merge reaches it in 42.
- **Scope of what is compared.**
  - Symbolic route only.
  - Advisory rows are counted, not judged.
  - The judge (neural route) is not part of this run.
- **Engine.** The in-process engine was used throughout. Its equivalence with Neo4j on this set is the base check (71/71) plus the earlier parity run (`Docs/v1.3/cypher-interpreter.md`). The transformed projects were not re-run on Neo4j.
