# v1.3 MT-B1 fix: a barrel outside every layer, seen through at graph build (2026-10-16)

> **DEVELOPMENT-SET AND EXPLORATORY NUMBERS.** The 71 reference variants are the cases v1.3 was built against. The external set (15 human-written projects) is unlabelled: a gained row is a candidate, not a confirmed true positive. Nothing here is pre-registered. No Cypher template, tier, preset, manifest or default option was changed.

Branch `v1.3-mtb1-barrel-fix`, cut from `origin/v1.3-metamorphic` @ `6efd7520` (PR #185). Node v22.22.0, dependencies from the lockfile. Engine: `--engine cypher-interp` throughout (in-process; no Neo4j, no credentials). No LLM was called. No `.env`, secret or `daedalus-sealed/` file was read.

- **Fix (OFF by default):** `src/neo4j-ingestion/layerless-barrel-edges.ts` (`liftLayerlessBarrelEdges`), applied in `ingestAPG` when `IngestionInput.literalThroughLayerlessBarrels` is set. CLI: `firewall evaluate --literal-through-layerless-barrels`, through `PipelineConfig.literalThroughLayerlessBarrels` and `IngestCommandConfig`.
- **Regression test:** `tests/unit/neo4j-ingestion/layerless-barrel-edges.test.ts` (6 tests) on the new fixture `fixtures/unit/v13-mtb1-layerless-barrel`.
- **Harness changes:** `metamorphic-run.ts` passes the new flag through; `graph-fidelity.ts --mtb1` measures the literal view after the step.
- **Outputs:** `results/v1.3-metamorphic/mtb1-fix-on/` (base + barrel-add + barrel-remove, flag ON), `results/v1.3-mtb1-fix/external-findings-off-vs-on.json`, `results/v1.3-mtb1-fix/external-coverage.json`.

## 1. Verdict

- **MT-B1 is reproduced and fixed, in the graph build only.** The root cause is a view/layer mismatch, not an extraction error. The extractor records both edges correctly. The literal view keeps only the edge to the barrel, and when the barrel has no layer the layer rules cannot see the import at all. The fix lets the literal view see through a barrel only when that barrel has no layer and is not a declared DDD public API or ACL.
- **No reference result changes.** With the option ON, the 71 untransformed variants give rows identical to the committed Neo4j run (71/71), blocking and advisory. This includes DDD g02, where the earlier extractor option (`--resolved-edges-in-literal-view`) added a FF-DS02 false positive.
- **Metamorphic barrel-add re-run: 67/71 invariant, the same count as before. The target of 68/71 was not reached, and cannot be with this fix.** The one MT-B1 case, nestjs v10, is fixed: FF-S01 and FF-S04 domain → infrastructure are kept, and the defining verdict no longer changes (1 → 0). But v10 is also an MT-B2 case: barrel-induced FF-S02 cycles that ADR-V13-01 counts as findings. So it stays non-invariant. The four remaining cases are exactly the MT-B2 set. barrel-remove is unchanged at 15/16 (MT-B3, intended).
- **External-set coverage: unchanged, and the 0.926 gap does not share the cause.** 0.926 is the coverage of the **v1.2E resolved-only graph** (`apg-v12e-default`). That graph has no literal barrel edge at all, so it is a different mechanism. The v1.3 literal view already covers tsc exactly (3717/3717). With the fix it still covers 1.000. Confirmation drops from 1.000 to 0.991, from 34 added edges in 3 projects. Each of those edges is the routed dependency behind a layerless barrel, which tsc does not report as a module edge.
- **External-set blocking findings: +16 rows in 2 of 15 projects, 0 lost, no verdict changed.**
  - **vivify (+1).** A real FF-S01 that MT-B1 hid on human code. `jwt.strategy.ts` (infrastructure) imports `UsersService` (application) through the layerless `src/modules/user/index.ts`.
  - **neoteric (+15 FF-S02).** These are cycle enumerations inside existing cycle components, not new cycles of modules. One row brings two files into the cycle list, only because a shortcut edge brings a cycle under the template's length bound of 10 (§4.3).

## 3. Root cause and fix (task 2)

**Where it happens.** With `reExportEdges: 'both'` (`V13_DEFAULT_OPTIONS`), `import { X } from '../registrations'` gives two IMPORTS edges (`import-resolver.ts`):
- the literal edge to `registrations/index.ts`, marked `reExportHop`;
- the resolved edge to the declaring file, marked `viaReExport` with `reExportBarrels: ['src/registrations/index.ts']`.

The layer templates read the literal view (`Docs/v1.3/edge-views.md`). `applyEdgeView` adds `NOT coalesce(r.viaReExport, false)`, so only the edge to the barrel remains. Under directory layers, a barrel sits in the same layer folder as what it re-exports, and the rule still fires on the barrel (the 21 "files-only" cases of the metamorphic run). Under file-name layers (NestJS `file_patterns`), a feature folder's `index.ts` matches no pattern. The surviving edge then ends at a layerless node, and no layer rule matches it.

**Why not the extractor.** The extractor has no layer model, so it cannot tell a layerless barrel from a layered one. Its only option is all-or-nothing. That is the existing `resolvedEdgesInLiteralView`, which the metamorphic run showed cannot be the default: it puts the resolved edge behind the DDD public-API barrel into context-isolation's view (g02 false positive). The decision needs the layers, and the layers are known at graph build (`annotateNodes`, the same annotator ingestion uses).

**The fix.** `liftLayerlessBarrelEdges(nodes, edges, annotations, layerModel)` runs in `ingestAPG` after annotation and before `ingestEdges`. It drops `viaReExport` from a resolved IMPORTS edge only when all three conditions hold:
1. Every barrel in `reExportBarrels` is a File node with no layer.
2. None of those barrels matches a DDD context's `public_api` or `acl` glob (`architecture.ddd.contexts`). Such a barrel is the boundary context-isolation checks (MT-B3, g02).
3. The declaring file has a layer. Otherwise no layer rule could see the edge anyway.

A lifted edge keeps `reExportBarrels` and gains `literalThroughLayerlessBarrel: true`, so its origin stays visible in the graph. What the step leaves unchanged:
- the barrel edge and its `reExportHop` mark;
- the resolved view;
- every other edge;
- the snapshot, which still stores the extractor's APG.

No template text is touched. The literal view's existing predicate simply admits the edge.

**OFF by default.** `literalThroughLayerlessBarrels` is absent from every default config. Without it, `ingestAPG` passes `apgResult.edges` unchanged, so the default graph is byte-identical. The option changes no reference result (§4.1), but it does change external-set findings (§4.3), so the task's rule applies the other way too: it stays OFF until a decision is made (§6).

**What it does to the literal view beyond the layer rules.** The step changes the graph, not one template, so every literal-view reader sees the lifted edge:
- no-cyclic-deps, which explains the extra cycle enumerations in §4.2 and §4.3;
- context-isolation, outside declared public APIs;
- the coupling metrics (FF-C01/C03 advisory rows).

A per-template choice (the edge-view table) would avoid this, but that is a fitness-compiler change. The task ruled it out ("extractor or graph build ONLY"), and §6 lists it.

### 4.2 Metamorphic barrel-add and barrel-remove, re-run

Both sides (untransformed and transformed) evaluated with the flag, the same comparison as the metamorphic run:

| | OFF (metamorphic run) | ON (this fix) |
|---|---:|---:|
| barrel-add invariant | 67/71 | **67/71** |
| barrel-add defining verdict changed | 1 (nestjs v10) | **0** |
| barrel-add lost (rule, layer pair) keys | 2 (FF-S01, FF-S04 domain>infrastructure, v10) | **0** |
| barrel-add files-invariant | 46 | 46 |
| barrel-remove invariant | 15/16 | 15/16 (MT-B3, ddd g02, intended) |
| non-invariant barrel-add cases | clean v09, nestjs v01, nestjs v10, hexagonal v02 | the same four |

Across all 158 runs (71 base + 71 barrel-add + 16 barrel-remove), exactly one run differs between OFF and ON: **barrel-add nestjs v10**.

- **Gained:** `FF-S01` and `FF-S04 src/domain/registration-policy.ts → src/registrations/in-memory-registration.repository.ts`. These are the two rows MT-B1 had lost, so the defining verdict now matches the untransformed variant.
- **Gained:** 12 more FF-S02 rows, and one more cycle layer set, `{domain, infrastructure}`.
  - The lifted edge `registration-policy.ts → in-memory-registration.repository.ts` is a shortcut past `registrations/index.ts` inside cycles OFF already reports. The cycle runs through `src/domain/index.ts` and `src/registrations/index.ts` (MT-B2).
  - The template enumerates simple cycles, so a shortcut adds enumerations. Every file of the 12 new rows already appears in OFF's cycle rows; no new component appears.
  - v10 was non-invariant through MT-B2 before the fix and stays so after it.
- **Advisory:** `FF-C01 src/domain/registration-policy.ts` (domain-stability): its fan-out now counts the repository.

**Why "67+1" is not reached.** v10 has two independent changes under barrel-add: MT-B1 (lost layer rows) and MT-B2 (gained barrel cycles). The fix removes the first. The second is intended under ADR-V13-01: "barrel-induced cycles are findings". Under the task's definition of invariance, v10 counts only when both are gone. Making it invariant would mean hiding a real module-load cycle, which this unit must not do. In the per-mechanism count, MT-B1 cases went from 1 to 0 and MT-B2 cases stay at 4.

- **vivify, +1 FF-S01 `src/modules/auth/jwt.strategy.ts → src/modules/user/user.service.ts`.**
  - `jwt.strategy.ts` is infrastructure (`**/*.strategy.ts`) and has `import { UsersService } from './../user'`.
  - `src/modules/user/index.ts` re-exports `user.service.ts`, which is application (`**/*.service.ts`). The barrel itself matches no layer of the vivify spec.
  - The spec orders the NestJS layers domain → infrastructure → application → presentation (inner → outer), so infrastructure → application is the direction FF-S01 forbids.
  - This is MT-B1 on human code: a real import across layers that the default graph hides. It is unlabelled, like every external finding. Whether the spec's NestJS layer order is right for vivify is the spec author's call (`spec-rationale.md`), not this tool's.

  So these are not new module cycles. They are an existing module cycle crossing the length bound. The same component already makes the project hard-block under FF-S02 (72 → 87 rows, verdict unchanged).

## 6. Recommendations (not done here)

1. **Keep the option OFF until the edge-view question is decided.** It changes no reference result, but on human code it changes FF-S02 enumerations. The cycle rule was meant to read the module graph as imported (ADR-V13-01). A per-template version is cleaner, and it is the metamorphic report's recommendation 1:
   - layer rules (`dependency-direction`, `no-layer-skip`, `no-domain-outward-dep`, `dependency-direction-graph`, `layer-skip-graph`, `core-isolation`) fall through a `reExportHop` edge whose barrel has no layer;
   - cycles, metrics and context-isolation keep the plain literal view.

   That needs an ADR-V13-01 amendment and a fitness-compiler change. This graph-build step is the measurement tool for it: its `literalThroughLayerlessBarrel` mark is exactly the set of edges such a view would admit.
2. **If the graph-build form is adopted instead,** document in `edge-views.md` that the literal view includes lifted edges. Then treat the FF-S02 change as the length-bound effect it is: report SCC membership, or raise the bound, rather than per-cycle enumerations.
3. **Stop quoting 0.926 as a barrel effect of the v1.3 graph.** It is the v1.2E graph's figure. The v1.3 literal view is 1.000 on this set.
4. **Label the vivify row** with the external-set labelling sheet. It is the one external case where MT-B1 changed a layer finding.

## 8. Limits

- **Development set plus one unlabelled external set.** The vivify row is a candidate, not a confirmed true positive.
- **cypher-interp only.** The ON graph was not run on Neo4j. The step runs before `ingestEdges`, which both engines share, and the OFF base equals the committed Neo4j run.
- **One fixture shape.** The regression fixture is the v10 shape: a barrel one hop from a layered file. Chains of several layerless barrels are covered by the unit test of the step (`every` over `reExportBarrels`), not by an end-to-end fixture.
- **DDD exemption by declaration only.** A context barrel that is the de facto public API but is not declared in `public_api` is lifted like any layerless barrel (ddd-forum declares none; no finding changed there).
