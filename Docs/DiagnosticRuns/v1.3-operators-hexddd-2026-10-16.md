# v1.3 hexagonal and DDD mutation operators: seeded detection on reference and real projects (2026-10-16)

Branch `v1.3-operators-hexddd`, base `origin/v1.3` at `2c64d1d5`. Catalogue `Docs/v1.3/operator-catalogue-hexddd.md` (DRAFT). The run used catalogue sha256 `4e35f808…a95d`. After review the catalogue text changed to describe where the new type values live (§5 item 5); `run.json` records the sha256 of the catalogue at merge time. Runner `scripts/v1.3/operators-hexddd-run.ts`, pure helpers `scripts/v1.3/lib/operators-hexddd.ts`, operators `scripts/lib/mutation/hexddd/`.

**Status: development data.** Nothing here is pre-registered. The operators, the real-project specs and this report were written by one author (Claude) in one session, and the specs were written after the projects' layouts were read. These numbers show that the operators plant what they claim to plant and that the tool sees it. They are not a registered SO4 recall estimate. The frozen catalogue `Docs/operator-catalogue.md` is byte-identical. No Cypher template, tier, preset or extractor file is edited.

## 1. Setup

- **Engine.** `--engine cypher-interp` was not on `v1.3` when this branch was cut (`2c64d1d5`); it was merged into `v1.3` later the same night (PR #128), after this run had started, and is not used here. The run uses Neo4j Community 5.26.0 with APOC core 5.26.0. Both came from the release tarballs and ran locally, with a password set for this run only. Every mutant was evaluated by `bin/firewall.ts evaluate --symbolic-only --format json` through the same CLI path as `validate-reference.ts`. The default v1.3 compile applies the role-token rule, member facts and v1.3 tiers. The engine was checked first: `validate-reference.ts --style hexagonal` and `--style ddd` reproduced 11/11 and 12/12 planted cases with no mismatch.

The real projects were cloned at their pinned SHA and installed with `--ignore-scripts`. DDH and bitloops have no lockfile, so the installed versions are whatever npm resolved on 2026-10-16. Nothing from them is committed. All three type-check with 0 errors under their own tsc. How the specs were written is in catalogue §5.

- **Sampling.** Per base and entry, `findSites` runs first, then the precondition pass (the pipeline's `evaluatePreconditions`, which includes its cycle cap). The sample is seeded (`mulberry32(fnv(baseId|opId) ^ 20261016)`) and holds at most 10 sites per positive and 6 per twin. The hexagonal operators run on `hexagonal` specs. MO-H01, H02 and H05 also run on `ddd` specs, because the DDD library composes `dependency-direction-graph` and `domain-purity`. The DDD operators run on `ddd` specs.
- **Detection and false fire.** Defined in catalogue §3. A positive counts as detected when every expected key appears as a row the baseline does not have. A twin false-fires when it adds any blocking row.
- **Run.** The eight bases ran one per process, one after another, because they share one Neo4j database. Wall clock was about 2.5 h. 780 rows: 471 detected, 10 missed, 297 silent, 0 false fires, 2 type-check rejections, 0 apply errors.

## 3. Compile success

778 of 780 applications type-check with the base's tsc (99.7 %). Both rejections are MO-H06 seeds on real projects, in `default-new` form. The added public `readonly` parameter property changes the host class's structural type. On zddd, an object literal elsewhere stopped being assignable to the DTO class `CheckSagaApiDto`. On bitloops, an `Either<…, InvalidTodosCounterError | …>` stopped matching a declared response type. These are honest rejections: the edit is legal code, but it breaks a structural contract the project relies on. Under BR-U5a-07 they are dropped and not repaired.

### The ten misses: FF-P06 cannot see optional injected parameters under `strictNullChecks`

All ten misses are MO-H06 on domain-driven-hexagon. In every one, FF-S01 and FF-S04 fired, but FF-P06 `domain-state-purity` did not. The table splits MO-H06 by injection form and by the project's null checking:

| Base | `strictNullChecks` | `default-new` (`x: T = new T()`) | `optional` (`x?: T`) |
|---|---|---|---|
| ref-hexagonal | on (`strict`) | 10/10 | — |
| zddd | **off** | 8/8 | 1/1 |
| bitloops | off (no `strict`) | 4/4 | 5/5 |
| ddh | **on** (`strict`) | — (no adapter there is constructible without arguments) | **0/10** |

The extractor writes CONSTRUCTOR_INJECTS from the parameter's type symbol (`src/apg-extractor/edge-extractor.ts`, `param.getType().getSymbol() ?? getAliasSymbol()`). Under `strictNullChecks` the type of `x?: T` is the union `T | undefined`, which has no symbol, so no edge is written and the rule sees nothing. With null checks off the union collapses to `T`, and the same edit is detected. The trial run predicted this before the full run; the full run confirms it on both sides. This is a **tool defect** (a recall gap of the blocking FF-P06 constructor half on strict projects), not an operator defect, so the misses stay in the figures. The same gap hides optional injected ports from the advisory FF-P02 ratio.

A proposed fix, not made here: resolve `getNonNullableType()` before taking the symbol. That is an extractor change; it touches the frozen instrument's extraction and needs the usual byte-identity check.

### Collateral

These are blocking rows that a positive adds beyond its expected keys. They are recorded, and they do not change detection:

- **Cycles.** All cycle collateral is FF-S02, because a new core→adapter or use-case→adapter edge closes a cycle wherever the adapter already imports the core (the usual case). Rows affected: MO-H01 6 of 40 hexagonal rows, MO-H02 1, MO-H03 1, MO-H06 9 of 38. The mutation pipeline's cycle cap (BR-U5a-13) bounds this; the cap rejected 16 MO-H01 sites.
- **One aggregate-boundary row.** One MO-D05 seed on ref-ddd imported an unpublished file of another context that is also an inner entity, so FF-DT01 fired as well.
- **Advisory rows.** These appear too, mainly FF-S03 (40), FF-P02 (20) and FF-C03 (20) on positives. Twins added only advisory metric/convention rows (FF-C03 7, FF-CV05 3, FF-C05 1). For example, a new created file has no test (FF-CV05).

## 5. Defects found and fixed during the work

1. **Twins on `ddd` specs (trial run).** MO-H01n and MO-H02n crossed bounded contexts and hit FF-DS02/DT01/DT02 (4/4 trial false fires). Fix: the `ddd-boundary` precondition. On a `ddd` spec, hexagonal-operator edges must stay inside a context, or reach only published files, and must never reach an inner entity from outside its aggregate. Applied to positives as well, so S01/S04 seeds are not attributed to DDD rules.
2. **MO-D03 on parameter properties (trial run).** Dropping `readonly` from `constructor(readonly value: string)` turned the property into a plain parameter, and the mutant did not compile. Fix: add `public` before dropping `readonly`.
3. **MO-D02 inside the aggregate module (trial run).** A repository created in the aggregate's own folder cannot breach FF-DT01. The key is now not expected there (`detail.notExpected`).
4. **MO-H04 role names (full run).** The first full run picked adapters with the frozen substring test (`c.name CONTAINS role`). The v1.3 compile selects by suffix instead (`src/fitness-compiler/v13-role-names.ts`), so one DDH seed, `SqlRepositoryBase`, lay outside the template's selection. The rule did not miss it: the operator chose a site the rule does not check. Fix: MO-H04 sites follow the suffix rule. MO-H04 and MO-H04n were re-run on the four hexagonal bases with the same seeds, and their rows replace the first ones in `run.json`. Before the fix: 9/10 recall, 21 candidates and 10 eligible. After: 9/9, 17 candidates and 9 eligible.

5. **Frozen files (owner review).** The first version widened the `SiteKind` / `PreconditionReason` unions in `scripts/lib/mutation/types.ts` and `PRECONDITION_REASONS` in `catalogue-parser.ts`. `types.ts` is hash-frozen for the judge catch test (`Docs/v1.3/judge-catch-frozen.md`, `b505a52a…`). Fix: both files are restored byte-identical to `v1.3`, and the new values live in `scripts/lib/mutation/hexddd/types.ts`. The pipeline treats kinds and reasons as opaque strings, so behaviour is unchanged. A count-only pass after the move reproduces all 124 feasibility cells of the run (candidates, eligible, rejections by reason), so the detection rows stand without a re-run.
6. **Third-party hunks (owner review).** The `diff` of each real-project row holds context lines from the three MIT-licensed projects. `results/v1.3-operators-hexddd/THIRD-PARTY-NOTICES.md` now gives the repositories, commits, copyright notices and the MIT text.

## 6. Limits

- **Specs and dependencies.** The real-project specs and aggregate declarations are the author's. A blind re-derivation (`Docs/v1.3/validation-protocol.md` §1) is not done. DDH and bitloops were installed without a lockfile.
- **Correlated sites.** Recall CIs assume independent sites. With 3 real projects, the per-project spread matters more than the interval. Recall was 1.0 on every base for every operator except MO-H06 on DDH (§4).
- **What the operators test.** They plant structural facts that the templates read directly. A recall near 1 shows that the queries, layer binding and extraction pipeline agree with the rule definitions on realistic code. It does not show that the definitions capture the styles; that is FR-V7 labelling and the blind manifests.
- **Not covered.** No operator for FF-S01 under a `ddd` spec at the context level (cross-context imports are DS02's). None for the FF-P06 field half (N/A by tier), the FF-DS02 deep-import gap (probe g03), or the advisory DT05, DT06 and P02.
