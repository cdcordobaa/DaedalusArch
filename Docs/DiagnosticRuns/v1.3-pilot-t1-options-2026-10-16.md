# v1.3 loop pilot: options for tool defect T1, re-scored offline (2026-10-16)

**Status: options built and measured. No option is applied and no decision is taken.** The author picks the construct option (§6). Base: `v1.3-pilot-run` at `f2de162f` (PR #170). Pilot report: `Docs/DiagnosticRuns/v1.3-loop-pilot-2026-10-16.md`. Memo: `Docs/v1.3/pilot-outcome-memo.md`.

## 1. Summary

- **T1:** the ISE inferred no aggregate from either DDD step-1 tree, so the frozen spec keeps FF-DT01 (aggregate-boundary) and FF-DT02 (repository-aggregate-root) with `aggregates: []`. The spec validator accepts this spec, but the pipeline rejects it with BR-SPEC-10. As a result, all 8 DDD snapshots are unscored and §5 is undetermined.
- **Four options, all off by default:** (a) not-applicable, (b) reject up front, (c) exclude and record, (d) vacuous pass. Option d is my addition. The default behaviour is unchanged (§2).
- **Re-score:** the 8 kept DDD snapshots were re-scored under every option, offline, with `--engine cypher-interp`. There was no LLM call, no Neo4j and no agent re-run.
- **Results:**
  - Options a, c and d give the same blocking counts. The `none` arm has **1 blocking finding at every step, and 0 are new**. The `gate` arm has 2 blocking findings at every step, and 0 are new.
  - Option b rejects both frozen specs, so every DDD snapshot stays unscored.
- **What memo §5 would conclude:**
  - Under a, c or d, the zero branch is met: Study 2's primary outcome would move to the advisory-tier erosion rate.
  - Under b, §5 stays undetermined, as it is now.
  - I have not applied either conclusion.
- **Construct point:** on these trees, FF-DT01 and FF-DT02 could not have produced a finding under *any* option, even with declared aggregates. The agent puts an aggregate's root and its entities in one file, and both rules work at file level (§5). So under a, c or d, the DDD "zero" rests on 5 of the style's 7 blocking rules.

## 3. Method (offline)

- **Script:** `scripts/v1.3/loop-pilot-t1-rescore.ts`. For each DDD run and step, it takes the step's `finalCommit` from the run's `snapshots.git` and evaluates it against the run's frozen spec, as recorded in `evaluatorSpec`. The evaluation uses the firewall CLI: `--symbolic-only --scoring v1.3 --engine cypher-interp`, the harness tsconfig, and `--empty-aggregates` set to `fail`, `not-applicable`, `exclude` and `vacuous` in turn.
- **Option b:** the validator runs with `rejectEmptyAggregates` on the frozen spec and the step-1 tree. It is read the way the freezer reads it (`freezeCheck`).
- **Memo §3:** applied as in `loop-pilot-analyse.ts`:
  - blocking findings come from the step's final snapshot;
  - FF-P06 FLOWS_TO rows are N/A;
  - a finding is new at step s ≥ 2 if no earlier step of the same run holds the same identity.
- **`node_modules`:** each run's `work/node_modules` linked into the pilot machine's harness root, which was not kept. So the pinned generator skeleton (`scripts/generator/skeleton/`) was reinstalled with `npm ci --ignore-scripts` in a scratch directory and linked in its place. The registry install was the only network use.
- **Engine check:** the in-process engine was also run on the 16 scored Clean and Hexagonal snapshots. It matched the recorded (Neo4j) blocking count at **16 of 16** steps. This is a weak check: every recorded count is 0. It shows the engine adds no spurious blocking finding on these trees; it does not show that it finds the same non-zero rows.
- **Command:** `npx tsx scripts/v1.3/loop-pilot-t1-rescore.ts --out-root experiments/loop-pilot/run-2026-10-16/outputs --work <scratch> --dest experiments/loop-pilot/run-2026-10-16/analysis-t1-options --node-modules <scratch>/skeleton/node_modules --engine-check`. Wall time was about 3 min.
- **Outputs** (in `experiments/loop-pilot/run-2026-10-16/analysis-t1-options/`):
  - `steps.json`;
  - `new-blocking.json` (empty);
  - `option-b.json`;
  - `engine-check.json`;
  - `check-correct-jobs.json` (empty, since nothing is new);
  - `reports/<option>/<run>/step-NN.json`, the full reports, with the scratch path written as `<work>`.

**The construct gap behind a, c and d.** FF-DT01 and FF-DT02 match `IMPORTS`/`RE_EXPORTS` edges between files: an importer outside the aggregate's module, and a target file that is an inner entity. In both DDD runs, the domain folders are flat. Each domain file holds its root together with its entities:
- `none`: `deployment.ts` and `volunteer.ts` have 1 class each;
- `gate`: `incident.ts` has 3 classes and `volunteer.ts` has 2;
- no domain file imports another domain file.

An inner entity that lives in the root's file has no file of its own, so no edge can target it. So even if the aggregates had been declared by hand, these two rules would have returned no row on any of the 8 snapshots. Under a, c and d, the DDD zero is therefore a zero over the strategic rules, FF-DT03, FF-DT04 and FF-S01. It says nothing about aggregate erosion. That is the construct question below.

## 6. Author question

**Question T1 (construct validity).** The DDD task's blocking set defines the style by seven rules. Two of them, FF-DT01 aggregate-boundary and FF-DT02 repository-aggregate-root, could not observe anything in either DDD run. No aggregate was inferred, and even with declared aggregates, these file-level rules cannot see entities that share their root's file. Does a DDD run that measured only the other five blocking rules (FF-DS01, FF-DS02, FF-DT03, FF-DT04, FF-S01) count as valid evidence for memo §5's "no new blocking finding in the `none` arm"?

- **A.** Yes, with the gap on the record. Score with option **a** (`--empty-aggregates not-applicable`): FF-DT01 and FF-DT02 appear in every DDD report as declared but `not-applicable`. The DDD `none` run then has 0 new blocking findings, so §5's zero branch applies. The §5 note must state that DDD aggregate erosion was not measured. Making the option a default for Study 2 needs an ADR and a development-set check (memo §6).
- **B.** No. A DDD run in which the aggregate rules cannot apply is not a measurement of the DDD style. Adopt option **b** (reject at validation and freeze). The DDD runs stay unscored and §5 stays undetermined until the DDD runs are re-run on a fresh out-root after a memo revision (pilot report option 2), or until the memo is revised to stand on two tasks (option 3).
- **C.** Yes, but treat the gap as a scoring decision for this pilot only. Score with option **c** (`--empty-aggregates exclude`): the rules are left out of the declared set and the exclusion is recorded as a warning. The numbers and the §5 branch are the same as under A, and the tool's rule semantics stay untouched for Study 2.

Option **d** (vacuous pass) is not offered. It gives A's numbers but records the two rules as checked and passed, which misstates what was measured.

**Recommendation: A.** Under a, c and d, the zero-branch reading rests on the same five rules. Option a is the only one that writes the limitation into each report, as a reason on the rule itself, so a reader of any DDD report sees it.
- B leaves the decision blocked behind a re-run that would probably hit the same blindness, because flat domain folders and co-located entities are the agent's own choice.
- C gives the same numbers as A, but keeps the gap only in a warning and in this document, and it shrinks the declared denominator.
