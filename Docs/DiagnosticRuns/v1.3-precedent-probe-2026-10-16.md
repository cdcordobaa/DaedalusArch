# v1.3 precedent-propagation probe: does an agent copy a shortcut that the tree already has?

**2026-10-16. Feasibility probe only. Exploratory, development set.** One Claude session (Opus, the session that wrote
this report) wrote the seed trees and acted as the coding agent in all 16 cells. This is not the loop harness, not the
loop pilot and not Study 2. n = 8 cells per condition, so every number below is a count, not an estimate. No sealed
directory was read. No frame, spec, preset, template or tier was changed. No construct switch was used. No LLM call was
made.

Plan, committed before any seed, step or score: `Docs/DiagnosticRuns/v1.3-precedent-probe-plan.md` (commit `ce958a0f`).
Seeds (fixtures): `examples/precedent-probe/`. Data: `results/v1.3-precedent-probe/`.

**For Study 2 (D1, D11):** this probe gives no support for proposing brownfield seeding as a lever *on the strength of
this agent*. It also does not rule the lever out (§4): the agent here is the agent least likely to copy (§5).

## 1. Why this probe

The floor probe (#161) found blocking erosion only as step-1 layout habits in layered code, and none in hexagonal code.
The human-written repositories of the external set (#133) fail in 10 of 15. One candidate mechanism for that gap is
brownfield imitation: a developer who extends a tree copies what the tree already does. If an agent does the same,
Study 2 could seed step 0 with a legacy tree and escape the floor, and the thesis would gain a mechanism statement.

## 2. Method (as planned; deviations in §6)

- **Domains.** Four new domains, none overlapping the reference apps, E1, the pilot tasks, #161's tasks or the unit
  fixture hosts (plan §2): `tool-library` and `bike-repair` (hexagonal, `presets/hexagonal.yaml`), `choir-rehearsals`
  and `kayak-rentals` (clean, `presets/clean-architecture.yaml`).
- **Seeds.** Each domain has two trees of 11–16 files (181–224 LOC). They differ in one use case only. In `planted/`
  the use case takes the concrete adapter class as a constructor parameter. In `control/` it takes the port interface.
  In both trees the port exists, the adapter implements it, and the composition root injects the same object. The
  precedent use case is the only existing user of the adapter that the steps need.
- **Seed acceptance** (before any cell): each planted tree has exactly one blocking finding, FF-S01 on the precedent
  edge (`dependency-direction-graph` for hexagonal, `dependency-direction` for clean). Each control has 0
  (`results/v1.3-precedent-probe/seeds/`). The precedent rule set is therefore {FF-S01}.
- **Cells.** 4 domains × {planted, control} × {x1, x2}. Each step was applied to the **seed** (not chained), in the
  seeded order of plan §6. The frame was `STYLED_NEXT_STEP_TEMPLATE`, rendered by hand
  (`results/v1.3-precedent-probe/scripts/cells.py`; every cell's prompt is in `cells/<cell>/prompt.txt`). Each cell
  was type-checked and committed in a scratch git repository outside the checkout. **All 16 were written before any
  was scored.**
- **Scoring.** `firewall evaluate --symbolic-only --engine cypher-interp --scoring v1.3` on each snapshot
  (`scripts/evalsnap.py`, `scripts/score_cells.py`). Identity follows the pilot memo §3. "New" means not present in
  the seed. "Same shape" means a source under `src/application/**`, a target under the precedent's outbound folder,
  and a rule in {FF-S01}. Then `check-correct.ts --tiers blocking` (`correctness/`) and `scripts/aggregate.py`.

## 4. Reading

The pre-stated reading applies: null (plan wording: "agents do not copy this shortcut at this n"). Scoped to the data, **this agent did not copy the shortcut**. It says only
that *this* agent, aware of the style and told to "follow the architecture the project already uses", typed each new
use case against the port in all 16 cells. It did so even when the nearest example in the tree did not, and even when
it had to widen a port that the precedent does not use.

What this does and does not mean for D11:

- It is **not** evidence that brownfield seeding fails as a Study 2 lever. The generator of record (the pilot's
  Sonnet via the CLI, blind to the instrument) was not tested, and §5 explains why this agent is the worst case for
  copying.
- It **is** evidence against the simplest version of the lever: a single precedent in a small, otherwise clean tree,
  with an explicit style frame, does not pull a strong agent off the port. A lever with a chance of working would need
  a precedent that is the *only* way the tree reaches the capability (no port exists), or several precedents, or a
  frame without the style name. Each of these is a new design that would need its own plan. None was tried here.
- So the recommendation to the author is: **do not propose brownfield seeding for D11 on this evidence.** If the
  author wants the lever tested, the test belongs in a blind run with the generator of record. That needs the
  author's login (backlog §3) and is out of scope for the cloud.

## 5. Limits

- **One agent, one session, and it knows everything.** The same Opus session wrote the plan, the hypothesis, the
  seeds and the step texts. It had read the tier table and the presets, and it wrote all 16 cells. This biases toward
  clean code, so toward this null, as in #161 §6. It can also bias the other way. Nothing here estimates a rate.
- **Paired cells are near-duplicates.** For each (domain, step), the planted and control cells were written by the
  same agent minutes apart, with the same design. They are not independent draws.
- **Seeds are small, uniform and author-written.** They have one precedent each, a clean remainder, and a port that
  exists. Real legacy trees are larger and messier and carry many precedents.
- **The cells are independent extensions of step 0.** Accumulation over a trajectory is not measured.
- **Only type-checked.** There are no acceptance tests (D12).
- **The domains are unchecked against the sealed list.** They were chosen without reading it. The author must check
  them before any reuse (backlog §3).

## 6. Options taken under delegation

1. Steps are applied to the seed, not chained (plan §6). This keeps the exposure at exactly one precedent per cell.
2. The clean spec is the canonical preset `presets/clean-architecture.yaml` (the source of the layout sentence), not
   the E1 spec `specs/clean-arch.yaml`.
3. The precedent is a constructor parameter typed by the concrete class, not a `new` inside the use case. The
   composition root builds the object in both conditions, so the trees differ in one file.
4. The frame says "step 2 of 3", and the domain titles were written for this probe.
5. The probe skeleton used `@types/express 5.0.3` and `@types/node 22.15.30`, not the E1 pins `5.0.6` / `22.19.15`.
   All trees were re-checked with the exact E1 skeleton: 0 errors (§3). Scoring does not depend on `@types`.
6. Python's `random.Random(20261016).shuffle` fixed the cell order (CPython 3.11).

## 7. Reproduce

```bash
# pinned skeleton (any directory): scripts/generator/skeleton/package.json, npm install --ignore-scripts
export PROBE_SKEL=<skeleton dir>
python3 results/v1.3-precedent-probe/scripts/evalsnap.py examples/precedent-probe/tool-library/planted presets/hexagonal.yaml   # one seed
python3 results/v1.3-precedent-probe/scripts/cells.py setup <cellsdir>        # 16 scratch projects at the seed (the steps are in cells/<cell>/step.diff)
python3 results/v1.3-precedent-probe/scripts/score_cells.py <cellsdir> $PWD/results/v1.3-precedent-probe
npx tsx scripts/v1.3/check-correct.ts --jobs results/v1.3-precedent-probe/correctness/jobs.json --tiers blocking --out results/v1.3-precedent-probe/correctness
python3 results/v1.3-precedent-probe/scripts/aggregate.py results/v1.3-precedent-probe
```

To replay a cell from a fresh setup, apply its `step.diff` with `git apply`.
