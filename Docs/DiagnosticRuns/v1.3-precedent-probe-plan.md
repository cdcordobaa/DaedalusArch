# v1.3 precedent-propagation probe: plan (committed before any seed tree, step or score)

**2026-10-16. Feasibility probe only** (night backlog job #6, F2). One Claude session writes the seed trees and acts as
the coding agent for every extension step. It is not the loop harness, not the loop pilot and not Study 2. No sealed
directory is read, no Study 2 task is named or derived, no LLM call is made, no frame, spec, preset, template or tier is
changed, and no construct switch is used (status-quo scoring only).

## 1. Question

Does an agent that extends an existing tree copy a shortcut the tree already contains? Concretely: when one application
use case already imports a concrete outbound adapter class (a blocking FF-S01 edge), does the agent's *new* use case,
written for a step that needs the same adapter, add a new blocking finding of the same rule and shape, more often than on
the same tree where that use case receives the port instead?

## 3. Seed trees

Each domain has two trees that differ in **one use case only**:

- **planted**: one existing application use case imports the concrete outbound adapter class directly and takes it as a
  constructor parameter of that class type. The port interface exists in the tree and the adapter implements it; only
  this use case bypasses it. Hexagonal: `src/application/**` imports `src/adapters/outbound/**` (FF-S01
  dependency-direction-graph, blocking). Clean: `src/application/**` imports `src/infrastructure/**` (FF-S01
  dependency-direction, blocking).
- **control**: the same tree, with that use case typed against the port and the concrete adapter injected by the
  composition root.

Size: about 10–15 files, in-memory storage, HTTP exposed with express, type-checked with the E1 pin (`typescript
5.9.3`, `express 5.2.1`, harness compiler options, as in #161 `scripts/mktsconfig.sh`). The precedent use case is the
**only existing user** of the adapter that the extension steps need, so it is the nearest example in both conditions.

Acceptance of the seeds (checked before any step is written): every planted tree's blocking findings are exactly the
findings on the planted edge (one source file, one target), and every control tree has 0 blocking findings. If the
planted edge triggers more than one blocking rule, all of them form the precedent's rule set (recorded in the report);
nothing is changed in the rules to make it one.

## 7. Outcome and analysis (fixed now)

- **Blocking finding**: a finding of a rule blocking for the style in `Docs/v1.3/rule-tiers.md`, from
  `firewall evaluate --symbolic-only --engine cypher-interp --scoring v1.3` with the domain's preset.
- **Identity** (pilot memo §3): rule id, template, file, target; for a cycle, the set of files; lines ignored.
- **New**: an identity in the cell's snapshot that is not in its seed tree's snapshot.
- **Same shape as the precedent**: a new blocking identity whose source file is under `src/application/**` and whose
  target is under the precedent's outbound folder (`src/adapters/outbound/**` for hexagonal, `src/infrastructure/**`
  for clean), of a rule in the precedent's rule set (§3). Every other new blocking identity is "other".
- A new identity counts only if `scripts/v1.3/check-correct.ts --tiers blocking` labels it `correct`; `incorrect` is a
  tool defect, logged and not counted; `not-checkable` is listed with a one-line reading of the code.
- **Cell outcome**: 1 if the cell adds ≥ 1 counted same-shape identity, else 0.
- **Primary quantity**: share of planted cells with outcome 1 (of 8) and share of control cells with outcome 1 (of 8),
  overall and as a 2×2 per style (2 domains × 2 steps per condition and style).
- Secondary, descriptive: new "other" blocking identities per cell; whether the precedent edge itself survives in the
  planted cells (the agent may repair it unprompted); new advisory counts are not analysed.

**Pre-stated reading.** Planted ≥ 4/8 (≥ 50 %) **and** control ≤ 0/8 (≤ 10 % of 8 rounds to 0) → "brownfield seeding is
a viable Study 2 lever; propose it to the author for D11". Anything else → "null; agents do not copy this shortcut at
this n". With n = 8 per condition there is no test and no interval; the numbers are counts.

## 8. Known limits (stated before running)

- One agent, one session, Opus, writing all 16 cells; it also wrote the seeds, the steps and this plan, and it knows the
  hypothesis and the instrument. Knowing the hypothesis can bias either way; nothing here estimates a rate.
- The seeds are author-written (by this session), small and uniform; real legacy trees are larger and messier.
- The cells are independent extensions of the seed, not a multi-step trajectory, so accumulation is not measured.
- Type-checked only; no acceptance tests (D12).
