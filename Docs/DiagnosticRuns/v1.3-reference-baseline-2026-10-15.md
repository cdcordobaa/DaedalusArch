### The views, and why there are four

- **Author, literal.** The runner's own comparison (`compare.ts`), unchanged. `report.md` is this view.
- **Author, cycle key normalised.** Every FF-S02 row from the tool puts the cycle path in `filePath` (`"src/domain/entities/Loan.ts,src/domain/entities/Member.ts,src/domain/entities/Loan.ts"`). Under the literal key that row never matches the manifest's `file`, so each planted cycle counts as one miss plus one false positive. The normalised view keys a cycle on its sorted file set, on both sides. Only FF-S02 changes between the two views.
- **Blind, expanded.** Each blind finding contributes its `ruleId` and every mapped id in its `alsoMatches`, with the same file and target. This is the headline blind view, because the author-manifests also list every rule that one defect breaks. FF-S02 is normalised here as well.
- **Blind, primary.** Only each finding's own `ruleId`. This is a sensitivity check. Pooled blocking recall is 0.83 (38/46) and pooled precision 0.35 (38/110). Precision falls because the tool reports FF-S04 and FF-P06 next to FF-S01, as the author-manifests expect.

### Blind name mapping

The mapping is in `blind-rule-mapping.json`. The hexagonal template names map through the library aliases (`dependency-direction-graph` = FF-S01, `layer-skip-graph` = FF-S03, `core-isolation` = FF-S04, `port-dependency-inversion` = FF-P02, `port-adapter-pattern` = FF-P03). The seven "DDD …" row names map through `DDD_RULE_TIERS`.

**Guessed mappings:** two, each used once.

1. `OTHER: shared code outside every declared layer and context` (ddd case-07, v07) → FF-DS01. Its construct is FF-DS01's condition, and FF-DS01 has no row in `rule-tiers.md`.
2. `OTHER: repository implementation depends on an application DTO` (nestjs case-09, v02) → FF-S01. The annotator listed FF-S01 in `alsoMatches`, but doubted that the nestjs layer list is a dependency order.

**Unmapped:** three, kept as rows in the sheet.

- `OTHER: public API publishes an application service; consumer bypasses its ACL` (ddd g02);

- `OTHER: cross-module import not via module exports`, which appears only in `alsoMatches`.

**Not scored:** nine blind findings name a rule outside the style's compared set:

- FF-S03 in clean and nestjs;
- FF-SO01;

**This is where the barrel defect shows.** Every literal disagreement in layered and ddd (18 + 18) is one barrel import seen from two sides:

- the blind graph has the literal edge to the barrel (`OrderingAcl.ts -> ordering/index.ts`, and `OrderView.ts -> business/model/index.ts` in layered n03);
- the tool has, in its place, the routed edge to the declaring file (`-> ordering/contracts/OrderSummary.ts`, `-> business/model/Order.ts`).

That routed edge is exactly the blind graph's `viaReExport` edge, so the tool scores 18/18 on viaReExport edges and **0/18 on the literal barrel edges**. The author's DDD expected graph shows the same defect (E1 in the DDD notes): its key edge `OrderingAcl.ts -> ordering/index.ts` is the only edge missing among the author graphs. The four patch-style author graphs contain no barrel import in the clean variant, so they agree 269/269.

**Hexagonal: a blind-package defect, not a tool defect.** The blind package was cut from a tree without `src/application/ports/out/` (the `.gitignore` `out/` defect, fixed in `b47c11c` by reconstructing the five port files). The blind annotator recorded the edges into those files as unresolved, but still listed them, so they match. The 60 tool-only edges are the outgoing edges of the five reconstructed port files, 4 per case. The annotator never saw those files. They are excluded from the precision above and shown separately. The same defect weakens the blind findings for hexagonal FF-P03 and FF-P02. The annotator judged them "as if the ports were where the imports say".

**Layers:** the tool and the blind annotator agree on every file, including the unassigned ones (`main.ts` in layered and nestjs; `index.ts` and `contracts/**` in ddd).

## Top mismatch causes

Ranked by rows affected. Each cause comes with one concrete example from `adjudication.csv` or `report.md`.

   - Neither manifest expects it. Under closed layering a business service holding a gateway is the intended dependency.
2. **The FF-S02 cycle key (tool output format).**
   - Scale: all five planted cycles are missed under the runner's key and each becomes a false positive. That costs 1 to 2 points of blocking recall in four styles.
   - Example: clean `v03-domain-entity-cycle`. The tool row has `filePath = "src/domain/entities/Loan.ts,src/domain/entities/Member.ts,src/domain/entities/Loan.ts"`, `target = "src/domain/entities/Member.ts"`. The manifest has `file = src/domain/entities/Loan.ts`. The cycle *is* detected.
   - Adjudication candidate: a tool defect in the output (filePath is not a file), or a harness gap in `normaliseFindingPath`.
3. **Name-heuristic false positives (TDC-2, TDC-3, RDQ-3).**
   - Scale: three of the four near-miss styles have a new false positive. Two of them are blocking FF-P03 rows.
   - Example: clean `n02` (case-04), FF-P03 on `src/infrastructure/http/CsvReportWriter.ts`, with `type=REPOSITORY_PATTERN_VIOLATION`. The class name contains "Repo" (Report).
   - The other two: hexagonal `n03` FF-P03 on `GatewayRetryPolicy.ts`, and nestjs `n03` FF-P02 on a sibling-service injection.
4. **Barrel routing (extractor semantics; the target of ADR-V13-01).**
   - Scale: 18 literal edges are missing, and one DDD author key edge.

## What the barrel fix (ADR-V13-01) should change

The fix keeps the barrel hop on an import edge, so the literal edge to the barrel file exists next to the routed edge. On this reference set it should:

- **Graph:**
  - turn the 18 blind-only literal barrel edges into matches, with the routed edges staying as the viaReExport edges;
  - lift ddd literal agreement from 0.984 and layered from 0.998 to 1.000;
  - restore the DDD author key edge (16/16).
  - The fix must not drop the routed edge. 18/18 viaReExport agreement and every rule that keys on the declaring file depend on it.
- **Findings:**
  - make `g03` separable from `g02`, so that FF-DS02 can flag the deep import (M2) without reopening the barrel false positive (M1). DDD blocking recall would rise from 0.78 to 0.89 (8/9) if FF-DS02 is rewritten to use the hop. The extractor change alone does not change the query.
  - The g02 literal-reading question (the blind manifest's ambiguity 7) becomes computable either way.
- **Should not change:** any other number in this report. Every other mismatch above has a cause unrelated to barrels: FF-P06 binding, the cycle key, name heuristics, construct readings, member facts. A rerun after the fix that moves any of them is a regression to explain.

The FF-DT03 miss (g01) still needs member facts. The cycle key (cause 2) is a separate one-line decision: change the tool's FF-S02 `filePath`, or teach the runner to read a cycle path. Neither is part of the barrel fix.

## Run notes

- **Neo4j interference.** The first live run was discarded.
  - Another worktree's jest suites used the same `daedalus-neo4j-bt` while it ran (01:09:10Z to 01:10:01Z). Each ingestion wipes the database.
  - Effect: `nestjs/v10` got FF-P03 rows on the DDD fixture's files (`src/billing/infrastructure/InMemoryInvoiceRepository.ts`), and lost its three expected findings. Three hexagonal raw files got FF-C04 rows on DDD files. The runner raised no error.
  - A guard then waited for 90 s of quiet, and polled once a second for any other jest or `firewall evaluate` process. Two guarded runs (`run1` 01:14:23Z, `run2` 01:17:39Z) saw none and produced **byte-identical** raw outputs. `run1` is the saved baseline (`run-provenance.json`).
  - The shared database has no isolation between agents. A Study run on it needs an exclusive lock, or its own instance.
- **Admission bypass.** The heavy-command hook blocked on swap (11.3 of 16 GB) while `memory_pressure` reported 43 to 54% free. `npm ci`, the live runs, the graph extraction and `tsc` were each run once with `HEAVY_ADMISSION_BYPASS=1`, one at a time.
- **Temporary copies.** The materialised variants were written under the session scratchpad (`TMPDIR`), not under the worktree. Inside the worktree, module resolution would reach the repository's `node_modules` (real `express` and `typeorm`), and the vendored ambient typings the patch projects rely on would no longer be in force. The copies were removed after each run.
- **Not run:** jest. No source under `src/` changed. `tsc -p tsconfig.scripts.json` is clean with the three new scripts.
