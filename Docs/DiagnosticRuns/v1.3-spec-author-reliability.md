# v1.3 K2: spec-author reliability on the external set

Development-set / exploratory result. Nothing here claims validity on its own. Plan, blinding and pass criterion:
`Docs/DiagnosticRuns/v1.3-spec-author-plan.md` (committed first, 70ca5fb2). Branch `v1.3-spec-author-reliability`.

## Verdict against the pre-stated criterion

**Not reliable at this threshold.** Pooled file-to-layer κ = **0.77** (raw agreement 0.78, 1,628 files); **4 of 15**
repos reach κ ≥ 0.80 (criterion: pooled κ ≥ 0.80 and ≥ 12/15 repos). And the downstream numbers move more than the
mapping does: Spearman ρ over blocking counts = **0.58**, same pass/fail verdict on **10/15** repos (verdict κ =
**0.21**), Bland–Altman 95 % limits of agreement on B − A blocking = **[−28, +33]** around a mean of +2.4.

## What was done

1. **Blinding.** Author B (this session) read only `results/v1.3-external/selection.json` from
   `origin/v1.3-external-set`, the cloned trees at the pins, their READMEs and `presets/*.yaml`. The 15 B specs and
   their rationale were committed and pushed at **d37841fb (2026-10-16T05:22:42Z)**, before any other file of #133
   was opened. The plan commit (70ca5fb2, 05:13:21Z) precedes both. Known to B anyway (stated in the plan): the
   night backlog's "10 of 15 fail" and "283 blocking" totals; no per-repo number.
2. **B protocol.** Preset copied verbatim; only layer globs, the DDD declarations and excludes authored; no layer
   added or renamed (`results/v1.3-spec-author-b/spec-rationale.md`, `generate-specs.py`). All 15 pass
   `firewall validate`.
3. **Same tool commit.** A was evaluated in #133 at 133c261a on Neo4j 5.26.24. Both A and B were evaluated here at
   `origin/v1.3` **a6723c34** with `firewall evaluate --symbolic-only --engine cypher-interp --scoring v1.3
   --format json`. A's re-run reproduces #133's blocking count on **all 15 repos** (18, 9, 0, 0, 8, 4, 0, 72, 6, 1,
   0, 3, 92, 50, 20), so engine and commit change nothing for A.
4. **Measures.** `scripts/v1.3/spec-author-agreement.ts` (labels + compare; statistics in
   `scripts/v1.3/lib/spec-author-agreement.ts`, unit-tested). Files: git-tracked `.ts` under the analysis root,
   minus `node_modules/`, `dist/`, `*.d.ts`. Labels: the layer (same first-match rule as the layer annotator),
   `excluded`, or `unmapped`. Label basis: layer name when A and B use the same name set, else resolved kind (the
   three clean-architecture repos, where A added layers). Pooled κ uses repo-qualified labels (a file's label is
   `<repo>:<layer>`), so its chance agreement is small (p_e = 0.02) and it sits close to raw agreement; the
   criterion fails on the per-repo count (4/15) whichever way the pooling is done.

### Where the disagreement comes from

- **Exclusion policy** (`excluded-vs-included`, 161 files). B excluded tests, mocks and fixtures; A mostly did not.
  Post-hoc sensitivity, not pre-stated: merging `excluded` with `unmapped` raises pooled κ to 0.82. It does not
  rescue finance-project-ddd (0.56), where A's domain and application globs also cover the `tests/` and `mocks/`
  folders inside those layers.
- **Layer granularity** (`directory-choice`). In clean-architecture A added layers the preset lacks (pvarentsov:
  `presentation` and `main`; B keeps three rings and puts the HTTP API in infrastructure). Under A, presentation →
  infrastructure config imports are 18 FF-S01 violations; under B they are inside one layer. Verdict flips from
  fail to pass on a decision about whether the interface-adapter ring is its own layer.
- **What counts as "domain" when a repo has none** (zeldaplay-api). The nestjs preset maps `src/models/**` to domain;
  B followed that for the repo's `models/` folders (DTO classes), A mapped them to application. 24 files, 0 → 22
  blocking (FF-S01 11, FF-S04 11), verdict flips to fail.
- **Cross-cutting folders.** talento90: B put all of `src/lib/**` (hasher, JWT, health) in persistence, A only
  `lib/database`; 4 → 19 blocking. event-sourcing-ddd: the two spec sets differ on **2 files** (`src/constants/*`,
  DI tokens): A puts them in composition, B leaves them unmapped; κ = 0.95, yet 20 → 4 blocking, because every file
  importing the DI tokens becomes an FF-S01 edge into composition under A.
- **DDD declarations** were near-identical across authors (same contexts, aggregates, inner entities, value-object
  and repository globs in finance-project-ddd; same aggregates in ddd-forum). DDD rule counts barely moved (ddd-forum
  DS02 26 → 24, DT01/DT02 equal; finance DS02/DT01/DT04 equal); the differences are in the hexagonal layering globs
  (FF-S01).

### Reading

File-level agreement between two blind authors is moderate-to-good (pooled κ 0.77; 0.82 if exclusion policy is set
aside), but the instrument amplifies small mapping differences: the blocking count is an edge count, and one
mapped-or-not decision on a widely imported folder (DI tokens, config, a shared `lib/`) can add or remove dozens of
edges. Per-repo verdicts on the external set should therefore be reported with the spec as a named degree of
freedom, and a spec-authoring convention (excludes; where composition roots, DI tokens and cross-cutting folders go;
whether to add layers beyond the preset) would remove most of the disagreement classes found here. Writing that
convention is an author decision and was not done.

## What this does not show

- **Same vendor.** Both authors are Claude sessions (V10). Their DDD declarations were strikingly similar, which is
  what a shared prior would produce. This is an upper bound on cross-human agreement, not an estimate of it.
- **Protocol asymmetry.** B's protocol forbade adding layers; A's did not. Part of the clean-architecture
  disagreement is protocol, not judgement. A third author under a common protocol would separate the two.
- **Blinding is by commit order** inside one account; it rests on this session's word that nothing else was read
  before d37841fb, and the backlog totals were known.
- **15 repos.** κ on small trees (21–34 files) is noisy; the verdict κ is computed on 15 binary outcomes.
- **No labels.** Agreement is not correctness: neither spec set is shown to be the right one.
- No construct switch, no LLM call, nothing under the hold-out. The 71 reference results are byte-identical (below).
