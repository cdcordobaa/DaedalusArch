## 0. Read this first: the ladder is this routine's definition, not the author's

The prompt asks for the ladder L1–L5 "as defined in the repo docs". **The repo does not define a spec ladder.** I
searched `Docs/v1.3`, `Docs/`, `docs/`, `aidlc-docs/`, `demo/` and the night backlog for `L1`, `L5`, `ladder`,
"spec level", "style name only" and "explicit rules":

- **The L1–L5 that do exist are graph layers.** They appear in the poster strategy and the tech-talk deck as the
  APG graph layers: files, declarations, dependencies, annotations, violations.
- **The repo's "spec levels" are agent prompts.** They are Study 1's prompt levels shown to the *generator*
  (`none`, `minimal-prose`, `full-aac`).
- **Study 2 has no spec-level arm.** `Docs/v1.3/study2-outline.md` §3 lists `none`, `daedalus-mcp` and `gate`.

I did not stop. I defined a **derivational** ladder and committed it before scoring:

- Every level is a deletion from the full spec the #133/#181 author already wrote, which is L5.
- Anything not yet supplied falls back to the style's preset.
- No new spec judgement was authored at any level.

If the author has a different ladder in mind (for example one that varies the *rules*), these numbers do not
answer it, and the generator is one file to replace.

| Level | Adds, verbatim from the full spec |
|---|---|
| L1 | Nothing: the style name, with everything else from `presets/<style>.yaml`. |
| L2 | The folder map: each preset layer gets the full spec's directories, kind and roles. |
| L3 | The layer set: layers the author added beyond the preset (clean-architecture `presentation` and `main`). |
| L4 | The exclusion policy (`default_exclude_paths`). |
| L5 | The DDD declarations (`ddd:` block). L5 is the full spec. |

**A structural fact found before any run: the rules never change along this ladder.** In all 35 full specs,
`fitness_functions` and `allowed_dependencies` are the preset's byte for byte (the generator asserts this). So on
this set "full explicit rules" adds nothing that the style name does not already imply. What the ladder actually
varies is **how much of the project the spec maps**.

Several levels are degenerate:

- **L4 equals L3 on all 35 projects.** The full specs keep the preset excludes.
- **L3 differs from L2 only on the 7 clean-architecture projects.**
- **L5 differs from L4 only on the 8 ddd projects.**

## 1. Runs and checks

- **Command.** Each run was `npx tsx bin/firewall.ts evaluate --project <clone>/<root> --spec <level>/<id>.yaml
  --symbolic-only --engine cypher-interp --format json`, with scoring v1.3 by default. The tool commit was
  `abfd4049` (the #186 head plus this branch's files; no `src/` change). Clones were taken at the
  `selection.json` pins. No Neo4j and no LLM call.
- **Reproduction.** At **L5 the committed #133/#181 blocking count is reproduced on 34/34 evaluated projects.**
- **bank-server: missing at every level.** #181 already found that its FF-S02 cycle query does not finish under
  the interpreter, and Neo4j is not allowed here. It is dropped from every paired statistic, so n = 34 (the bank-server runs at the 15-min timeout are recorded in `results/v1.3-spec-ladder/run-status.txt`).
- **`firewall validate`** (scratch outputs) flags preset layers that match no file at L1 on 33/35 projects. At
  L2–L5 it flags only staart-api's and zeldaplay-api's `domain`, as their full specs already did. `evaluate` does
  not run this check.

The rules fall into four groups by what they need from the spec:

- **Spec-free: FF-S02.** Cycles do not depend on the spec at all. Same count, same 13 projects at every level
  (κ 1.00). FF-S02 is the only blocking rule a style name alone fully determines.
- **Mapping-dependent: FF-S01, FF-S03, FF-S04, FF-P01, FF-P03, FF-DT04.** These switch on mostly at L2.
  - FF-S01 is the main mover: it fires on 3 projects at L1, 16 at L2 and 20 at L3. The 4 projects added at L3
    include luizomf-clean-api, a pass-to-fail flip.
  - Once the folder map is present, the per-rule "fires" indicator matches L5 with κ = 1.00 for every one of
    these rules except FF-S01 at L2 (κ 0.77).
- **Declaration-dependent: FF-DS02, FF-DT01, FF-DT02.** These switch on only at L5. They need the hand-written
  contexts and aggregates, so no lower level can produce them.
- **FF-DS01 is a fallback artefact of this ladder, not a finding about the projects.** At L1–L4 the ddd specs
  carry the preset's *example* `ddd:` block, whose contexts are `src/ordering/` and `src/billing/`. FF-DS01 then
  reports almost every file as "lies in no declared bounded context": 695 findings, 7 projects.
  - Strip FF-DS01 out, and the ddd blocking counts rise along the ladder instead of falling. For ddd-forum they
    go 0 → 40 → 40 → 40 → 92.
  - One verdict flip comes from it: camps-graphql-api fails at L1–L4 on FF-DS01 alone and passes at L5.
  - A different fallback (drop `ddd:` below L5) might fail validation for style ddd. I did not try it after
    seeing results, so as not to tune the ladder to the outcome.

## 4. Monotonicity

Blocking count over L1→L5 (n = 34):

| Trend | Projects |
|---|---:|
| non-decreasing | 21 |
| constant | 5 |
| non-increasing | 3 |
| neither | 5 |

All 8 non-monotone projects are explained by two mechanisms:

- **The 7 ddd projects.** Their drop at L5 is the FF-DS01 artefact. Without FF-DS01, every ddd series is
  non-decreasing.
- **pvarentsov-clean.** It goes 37 → 0 → 18. At L1 the preset globs map `src/application/**`, which holds the
  repo's HTTP API and DI, as application, and `src/infrastructure/**` as infrastructure. That gives 37 FF-S01
  findings. At L2 the author's folder map moves those files, but the author's `presentation` and `main` layers are
  not yet present, so they fall unmapped and nothing fires. At L3 they appear and give the 18 findings #186 already
  discussed. This is the same "layer granularity" disagreement #186 found between two authors, here between two
  levels.

Verdicts (fail = 1):

| Trend | Projects |
|---|---:|
| constant | 24 |
| non-decreasing | 8 |
| non-increasing | 1 |
| neither | 1 |

- **Non-decreasing (8): pass turns into fail as information is added.** Each flip happens at the folder map (L2)
  or the layer set (L3).
- **Non-increasing (1): camps-graphql-api,** the FF-DS01 artefact.
- **Neither (1): pvarentsov-clean.**

**Net: outside the two mechanisms above, adding spec information only ever adds blocking findings.** A spec that
maps less of the project hides violations; it does not create them. The one exception to "it does not create
them" is FF-DS01 with a placeholder context list.

## 5. What this means for Study 2's spec-level arm

1. **There is no spec-level arm in the Study 2 outline today.** The arms are `none`, `daedalus-mcp` and `gate`.
   The spec level the thesis has measured so far (Study 1, `none` / `minimal-prose` / `full-aac`) varies what the
   **agent** is told. This ladder varies what the **evaluator** is given. So this evidence speaks to the
   instrument, not to agent behaviour.
2. **If Study 2 adds an agent-facing spec-level factor, the evaluator spec must stay fixed at the full spec per
   task across every level and arm**, as E1 did with `specs/clean-arch.yaml`. The ladder shows why: scoring
   with less than the full spec is a different measuring instrument.
   - With a style name only (L1), 8 of the 29 failing projects pass, and verdict κ is 0.33.
   - With the folder map only (L2), κ is still 0.68.
   - Letting the agent-facing level leak into the evaluator spec would confound the factor with instrument
     sensitivity of this size.
3. **The folder map is the decisive and least reliable part of the spec.**
   - On this ladder, nearly all of the blocking signal outside ddd switches on when the folder map is added: L2
     takes 21 of 23 eventual non-ddd failures, and L3 adds the other 2.
   - #186 found the folder map is also where two blind authors disagree most (verdict κ 0.21).
   - For Study 2's own tasks the author writes the evaluator spec for a known greenfield layout, so the map is
     fixed by the task, not inferred from foreign code. That removes most of this risk for Study 2, but the
     external-set verdicts (30/35 fail) remain a property of one author's maps.
4. **DDD verdicts depend on declarations no style name supplies.**
   - FF-DS02, FF-DT01 and FF-DT02 exist only at L5.
   - A placeholder `ddd:` block produces hundreds of spurious FF-DS01 findings.
   - So any ddd task in Study 2 needs its contexts and aggregates declared in the evaluator spec before the run,
     and must never fall back to the preset's example block.
5. **FF-S02 is the only spec-level-invariant blocking rule.** If Study 2 wants an outcome robust to spec-authoring
   choices, a cycle-only secondary outcome is the one this evidence supports. Choosing outcomes is the author's
   call.

## 6. Limits and what was NOT done

- **The ladder is provisional and mine.** Its order (map → layer set → excludes → ddd) and its fallback (the
  preset) are design choices, fixed before scoring. A ladder that varied the rules themselves cannot be built from
  these specs, because their rules are the preset's.
- **Same author everywhere.** A single author family (Claude) wrote the selection and the full specs, and #186
  shows their maps are author-dependent. No second author ladder was run.
- **bank-server is missing.** n = 34, not 35.
- **No correctness labels.** "More findings" is not "more correct findings".
- **No rule, threshold, preset, template or tier was changed.** No construct switch, no LLM call, no Neo4j,
  nothing under the hold-out, nothing in `daedalus-sealed/`.
- **Interactive AI-DLC stages skipped.** This was an unattended routine.
