# v1.3 SO5 spec ladder: plan (committed before any evaluation)

Development set, exploratory. Branch `v1.3-k2-ladder`, from `v1.3-spec-author-reliability` (#186). Report:
`Docs/DiagnosticRuns/v1.3-spec-ladder-2026-10-16.md`.

## The ladder definition was not in the repo

The routine prompt says to use the ladder L1–L5 "as defined in the repo docs". A search of `Docs/v1.3`, `Docs/`,
`aidlc-docs/`, `docs/`, `demo/` and the night backlog for `L1`, `L5`, `ladder`, "spec level", "style name only" and
"explicit rules" finds **no specification ladder**:

- **What the L1–L5 that do exist are.** `Docs/DiagnosticRuns /poster-design-strategy.md` and
  `demo/tech-talk-deck/slides.html` use them for the APG graph layers (L1 files, L2 declarations, L3 dependencies,
  L4 annotations, L5 violations), which is not a spec ladder. `L1` in the night backlog is a job id.
- **What spec levels the repo does define.** These are Study 1's *prompt* levels shown to the generator (`none`,
  `minimal-prose`, `full-aac`; `Docs/analysis-plan.md`). They are not evaluator spec levels.
- **Study 2's spec-level arm.** `Docs/v1.3/study2-outline.md` §3 has three arms (`none`, `daedalus-mcp`, `gate`) and
  no spec-level factor.

So the ladder below is **this routine's provisional definition**, not the author's. To keep researcher degrees of
freedom low, it is **derivational**:

- Every level is produced by deletion from the full spec that the #133/#181 author already wrote.
- Every missing piece falls back to the style's preset.
- No new spec judgement is authored at any level.

The definition and all 175 specs are committed and pushed before any `firewall evaluate` run on them.

## Ladder (cumulative; level k = preset + the first k−1 kinds of project information)

| Level | Name | What the spec contains |
|---|---|---|
| L1 | style name only | Contains the `style:` and everything else from `presets/<style>.yaml` verbatim. That covers the preset layers and their default globs, `allowed_dependencies`, the preset `ddd:` example block for ddd, and the preset `default_exclude_paths`. |
| L2 | + folder map | Each preset layer is replaced by the full spec's layer of the same name: directories, kind and roles. Layers the full spec adds are not yet present. |
| L3 | + layer set | Takes the full spec's `layers:` list verbatim, including the layers the author added beyond the preset (clean-architecture: `presentation`, `main`). |
| L4 | + exclusion policy | Takes the full spec's `default_exclude_paths`. |
| L5 | + DDD declarations | Takes the full spec's `ddd:` block (contexts, public API, ACL, aggregates, value objects, repositories, event types, application services). **L5 = the full spec**: the generator asserts that L5 equals the full spec. |

Generator: `results/v1.3-spec-ladder/generate-ladder.py`. It asserts that `fitness_functions`,
`allowed_dependencies`, `scoring` and `confidence_thresholds` in every full spec are the preset's, and they are, on
all 35. **So the rules themselves never change along this ladder**: on this set, "explicit rules" add nothing
beyond the preset's, and what varies is how much of the project the spec maps.

Known degeneracies, found by the generator before any evaluation (`specs/manifest.json`):

- **L3.** It differs from L2 only on the 7 clean-architecture projects.
- **L4.** It equals L3 on all 35: the full specs use the preset's excludes unchanged.
- **L5.** It differs from L4 only on the 8 ddd projects.

`firewall validate` (scratch) flags every preset layer that matches no file at L1 (33/35 projects). At L2–L5 it
flags only staart-api and zeldaplay-api `domain`, the same as their full specs (#181 addendum; #133). `evaluate`
does not run that check, so every level is evaluable.

## Runs

- **Command.** For each level and each project: `npx tsx bin/firewall.ts evaluate --project <clone>/<root> --spec
  results/v1.3-spec-ladder/specs/<L>/<id>.yaml --symbolic-only --engine cypher-interp --format json`, with scoring
  v1.3 by default.
- **Clones.** Each project is cloned at its pinned sha from `selection.json` (#133, #181).
- **Timeout.** 15 min per run. No Neo4j is allowed, so a run that does not finish under the interpreter
  (#181: bank-server FF-S02) is recorded as missing at that level, and its project is dropped from the paired
  statistics.
- **Check.** L5 must reproduce the committed #133/#181 blocking counts. If it does not, that is reported first.

## Measures (fixed now)

1. Per level: the number of projects failing the v1.3 verdict, total blocking findings, and blocking findings by
   rule id.
2. **Agreement with L5.** Cohen's κ on pass/fail verdicts at each level against L5, plus raw agreement and the
   count of verdict flips in each direction. The same measure is also given for the per-rule "rule fires at all"
   indicator.
3. **Monotonicity.** For each project, whether the blocking count is non-decreasing L1→L5, non-increasing, or
   neither. The same is reported for the verdict (fail never turns into pass as information is added).
4. **Rule switch-on.** For each rule id, the share of projects where it first has a blocking finding at L1, L2, L3
   or L5, and where it fires at a lower level but not at L5 (switch-off).

No rule, threshold, preset or template is changed. No LLM call and no Neo4j.

## Pre-stated reading for Study 2

The ladder varies the **evaluator's** spec, while Study 1's and any Study 2 "spec level" varies the **agent's**
prompt. The two are different constructs, so these results bear on Study 2 only as instrument sensitivity.

- **If verdict κ(L2, L5) < 0.60.** The folder map alone does not reproduce the full-spec verdict. Study 2 must then
  hold one evaluator spec per task fixed across all arms and levels, as `specs/clean-arch.yaml` was for E1. It must
  also not let an agent-facing spec level change what the evaluator is given.
- **If κ(L2, L5) ≥ 0.80.** The mapping, not the extra declarations, carries the verdict. A minimal-spec arm can then
  be scored with a folder-map spec without a large instrument shift.
- **For the DDD declarations.** Movement at L5 on the 8 ddd projects shows how much of the DDD verdict depends on
  hand-written context and aggregate declarations that a style name cannot supply.
