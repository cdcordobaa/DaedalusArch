# v1.3 stage-0 ORM instrument probe

**2026-10-16. Instrument probe on planted fixtures; zero model cost; no Neo4j.** No model was called, no sealed
directory was read, and no rule, tier, template, preset or spec was changed. Engine: the in-process Cypher interpreter
(`--engine cypher-interp`), v1.3 scoring with the tier table of Docs/v1.3/rule-tiers.md.

## 1. Purpose

Docs/v1.3/floor-escape-design-2026-10-16.md keeps one part of the rejected persistent-stack (TypeORM) task family: a
stage-0 instrument probe, listed in section 3.6 (last bullet) and section 4. The probe plants five TypeORM constructs an
agent might write: a decorated domain class, a version column, a DataSource in a use case, a Repository without a port,
and a QueryBuilder in business logic. For each one it records what the instrument reports in four places: the graph
tier, check-correct, check_file and check_import. The design predicts from the templates that only the
decorated-domain case is blocking, and asks for that coverage statement to go into the pre-registration. This run
measures it.

## 2. Setup and command

- Fixtures: `fixtures/v1.3-stage0-orm-probe/<case>/{clean,hexagonal}/` (README there). There is one small
  order-placing project (6 to 8 files), written twice: once in the Clean layout of `specs/clean-arch.yaml` and once in
  the Hexagonal layout of `presets/hexagonal.yaml`. Each case changes the clean control in one place only. `typeorm` is
  not installed, so its imports are import statements only. With a stub declaration of the TypeORM names used, every
  fixture type-checks; without it, the only errors are TS2307 (module not found).
- Driver: `scripts/v1.3/stage0-orm-probe.ts`. Per case and spec it runs:
  1. **Graph tier**: `bin/firewall.ts evaluate --symbolic-only --engine cypher-interp --scoring v1.3 --format json`
     on the planted tree. The child gets only PATH and HOME, so no NEO4J_* variable reaches it.
  2. **check-correct**: `scripts/v1.3/check-correct.ts --jobs <out>/jobs.json --tiers blocking --out <out>/check-correct`
     over the twelve reports.
  3. **check_file**: the MCP handler `checkFileTool`, with the control tree of the same layout as the project root
     (the agent asking before it writes the planted file into the clean tree). It runs twice: once on the fast path
     (the default) and once with `templates: true`, which runs the compiled templates on cypher-interp over the whole
     project before and after the change.
  4. **check_import**: the MCP handler `checkImportTool` for every `import ... from 'typeorm'` in the planted file.
- Command (about 1.5 minutes):

  ```
  unset NEO4J_URI NEO4J_USER NEO4J_PASSWORD
  npx tsx scripts/v1.3/stage0-orm-probe.ts            # --out results/v1.3-stage0-orm-probe (default)
  ```

- Output: `results/v1.3-stage0-orm-probe/results.json`, plus `reports/<case>.<layout>.json`, `jobs.json` and
  `check-correct/correctness.{json,csv}`. Run ids, wall times, cache states and absolute paths are stripped. Two runs
  gave byte-identical results.
- Test: `npx jest --maxWorkers=2 tests/unit/scripts/v1.3/stage0-orm-probe.test.ts` repeats the fast-path check_file and
  check_import verdicts on the fixtures and checks the recorded results file (11 tests, about 2 s).

Details:

- The decorated domain class gives one FF-P01 finding per import statement, not one per decorator. Using the
  decorators does not add findings. check-correct's reason: `'typeorm' at line 1 imports typeorm (forbidden by 'typeorm')`.
- check_import passes `typeorm` from the application layer in both specs. Neither spec has a rule for an application
  file importing an external package. Only `domain-purity` (FF-P01) has a forbidden-package list, and it applies to the
  domain layer only.
- repository-without-port: FF-P03 (repository-pattern in Clean, port-adapter-pattern in Hexagonal) gives no finding
  when there is no repository interface or class at all. FF-P02, the advisory dependency-inversion ratio, is unchanged.
- The only output any per-file tool gives for the DataSource and QueryBuilder cases is the fast-path hint
  `CHEAP.repository-bypass`: "direct persistence use outside a repository and outside infrastructure". This hint is
  advisory by design (tier source `hint`). It is not in the tier table and does not count in any v1.3 outcome.
  repository-without-port gets no such hint, although its `this.orders.save(...)` also reaches TypeORM directly. The
  hint fires on a call through a field whose declared type is on the raw-database list `RAW_DB_TYPES`
  (`src/apg-enrich/cheap/behaviour.ts`: DataSource, EntityManager, QueryBuilder, ...). `Repository` is not on that list.
- FF-CV03 (naming-repos, advisory) fires on `OrderReportService` because the name contains `Repo` (in "Report").
  `src/mcp-server/file-check.ts` checks `cls.name.includes('Repo')`. This is a naming false positive unrelated to the ORM.
  FF-C04 (orphan) appears only in the check_file templates run, because the control tree's composition root does not
  import the new service. The planted tree does import it, so the graph tier does not report FF-C04.

## 4. Coverage statement for the pre-registration

**The measurement confirms the prediction.** Of the five planted TypeORM constructs, the v1.3 instrument scores exactly
one as blocking: the decorated domain class. It is scored through its `import ... from 'typeorm'` in a domain file
(FF-P01 domain-purity), in both Clean and Hexagonal, and check-correct labels the finding correct. The graph tier,
check_file (fast path and templates) and check_import agree on this.

The other four constructs produce no blocking finding in any of the four places, in either spec: a version column on a
persistence entity, a DataSource injected into a use case, a TypeORM Repository used by a use case with no port, and
QueryBuilder SQL carrying a business rule in an application service. Two of them, DataSource and QueryBuilder, get only
an advisory check_file hint, which the outcome does not count. So for Clean and Hexagonal, a Study 2 outcome built on
blocking findings can see TypeORM only when typeorm is imported into a domain file. Persistence in the application
layer, with or without a port, scores zero by construction.

Suggested wording: "In Clean and Hexagonal, the instrument counts TypeORM use only as an import of `typeorm` into the
domain layer (FF-P01). TypeORM in the application layer (DataSource, Repository without a port, QueryBuilder) and
persistence-entity details (version columns) are not scored as blocking (stage-0 probe, 2026-10-16)."

## 5. Limits

- Clean and Hexagonal only. Layered and DDD, the strata the design proposes as confirmatory, were not run. The fixtures
  have no layout for them, and the Layered preset is under repair (design 3.6). In `presets/layered.yaml` the
  business layer has kind `domain` and carries the same FF-P01 forbidden list. A DataSource, Repository or QueryBuilder
  in a Layered business service may therefore score differently. That is not measured here.
- Each fixture is a small hand-written tree with one construct. Agent code may combine constructs, use other TypeORM
  APIs (EntityManager in controllers, `@InjectRepository` through NestJS, which FF-P01 forbids in the domain separately),
  or put a QueryBuilder in a domain service. A domain service would import typeorm into the domain and fall under the
  same FF-P01 path as case 1. That follows from the rule, but no fixture tests it.
- `typeorm` is not installed. The graph sees it as a Package node from the import specifier. Checks that need the
  type checker to resolve TypeORM declarations (the cheap behaviour proxies of `src/apg-enrich/cheap`) were not
  exercised in the graph tier: `evaluate` ran `--symbolic-only` with no enrichment flags.
- check_file ran against the control tree with only the main planted file overlaid. For the two cases that change
  more than one file (decorated-domain-class removes `OrderRecord`; repository-without-port removes the port and the
  adapter), the templates run sees a mixed tree. The graph-tier column is the full planted tree.
- Engine: cypher-interp, not Neo4j. The design names a capped Neo4j as the engine of record for the validation pilot.
  The interpreter's row-for-row parity with Neo4j is documented in
  Docs/DiagnosticRuns/v1.3-default-view-coverage-2026-10-16.md (item 7). Nothing in this probe needed Neo4j.
