# v1.3 validity from developer behaviour: do maintainers remove what the tool flags? (2026-10-16)

Branch `v1.3-validity-fixes-mined`, base `origin/v1.3` at `f57a4918`. Node v22.22.0. Run on 2026-10-16. Engine: the in-process Cypher interpreter (`graphEngine: cypher-interp`), `symbolic-only`, v1.3 tiers (`Docs/v1.3/rule-tiers.md`), instrument v2.

**Status: exploratory evidence unit, no human raters.** It uses developer behaviour as the ground truth. The question: when a project's own maintainers later delete the exact dependency the tool flags, keeping both files in place, is that more frequent and faster for **blocking-tier (defining-rule)** findings than for import edges the tool does not flag? Corpus, specs and protocol were committed and pushed in `cd9910c3` (2026-10-16 02:18 UTC), before any tool run on a corpus project. `results/v1.3-fixes-mined/protocol.md` fixed the definitions and thresholds. §6 is labelled post hoc.

## Verdict

**No robust validity signal.** The pooled blocking-tier removal rate is 2.65× the cross-layer baseline (74 vs 110 credited removals, 95% CI 1.97–3.56). That ratio rests on **one commit**: amplication PR #93, "Lint Imports". It enabled `import/no-cycle`, broke 48 of the flagged cycles and suppressed the rest with `eslint-disable-line import/no-cycle`. Each check that does not depend on that commit points the other way or comes out even:

- **Without that commit:** the ratio is 0.93 (0.61–1.43).
- **One credit per fix commit:** 1.00 (0.56–1.80). Only 14 distinct commits removed a blocking finding in 36 histories.
- **Repository bootstrap:** 0.37–7.54.
- **Sign test:** only 6 of 21 non-tied repositories remove blocking findings faster than their own baseline (two-sided p = 0.078, in the *wrong* direction).
- **Dependency rules:** the dependency-direction family (FF-S01, FF-S03 layered, FF-S04) is removed **less** often than unflagged cross-layer edges (rate ratios 0.65, 0.38 and 0).
- **Survival:** blocking findings are not removed faster (one-year survival 0.76 without cycles, 0.71 with them, vs 0.75 for unflagged cross-layer edges).
- **Commit messages:** fix commits mention architecture words no more often than baseline-removal commits (5/14 vs 21/55).

The one rule with a signal is **FF-S02 (cycles)**. After the cycle-length adjustment (a cycle is credited when *any* of its edges goes) it is still about 3.9× the per-edge baseline. Without the "Lint Imports" commit it is 2.7× (1.5–5.1) per exposure and below the length-adjusted expectation. The amplication commit is itself the clearest evidence in the set: the maintainers adopted an import-cycle lint and worked through its findings.

What this does **and does not** say. Maintainers almost never delete these dependencies: blocking findings survive. That fits two readings, and this method cannot separate them:

- the findings are wrong for these projects (the specs or the rules do not match the projects' real intent);
- the findings are right, but developers tolerate the debt (the classic result in technical-debt mining).

Under this design, developer behaviour does not validate the dependency-direction rules. It is weak, one-commit-driven evidence for the cycle rule.

## 1. Method

`results/v1.3-fixes-mined/protocol.md` is the full definition. In short:

1. **Commits.** The first-parent commits touching the analysis path, up to the pin; 200 of them evenly spaced (all of them when there are fewer).
2. **Evaluation.** Each sampled commit C and its first parent P is checked out (sparse, analysis path only) and evaluated by the pipeline in process, with the committed spec. The harness tsconfig is flattened from the project's own chain (`src/` production code, tests excluded), and no dependencies are installed.
3. **Snapshot cache.** One snapshot per (tree, tsconfig blob). The walks report 8,319 evaluations in total (`snapshotsEvaluated`, summed over `repos/*/walk.json`) and 536 snapshot failures counted per pair occurrence (`snapshotErrors`). The shared cache holds 8,430 distinct snapshots: those 8,319 plus 111 evaluated by the smoke test and the interrupted first run, which the final walks reused from cache. Of the 8,430, 7,904 evaluated successfully (the parity and timing figures below are over these) and 526 had no source files on the path (early history, such as etherpad before its TypeScript migration, or immich before `server/src`); those pairs are skipped. Median 1.7 s per snapshot, p95 5.0 s.
4. **Disappearance at P→C.** A finding present at P and absent at C gets the first cause that matches:
   1. RENAMED: a named file is a rename source in `git diff -M50%`;
   2. FILE-DELETED;
   3. MASS-OR-BOT: a bot author, or ≥100 files / ≥25% changed, or ≥20 / ≥10% renamed or deleted;
   4. RESOLVED-IN-PLACE: a file-level finding whose file stays;
   5. **FIXED-BY-DEV**: an edge-shaped finding, files in place, at least one of its file edges has no APG relation at C;
   6. OTHER.
5. **Baselines.**
   - (a) Every internal IMPORTS/RE_EXPORTS edge at P that no finding rests on, classified the same way. Three sets: all edges; both files layered; and the primary set, **cross-layer** (both files layered, different layers). Every dependency-direction finding is a cross-layer edge, so this is the like-for-like comparison.
   - (b) Advisory-tier findings.
6. **Rates.** Credited removals per exposure (finding × sampled pair), with Wilson 95% intervals.
7. **Effect sizes.** Rate ratio with a log-normal CI and a repository-cluster bootstrap (2,000 resamples, seed 20261016), Cohen's h, and a per-repository sign test.
8. **Survival.** The sampled commits form a grid. A lineage runs from the first grid point a finding (or unflagged edge) appears to the first point it is absent. Lineages present at the first grid point are left-censored and dropped. Time is committer-date days; the estimate is Kaplan-Meier.
9. **Cycle cap.** The FF-S02 template returns at most 100 cycles. Pairs and grid points at the cap are excluded from FF-S02 statistics: in a capped list a cycle can appear or vanish while the code stays the same.
10. **Architecture words.** In the commit subject and body (for a merge, the PR title): layer, dependenc*, decoupl*, refactor*, the whole word port(s), adapter*, domain*.

### 1.1 The cycle queries in the harness (no template change)

The interpreter expands `-[:IMPORTS|RE_EXPORTS*2..10]->(f)` by enumerating every relationship-unique trail of up to ten hops and filtering afterwards. On a NestJS code base with module cycles that is exponential: in calibration on ToolJet `server/` (excluded from the corpus by size), it took 55 s + 52 s of a 112 s snapshot.

`scripts/v1.3/lib/fast-cycles.ts` is a `GraphRepository` that answers **exactly those two query texts** (the FF-S02 template and the `cyclicDependencyCount` metric, matched character for character) with an equivalent bounded search. It sends every other query to the interpreter unchanged. The design:

- a depth-first search in `filePath` order, closing edge first, which is the `ORDER BY cycle` order, so it can stop at the 101-row sentinel;
- pruning by reverse-BFS distance;
- for the count, a shortest-path test plus the self-loop case.

Parity:

- 6 randomized graphs in the unit tests, plus an ordering test at the sentinel;
- live on every snapshot of at most 100 files: **5,175 checks, 0 mismatches, 0 fallbacks**;
- the 214-file ToolJet snapshot: identical results, 112 s → 2.2 s.

No Cypher template, tier or `src/` file was changed.

## 7. Reading the tables

- **Removals are rare for everything.** About one exposure in 2,000–10,000 ends in a removal by a developer (blocking 1 in 2,400, unflagged cross-layer edges 1 in 6,400). Over 36 histories, 74 blocking findings were removed this way, in 14 commits. Persistence is the norm: half of all blocking edge-shaped lineages are still present 1,500 days after they appear.
- **Dependency direction.** FF-S01 is removed at 0.65× the cross-layer baseline (8 removals in 78,528 exposures), FF-S03 (layered) at 0.38×, FF-S04 never (20,412 exposures). Developers in these projects keep the edges the specs call upward or outward. That is consistent with mis-specified layers as much as with tolerated debt.
- **Cycles.** FF-S02 is the only rule above baseline. It also has the most commit clustering (48 of 59 removals in one PR) and the most mechanical advantage (any of about 3.8 edges counts).
- **DDD rules** (FF-DT01, FF-DT02) show 2 removals each, both in one ddd-forum commit ("Remove unnecessary imports"). The rate ratios of 9.6 and 28 come from n = 2.
- **Advisory, file-level.** These findings are "resolved in place" at about the baseline rate (1.17×, CI 0.91–1.49); that is not an edge removal and is shown for scale only. Advisory edge-shaped findings (FF-S03 outside `layered`) have too few exposures (831) to say anything.
- **Messages.** 36% of blocking fix commits use an architecture word, against 38% of baseline-removal commits and 16% of all sampled non-bot commits. Commits that delete dependencies are refactors in general; flagged ones are not special.

## 8. Threats

- **Survivorship and sampling.** Only the first-parent history up to the pin is walked, with 200 sampled commits per repository. A removal between a sampled commit and its parent is seen only when that commit is sampled: pair-level rates are per sampled commit, not per calendar time. The grid survival analysis covers the rest, at grid resolution (interval-censored, treated as exact at the next grid point). Projects that died, or whose history was squashed, are not in the corpus. Teaching repositories with short histories contribute exposures but almost no removals.
- **Spec drift.** Each spec describes the layout **at the pin**. Earlier history may use other folders, so files outside every layer are not checked, and a layer can "move" under a finding. The first-sampled snapshots of several projects have no layered files at all.
- **Mass refactors and renames.** Fixed thresholds (≥100 or ≥25% changed, ≥20 or ≥10% moved) and `-M50%` rename detection. A rename below 50% similarity counts as delete + add (FILE-DELETED), never FIXED-BY-DEV, so the bias is towards fewer credited fixes, equally for findings and baseline. In small projects the 25% share marks many early commits as mass changes (dannielhugo 36 of 82 pairs; finance-project-ddd 83 of 200).
- **Bots.** Detected by author name or e-mail (`isBotAuthor`), and their commits are excluded from credit. Bot pairs: immich 42, hedgedoc 125, mikro-orm 184 (Renovate), etherpad 32, directus 20. A squash-merged bot PR committed by a human is not detected.
- **Edge identity.** An edge counts as removed when no APG relation of any type remains between the two files. A dependency moved to another file of the same layer counts as removed (both for findings and baseline). A dependency kept through a re-export counts as present.
- **Cycle cap and length.** Capped pairs and grid points are excluded (FF-S02 survival keeps 333 of 12,038 lineages once capped grid points are dropped). The remaining cycle statistics still favour cycles mechanically; §6 gives the length adjustment.
- **Clustering.** Exposures within a repository are not independent: the same edge is exposed at many pairs, and one commit can remove many findings. The log-normal CIs ignore this. The bootstrap, leave-one-out, sign test and per-commit rows do not, and they are the ones to read.
- **Measurement.** Dependencies are not installed: package types are `any`, and resolution relies on the tsconfig paths alone. The harness cycle search is verified for parity only where the interpreter is fast enough (≤100 files). Larger snapshots rely on the proof in `fast-cycles.ts` and the randomized tests.
- **Construct.** A developer removing an edge is evidence that the edge mattered to them, not that the rule is right. A developer keeping it is not evidence that it is fine. The baseline controls for general churn, not for intent.
