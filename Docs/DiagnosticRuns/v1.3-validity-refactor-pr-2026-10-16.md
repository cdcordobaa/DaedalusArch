## Verdict

**NULL.** The tool's blocking count does not drop more across declared architecture refactors than across size-matched ordinary changes in the same repositories.

| | value |
|---|---|
| matched, valid refactors (n) | **76** in 17 repositories (≥30 ✓) |
| controls (valid / selected) | 218 / 275 |
| mean d = Δ refactor − mean Δ controls (repo-cluster bootstrap 95% CI) | **−0.27 [−0.95, 0.24]** |
| median d (95% CI) | 0.00 [0.00, 0.00] |
| d < 0 / d > 0 / d = 0 | 16 / 12 / **48** |
| share d < 0 of the non-zero d (Wilson 95%) | 57.1% [39.1, 73.5] |
| exact two-sided sign test | **p = 0.572** |
| one-commit guard: without ghostfolio #5925 (d = −11) | mean −0.13 [−0.58, 0.25], 15 / 12, p = 0.701 |
| leave-one-repository-out | mean d stays between −0.36 and −0.02 and the negative d stay the majority in all 17 folds. No fold has a sign test below p = 0.405 |

The decision-rule checks (plan §7): n ≥ 30 **yes**; sign test p < 0.05 with more negative d **no**; CI of mean d below 0 **no**; LORO keeps the direction **yes**; one-commit guard holds **no**; contradicted **no**. The rule therefore gives **NULL**.

What the null looks like:

- **The tool mostly does not register the declared refactor.** 59 of 76 refactors (78%) leave the blocking count unchanged. Only 17/76 = 22.4% [14.5, 32.9] change it, against 29/202 = 14.4% [10.2, 19.9] of the controls.
- **When the count moves, it does not move down.** Across refactors, 6 drop and 11 rise (sign p = 0.33). Across controls, 8 drop and 21 rise (p = 0.024): ordinary changes add blocking findings. Refactors add them about as often.
- **The point estimate leans in the hypothesised direction.** That lean comes from a few commits:
  - ghostfolio #5925 "enforce module boundaries for api and common modules" (−11 FF-S01);
  - outline #4861 "Plugin architecture" (−7, against controls −9, +4, +2);
  - ghostfolio #100 "reorganize helper lib" (−4).

  The effect is not robust to removing the largest one.

## 1. Deviations from the task wording (recorded in the plan before the search)

## 2. Method (summary; the plan is normative)

1. **Universe.** Per repository: the first-parent commits that touch the analysis root, without bots or reverts.
2. **Declared refactor.** The commit text (subject + body, merge-branch line and trailers removed) matches one of seven fixed families:
   - A: cycle removal;
   - B: decoupling;
   - C: moving logic out of controllers or routes;
   - D: boundaries, dependency direction or a named architecture;
   - E: "X layer" with a refactor verb;
   - F: repository / port / adapter pattern with a refactor verb;
   - G: architect* / restructur* / reorganiz* with a refactor verb.

   At most 10 per repository, evenly spaced.
3. **Controls.** Commits that match no family and none of a loose list of architecture words. Up to 3 per refactor, nearest by `|Δln(1+files)| + |Δln(1+lines)|` within a caliper of 1.5, each used once.
4. **Measurement.** Each commit C and its first parent P is evaluated in process with the frozen spec. `B(x)` = distinct blocking-tier symbolic findings. `Δ = B(C) − B(P)`. FF-S02 is dropped from both sides when either side hits the 100-row template cap. A commit is valid if both snapshots succeed and at least 20% of P's files are in a declared layer.
5. **Matched difference.** `d = Δ_refactor − mean(Δ_controls)`.
   - Primary statistics: mean d with a repository-cluster bootstrap CI (10,000 resamples, seed 20261016) and the exact sign test.
   - Robustness: leave-one-repository-out and a one-commit guard.

**CLI cross-check (plan §5).** For the first 10 refactor parent snapshots of at most 300 files, `firewall evaluate --engine cypher-interp --symbolic-only --format json` was run through the CLI. All 10 produced **the identical blocking-finding key set** to the in-process run (`cli-check.json`; counts 0 to 30).

**Runtime.** 17 repositories had at least one selected refactor. They needed 727 snapshot evaluations (cached per tree) and about 25 min of wall time on 2 workers.

The stricter the ground truth, the more negative the point estimate. Each stricter subset is also smaller, and none reaches significance. The strictest subset (9 commits; the explicit statement is in the PR title) has two non-zero d values, both negative: ghostfolio #5925 "enforce module boundaries" (d = −11) and awesome-nest "moved utils functions" (d = −1). This is a direction to test with a larger, title-level ground truth. It is not evidence.

## 7. Why the ground truth is weak (a threat the plan named; quantified here by fixed rules only)

- **Body matches.** Only 21 of the 76 refactors carry the phrase in the subject line. The other 55 match on body text: a squash-merge description, a commit list or release notes. Subjects of body-only matches include "Release Version 3.2.5 (#5046)", "docs: document UUID v7 strategy…" and "chore: use pnpm for builds (#19752)". No match was removed by hand, because the plan forbids manual pruning and labelling. The primary n therefore includes commits whose stated intent is not an architecture refactor. That biases the primary toward the null. The post hoc subject-line subsets (§6) are the cleaner reading, and they are small.
- **Recall.** Real architecture refactors described in other words are missed. The loose word filter on controls keeps most of them out of the control group too.
- **Spec drift.** The frozen specs describe each project at its pin. Nine selected refactors fail because the analysis root has no source files at that commit, and four fall under the 20% layered-files rule.
- **Analysis root.** A refactor outside the analysis root, such as ghostfolio #896 in `libs/common`, cannot move the count.

## 8. What this adds to #168 and #198

The three designs are independent. They share the pool, but neither the ground truth nor the unit:

- #168 used maintainers' edge deletions;
- #198 used known groups;
- this study uses the developers' own stated intent per commit.

All three come out null for the blocking tier as a whole. This design also shows that the tool is **mostly silent** on changes its developers call architecture refactors: 78% leave the blocking count unchanged. When it reacts, its direction is not distinguishable from ordinary changes. The only encouraging data are anecdotal. The clearest boundary-enforcement PR in the pool, ghostfolio #5925, removes 11 FF-S01 findings. A ground truth restricted to PR titles points the right way but is far too small.
