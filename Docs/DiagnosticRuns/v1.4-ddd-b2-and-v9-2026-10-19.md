## 3. B2: DDD re-score

### 3.1 Method

`scripts/v1.4/ddd-b2-t1-rescore.ts --engine cypher-interp`:

- Each snapshot is materialised from `snapshots.git` into scratch, with the skeleton `node_modules` and the harness tsconfig.
- Each snapshot goes through the firewall CLI: `evaluate --symbolic-only --scoring v1.3 --format json --engine cypher-interp`.
- There are four spec variants, all built from the run's own frozen spec:
  - **`a0`**: frozen spec, `--empty-aggregates not-applicable` (#229 option a, the baseline);
  - **`a0-acl0`**: `a0` with `acl: []`;
  - **`dc`**: frozen spec plus §2.1's declaration, default policy. This is D15 "static spec with declared aggregates, evaluator only".
  - **`dc-acl0`**: `dc` with `acl: []`.
- Each variant runs with `--post-seal off` (the sealed v1.3 rule set) and with `--post-seal on`.

Y is the number of blocking identities at a step. New identities at steps 2..k use the pilot memo identity rule: rule, template, file, target, and a cycle by its file set (`ops/notes/g08-violation-identity.md` §1, row "Loop pilot outcomes"). Drift D, using the shared step-1 tree, is the number of new identities summed over steps 2..4. The drift-D edge grain (`scripts/lib/drift/study2-d.ts`, `STUDY2_S2D01`, k = 4) is reported beside it.

Every new blocking finding went through the deterministic checker `scripts/v1.3/check-correct.ts --tiers blocking`, which reads source and spec only, never the graph and never a model. Only `correct` findings count.

Machine outputs are in `results/v1.4-ddd-b2-v9/`:

- `cypher-interp/rows.json`: one row per evaluation (124);
- `cypher-interp/drift.json`;
- `cypher-interp/cli/...`: the CLI reports;
- `cypher-interp/check-correct-new.json`;
- `specs/`: the four variants per arm;
- `rule-reach.json`.

### 3.3 Which of the 7 DDD blocking rules can fire

The 7 blocking DDD rules in the frozen spec are FF-DS01, FF-DS02, FF-DT01, FF-DT02, FF-DT03, FF-DT04 and FF-S01. A rule *can fire* when the files its template needs exist. This is a precondition read from the tree's file list and the `dc` spec's globs (`scripts/v1.4/ddd-b2-rule-reach.ts`), not a finding. Two template facts shape it:

- FF-DT01 reads only the aggregate's `module` and `inner_entities`, never `root` (`src/fitness-compiler/ddd-templates.ts`, `aggregate-boundary`).
- FF-DT02 needs a repository file that imports an inner-entity file.

| Rule | Can fire (of 8) | Fired (of 8, `dc`) | Why |
|---|---|---|---|
| FF-DS01 bounded-context-modules | 8 | 8 | `src/shared/http.ts` in every tree |
| FF-DS02 context-isolation | 8 (two contexts with files) | gate 4, none 0; with `acl: []`, 8 | none's only cross-context imports sit in `deployment/acl/` |
| FF-DT01 aggregate-boundary | **0** | 0 | **no file matches any inner-entity glob.** Both agents keep skills, certifications, shifts and assignments inside `volunteer.ts` / `incident.ts` / `deployment.ts` |
| FF-DT02 repository-aggregate-root | **0** | 0 | no inner-entity file. The gate tree also has no file matching the repository globs. In none, `inMemoryVolunteerRepository.ts` matches |
| FF-DT03 value-object-immutability | **0** | 0 | no file under `src/**/value-objects/**` |
| FF-DT04 domain-purity | 8 (2-4 domain files) | 0 | no forbidden import in the domain |
| FF-S01 dependency-direction | 8 | 0 | no layering inversion inside a context |

Two more details:

- The `none` tree has no `incident*.ts`: its deployment aggregate is `deployment.ts`. The declared Incident root therefore matches nothing there. The templates never read `root`, so this changes no number.
- **`a0` and `dc` give identical findings on all 8 snapshots.** On these trees the declaration's only effect is that FF-DT01 and FF-DT02 run, rather than being recorded as disabled. They then find nothing, because they have nothing to look at.

### 3.4 What each D15 option implies for the DDD pilot bar

The pilot bar (`Docs/v1.4/study2-deviation-2026-10-19-drift.md` §2, item 1) is mean D ≥ 1.0 over the 6 `none@L2` runs, k = 5, using only `correct` findings.

| Option | Scores T1 snapshots? | DDD rules that can fire here | D, none run (sealed / post-seal) | D, gate run | Reading for the bar |
|---|---|---|---|---|---|
| `fail` (default, BR-SPEC-10) | **no**, 0/8 | — | unscored | unscored | DDD cannot be scored at all. The bar cannot be met |
| #229 a, `not-applicable` (`a0`) | yes | 5 of 7 nominally (DT01/DT02 disabled); 4 in practice | 0 / 1 | 0 | below the bar |
| `a0` + `acl: []` | yes | as above | 0 / 1 | 0 | Y rises by 2 at every step; D unchanged |
| **D15 static spec, declared aggregates (`dc`)** | yes | 7 of 7 compiled; **4 can fire** (DS01, DS02, DT04, S01) | 0 / 1 | 0 | below the bar; identical to `a0` here |
| `dc` + `acl: []` | yes | as above | 0 / 1 | 0 | Y rises by 2 at every step; D unchanged |

What this implies:

1. **D15's declared-aggregate mode fixes scoring (T1) but not measurement.** At file grain it is inert on agent trees that keep each aggregate in one file. FF-DT01, FF-DT02 and FF-DT03, three of the seven blocking rules and the DDD-specific tactical ones, cannot produce a finding on any of the 8 snapshots. The remaining reach is the strategic pair plus domain purity and layering. Of those, only FF-DS01 and FF-DS02 fired, and they fired at step 1 and persisted, so they add to Y₁, never to D.
2. **`acl: []` changes Y, not D.** The ACL imports exist from step 1 in both arms. Dropping the ACL exemption adds 2 persistent FF-DS02 identities per step. It is a construct question (is an ACL that imports the other context's domain an isolation breach?), not a lever on drift.
3. **The pilot bar is not met on this evidence under any option.** Only the `none` run is a `none@L2`-type run, and it has D = 0 on the sealed rule set. With the post-seal overlay on, D = 1, from a single FF-S02 cycle. The post-seal rule is not one of the 7 DDD blocking rules. The bar needs mean D ≥ 1.0 over 6 runs, with ≥ 3 of 6 runs at D ≥ 1.
4. **This is n = 1, k = 4, one task, one generator (Claude Sonnet).** The pilot proper has k = 5, 2 new DDD tasks and 2 generators. These are indicative only.
5. If DDD is to have tactical reach, there are three ways to get it:
   - (a) the new DDD tasks force inner entities into their own files;
   - (b) the aggregate rules gain a class or member grain;
   - (c) the author accepts that DDD's measurable drift is strategic only.

   Each of these is an author decision outside this run.

## 4. V9: MCP `check_diff` vs the full evaluation

### 4.1 Method

`scripts/v1.4/mcp-fast-vs-full-loop.ts` covers every step s of every run (Layered 14; DDD 8 under `dc` and under `dc-acl0`; Clean/Hex 16).

- The step s-1 → s diff (step 1 is taken from the run's skeleton base) is given to `check_diff` in after-write mode, with the project root on the step-s tree.
- The full evaluation's answer is the step-s blocking findings minus the step s-1 findings (a multiset on rule, file and target), read from §3's stored CLI reports. They are compared with `compareVariant` (`scripts/v1.3/lib/mcp-consistency.ts`).
- There are two configurations:
  - **post-seal-on**: the tools' production default, against the full evaluation with `--post-seal on`. It runs on the default fast path and with `--fast-rules-engine cypher-interp`.
  - **sealed**: loader `postSeal: false`, fast path only, against `--post-seal off`.

Per-rule and per-snapshot agreement comes from `scripts/v1.4/v9-per-rule.ts`. A rule agrees when it is in both answers or in neither. Locations compare file sets, and a cycle compares its file set: the full evaluation lists a cycle as a comma list, the fast path as one row per edge, and the interpreter option as one row.

## 6. Limitations

- **Small sample.** One DDD task, 2 runs, k = 4, one generator. The DDD V9 comparison has 3 blocking steps. Agreement on the DDD tactical rules is vacuous, because they never fire.
- **Unsigned declaration.** The aggregate declaration is an unsigned proposal (§2.1). A different declaration whose inner entities match files would make FF-DT01 and FF-DT02 reachable on other trees, but not on these 8, which have no separate inner-entity files under any glob.
- **Persistent FF-DS01.** FF-DS01 on `src/shared/http.ts` comes from the frozen spec, whose `outside_contexts` omits the shared kernel the ISE reported. It adds to Y at every step and never to D.
- **Different authorship.** The Layered snapshots are probe 1's, Opus by hand, not loop runs. Their D (memo 2/2/7, edge 1/2/5) is a by-product here, not a pilot-bar figure.
- **The rule-reach table is a precondition check on file names and globs.** It is not a proof that a rule cannot fire under other import shapes.
- **Interpreter only.** Every figure here comes from the interpreter. Neo4j figures, and their agreement with these, are the separate T1/D8 work.

## 7. Reproduce

From the repository root, with a scratch dir `$W` and the generator skeleton installed (`npm ci --ignore-scripts` in a scratch copy of `scripts/generator/skeleton/`) at `$NM`:

```bash
npx tsx scripts/v1.4/ddd-b2-t1-rescore.ts --engine cypher-interp --work "$W" --node-modules "$NM"
npx tsx scripts/v1.4/ddd-b2-rule-reach.ts
npx tsx scripts/v1.3/check-correct.ts --jobs "$W/check-correct-jobs-cypher-interp.json" --tiers blocking --out "$W/cc"
npx tsx scripts/v1.4/mcp-fast-vs-full-loop.ts --work "$W" --node-modules "$NM"
npx tsx scripts/v1.4/v9-per-rule.ts
```

`check-correct-new.json` keeps the checker's rows for the new keys only. The jobs file holds absolute scratch paths and is not committed.
