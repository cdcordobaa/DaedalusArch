# v1.4 DDD-BETA: can the instrument represent a DDD project, and can it enforce the DDD rules on it?

**Date:** 2026-10-19 (run 2026-10-20 UTC). **Decision it serves:** DDD-BETA (`ops/decisions.md`, 2026-10-19): DDD is a beta
instrument, and the capability itself is measured before DDD enters any study.
**Calls:** zero model calls (no LLM, agent CLI, generator or model API). **Engine:** `cypher-interp` only. No Neo4j was
started: the optional parity spot check was not needed, because TIER-A4 already showed interpreter/Neo4j byte parity on
every DDD report it ran (`Docs/DiagnosticRuns/v1.4-ddd-t1-and-d8-2026-10-19.md` §4.2). That parity is not re-shown on these trees.
**Status:** development data. No pre-registration. This is not a registered SO4 estimate. **Decisions taken:** none.
**Not opened:** any `*sealed*` path (not even `Docs/v1.3/sealed-hashes.md`, which was not needed), the sealed DDD hold-out,
and `results/v1.3-meaning/mean-01-sample.*`.

## 0. Summary

- **Representation.** The spec language can declare 9 of the 13 DDD concepts asked about, 4 of them only partly. It
  declares them **by file glob**, with one exception: domain events, which are declared by type name.
  - The 15 real DDD repositories mostly fit that grain. In their domain layers, one class per file is the norm: 10 of
    413 domain files hold more than one class, and no entity class shares a file.
  - Agent code does not fit it. The two kept loop-pilot trees put their inner entities (and, in one tree, the whole
    model) in the root's file, as interfaces, type aliases and functions.
- **Enforcement.** Over 18 bases (15 real repositories, the DDD reference project and 2 agent trees), the existing
  operators planted 548 evaluated positives that carry a DDD blocking key. **All 548 were detected**: there was no miss
  on any rule.
  - Twins: 536 were evaluated and 46 added a blocking row. When every false fire was inspected, each one turned out to
    be a correct finding produced by a twin that is not legal under DDD. None was an instrument false fire (§B.3).
  - **Beta-ready under the proposed bar** (reach on ≥ 3 real repositories, seeded recall ≥ 0.90, 0 twin false fires),
    reading twin false fires as adjudicated:
    - **ready:** FF-DS01, FF-DS02, FF-DT01, FF-DT03, FF-DT04, FF-S01 and the post-seal FF-S02;
    - **not ready:** FF-DT02 (reached on 2 real repositories) and FF-P07 (no operator, so no recall estimate; native reach on 1 repository).
  - Read raw, FF-DS02 and FF-S02 also fail the bar.
- **The gap is the agent code, not the real repositories.** On both agent trees FF-DT01, FF-DT02 and FF-DT03 have no
  precondition: there is no inner-entity file and no value-object file. No seed can reach them, and none was planted.
  This confirms TIER-A3 with a different method.
- **What closing the gap needs.** A declaration-grain version (classes, interfaces *and* type aliases) of
  FF-DT01/DT02/DT03. That is a post-seal deviation; §C gives the facts it needs, the effort and the deviation.

- **Clones.** All 15 repositories were cloned at their pinned SHAs into scratch. Each SHA is checked before use, and
  nothing from them is committed. Nothing was installed; missing packages are stubbed (below).
- **Tool.** `scripts/v1.4/ddd-beta-capability.ts`, with its helpers in `scripts/v1.4/lib/ddd-beta.ts`. The helpers'
  unit tests are in `tests/unit/scripts/v1.4/ddd-beta.test.ts`. Four modes:
  - **census.** Each base is evaluated by the CLI (`evaluate --symbolic-only --scoring v1.3 --engine cypher-interp`),
    with `--post-seal off` and with `--post-seal on`. A ts-morph census of the tree records every class, its base and
    interfaces, the interfaces and type aliases, and the resolved named imports. From these the mode builds:
    - the concept map;
    - the grain census;
    - a shadow class-grain FF-DT01 count. This is a measurement only; no rule uses it.
    - the rule preconditions.
  - **fixtures.** Every reference variant is materialised and evaluated with both post-seal settings, then compared
    with its `expected-findings.json` on rule, file and target.
  - **recall.** The existing operators, applied as in U10 (`seeded-recall-agent.ts`):
    - the U5a catalogue operators with symbolic coverage, plus the hex/DDD operators of style `ddd`;
    - **MO-H07 / MO-H07n added on `ddd`**, because the post-seal overlay puts FF-S02 `no-cyclic-deps` into the DDD rule
      set. This is the only extension, and it adds no new operator.
    - A seeded sample (seed 20261019) of at most 4 positive and 3 twin sites per operator and base; 10 and 6 on the
      reference project.
    - Type-check gate: the repository's TypeScript on the base's own tsconfig, with missing packages stubbed alike in
      the unmutated copy and every mutant (BR-U5a-10). A mutant with more errors than its base is not evaluated.
    - Evaluation in process, with post-seal on.
    - Detection and false fire follow the hex/DDD run's rule. A positive is detected when every expected key is matched
      by a violation the unmutated tree lacks. A twin false-fires when it adds a blocking violation.
  - **report.** The reach matrix and the per-rule verdicts.
- **Reach.** A rule *reaches* a repository when it fired there: natively on the unmutated tree, or on a seed. The
  *precondition* is weaker: it only says the files the rule's template needs exist (as in
  `scripts/v1.4/ddd-b2-rule-reach.ts`, extended to FF-S02 and FF-P07).

### A.3 How the repositories' own structure compares with the rules' grain

The DDD rules assume **file grain**: one aggregate's inner entity, value object or repository per file, selectable by glob.

1. **Real repositories: file grain mostly holds.**
   - Across the 15 repositories, 10 domain files out of 413 hold more than one class. The 33 of 328 domain classes that
     share a file sit mainly in DDH, dlydiard (validators beside models), zddd and meetinger.
   - Entity classes (an `*Entity*`/`*AggregateRoot*` ancestor) never share a file: 0 of 62.
   - Where a repository has inner entities, they are in their own files, and a folder or name rule finds them.
2. **But inner entities are rare in real repositories.** Only 4 of 15 have one at all. 28 of the 37 aggregates are
   single-entity, or their other entities were declared as aggregates of their own (meetinger `Attendee`,
   camps `Comment`).
   - That bounds FF-DT01/DT02 reach before grain matters. DDH and bitloops have no inner entity a folder rule can
     identify (hex/DDD catalogue §5).
3. **Some real repositories model the domain without classes.** In talyssonoc and camps the declared roots name no
   class (types and functions). On those, FF-DT03 (class-based) can never fire, and a class-grain FF-DT01 would not help.
4. **Agent code breaks file grain.**
   - `gate` keeps `Shift` and `DeploymentError` as classes inside `incident.ts`, and `Certification`, `VolunteerSkill`
     and `Skill` as interfaces and a type alias inside `volunteer.ts`.
   - `none` writes the whole registry model as interfaces, a type alias and free functions in `volunteer.ts`, with
     `Volunteer` an interface, not a class.
   - In both trees, outside files import these inner names from the root's file: the shadow class-grain FF-DT01 count
     is 6 per tree (§C). At file grain those imports point at the root file, so they are legal.
5. **Contexts in layer-first repositories** (§A.1) are representable only over one layer folder. This is a
   representation limit, not an agent one.

## C. Grain: what a class or member grain needs, per rule that cannot fire on agent code

**Graph facts that exist today** (`src/shared/types/enums.ts`, `src/apg-extractor/`):

- nodes: `File`, `Class`, `Interface`, `Method`, `Function`, `Package`;
- edges: `DECLARES` (file → class/interface/function), `CONTAINS`, `EXTENDS`, `IMPLEMENTS`, `CONSTRUCTOR_INJECTS`,
  `CALLS`, `IMPORTS`/`RE_EXPORTS` with **`importedNames`** on the edge;
- **member facts are merged** (#90; construct-decisions Q14 "the status quo is now C's behaviour",
  `construct-switches.md`): `publicFields`, `readonlyFields`, `setAccessors`, `mutatorMethods` and more on `Class`, and
  `visibility`/`assignedFields` on `Method`;
- APG v2 (off by default) adds `SIGNATURE_USES` (method/function → class/interface) and `EXPORTS_SYMBOL`.

**Missing:** type aliases and enums are not nodes, and interfaces carry no member facts (no `readonly` per property).

**Shadow measurement** (`shadowClassGrainDt01` in `census.json`): imports from outside an aggregate's module that bind
the name of a non-root entity class or type of that module.

- **6 on each agent tree.** Examples: `registry/application/*-service.ts` imports `Certification`/`VolunteerSkill`/`Skill`
  from `volunteer.ts`; `deployment/api/routes.ts` and the deployment service import `Shift` from `incident.ts`.
- It is 0 on the reference project and on finance and lucashang.
- Large counts appear where a flat domain folder makes every sibling look "inner" (ddd-forum 144, meetinger 53), so it
  is a measurement of what the rule would have to decide, not a finding count.

| Rule | Why it cannot fire on agent code at file grain | What a declaration-grain version needs | Facts today | Effort (zero-call engineering) | Deviation it requires |
|---|---|---|---|---|---|
| FF-DT01 aggregate boundary | Inner entities are declarations inside the root's file. An outside import of the root file is legal at file grain | `inner_entities` by **name** (class, interface or type alias), checked as `IMPORTS.importedNames ∋ name` from outside `module`, with the name resolved to its declaring file by `DECLARES` | `importedNames` and `DECLARES` exist for classes and interfaces; **type aliases are missing** (`Skill`) | ~1.5–2 days: spec schema and `bindDddModel` validation, one template plus its literal-view text, an interpreter check, a reference variant (inner entity in the root file), an MO-D01 site kind by name, tests | Post-seal ADR: it changes the text of a sealed blocking template (ADR-V14-01/02 precedent). Q19 A then counts every named import, including transient use, so on agent code it would add about 6 persistent findings per tree at step 1 (Y, not D) |
| FF-DT02 repository for aggregate roots only | No inner-entity file exists. In `none` the repository interface itself sits in the root's file | Repository selection by **declaration name** (class or interface), and "names an inner entity" read from signatures: `SIGNATURE_USES`, or, without APG v2, interface method types | `SIGNATURE_USES` exists only in APG v2 (off by default); interface methods are `Method` nodes | ~2–3 days, plus a graph-default question: either APG v2 `SIGNATURE_USES` turned on for DDD, or a narrower new edge | ADR plus an extractor-default change for DDD, and a re-run of the development-set DDD rows once (Q16 procedure) |
| FF-DT03 value-object immutability | No value-object file. Agents write value-like shapes as interfaces or type aliases, or keep them inline | VO selection by **class or type name** or by base type (`extends ValueObject`). For interfaces, `readonly` per property. Type aliases of object type need nodes | Class member facts: yes (Q14 merged). Interface member facts and type-alias nodes: **no** | ~0.5 day for class-name selection (template unchanged, the binding reads names); ~1.5–2 days more for interface and type-alias facts | Class-name selection: a spec-language extension, ADR-light (the template is unchanged). Interface/type-alias facts: an extractor change and an ADR (new facts, like #90) |

**Combined estimate:** about 5–7 days of zero-call engineering for all three, plus one development-set run and a review
round. **What it would deviate from:**

- the sealed v1.3 DDD templates: three new post-seal rule texts;
- `Docs/v1.3/rule-tiers.md`: unchanged, but the scored rule set changes as with ADR-V14-01;
- the hold-out pre-specification: it has to be done before the freeze, never on hold-out results (`holdout-prespec.md` §6).

It does not resolve Q19: a name-grain FF-DT01 makes the "stricter than Evans" reading bite much harder on agent code.
Nothing was implemented here.

## D. DDD beta verdict (one page)

**What the instrument can claim for DDD today.**

1. **Representation of real DDD repositories at file grain.**
   - Bounded contexts (module-first layouts), aggregates, file-level inner entities, value objects, repositories,
     domain events (by type), ACL folders and published barrels can be declared.
   - On 15 public DDD repositories most declarations map to code. The exceptions are named in A.1: roots without
     classes in 2 repositories, value-object globs that match no class in 5 (one of them because its value objects are
     `.d.ts` files), and a repository glob that matches nothing in 1.
2. **Enforcement on real code.** Seven of the nine DDD blocking rules reach ≥ 3 real repositories with no seeded miss:
   FF-DS01, FF-DS02, FF-DT01, FF-DT03, FF-DT04, FF-S01 and FF-S02. In this run the existing operators planted 548
   evaluated keys and 548 were detected. The reference fixtures give 10/10, with clean and near-miss controls silent.
   Read with adjudicated twins, these seven meet the proposed beta bar.
3. **Strategic and layering enforcement on agent code.** FF-DS01, FF-DS02, FF-DT04, FF-S01 and FF-S02 fire on the two
   agent trees on every seed.

**What it cannot claim.**

1. **Tactical DDD on agent code.** FF-DT01, FF-DT02 and FF-DT03 cannot fire on either kept agent tree: they have no
   precondition and no operator site. Agents keep inner entities, repository interfaces and value shapes inside the
   root's file, often as interfaces and type aliases. That is the D5 finding, now measured on a second axis (operators)
   and explained (grain census).
2. **FF-DT02 and FF-P07 beta-ready.**
   - FF-DT02 reaches 2 real repositories; real code rarely has inner entities.
   - FF-P07 has no seeded operator, and natively it fired once.
3. **Context-map semantics.** There are no Conformist, Shared-Kernel-usage or customer/supplier relations; the shared
   kernel is only an exclusion list. Contexts in layer-first layouts can be declared over one layer only.
4. **Independent validity.** Everything here is development data, by one author and vendor. The hold-out cannot pass
   its DDD lower bound by size (n < 35).

**Minimal path to a study-ready DDD.** These are proposals for the author; none is taken here.

1. **Declare DDD strategic-plus-layering for studies (D5 as is).** Use FF-DS01, FF-DS02, FF-DT04, FF-S01 and FF-S02,
   with FF-DT01/DT03 reported on real-repository runs only, and FF-DT02 and FF-P07 reported N/A for recall. This needs
   no code; it is a claim restriction.
2. **To make tactical DDD measurable on agent code, choose one** (the D5 follow-up):
   - (a) the DDD tasks require inner entities and value objects in their own files (a task-writing constraint, no code);
   - (b) the declaration-grain FF-DT01/DT02/DT03 of §C (~5–7 days plus a post-seal ADR, before the freeze).
3. **Operator hygiene before any DDD recall claim** (zero-call, about 1 day):
   - a DDD-aware filter for the U5a twins: no cross-context edge into an unpublished file;
   - a barrel-aware cycle check in the twin preconditions;
   - one FF-P07 operator: an application file imports an HTTP framework package, plus its twin.
   This makes the raw bar equal the adjudicated one, and gives FF-P07 a recall estimate.
4. **Sign the open items:** the aggregate declaration for the DDD tasks (TIER-A3 §2.1, unsigned), and Q15 (FF-DS01 tier).

## 6. Limitations

- **Small n.** At most 4 positives and 3 twins per operator and base (10/6 on the reference project). FF-DT01/DT02 rest
  on 4 and 2 real repositories. A recall of 1.00 at these n gives lower bounds of 0.77–0.98 (table B.2).
- **Weak type-check gate on real repositories.** Nothing was installed, so the unmutated copies already carry type
  errors: finance 1408, meetinger 865, others 0–226. The gate only rejects mutants that *add* errors; 28 twins were
  rejected. A mutant that typechecks no worse can still be semantically odd.
- **Native findings are not correctness-checked.** Reach is supported mainly by seeded detections.
- **Specs by one author, after reading the layouts.** The wave and hex/DDD specs are frozen and unchanged here.
- **Agent trees.** Two trees, one task, one generator (Claude Sonnet), final step only. The aggregate declaration is
  TIER-A3's unsigned proposal.
- **Heuristic census.** Entity classes are classes with an `*Entity*`/`*Aggregate*` ancestor. The shadow DT01 count
  treats every non-root, non-VO declaration in a module as inner, which over-counts on flat domain folders.

## 7. Reproduce

From the repository root, with each repository of §1 cloned at its pinned SHA into `$C/<id>` (`$C/zddd`, `$C/ddh`,
`$C/bitloops` for the hex/DDD bases) and a scratch directory `$W`:

```bash
npx tsx scripts/v1.4/ddd-beta-capability.ts census   --clones "$C" --work "$W/census" --out results/v1.4-ddd-beta
npx tsx scripts/v1.4/ddd-beta-capability.ts fixtures --work "$W/fix" --out results/v1.4-ddd-beta
npx tsx scripts/v1.4/ddd-beta-capability.ts recall   --clones "$C" --work "$W/r0" --out "$W/r0" --bases ref-ddd --k 10 --k-twin 6
npx tsx scripts/v1.4/ddd-beta-capability.ts recall   --clones "$C" --work "$W/r1" --out "$W/r1" --bases <ids> --k 4 --k-twin 3   # repeated per group
npx tsx scripts/v1.4/ddd-beta-capability.ts merge    --out results/v1.4-ddd-beta "$W/r0,$W/r1,..."
npx tsx scripts/v1.4/ddd-beta-capability.ts report   --out results/v1.4-ddd-beta
npx jest --maxWorkers=2 tests/unit/scripts/v1.4/ddd-beta.test.ts
```

The two agent bases ran first with an absolute-path harness tsconfig, which made their copies empty: 0 sites. They were
re-run after the fix (relative paths), and `merge` keeps a base's last run. The four groups ran as parallel processes,
about 70 min of process time in total.

Outputs in `results/v1.4-ddd-beta/`:

- `census.json`: per base, the CLI rule rows (post-seal off and on), the concept map, the grain census, the shadow count
  and the preconditions;
- `fixtures.json`;
- `recall/run.json`: bases, feasibility cells, every row with its diff;
- `recall/summary.json`;
- `summary.json`: the verdicts, recall by rule, twins and the reach matrix data;
- `reach.md`.

The row diffs contain short hunks of the MIT/ISC-licensed repositories. Their notices are in
`results/v1.3-external*/NOTICE.md` and `results/v1.3-operators-hexddd/THIRD-PARTY-NOTICES.md`.
