## Item 5 (C1e/C5): N123 re-scored with the violation-identity rule

### Question

N123 says one-year survival of blocking findings is 0.76 without cycles (0.71 with them), against 0.75 for unflagged cross-layer edges (`Docs/v1.3/compendium/nulls-and-limits.md:148`, from `Docs/DiagnosticRuns/v1.3-validity-fixes-mined-2026-10-16.md:16-17` and its §5a table, lines 226-231). The grid lineages behind it end a violation when a file it names is renamed. At pair level, 45 of the 233 blocking edge-shaped disappearances were renames (`ops/notes/g08-violation-identity.md` §1, from `results/v1.3-fixes-mined/summary.json`). G08 §2.2 says a rename at ≥ 50 % similarity *continues* the violation. Does N123 hold under that identity?

### Data

- The committed grid lineages and pairs of the 36 walked histories: `results/v1.3-fixes-mined/repos/<id>/{lineages,pairs}.json.gz`, read through `scripts/lib/drift/metrics.ts` (the U4 module; its published-figure regression is in `aidlc-docs/construction/v1.4/U4/code/summary.md` §5).
- The rename map ρ between every pair of consecutive valid grid points: 4,622 transitions holding 3,638 renames, with 0 transitions where git skipped rename detection (`results/v1.4-tier-a/item05-n123-rescore.json`, `totals`). It was collected from public clones at the pinned shas in `results/v1.3-fixes-mined/corpus.json`, with the walkers' own command `git diff --name-status -M50% -l5000 <a> <b> -- <historyPath>` (`scripts/lib/drift/git-rename.ts`), one diff per grid interval, never composed per commit (G08 §2.2). It is committed as `results/v1.4-tier-a/item05-rename-maps.json.gz`, so the re-score runs without the clones.

### Method

`scripts/v1.4/tier-a/n123-rename-rescore.ts` (pure part in `scripts/v1.4/tier-a/lib/n123-stitch.ts`, tests in `tests/unit/scripts/v1.4/n123-stitch.test.ts`, 8 passing under `npx jest --maxWorkers=2`).

1. **Stitching.** A lineage that ends at grid point j continues as the lineage born at j whose key equals its own key with ρ applied (`mapFinding` and `fineKey` of `scripts/lib/drift/identity.ts`; a cycle is re-canonicalised after the mapping). A born-at-j lineage is claimed at most once, by the earliest-born predecessor, with ties going to the smaller key (G08 §2.3, §2.4). Every committed key round-tripped (0 unparsed). The unflagged-edge baseline (`s|t` keys) is stitched in the same way, so both sides of the comparison lose the rename bias.
2. **Survival.** The published `survival()` and the KM of `scripts/lib/drift/metrics.ts`, unchanged: the same groups, the FF-S02 cap rule and left-censoring at grid index 0. S1 (`first-valid` left-censoring) is computed beside it as a sensitivity.
3. **Intervals.** For S(365): a Greenwood log-log 95 % interval, plus a repository-cluster percentile bootstrap (2,000 resamples, seed 20261019). For the N123 contrast (blocking without cycles minus unflagged cross-layer): a paired repository bootstrap.

**Check.** Under the old policy (a rename ends the lineage), the script reproduces the published §5a rows exactly: 2413 / 874 / 0.709, 2080 / 654 / 0.760, 333 / 220 / 0.373, 11211 / 3790 / 0.746.

- The grid is interval-censored and treated as exact at the next grid point, as in the original (`v1.3-validity-fixes-mined-2026-10-16.md:285`).
- The specs describe the layout at the pin (spec drift, `:286`). This is not addressed here.
- The pooled Greenwood intervals assume independence. The repository bootstrap is the interval to read.
- The published §5a table and N123 were not edited. This note reports the re-score beside them.

## Item 6 (C1a): type-resolution rate and FLOWS_TO yield on the external sets

### Question

(a) What share of the type references in real TypeScript code does the v1.3 extractor resolve? The registered plan dropped this rate as a declared deviation, because it "had no measured denominator" (`Docs/prereg-reasons.md:52`). `Docs/analysis-plan.md:265-269` gives the reason in full: the APG records import resolution, and it records the type-checker edges (CALLS, EXTENDS, IMPLEMENTS, CONSTRUCTOR_INJECTS) "without a per-reference resolution outcome". This item builds that denominator. Rows SO2-3 and C1a.

(b) How many `FLOWS_TO` edges does the extractor yield on real projects, and why so few? Null N40 (`Docs/v1.3/compendium/nulls-and-limits.md:55`) and row SO2-2.

### Data

- **External sets.** 60 repositories: 15 + 20 + 25 entries in `results/v1.3-external/selection.json`, `results/v1.3-external-2/selection.json` and `results/v1.3-external-3/selection.json`. The repo commits no graphs for them. The findings reports hold only edge counts per type (`results/v1.3-external*/findings/<id>.json`, `graphStats`). So each entry was fetched shallow at its pinned sha into the session scratchpad (`clones6/<id>`). All 60 fetched, and HEAD equals the pinned sha for all 60; the script checks this. As in the committed runs, no `node_modules` were installed (`results/v1.3-external*/run-provenance.json`, `dependenciesInstalled`).
- **Committed so2 output** for (b): `results/apg-ablation/so2/flows_to_stores.csv`, 4 corpus bases and 5 fixtures.
- **Output:** `results/v1.4-tier-a/item06-type-resolution.json`, written by `scripts/v1.4/tier-a/item06-type-resolution.ts`.

### Method

**Run.** `npx tsx scripts/v1.4/tier-a/item06-type-resolution.ts --clones <scratchpad>/clones6`. Zero model calls, no Neo4j and no network: a guard that blocks non-IPC sockets and `fetch` was preloaded and never fired. Two runs gave byte-identical output.

**Graph.** For each project the script calls `extractAPG` in-process, exactly as `ExtractCommand` does (`src/pipeline/commands/extract-command.ts:31-38`): the v1.3 defaults, the spec's `default_exclude_paths` (`readSpecExcludePaths`), and `<root>/tsconfig.json`. It then reopens the same ts-morph project with the same filter for analysed files, and uses `extractNodes` for the node lookup.

**Definitions, stated and used:**

- **Family A, all type references (the primary rate).** A type reference is any `TypeReference` node, plus any `ExpressionWithTypeArguments` in a heritage clause, in an analysed file. References to type parameters are excluded (1,489 pooled).
  - *Resolved* means the type checker binds the name to a declaration and the type is not the checker's error type.
  - *Unresolved* means it does not.
  - **Type-resolution rate = resolved ÷ all type references.**
  - Resolved references split into *internal* (declared in an analysed file) and *external* (`lib.d.ts`, etc.).
  - Unresolved references split by where the leftmost name comes from: *package* (an import with a bare specifier, i.e. a package that is not installed), *relative* (a relative import), *global* (no import; an ambient name).
- **Family B, the references the extractor turns into type-checker edges** (`src/apg-extractor/edge-extractor.ts`):
  - class `extends` clauses (EXTENDS, lines 164-176);
  - `implements` clauses (IMPLEMENTS, both resolution paths, lines 177-229);
  - annotated parameters of the first constructor whose annotation is not a primitive or a one-letter type parameter (CONSTRUCTOR_INJECTS, lines 231-271).

  Each reference has one of three outcomes: *edge* (the replicated extractor logic writes an edge to an extracted node), *boundOutsideGraph* (the checker binds it, but the declaration has no node), or *unresolved*. Two rates are reported: checker-resolved = (edge + boundOutsideGraph) ÷ n, and graph-edge = edge ÷ n.

**Checks** (`check` in the JSON, per project):

- The replicated EXTENDS, IMPLEMENTS and FLOWS_TO store counts equal the extractor's in 60/60 projects.
- The distinct CONSTRUCTOR_INJECTS (class, target) pairs equal the graph's edge count in 60/60. At reference level the replicated count is higher in 3 projects, because two parameters of the same type make one edge.
- **Against the committed reports:** the edge counts per type are identical on 53/60. Seven differ by 1 to 45 edges, from extractor changes made after the v1.3 runs:
  - CONSTRUCTOR_INJECTS on luizomf, nutes and lucashang (+1, +5, +3), consistent with N38 `nullableInjects`;
  - CONTAINS on w3tec and typeplate (−1, −2);
  - IMPORTS on felixle-node-core and msc29-clean (+45, +11), the two repos whose extractor fixes are being re-run separately.

  These figures therefore describe the extractor at branch HEAD `4aeeccb0`.

**Intervals.** 95% Wilson intervals, per project and pooled. Pooled rates also get a repository-cluster bootstrap (2,000 resamples, seed 20261019), because references within a repository are not independent.

**FLOWS_TO.** The extractor's own store tally (`flowsTo`), plus the same D8-scope stores re-enumerated with the type of the stored value classified. The script also counts what D8 leaves out by design: constructor parameter properties (which go to CONSTRUCTOR_INJECTS) and non-`new` assignments in the constructor body.

**Why the yield is low** (`pooled.flowsTo.storesReclassified`; code in `src/apg-extractor/flows-to-deriver.ts`):

1. **The scope leaves out the dominant pattern.** Dependency-injected code stores collaborators through constructor parameter properties: 1,458 on the external repos. Together that is 2,244 field writes outside scope, against 492 stores in scope.
2. **Most in-scope stores have no extracted Class or Interface as their value type.** Of 492 stores:
   - 127 have a type the checker cannot resolve (package not installed);
   - 101 are a class or interface that is declared but not extracted (a library or `lib.d.ts`);
   - 81 are a primitive or a literal;
   - 12 are `any` or `unknown`;
   - 6 are anonymous or other declarations.

   All of these become `skippedUnextractedTarget` = 327 (lines 186-192).
3. **Union and intersection types are not unwrapped:** 53 stores, (line 183, "no unwrapping (Q9 A)").
4. Of the 112 candidates left, one edge is kept per (class, target) (line 89), which leaves 96 edges.

The yield is low by construction. The deriver models field stores of `new T()` and setter-style assignments to project classes. Real backends wire collaborators through the constructor, and the extractor already records that as CONSTRUCTOR_INJECTS: 1,276 edges on the same 60 repos (`pooled.flowsTo.constructorInjectsEdges`).

### What it closes in the instrument map

- **SO2-3 / C1a: PARTIAL → reportable.** The type-resolution rate now has a measured denominator, with a stated definition: 0.812 [0.807, 0.817] over 21,813 references, cluster interval [0.767, 0.852].
  - It also has a cause split: 93% of failures come from packages not installed in the clones.
  - The extractor's own type-edge references resolve at 0.809 and become edges at 0.730.

  The "declared dropped" deviation (`Docs/prereg-reasons.md:52`) stays declared, because this is exploratory, after the registration. It can be reported as a descriptive replacement.
- **SO2-2 / N40: PARTIAL → reported as a finding, with a correction.** FLOWS_TO is 0 on the 4 corpus bases, but 96 edges over 21/60 external repos (0.008 per resolved import). The low yield follows from the D8 scope: constructor injection is excluded by design, and unresolved or unextracted value types are skipped. It is not an extraction fault. N40's wording ("empty on real code") should be narrowed to the corpus bases.
- **C1a/C1b AMBER (class facts):** quantified. The rows behind the DDD class-fact rules are EXTENDS, IMPLEMENTS and CONSTRUCTOR_INJECTS. On these rows the graph misses 27% of the references (905/3,354), mostly silently.

### Limitations

- **The rate is the instrument as it was run, not its ceiling.** No `node_modules` were installed, so 3,823 package references cannot resolve. The rate without that cause (0.985) is a counterfactual, not a measurement with dependencies installed.
- **The definition is ours, set after the fact.** Family A counts syntactic `TypeReference` nodes only. It leaves out inferred types, `typeof` queries and import types, and counts a reference to a type parameter as excluded, not resolved. Family B replicates the extractor's logic in a separate script. It matches the graph's edge counts on 60/60, but it is not the extractor's own instrumentation.
- **Resolved means bound, not correct.** A reference that binds to the wrong declaration (declaration merging, duplicate names) counts as resolved. This rate is not a fidelity rate. C1b covers fidelity for imports only.
- **The measurements are at HEAD `4aeeccb0`.** 7/60 graphs differ slightly from the committed v1.3 reports (listed under Method), so this item and the committed findings are not from identical graphs on those 7.
- **Pooled Wilson intervals understate the uncertainty.** They treat references as independent. The cluster bootstrap is the honest interval, and the macro mean (0.734) shows how much the large repos weigh in the pooled figure.
- **External set only.** The corpus bases of N40 were not re-measured here. For them the committed `flows_to_stores.csv` is the source.

## Item 9 (C3): external correctness 283/283: counts, repositories and clustered intervals

### Question

The C3 row reports "correctness 283/283 external; clustered at the repo level, 11/11 repos, Wilson [0.741, 1]" (`ops/01-instrument-map.md:177`). Claims ledger K174 (`Docs/v1.3/compendium/claims-ledger.md:165`) says to quote 283/283 with that clustered bound.

2. How many repositories contribute findings?
3. Do the intervals recompute?
4. What is a defensible interval for the finding-level proportion once findings are clustered in repositories?
5. Are there any discrepancies with the ledger?

### Data

- `results/v1.3-external-correctness/blocking/correctness.csv` has one row per blocking finding, with the deterministic checker's verdict. Its sha256 is `4bd6c579…09b1b3`, the same as stated in `Docs/DiagnosticRuns/v1.3-external-cluster-bootstrap-2026-10-16.md:12`.

- `Docs/DiagnosticRuns/v1.3-external-cluster-bootstrap-2026-10-16.json` holds the earlier figures. They are compared against, not reused.

### Method

- Script: `scripts/v1.4/tier-a/item09-external-correctness.ts` (`npx tsx`). It uses the repository's `scripts/lib/stats.ts` (`wilson`, `wilsonProportion`, `clopperPearson`, `clusterBootstrap`). Two runs gave byte-identical output.
- Outputs:
  - `results/v1.4-tier-a/item09-external-correctness.json`
  - `results/v1.4-tier-a/item09-per-repo.csv`
- The script counts verdicts per repository and computes four kinds of interval. They answer **different questions**:
  - **A. Finding level.** Wilson, Clopper-Pearson, rule of three (1 − 3/n) and the exact one-sided 95% lower bound (0.05^(1/n)), on 283 findings. This treats findings as independent, which they are not.
  - **B. Repository level.** The same intervals with the repository as the unit. Success means "all of this repository's blocking findings are correct". This is a different estimand: the share of repositories with no error, not the share of correct findings.
  - **C. Cluster-adjusted finding level (new).** This uses the Kish design effect for unequal cluster sizes, Deff = 1 + (m̃ − 1)·ICC. Here m̃ = Σm²/Σm is the size-weighted mean cluster size. Then n_eff = 283 / Deff, and Wilson is computed on (p = 1, n_eff).
    - The ICC cannot be estimated when there are 0 errors, so a grid of ICC values is reported.
    - ICC = 1 is the worst case: every finding in a repository shares one outcome. Then n_eff = (Σm)² / Σm².
    - Each grid point also has a rule-of-three bound on n_eff.
  - **D. Repository-cluster percentile bootstrap.** 10,000 resamples, seed 20261016, ratio of sums. It is reported only to show that it is degenerate here.

## Item 10 (SO1-4): schema expressiveness: share of style-rule source rows the spec language can express

### Question

The gap review defines SO1-4 "expressiveness" as rows expressible ÷ rows (REV-04, `ops/notes/rev-04-gaps-and-promises-2026-10-19.md:176` on `origin/v14/study2-drift-deviation`). Here a row is a row of the style-rule source tables.

Per style:

- How many source rows are there?
- How many can the spec language express?
- Which rows cannot be expressed, and why?

### Data

- `Docs/v1.3/style-rule-sources.md`: the sealed source table, lines 7–19, with 13 rows. It is read only.
- `Docs/v1.3/style-rule-sources-supplement.md`: lines 21–28, with 8 rows for the rules the sealed table missed.
- `Docs/v1.3/style-rule-sources-errata.md`: corrections only. It has no source-row table, so it contributes 0 rows.
- `results/v1.3-validity-convergent/translation-table.json`: the 89 rule × style rows the v1.3 presets compile. This is used as the record of what the spec language encodes per style.
- `src/scoring-engine/rule-tiers.ts` (`DDD_RULE_TIERS`, line 131 onward): maps the sealed DDD row names to DDD templates.

The source rows have no "encoded?" column. So expressibility is decided from the Rule and Style cells of each row, by the rule below.

### Method

Script: `scripts/v1.4/tier-a/item10-expressiveness.ts` (`npx tsx`). It parses the markdown tables and applies the coding rule mechanically. Two runs gave byte-identical output.

Outputs:

- `results/v1.4-tier-a/item10-expressiveness-rows.csv`: one line per (row, style) instance, with the code and the reason.
- `results/v1.4-tier-a/item10-expressiveness.json`: the totals.

**Coding rule (stated before it is applied):**

1. **What counts as a row.** A source row is a body row of a markdown table whose header is exactly `Style | Rule | Source | Constraint (paraphrase)`. The other tables are not source rows: the errata corrections and the supplement's "Summary of findings".
2. **Styles.** The Style cell is split on commas. Clean, Layered, NestJS, Hexagonal and DDD become the preset styles. A row naming two styles counts once per style.
   - A parenthetical "(X: not applied)" marks style X as excluded. It is listed but is outside every denominator.
3. **Resolving the rule.** The rule is resolved from the Rule cell, in this order:
   - (a) any FF id;
   - (b) any template name of the compiled rule set;
   - (c) for DDD rows with neither, the `DDD_RULE_TIERS` entry whose sealed row name starts with the cell's label, or contains its parenthetical. For example, "Isolated domain (framework-free)" matches "DDD framework-free domain", which is domain-purity.
4. **Expressible or not.** A (row, style) is **expressible** if step 3 finds at least one rule, and every rule it finds is in that style's compiled v1.3 rules. It is **not expressible** if nothing resolves, or if a rule it names is not compiled for that style.
5. **Partial.** An expressible instance is **partial** if the Rule cell says only part of the rule is encoded ("half only", "partial"). The primary ratio counts partial instances as expressible. The strict ratio does not.

- The denominators are small (2–9 per style), so the per-style intervals are wide.
