# v1.5 CN-02: development revision of the DDD rows that CAL-02 did not admit

Date: 2026-10-27. Zero model calls. **Development evidence only.** The rules were revised while reading the CAL-02
cases they missed, so these numbers say nothing about accuracy on new code. No row is admitted from this report. Rows
are admitted only by a fresh sealed set, CAL-03, scored once under a design committed before its cases exist.

## Goal

The Pareto set (`Docs/v1.5/ddd-detection-paths.md` §2) has seven rules. CAL-02 admitted rows for rules 1, 3, 4, 6
and 7. Rules 2 (domain purity) and 5 (invariants inside the aggregate) had no admitted row. The target is all seven
rules covered, with at least 13 of the 16 catalog rows admitted (81%). K06, K11 and K13 are the three rows that may
stay exploratory: their rules are already covered by other rows.

## Revisions (CN-02)

- **R-D5, guard sites (`facts.ts` RULE_SITE):**
  - Any read of a declared aggregate instance in a guard condition counts: a predicate, a collection test, a
    comparison method, `.length` of its collections.
  - Rejections by returning a value (an error result) count, besides throws.
  - Values are followed through locals (`total` ← `lines`) and through wrapping calls.
  - An adapter that tests a value against something it read and then hands the value to a command is reported (check
    then act).
  - An input rule that equals a guard of the aggregate method receiving the same value is reported as duplicated.
- **Exclusions, from the development evidence:**
  - conditions over two different aggregate instances (`from.currency !== to.currency`): such a rule cannot live in one
    aggregate (13 P1 agent trees the oracle judged clean);
  - elements of a set of aggregates in a callback (`open.some((o) => …)`, precision fixture p10);
  - the arguments of a repository lookup, and repository classes themselves (store-enforced uniqueness);
  - the new checks apply to declared roots only, as R-REF does. With inferred roots (Hexagonal trees) an entity's own
    query is not a boundary. Three Hexagonal clean study solutions were flagged before this limit.
- **R-D3:** the computed value may sit anywhere inside an aggregate call's arguments, and aggregate state is followed
  through locals. Value-object arithmetic (`total.times(rate)`) was tried and removed: it flagged a P2 tree the
  oracle judged clean, and no CAL-02 case needed it.
- **R-PURE (new, family D2):** a domain file (by layer or inside a declared aggregate module) imports an I/O package,
  classified by the existing apg-enrich I/O table (database, HTTP client, mail, file system, messaging, web framework).
  Type-only imports are not reported.
- **R-D4R (new, family D4):** a repository write method takes two aggregate-root instances (always reported), or a
  collection of them (reported once a command calls it). A batch the spec declares through an R-D4 allowance covers
  the repository methods its command calls (precision fixture p06).
- **Row map (`experiments/cal-01/score.ts`):** K02 adds R-PURE, K04 adds R-D4R, K10 adds R-D5 (both are family D5).
  The CAL-03 design registers this map before its cases exist.
- **Scorer:** `--only <rows>` and `--out <file>` for development runs, so a sealed set's `result.json` is never
  overwritten.

## What follows

CAL-03: design committed first (`ops/notes/cal-03-admission-design.md`), then blind sessions build new domains with
varied shapes per row, then pre-flight on the bases, the per-row count check, the seal, and one scoring.

The CN-02 changes sit in the guard, calculation and new repository and import sections of `facts.ts`; the facts
behind the seven CAL-02 rows (write footprints, context writes, remote calls in a transaction, contracts, injections,
references) did not change, and those rows score as before on every set above. The sealed rule hash still changes,
because it covers the whole file. CAL-03 therefore carries all 16 rows, and the seven rows admitted by CAL-02 must
pass again on it under the CN-02 code.
