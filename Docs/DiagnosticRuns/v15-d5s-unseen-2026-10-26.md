# v1.5 C1: R-D5S on the sealed unseen cases (S2 re-run)

## Setup

- **Cases:** 16, in 2 new domains (clinic scheduling, warehouse storage): per domain 3 positives, 3 twins (the check
  moved into the owner) and 2 legitimate cases (one uniqueness check through the store, one single-instance check
  inside its aggregate). Built by a separate session briefed with the note's §2–§3 and the spec format only. All
  16 trees type-check under `tsc --strict`.
- **Seal:** `experiments/d5-unseen/SEAL.sha256` (root hash in `SEAL.root`), committed in `2146e061e` before any
  scoring. The scorer checks the seal first.
- **Rule:** R-D5S as committed in `8de84ffb6`. Not changed after the run.
- **Scorer:** `experiments/d5-unseen/score.ts`; record `experiments/d5-unseen/result.json`.

## Result

| Measure | Gate | Result |
|---|---|---|
| Recall on the 6 positives | ≥ 5/6 | **4/6** |
| False positives on the 6 twins and 4 legitimate cases | 0 | **2/10** |
| Tie-breaks | reported | 0 |

**Verdict: the gate fails.** Under C1, DDD runs as an exploratory style in the final study, and Hexagonal is the
confirmatory style.

## Why it failed (read from the evidence, not fixed)

1. **Misses (2):** both `pos-3` cases put the violating check in an infrastructure entry point: an HTTP controller
   (clinic) and a message handler (warehouse). R-D5S found nothing in either. The guard facts R-D5S builds on only
   take if-statements whose branch throws. The likely cause is that an entry point rejects by returning a response
   or skipping the message instead of throwing. This was not confirmed by reading the cases.
2. **False positives (2):** in clinic `legit-1` and `twin-2`, the overlap check sits in `DoctorDay`, the owner of
   the overlap invariant, which is the right place. It also uses a term of a second declared invariant
   (`cancel-notice-window`, owner `Appointment`). R-D5S matches by term names and does not prefer the invariant
   whose owner holds the guard, so it reports the check against the wrong invariant.

Both are properties of the rule, not of the labels. The case author also wrote the code with the declared term
names, which favours the rule; the failures happened despite that.

## What it means

- Declaring invariants moves the D5 judgement into the spec, as intended. Matching code to an invariant by names
  alone is still too weak: it needs the owner-first preference and non-throwing rejections.
- Any change now is development work. It would need a new set of unseen cases, so it is not done before the freeze.
  It becomes a Kap9 item.
- R-D5S stays in v1.5 as an exploratory rule. It is silent when a spec declares no invariants, so it changes no
  existing result (regression 0 mismatches over 260 steps).
