# v1.5 U3: S1 severity calibration (C4 rubric), development pilot

**Result: U3 passes its gate on development material.** With the severity rubric (`c4-v0.2+u3-r1`), C4 got all 24 targets right in both runs: the v1.4 six-case set and six new pairs whose answers were written first. A 4-call control arm with the frozen prompt reproduces the v1.4 severity failure on case 5. This is exploratory development evidence. It is not a registered result, and it changes nothing in Study 2b.

## 4. Control arm (frozen `c4-v0.2`, same model)

| Project | Severity (r0, r1) | Allowed | Intent (r0, r1) | Scorer |
|---|---|---|---|---|
| c4-04t-superseded-adr | medium, medium | high/medium | contradicts, **consistent** | not correct (intent, run 1) |
| c4-05-intent-contradicted | **medium, medium** | high | **consistent**, contradicts | not correct (severity, both runs; intent, run 0) |

- **Case 5's severity failure reproduces** on Sonnet with the frozen prompt: medium in both runs, as Opus gave in v1.4. The rubric arm gave high in both runs.
- Twin 4's severity is medium on Sonnet, which the manifest allows. Opus gave low in v1.4. So twin 4's v1.4 miss is partly a model effect.
- **New: an intent-label slip.** In 2 of 4 runs the frozen prompt labels intent `consistent-with-declared-intent` while the explanation says the code breaks the README or the accepted ADR. Run 0 on case 5, for example, says "The README states the same rule: a controller never imports a repository". The model read "consistent" as "the rule is consistent with the docs", not "the code is consistent with them". The rubric's step b defines `contradicts-declared-intent` as "a current doc declares the rule this code breaks", and the slip does not occur in the rubric arm (0 of 48 runs).
- The control is 2 targets and 4 calls. It shows that the failure reproduces; it does not estimate a rate.

## 6. Reading and limits

- **What this shows.** On these 24 targets, an explicit rubric removes the severity failure that blocked the v1.4 precondition. It keeps exception and intent reading intact, and the answers are fully stable. The new pairs test the rubric's axes, each through a twin that moves one fact:
  - read vs write;
  - active vs expired grant;
  - Accepted vs Proposed ADR;
  - value type vs foreign write;
  - grant scope;
  - comment grant vs TODO.
- **A ceiling result is a warning as much as a pass.**
  - One session wrote the rubric and the new cases, so the cases follow the rubric's own categories. They are clean, small and unambiguous by design. Real findings are not.
  - The rubric maps intent to severity for steps a and b, so on those targets severity follows from the intent label. Only step c (10 of 24 targets) ranks by what the dependency does.
  - 24/24 is a go/no-go check on a designed set, not a rate. The Wilson 95 % interval for 12/12 is [0.76, 1.00].
- **The original set is calibration, not a test** (note §1): the rubric was written knowing which two fields failed.
- **Same vendor.** Claude wrote the cases and Claude reads them. No swap arm has run; Gemini is planned after its quota resets.
- **Model change.** v1.4 used Opus with effort high on the frozen pin; this pilot uses Sonnet on the current CLI. The control isolates the prompt effect on 2 targets only.
- **Target-only scope.** Pair 4's two non-target findings, which v1.4 interpreted, were not interpreted here. "Clean" is per target.
- **No temperature control.** Two runs are not two draws at a known temperature (C4-01 §4.2 rule 6).
- **Not a registered result.** Study 2b's D_sem stays "not run: precondition not met" as registered. Nothing here re-opens it.
