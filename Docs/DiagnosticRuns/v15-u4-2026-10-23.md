# v1.5 U4: S3 facts and S2 confirmation, development pilot

**Result: S3 passes its gate on development material. S2 fails it.**

- **S3.** The model's aggregate roots recover 22 of the 23 declared roots on the 10 repositories with class-level truth, with no wrong root (19 of 23 when the declared label must match the class name). The DETECT-02 rules run on those roots keep the one true hit (lucashang-ddd-payday) and add no false hit. But R1–R3 had already removed the 12 earlier false hits symbolically, so **S3's lift on the hit count is zero**. The lift is in the root set itself: inferred roots get 13 of 31 right.
- **S2.** Confirmation does not raise D5 recall above 11/16. The relaxed proposer reaches every lock-form tree, but the model reads the lock-form overlap check as a "cross-aggregate check", which the D5 rule text exempts, and rejects it.
  - One dated fix (r2, the rule's exemption reworded for set invariants) confirms the lock form 5/5. It also confirms a labelled negative and a legitimate precision fixture. It is post-hoc and it does not change the verdict.

This is exploratory development evidence. It is not a registered result, and it changes nothing frozen.

## 5. r2: the one fix (post-hoc, not the S2 result)

**The failure, and why.** Five of the six lock-form answers give the same reason: the check compares a stay with all the bookings of the room, so it is "a cross-aggregate check, which the rule exempts". That is what `FAMILY_RULE.D5` says. The hand label reads the same code as D5 because the set invariant has no owning aggregate, and the twin shows the fix (a `RoomSchedule` aggregate). So the rule text and the label disagree.

**The fix.** r2 rewords the exemption: uniqueness across the store stays exempt, but a set invariant that no aggregate owns is a violation, lock or not. It was asked once, on 9 candidates:

| Item | Label | r1 | r2 |
|---|---|---|---|
| Lock form: c1 positive, pilot S1 steps 2–5 | D5 | 0/5 confirmed | **5/5 confirmed** |
| Pilot S1 step 1: the same check, before the lock | negative | reject | **confirm** |
| Pilot S2 step 0: `!customer.canOrder()` | negative | reject | reject |
| P10 legit: duplicate-order check | negative (legitimate fixture) | reject | **confirm** |
| Puzzle c10 step 1: currency check | negative | confirm | confirm |

r2 moves the boundary rather than sharpening it. Applied to the 16 trees, it would give 16/16 recall, but it confirms a violation on a legitimate precision fixture, which is itself an S2 failure condition (§5).

The pre-lock tree shows why. Step 1 and step 2 contain the same unowned set invariant. The label separates them only because the agent added the lock at step 2, and the hand read logged violations the agent introduced. A question that reads the code alone cannot tell step 1 from step 2. This is the note's predicted hardest case, now shown.

r2 was written after reading the r1 answers on these trees, so it is reported as development evidence only.

## 8. Caveats

- **Development material throughout.**
  - The DETECT-02 rules and the relaxed proposer were written while looking at these trees.
  - The S2 scope was cut by hand before any call (r1). The asked subset is not the full 120.
  - The 13 repositories are the same ones the precision note used to motivate R3.
- **Truth is thin on the human repositories.** The declared specs were written by this project, not by the repositories' authors, and S3-d mostly reads folder names. The only true hit is a single command.
- **One vendor, one model.** The same session wrote the S3 question and scored it. There is no non-author row and no Gemini arm yet.
- **Rebuilding the pilot S1 step trees needs the seed builder.** The committed `s1-hex-debt` seed lacks `src/application/ports/out/` because of the `.gitignore` gap already open in the research log. `build-seeds.mjs` was run in a scratch copy, and the committed seed is unchanged.
