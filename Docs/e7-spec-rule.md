# E7 Spec Rule (mechanical directory-to-layer mapping)

Dated 2026-10-08, committed before any E7 or dev-nest spec is generated and before any site-feasibility count on those projects (ADR-019 items 1 and 3; ADR-015 items 1 and 3; ADR-012; OI-12; Build and Test Step 55). It is a registered artefact (`corpus/prereg.json`, BR-U5b-51).

**Why this rule exists (Ch7 declaration).** The E7 specs, and the ADR-017 item 4 domain-layer remap before them, are **floor-motivated**: they were written because the SO4 held-out capacity was below the floor of 80 (BR-U5a-37 `CAT_SHORTFALL`, E-1). To keep them from being tuned towards N, every spec for dev-nest and the five E7 projects is generated by `scripts/generate-e7-specs.ts` from this rule alone. Hand edits are not allowed. The site-feasibility count on the generated specs runs once. After that count, no spec is edited in a way that changes N. A generated spec that is invalid (§5) excludes its project, with the reason recorded. Such a spec is not repaired.

**E7-x additions (dated 2026-10-10; ADR-027 item 5).** The rule is unchanged (version 1). The six E7-x selections were appended to `projects` and generated by `scripts/generate-e7-specs.ts` with no hand edit; `--check` stays byte-identical for every earlier spec. `fairnesscoop__permacoop` is invalid under §5 (b) (one layer receives a file: its directories are capitalised, `src/Domain|Application|Infrastructure`, and the globs are case-sensitive), so it has no spec. `khusenov__backend-boilerplate`, `pvarentsov__typescript-clean-architecture` and `DanielAraldi__mailer` generated valid specs but failed the base type-check (BR-U5a-07) and were excluded without repair. Only the two admitted projects stay in `projects`; the generation output for all six is `Docs/DiagnosticRuns/e7x-spec-generation.json`, and the evidence per project is `Docs/DiagnosticRuns/e7x-preparation.json`. These specs are E7-only: they enter no SO4 count, and the count-once constraint of the SO4 feasibility count does not apply to them.

## 1. Inputs (per project)

- **Files**: the C2 file set of `Docs/corpus-criteria.md`. These are the paths under the root `src/` that end in `.ts`, excluding `*.spec.ts`, `*.test.ts` and `*.d.ts`, read with `git ls-tree -r --name-only <commitSha> src` in the fetched clone.
- **Segments**: every directory name on those paths below `src/`, lower-cased.
- **Suffixes**: for a file named `<a>.<x>.ts`, its suffix is `x`, lower-cased; a file `<a>.ts` has no suffix.
- **Framework**: whether `@nestjs/core` is in `dependencies` of the root `package.json` at `commitSha`.

## 2. Groups (fixed vocabulary)

Each group is a set of directory segments and a set of file suffixes. No word is in two groups.

| Group | Segments | Suffixes |
|---|---|---|
| D (domain) | domain, entities, entity, models, model, core, aggregates, aggregate, value-objects, valueobjects | entity, model, aggregate, vo |
| A (application) | application, applications, use-cases, usecases, use-case, services, service, commands, queries, handlers, dto, dtos | service, usecase, use-case, handler, dto, command, query |
| I (infrastructure) | infrastructure, persistence, repositories, repository, dal, database, db, adapters, prisma, orm | repository, repo, dao |
| P (presentation) | presentation, controllers, controller, routes, routers, resolvers, gateways, middlewares | controller, resolver, gateway, router, routes |

The clean-architecture markers are `domain` (from D); `application`, `applications`, `use-cases`, `usecases` and `use-case` (from A); and `infrastructure` (from I).

## 3. Style (first matching row wins; this order is the tie-break)

| Order | Condition | Style |
|---|---|---|
| 1 | The segments contain markers from at least two of {D, A, I} | `clean-architecture` |
| 2 | Framework is `@nestjs/core` | `nestjs` |
| 3 | otherwise | `layered` |

The style found here is the spec style. If it differs from the query-derived `style` in `corpus/corpus.json`, the difference is recorded in `Docs/corpus.md`. It is not reconciled.

## 4. Layer globs

The spec is the preset `presets/<style>.yaml`, unchanged except for the layer lists. Each preset layer takes the groups below. For each group, every segment `s` found in the project appends `**/<s>/**` to that layer's `directories`, and every suffix `x` found appends `**/*.<x>.ts` to its `file_patterns`. The preset's own entries come first, then the appended entries in alphabetical order, with no duplicates. Layer order, names, kinds, roles, functions, thresholds, severities, weights and rubric text stay as in the preset (ADR-015 item 1).

| Style | Layer ← groups |
|---|---|
| clean-architecture | domain ← D; application ← A; infrastructure ← I, P |
| nestjs | domain ← D; infrastructure ← I; application ← A; presentation ← P |
| layered | persistence ← I; business ← D, A; presentation ← P |

A file matching several layers takes the first layer whose `directories` match it, and otherwise the first whose `file_patterns` match (`layer-annotator.ts`, `layerOf`). The rule adds nothing to change this.

After the mapping, the registered corpus-spec chain is applied in order, as for the core specs (BR-U5b-77, BR-U4-RUB-03): `migrate fr22`, `migrate cv02`, the ADR-017 item 4 domain remap, and the FR-22 (U4 rubric) step. A rerun of each tool on the output prints `no change`.

The header comment of every generated spec records:
- the rule version;
- the commit;
- the style row that matched;
- the found segments and suffixes per group;
- the number of files per layer.

## 5. Validity (exclusion, never repair)

A generated spec is invalid, and its project is excluded with the reason recorded, when:
- (a) it does not compile (`firewall validate`, U1 compiler); or
- (b) fewer than two layers receive at least one file of the C2 set under §4's precedence.
