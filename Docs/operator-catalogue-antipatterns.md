# Anti-pattern Operator Catalogue (DRAFT)

> **Status: DRAFT 2026-10-12 (v1.3, branch `v1.3-judge-antipatterns`).** Not registered, not frozen, not part of pre-registration. It does not change, extend or replace the frozen catalogue `Docs/operator-catalogue.md`, and no file listed in `scripts/lib/prereg.ts` `REGISTERED_ARTEFACTS` is edited by this work.
> **Purpose**: realistic semantic and integrity violations for testing whether the LLM judge (FF-N01 `architectural-integrity`, FF-N02 `intent-alignment`) catches what the symbolic rules miss. They replace nothing. The frozen judge probes MO-X02 and MO-X03 placed 0 seeds on the 7 held-out bases and in the 65 E1 cells (`Docs/DiagnosticRuns/judge-probe-e1-site-count.md`), because their precondition (a boolean entity guard method used only in `if (!e.m()) throw`) is rare in real and generated code.
> **Source of truth**: the operators are built in code (`scripts/lib/mutation/antipatterns/`). The registry (`antipatterns/index.ts`) is separate from the frozen one. Its `catalogueVersion` is the sha256 of this file, so no row of these operators can carry the frozen catalogue's version. `tests/unit/scripts/mutation/antipatterns.test.ts` asserts that the entry table below and the registry match one to one (id, twin, dimension, expected templates, coverage, source). `scripts/mutate.ts --operator AP-…` routes to this registry.
> **Design pre-registration draft**: `Docs/prereg-drafts/judge-antipattern-test.md`.

## 2. Site rules and edits

Shared definitions (`antipatterns/common.ts`):
- **Service class**: a named class of an application-kind layer file (C4 binding), not a controller, without a data-class suffix (`Dto`, `Command`, `Query`, `Event`, `Input`, `Output`, `Request`, `Response`, `Entity`, `Model`), with a constructor parameter or a `Service` / `UseCase` / `Interactor` / `Handler` name.
- **Parameter rule**: a top-level `if (<cond>) { throw <e>; }` statement of a method (no `else`) whose identifiers are the method's own plain parameters (at least one), default-library globals, named imports of a bare package, or exported declarations of a project file. It reads no `this`, awaits nothing and holds no function literal. It can therefore be moved or copied without its class.

## 6. Threats specific to this catalogue

- **Author-written operators.** The operator author also designed the experiment, and the edits are templates. A judge may learn template cues (the `validate<Method>` name, the `assert<Method>Rule` helper, the `_request` spelling) rather than the defect. Mitigation: each twin uses the same template machinery and similar names, so a cue that is not the defect also appears in the twin and shows up as false alarms.
- **Circularity.** The judged-function assignment (§1) was made after reading the frozen rubric. The rubric's fail clauses ("bypass", "duplicate a rule", "persistence, transport or framework logic") name these defect families. The operators come from §4, not from the rubric, and the rubric is frozen (RUB-01) and was written before them. A high detection rate is still partly by design, because the probes test exactly what the rubric asks. Ch7 must state this.
- **Realism.** The preconditions were tuned against the corpus clones (§5 diagnostic) to find common shapes. That is a selection on the held-out bases, with no labels and no detector or judge output. Every change to a precondition is recorded in the changelog below.
- **No install.** The counts above ran without `npm ci`. With installs, more declarations resolve. Ambient `@types` namespaces such as `Express.Multer.File` become writable, which can add AP-DUP-RULE sites, and the type-check gate can reject some applications. The run counts are the ones taken at seeding time.

## 8. AP-DUP-RULE v2: twin rationale (written 2026-10-15, before the v2 code and before any v2 judge call)

**Why v1's twin is not a control.** AP-DUP-RULEn adds the same `validate<Method>` method to the second service as the positive does; only its body differs (a forwarder to the first file's `assert<Method>Rule` instead of the copied rule). In round 2 the judge failed 5/5 of these twins. Every run cited the twin's own edit: the second service gains a method about a concern of another service ("CatalogueService.validateCombineItems handles an order-item concern that has nothing to do with the catalogue"). The forwarder is a misplaced responsibility in its own right. So the v1 pair compared *foreign method with a copied rule* against *foreign method with a forwarder*. Both are defects, and a fail on both says nothing about duplication.

**What a valid twin must be.**
- **Behaviour-equivalent** to the base: no new check, no new throw path, no new public surface on a service that does not own the rule.
- **No architectural smell**: nothing that the frozen rubric's FF-N01 clauses (bypassing the module's abstractions, duplicating a rule or invariant) or the FF-N02 clause (a responsibility in the wrong layer kind) could fairly name.
- **Same machinery**: the twin touches the same rule, through the same site pass, with the same rule text, the same `assert…` naming family and the same file style, so a judge that reacts to template cues (catalogue §6) would also react to the twin.

**Options considered.**
1. *The second service calls an existing shared domain policy.* That needs a method of the second service where the rule applies. A label-free scan of the 16 E1 cells with DUP-RULE sites found no second-service method that takes a parameter with the rule parameter's name and type (0 matches over the 24 parameter rules of those cells). Any call would have to sit in a new method of the second service, which is the forwarder again.
2. *The second service gains nothing; the rule moves, once, into a policy function in the domain* (the author's suggestion). This is an Extract Function into the layer where business rules belong (Evans 2003, ch. 5 "Specification" and ch. 6; Fowler 1999, "Extract Function", "Move Function"). The rule still exists exactly once. The first service now calls it. Behaviour is unchanged.
3. *The same, in the first service's own file*, for rules whose names live outside the domain: an application DTO type, an application error class, or a framework package (`BadRequestException` from `@nestjs/common` on `antipattern-nest`). Moving those into the domain would create a domain → application or domain → framework dependency, which is a real defect (FF-P01/FF-P02 territory). The lowest layer the rule's names allow is then the application layer itself.

**Chosen.** Option 2, falling back to option 3 per rule:
- **Domain host.** Every name the rule needs (condition names, error class, parameter types) is a declaration of a domain-layer file. The host is the domain file that declares a name the *condition* or a parameter type uses, so the guard sits next to the concept it guards (for `if (!isOrderStatus(status)) throw …`, the host is the file of `isOrderStatus`). The helper is exported and named `assert<X>` after the `is<X>` guard it wraps (`assertOrderStatus`), else `assert<Method>Rule`.
- **Own-file host** otherwise. The helper is a module-level, non-exported `assert<Method>Rule` in the first service's file (Extract Function; the v1 twin's helper without the export and without the forwarder).
