# v1.3 DDD library: design notes

Branch `v1.3-ddd`, cut from `v1.3-hexagonal` (FR-V4, with the DDD part of FR-V3). Draft, **not for merge into `v1.2e`**. It adds a Domain-Driven Design style library behind a new style, `ddd`, and a DDD reference project. The frozen v1.2E behaviour does not change (§7).

Order of work, kept on purpose and visible in the commit history: (1) each rule was defined from the literature and given a tier (§1, §2); (2) the reference project and its manifests were written from those definitions (§5); (3) only then were the templates implemented and the tool run; (4) the differences between the tool and the manifests are recorded in §6, and the manifests were not edited to match.

## 1. Rules, defined from the literature

Sources:

- **[E]** Evans, E. (2003). *Domain-Driven Design: Tackling Complexity in the Heart of Software*. Addison-Wesley.
- **[V]** Vernon, V. (2013). *Implementing Domain-Driven Design*. Addison-Wesley.

Chapters are cited, not pages, because the pattern summaries below are quoted from memory of the pattern statements; check the page against the edition at hand before quoting them in the thesis.

Rule ids follow the spec grammar `FF-[A-Z]{1,3}[0-9]{2}`: `FF-DT..` tactical, `FF-DS..` strategic. Two layering functions of the hexagonal library are composed in (`FF-S01`, `FF-S03`, §3).

### Tactical

**FF-DT01 `aggregate-boundary`.** *Literature.* [E] ch. 6, AGGREGATES: choose one entity as the root of each aggregate and control all access to the objects inside the boundary through the root; external objects may hold references to the root only. The rule list in that section says that nothing outside the aggregate boundary can hold a reference to anything inside except the root entity, and that the root may hand out transient references to inner entities or copies of value objects. [V] ch. 10 restates this as "protect business invariants inside aggregate boundaries" and adds "reference other aggregates by identity". *Definition used.* For every declared aggregate (a module glob, its root file, and its inner-entity files): no file outside the aggregate module may import or re-export an inner-entity file. Value objects inside the module are not inner entities ([E] allows handing out value-object copies) and are not checked. A type-only import is a reference and counts. *Not covered:* [V]'s "reference other aggregates by identity" (an aggregate holding another aggregate's root object) is a separate rule and is not implemented (§4).

**FF-DT02 `repository-aggregate-root`.** *Literature.* [E] ch. 6, REPOSITORIES: provide repositories only for aggregate roots that actually need direct access; all other objects are found by traversal from the root. [V] ch. 12: one repository per aggregate type. *Definition used.* A repository (a file matched by the declared repository globs) must not import or re-export an inner-entity file of any aggregate. The reading: a repository whose contract names an inner entity gives global access to an object that [E] says is reachable only by traversal. *Definition question:* this is stricter than [E] in one case, a root's repository with a query keyed by an inner entity (`findByLine(line)` returning `Order`); it is flagged although it returns a root. Recorded in §4.

**FF-DT03 `value-object-immutability`.** *Literature.* [E] ch. 5, VALUE OBJECTS: treat the value object as immutable; operations return new instances (side-effect-free functions, ch. 10). [V] ch. 6, "Immutability". *Definition used (literature).* A class in a declared value-object file has no public setter (no `set` accessor and no public method that assigns a field) and every field is `readonly`. *Definition implemented (proxy).* The extractor does not record field modifiers, accessors or method visibility, so the tool can only check method names: a non-static method named `set` + capital letter on a class in a value-object file. See §4.

**FF-DT04 `domain-purity` (framework-free domain).** *Literature.* [E] ch. 4, LAYERED ARCHITECTURE: concentrate the domain model in one layer and isolate it from user interface, application and infrastructure code; the domain layer is "the heart of business software". [V] ch. 4 (Hexagonal) puts the domain model at the centre with no dependency on frameworks or delivery mechanisms. *Definition used.* No file in the domain layer imports or re-exports a package in the declared framework list (`@nestjs/*`, `typeorm`, `@prisma/*`, `prisma`, `express`, `sequelize`, `mongoose`, `@mikro-orm/*`, `class-validator`, `class-transformer`, `inversify`, `tsyringe`). Implemented by the existing `domain-purity` template, unchanged, under a new id.

**FF-DT05 `domain-event-placement`.** *Literature.* [E] 2003 has no domain-event pattern (Evans added it after the book). [V] ch. 8, DOMAIN EVENTS: model information about activity in the domain as a series of discrete events and represent each event as a domain object; events are published by aggregates and live in the domain model's modules. *Definition used.* A class that implements or extends (directly or transitively) a declared domain-event type (`DomainEvent` in the preset) is defined in a domain-layer file. *Not covered:* "raised in the domain" (FR-V4 wording) would need to know which code instantiates the event; the graph has no instantiation edge for this, so only placement is checked (§4).

**FF-DT06 `application-service-thin` (heuristic).** *Literature.* [E] ch. 4: the application layer is kept thin; it does not contain business rules or knowledge, it only coordinates tasks and delegates work to domain objects. [V] ch. 14, APPLICATION SERVICES: keep them thin, use them only to coordinate tasks on the model. *Definition used.* A business rule is not a structural fact, so the rule is a proxy: a class in a declared application-service file declares more methods than the threshold (3, chosen before measuring: a command-style service exposes one or two use-case methods; extra methods are helpers, which is where rules accumulate). *Advisory by construction.*

### Strategic

**FF-DS01 `bounded-context-modules`.** *Literature.* [E] ch. 14, BOUNDED CONTEXT: explicitly define the context in which a model applies and set its boundaries in terms of team organisation, usage, and physical manifestations such as code bases. [E] ch. 5, MODULES; [V] ch. 9 (Modules) and ch. 2: one bounded context per top-level module, named after the context. *Definition used.* Every declared context root is a top-level module (`<source_root><name>/`, checked when the spec is bound; a nested root is a spec error). Every file under the source root lies in a declared context root or in a path declared outside the contexts (the shared kernel, [E] ch. 14 SHARED KERNEL, and the composition root).

**FF-DS02 `context-isolation`.** *Literature.* [E] ch. 14: CONTEXT MAP, OPEN HOST SERVICE / PUBLISHED LANGUAGE (other contexts integrate through a published protocol), ANTICORRUPTION LAYER (an isolating layer that translates the other model into the client's own and talks to the other system through its existing interface). [V] ch. 3 (Context Maps) and ch. 13 (Integrating Bounded Contexts). *Definition used.* An import (or re-export) from a file of context A into a file of context B (A ≠ B) is a violation unless the target is in B's declared public API (its barrel `index.ts` or a declared `contracts` folder) or the importing file is in A's declared anti-corruption-layer folder. This follows the task wording. The stricter reading of [E] (the ACL still talks through B's published interface) is not enforced; a spec can get it by declaring no ACL folder.

### Composed layering (inside each context)

The DDD preset composes the hexagonal library's graph layering, applied per file regardless of context: `domain`, `application`, `infrastructure` (persistence and ACL adapters), `api` (inbound), `composition` (the composition root), with the allowed edges `application -> domain`, `infrastructure -> application, domain`, `api -> application, domain`, `composition -> all`. **FF-S01 `dependency-direction-graph`** flags an import against an allowed edge and **FF-S03 `layer-skip-graph`** an import between layers with no edge either way. Sources: [E] ch. 4 (layers depend downward only); [V] ch. 4 (hexagonal). The templates are the hexagonal ones, unchanged; their definitions are in `Docs/v1.3-hexagonal-notes.md` §3. Cross-context imports are judged by FF-DS02, not by the layering (a layer pair says nothing about which context a file belongs to).

## 2. Tiers, assigned before any measurement

Rule of thumb applied: a rule whose condition, as the tool evaluates it, is a precise structural fact about the declared model is **blocking**; heuristics, thresholds and naming proxies are **advisory**. Globs declared in the spec (a context root, an aggregate module, the repository files) count as declarations by the architect, not as heuristics: the condition over them is exact. Name matching *inside* the tool (guessing a role from a name) is a heuristic. The tier is assigned from the condition the tool evaluates, not from the literature rule, because the tier governs what may fail a verdict.

| Id | Rule | Tier | Reason |
|---|---|---|---|
| FF-DT01 | aggregate-boundary | blocking | An import edge into a declared inner-entity file from a file outside the declared aggregate module. Exact over the declarations. |
| FF-DT02 | repository-aggregate-root | blocking | An import edge from a declared repository file into a declared inner-entity file. Exact over the declarations; the stricter-than-[E] corner case (§1) is a definition question, not imprecision in evaluating it. |
| FF-DT03 | value-object-immutability | advisory | The literature rule is structural, but the extractor cannot see `readonly`, accessors or visibility, so the evaluated condition is a method-name proxy (`set[A-Z]…`). A naming proxy is advisory. It becomes blocking only if the extractor records member modifiers (§4). |
| FF-DT04 | domain-purity | blocking | An import edge from a domain-layer file to a package in a declared list. Exact. |
| FF-DT05 | domain-event-placement | blocking | An IMPLEMENTS/EXTENDS path to a declared event type, plus the file's layer. Exact over the declaration of the event type. |
| FF-DT06 | application-service-thin | advisory | A method-count threshold standing in for "holds business rules". Heuristic and threshold, advisory by construction (the task also pre-marks it advisory). |
| FF-DS01 | bounded-context-modules | blocking | A file path outside every declared root. Exact. |
| FF-DS02 | context-isolation | blocking | An import edge between two declared contexts whose target is not in a declared public-API glob and whose source is not in a declared ACL glob. Exact over the declarations. |
| FF-S01 | dependency-direction-graph | blocking | An import edge against a declared allowed edge. Exact. |
| FF-S03 | layer-skip-graph | blocking | An import edge with no declared allowed edge either way. Exact. |

Severity follows the tier: blocking rules are `critical`, FF-DT03 is `minor`, FF-DT06 is `advisory`.

The `tier` field exists in the spec and in the parsed `FitnessFunction` only for the `ddd` style (another style gets `SPEC_001`, and the field is dropped). It is not yet read by scoring: making only blocking rules able to fail a verdict and weighting advisory rules out of the AHS is FR-V6, a separate unit with its own scoring ADR. Until then the tier is carried data.

## 4. What is and is not expressible

Declared, not inferred. The extractor produces files, classes, interfaces, methods and IMPORTS / RE_EXPORTS / IMPLEMENTS / EXTENDS / CONTAINS / CALLS / CONSTRUCTOR_INJECTS edges. It does not know DDD roles, so the spec declares them (`architecture.ddd`): context roots, each context's public-API and ACL globs, the paths outside the contexts, each aggregate's module, root and inner-entity files, and the globs of value objects, repositories and application services, plus the names of the domain-event base types. Binding checks the declarations for consistency (a context root is `<source_root><one segment>/`; public-API, ACL and aggregate paths lie in their context; a root is not also an inner entity; no duplicate context) and refuses the spec otherwise.

Expressible:

- any number of top-level contexts, each with its own public API (barrel and/or contracts folder) and ACL;
- any number of aggregates per context, with zero or more inner entities;
- the hexagonal layer graph inside every context, by layer globs with a context wildcard (`src/*/domain/**`);
- a shared kernel and a composition root outside the contexts;
- event classes that reach the declared base type through a chain of `extends`/`implements`.

Not expressible, or only by proxy:

- **Value-object immutability** (FF-DT03). No `readonly`, accessor or visibility facts in the graph: `set x(v)` accessors, public mutable fields and assignments in ordinary methods are invisible; only setter-named methods are seen. Probe g01 records the miss. Blocking this rule needs member modifiers from the extractor (an extractor change, outside this unit).
- **"Raised in the domain"** (FR-V4 wording for events). The graph has no instantiation edge, so who creates an event is unknown; only where it is defined is checked.
- **Reference other aggregates by identity** ([V] ch. 10). Not implemented. It would be an import from one aggregate module to another aggregate's root file, but identity types usually sit in the referenced aggregate's module (as `CustomerId` does here), so it needs a declared "identity type" per aggregate first.
- **Business rules in application services** (FF-DT06). Only a method count; a long single method full of rules is not seen.
- **Through the public API, under barrel routing** (FF-DS02). The extractor resolves an import of a barrel to the file that declares the name, so the graph has no edge to `index.ts` (§6, E1). The rule therefore counts a file re-exported by a public-API file of the target context as published. A deep import of such a file, bypassing the barrel, is missed (probe g03).
- **Stricter ACL reading** ([E] ch. 14: the ACL still talks through the other context's published interface). Not enforced; the ACL may import anything of the other context, per the task wording.
- **Shared kernel direction.** Files outside the contexts are not checked by FF-DS02, so a shared kernel importing a context file is not reported.
- **Public-API files carry no layer** in the preset (`index.ts`, `contracts/`), so the layering rules do not see imports to or from them.
- **Repositories, value objects and services are found by path globs**; a repository outside the declared globs is not checked.
- **Persistence mapping** (FF-DT01). A repository implementation that rebuilds inner entities to rehydrate an aggregate imports them and is reported. That follows [E] literally; a team that accepts it adds `exclude_paths` to FF-DT01 for its persistence folder.

## 5. Reference project

`tests/fixtures/v1.3-reference/ddd/` (README there): 31 files, two contexts (`ordering`: aggregates `Order` with inner entity `OrderLine` and `Customer`; `billing`: aggregate `Invoice` with inner entity `InvoiceLine`), a shared kernel (`DomainEvent`, `Money`) and a composition root. Billing reads ordering only through an ACL (`billing/acl/OrderingAcl.ts`) that implements billing's port and imports ordering's public barrel. The clean variant compiles with `tsc` (strict, NodeNext).

Variants are overlays (`variants/<id>/overlay/` replaces or adds files, `variant.json` lists deletions): the simplest form that cannot drift from `clean/` silently, since only the changed files are stored, whole, without patch offsets. Ten `v..` variants each plant one violation of a different rule (all ten rules); `n01` is a negative control for the ACL exception. `expected-graph.json` gives the layer and context of every clean file (plus aggregate roles), sixteen key edges and three absent-edge rules. Every manifest was committed (commit `99aaabca`) before any template existed.

Three probes `g01`–`g03` were added **after** the first tool run, each to test a specific limit: g01 one predicted from the extractor's facts, g02 and g03 from the expected-graph mismatch E1. Their manifests are also written from the definitions, not from the tool, and they are kept apart (`g` prefix) from the a-priori variants.

## 6. Results against the manifests, and every mismatch

Evaluated by the TypeScript mirror of the queries over the real extractor and annotator output (no Neo4j, §8).

First run (templates as first written, commit order visible in history): clean, n01 and v01–v10 all equal their manifests; one expected-graph mismatch (E1). After E1 the probes were written and run.

| # | Where | Manifest says | Tool says | Classification | Action |
|---|---|---|---|---|---|
| E1 | expected-graph key edge `billing/acl/OrderingAcl.ts -> ordering/index.ts` | edge exists | edge goes to `ordering/contracts/OrderSummary.ts` | extractor semantics, by design (per-name barrel routing); a rule-definition question for FF-DS02, which was written in terms of the barrel | manifest kept; test asserts the difference |
| M1 | g02 (barrel re-exports `GetOrderSummary`; billing API imports the barrel) | no finding | FF-DS02 `billing/api/InvoiceController.ts -> ordering/application/GetOrderSummary.ts` (first version) | tool defect: false positive caused by E1 on the main public-API idiom | **fixed**: files re-exported by a public-API file of the target context count as published (`context-isolation` template, notes §4) |
| M2 | g03 (same barrel; billing API imports `GetOrderSummary.ts` directly) | FF-DS02 | no finding (after the M1 fix; the first version found it) | tool gap left by the M1 fix: the graph cannot tell a barrel import from a deep import of a re-exported file | kept; recorded in the test. Closing it needs the barrel hop in the graph (keep the specifier's resolved file on the edge) |
| M3 | g01 (`set value` accessor on `Quantity`) | FF-DT03 | no finding | tool gap (extractor: no accessor or modifier facts); predicted in §2 when FF-DT03 was made advisory | kept; recorded in the test |

The M1 fix trades a systematic false positive for a narrower false negative. The choice: a barrel is how TypeScript projects publish a context's API, so a blocking rule that fires on every barrel import of a published service would be unusable; a deep import of a file the context does publish is the milder breach. A Study 2 spec author may prefer the other side; the probes measure both.

Per rule on this reference set (12 a-priori cases plus 3 probes): every rule detects its planted case; FF-DT03 misses g01 and FF-DS02 misses g03; there is no false positive on clean, n01 or g02 after M1.

**What these numbers are not.** The rules, the reference project, the manifests and the templates were written in one session by one author (Claude). Agreement between them shows that the implementation does what the definitions say on cases its author thought of; it is not a validity estimate. Independent cases are the job of FR-V5 (runner over all reference projects), FR-V7 (labelled precision) and FR-V10 (pilot generations). The mirror is also not the Cypher: the queries have not run on Neo4j (§8).

## 9. Known gaps and next steps

1. Run `ddd-neo4j.test.ts` on a local Neo4j (the Cypher, not the mirror). The `EXISTS { … RE_EXPORTS*1.. … }` subquery and `UNWIND $aggregates` with map parameters are the parts most worth seeing run.
2. FR-V6 must make scoring read `tier`; until then advisory rules weigh in the score like any other.
3. Extractor member facts (field `readonly`, accessors, visibility), behind an option so v1.2E extraction stays byte-identical, would let FF-DT03 check the literature rule and become blocking (closes M3).
4. Keeping the barrel hop on an import edge (the resolved barrel file next to the routed target) would let FF-DS02 tell a barrel import from a deep import (closes M2 without reopening M1).
5. Not implemented: [V]'s "reference other aggregates by identity", "events raised in the domain", the stricter ACL reading, shared-kernel direction (§4).
6. FF-DT06's threshold (3) and FF-DT02's strict reading are uncalibrated definitions; FR-V7 labelling decides whether they stay.
7. The preset declares this reference project's contexts and aggregates. A real project replaces the `ddd:` block; a generator for it (for E7-style corpora) would be a registered rule like `Docs/e7-spec-rule.md`, written before use.
8. The FR-V5 runner can read these manifests unchanged (`variant.json` + `expected-findings.json` per variant).
