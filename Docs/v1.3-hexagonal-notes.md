# v1.3 hexagonal library: design notes

This branch adds a Hexagonal (ports and adapters) library behind a new style, `hexagonal`, and changes nothing for the other three.

## 2. Why the compiler needed a graph

The compiler only supports a total order. `dependency-direction` flags an import whose source layer index is lower than its target's; `no-layer-skip` allows only the step to the adjacent layer (`allowedTransitions` is built from list order). Hexagonal is not an order: an inbound and an outbound adapter are peers that must not import each other, and both may import the core. No list order says that (this is the expressiveness limit recorded in `Docs/AoC Specification and Fitness Functions — System Description and Findings.md`, F8). So the new style carries the graph the proposal described, `allowed_dependencies`, and its own templates read it. The Cypher uses the same device as `no-layer-skip` (`src.layer + '>' + tgt.layer IN $list`), so no new query feature is needed.

## 3. Hexagonal semantics

Layers (`presets/hexagonal.yaml`), with the kind each binds to:

| Layer | Kind | Role | Directories |
|---|---|---|---|
| `domain` | domain | the core: entities, value objects, domain services, outbound ports | `src/domain/**` |
| `application` | application | use cases and the ports they expose or need | `src/application/**` |
| `adapters-inbound` | presentation | controllers, CLI, consumers | `src/adapters/inbound/**` |
| `adapters-outbound` | infrastructure | persistence, external API clients, gateways | `src/adapters/outbound/**` |
| `config` | application (placeholder) | composition root | `src/config/**` |

Allowed dependencies (`from` may import `to`); everything else across layers is a violation:

```
application       -> domain
adapters-inbound  -> application, domain
adapters-outbound -> application, domain
config            -> domain, application, adapters-inbound, adapters-outbound
```

Two judgement calls are data in the preset, not code: adapters may import `domain` directly (to name entities and map them), and the core is `domain` alone with `application` allowed to depend on it. A stricter team deletes the `adapters-* -> domain` edges.

The composition root is found structurally: the layer no allowed edge points to that may import every other layer. It is dropped from the use-case layers when binding, so classes that wire concrete adapters by design do not count against dependency inversion. Its kind is `application` only because the kind resolver needs one of four values.

### Mapping onto the existing templates

| Requested semantics | Existing template | Hexagonal function (id) | Behaviour |
|---|---|---|---|
| dependency direction | `dependency-direction` (total order) | `dependency-direction-graph` (FF-S01) | import `A -> B` where `A>B` is not allowed **and** `B>A` is: an allowed edge run backwards (core importing an adapter, a use case importing an adapter) |
| layer skip | `no-layer-skip` (adjacent step only, `layered` only) | `layer-skip-graph` (FF-S03) | import between two layers with no allowed edge either way: the sideways step, mainly inbound adapter to outbound adapter |
| core depends on nothing outward | `no-domain-outward-dep` (Clean/NestJS only) | `core-isolation` (FF-S04) | any `domain` file importing any other layer |
| domain purity | `domain-purity` (every style) | reused unchanged (FF-P01) | forbidden packages in `domain`; `domain-state-purity` (FF-P06) also reused, binding domain and outbound adapters |
| repository pattern | `repository-pattern` (Clean/NestJS only; any interface) | `port-adapter-pattern` (FF-P03) | an outbound adapter class named `*Repository`, `*Repo`, `*Adapter` or `*Gateway` must implement an interface whose layer is `domain` or an application layer (port in the core or application, implementation in the adapter) |
| dependency inversion | `dependency-inversion` (Clean/NestJS only) | `port-dependency-inversion` (FF-P02) | same ratio of injected interfaces, threshold 0.85, over the use-case layers only |

The split between direction and skip is disjoint by construction (the reverse edge is allowed or it is not), so one import is never reported by both. `core-isolation` deliberately overlaps `dependency-direction-graph` when the core imports an adapter, as `no-domain-outward-dep` overlaps `dependency-direction` in Clean Architecture (MO-S01 expects both).

Dropped from the layered function set, because they presuppose the Clean layout or a total order: `use-case-isolation` (FF-P04, subsumed by the graph), `controller-no-entity` (FF-P05, hexagonal inbound adapters may name domain types), `domain-stability` (FF-C01). The generic functions (cycles, fan-out, instability, orphans, SOLID proxies, naming, the two neuronal functions) are kept with the layered preset's values. FF-CV01 and FF-CV04 stay disabled with the same ADR-016 b reason. The Clean-only templates stay disabled for the style (`not applicable to style hexagonal`) if a spec declares them.

## 4. What is and is not expressible

Expressible:

- any directed graph of allowed layer-to-layer imports, including peers that may not touch (adapter to adapter) and a root that sees everything;
- several application layers, one domain, one inbound and one outbound layer by kind;
- ports in the core or in the application layer, checked as interfaces by layer.

Not expressible (carried over from the spec format, not new):

- **Inbound versus outbound port.** A port is an interface in `domain` or `application`; the checker cannot tell a driving port (called by an inbound adapter) from a driven one (implemented by an outbound adapter). A controller that imports a driven port is not caught, and an outbound adapter that implements a driving port satisfies `port-adapter-pattern`.
- **Several adapters per direction as separate layers.** Binding takes the first `presentation` and the first `infrastructure` layer. Two outbound layers need both to be declared, but only the first is checked by `port-adapter-pattern` and `domain-state-purity`. `allowed_dependencies` itself handles any number of layers.
- **Per-module isolation** (two adapters of the same direction must not import each other when they share a layer): the graph works on layers, so files of one layer may import each other freely.
- **Adapter naming is a heuristic.** `port-adapter-pattern` selects classes by name (`Repository`, `Repo`, `Adapter`, `Gateway`); an outbound class named otherwise is not checked. `adapterRoles` is fixed, not yet a spec field.
- **Dependency inversion is a ratio proxy**, as in Clean: it counts constructor-injected interfaces, so a use case injecting a concrete sibling use case lowers it.
- **Composition root detection** is structural (§3); a root that cannot import every layer is treated as an ordinary application layer.

## 5. Frozen v1.2E instrument and the pre-registration

- `CYPHER_TEMPLATES`, the applicability table, the role exemptions and `TEMPLATE_REGISTRY` are not edited. `corpus/frozen-instrument.json` is exported from those, so it is unchanged (the existing frozen-instrument test passes).
- No registered artefact is modified: the three existing presets and `Docs/operator-catalogue.md` are byte-identical. `npx tsx scripts/run-experiment-cli.ts --check-prereg experiments/<each>/plan.json` prints `pre-registration v25 ok: 85 registered artefacts unchanged` for all twelve plans.
- `presets/hexagonal.yaml` matches the registered pattern `presets/*.yaml` (`PRESET_PATTERN`). The gate hashes the files listed in `corpus/prereg.json`, so a new file does not trip it, but **the next prereg bump will hash it**. Until then it is not a registered artefact and no registered plan may evaluate with it.
- The mutation catalogue is not extended. No operator targets the hexagonal templates, so SO4 recall for them is unmeasured. A hexagonal operator pair (the fixture's five defects are the natural sites) would be a new catalogue version, registered before use.

## 6. Tests and fixture

`tests/fixtures/hexagonal/clean` follows the graph. `violating` has five defects, each owned by one template:

| Defect | Template |
|---|---|
| `Order` (core) imports `SqlOrderGateway` (outbound adapter) | `dependency-direction-graph` and `core-isolation` |
| `PlaceOrderUseCase` imports and injects the concrete `InMemoryOrderRepository` | `dependency-direction-graph` and `port-dependency-inversion` |
| `OrderController` (inbound) imports `InMemoryOrderRepository` (outbound) | `layer-skip-graph` |
| `SqlOrderGateway` implements no port | `port-adapter-pattern` |

`hexagonal-fixture.test.ts` runs the real extractor, the real layer annotator and the real compiler over both variants, and asserts the clean one has no row and the violating one has exactly the six rows above. **Caveat:** no Neo4j in the unit run, so the compiled queries are evaluated by a TypeScript mirror of their predicates, not by Cypher. The Cypher text is pinned by string assertions only. Running the five queries against a database (a golden case in `tests/golden/`, `npm run test:golden`) was **not done** and is the first thing to do before trusting the queries on a real project.

`hexagonal-preset.test.ts` covers the preset, the registry entries, the frozen-set guard, graph binding and its refusals (missing graph, unknown layer, self edge, missing role), the `SPEC_001` for another style, and the Clean-only disablement.

## 7. Re-evaluating the two hexagonal E7 projects in a future registered round

`zhuravlevma__typescript-ddd-architecture` (commit `025ace5c`, 187 C2 files) and `raouf-b-dev__ecommerce-store-api` (`08b0760a`, 793 files) were admitted in the E7-x extension and evaluated under styles the mechanical rule picked: `nestjs` for the first (row 2), `clean-architecture` for the second (row 1); the extension mapped hexagonal candidates to Clean because no hexagonal library existed (ADR-027 item 4). Their layout was not re-inspected here (no clone in this run); that they are hexagonal comes from the task statement and the E7-x selection.

What a re-evaluation needs, none of which is done here and all of which must be registered before the first run:

1. **A new spec rule, not an edit.** `Docs/e7-spec-rule.md` and the generated specs in `corpus/specs/` are registered; leave them. Add a separate rule document (for example `Docs/e7-spec-rule-hexagonal.md`) and generator output in a new directory (for example `corpus/specs-hexagonal/`), with the pattern added to the registered artefacts in the bump. The rule needs a hexagonal row that is mechanical like the existing ones: segments for the core (`domain`, `core`), use cases (`application`, `use-cases`), inbound (`controllers`, `presentation`, `inbound`, `http`, `cli`), outbound (`infrastructure`, `persistence`, `adapters`, `outbound`, `repositories`) and composition (`config`, `main`, `*.module.ts`), and the default edge list of §3. Whether the style is chosen by the rule or fixed by the round is a design decision to make before seeing results.
2. **A decision on `adapters` and `dal`.** The old rule files `adapters` and `repositories` under infrastructure with no inbound/outbound distinction; hexagonal needs the split. The raouf project has `adapters`, `gateways` and `infrastructure` directories, so the mapping of each is where the risk of tuning sits; fix it by rule, as ADR-019 did.
3. **Prereg bump.** New version registering the rule, the generator change, the new specs, `presets/hexagonal.yaml` and these templates' source hash, plus a statement of which numbers are comparable (hexagonal specs change N for the same projects; the Clean and NestJS readings stay as registered and are not replaced).
4. **Instrument version.** Adding templates changes what the instrument computes for a new style. Either record it as instrument v3 for the hexagonal style only (v1 and v2 outputs for the old styles unchanged and re-checkable) or keep the hexagonal library under its own label in the report.
5. **Base type-check and site feasibility** for the two projects under the new specs, run once per the count-once constraint, with exclusion rather than repair on failure (§5 of the spec rule). Raouf is above the 300-file latency claim and near the 800-file limit (819 parsed).
6. **Golden run against Neo4j** for the five queries (the part this branch could not do), then the mutation side if hexagonal recall is to be reported (§5).
7. **Reporting.** State per project the style used in round 1 and in the hexagonal round, and that the hexagonal specs were written after the round-1 results were known (a post-hoc relation for the comparison, pre-registered for the new run only if steps 1 to 3 are committed first).
