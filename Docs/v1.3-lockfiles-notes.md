# v1.3 lock files: reproducible pnpm and yarn installs (notes)

Branch `v1.3-lockfiles`, from `v1.2e`. **Nothing registered changes.** No file in `REGISTERED_ARTEFACTS` (`scripts/lib/prereg.ts`) is edited, `corpus/corpus.json` still holds only `none` and `npm-ci-ignore-scripts` entries, `Docs/corpus-criteria.md` C5 still reads "npm only", and `--check-prereg` passes unchanged. This note records what the tooling now guarantees, what it does not, how a later registered round could use it, and what that would change for the E7-x candidate list.

Disclosure: the tooling was written after the 18 candidates in §3 were known (ADR-027 listed them as `no-package-lock`). It was run only on fixture projects (§1.4). **No candidate was cloned, installed or run.**

### 1.2 Install policies

`install` in a corpus entry gains three policies. Each carries `lockSha256` and an exact `packageManager` pin; the schema rejects a missing, floating (`pnpm@latest`, `pnpm@^9`) or extra field, and the TypeScript check `pinMatchesPolicy` rejects a pin that names the wrong manager (yarn 1.x for berry and the reverse).

| Policy | Lock file | Command (run as `npm exec --yes --package=<pin> -- …`) |
|---|---|---|
| `pnpm-frozen-ignore-scripts` | `pnpm-lock.yaml` | `pnpm install --frozen-lockfile --ignore-scripts` |
| `yarn-classic-frozen-ignore-scripts` | `yarn.lock` (`# yarn lockfile v1`) | `yarn install --frozen-lockfile --ignore-scripts --non-interactive` |
| `yarn-berry-immutable-ignore-scripts` | `yarn.lock` (`__metadata:`) | `yarn install --immutable --mode=skip-build`, package `@yarnpkg/cli-dist@<pin>` |

`npm-ci-ignore-scripts` and its code path are unchanged. Detection (`detectLockKind`) keeps the v1.2E precedence: a tracked `package-lock.json` always wins, whatever else is present (truthy-demo tracks a `yarn.lock` next to its `package-lock.json` and always used npm; ADR-027 notes npm once rewrote that `yarn.lock`). Without it, `pnpm-lock.yaml` together with `yarn.lock` is `ambiguous`, and a `yarn.lock` of neither format is `unknown-yarn-format`; neither is installed.

### 1.3 Pinned manager, not corepack

The host's pnpm or yarn is never used. The pin in the entry is the version that runs, through a pinned `npx` (`npm exec --package=pnpm@10.28.0 -- pnpm …`). Corepack was not chosen because it adds a second toolchain (corepack's own version, its signature keys, `COREPACK_*` behaviour) and defers to the project's `packageManager` field, which is exactly what a pin must not do. Instead:

- pnpm: `npm_config_manage_package_manager_versions=false`, so pnpm will not switch to the project's `packageManager` version.
- yarn: `YARN_IGNORE_PATH=1`, so a committed `yarnPath` release is not executed.
- berry: `YARN_NODE_LINKER=node-modules` (Plug'n'Play would leave no `node_modules` for the type-check; the install is refused if none exists), `YARN_ENABLE_SCRIPTS=false`, `YARN_ENABLE_IMMUTABLE_INSTALLS=true`, telemetry off.
- `CI=true` everywhere (no prompts).

`defaultPackageManager` proposes the pin from the lock format: pnpm `lockfileVersion` 5 → 7.33.7, 6 → 8.15.9, 9 → 10.28.0; yarn classic → 1.22.22; berry `__metadata.version` 6 → 3.8.7, 8 → 4.5.3. A format outside the table gives `unsupported-lock-format`: the candidate stays ineligible and nothing is installed with a guessed manager. The table is a starting point; the registered pin is whatever the corpus entry says, and the fetch fails closed if that manager cannot read the lock without rewriting it.

- Unit: detection, plans (flags and env per policy), pin rules, schema, the readers on pnpm v5/v6/v9, yarn 1 and berry samples, `c5v2Reason`, hash mismatch (no process started), non-zero exit, a lock rewritten by the install, a berry install without `node_modules`, `--no-install`.

## 2. Reproducibility guarantees

### 2.1 Guaranteed (checked by the code)

1. **Lock bytes.** `sha256(lock)` equals the registered `lockSha256` before the install (`INSTALL_LOCK_MISMATCH`) and again after it. A frozen install that rewrote the lock fails; nothing is patched.
2. **Resolution is frozen.** `--frozen-lockfile` / `--immutable` make the manager fail instead of re-resolving. The resolved tree is therefore the lock's tree. pnpm and berry locks carry per-package integrity hashes, which the manager verifies on download.
3. **Manager version.** Exact pin, fetched by version, not influenced by the host or by the project (§1.3).
4. **No lifecycle scripts of dependencies or of the project** (`--ignore-scripts`, `--mode=skip-build`, `YARN_ENABLE_SCRIPTS=false`), as with `npm ci --ignore-scripts`. The fixtures carry a `postinstall` that would write a marker; it never runs.
5. **Same layout class for the type-check.** pnpm's default isolated layout, yarn classic's flat layout and berry's `node-modules` linker all give a `node_modules` tree that `tsc` resolves; a berry install that produced none is refused.
6. **Tree hash unchanged in meaning.** `treeHash` still hashes source plus overlays and excludes every `node_modules`; the new policies add no tracked file to the clone.
7. **Copies resolve like the source** (§2.2).

### 2.2 pnpm's symlinked `node_modules` in copies

ADR-027 left this open ("checked against U5a `copyBase`, which copies links verbatim"). The finding: `copyBase`'s verbatim copy is already correct for pnpm's usual *relative* links that stay inside the base, because the virtual store `node_modules/.pnpm` is copied too, and `tsc` follows them. It breaks for two link shapes, both of which occur with a sub-path base in a pnpm workspace:

- an **absolute link into the base** keeps pointing at the original, so the copy reads (and a stub write could reach) the source;
- a **relative link leaving the base** (`apps/api/node_modules/x → ../../../node_modules/.pnpm/…`) resolves to a different place from the copy, usually to nothing.

`relinkPnpmCopy` rewrites the first to a relative link inside the copy and the second to an absolute link to the original target (read-only for the analysis, the same convention as the `monorepo-context` mirror). Dangling links are reported and left as they are (pnpm leaves skipped optional dependencies that way). It only runs for a base with `node_modules/.pnpm`, so **an npm or yarn base is copied exactly as in v1.2E**; a test asserts that an absolute link in an npm base is still copied verbatim. The step is idempotent.

### 2.3 Not guaranteed (limits, stated so that nobody assumes them)

- **Registry availability and content.** The lock fixes versions, not availability: a yanked or deleted tarball fails the install (fails closed). yarn classic locks carry only a SHA-1 fragment in `resolved` (older ones none), so classic content is verified more weakly than pnpm or berry. The npm path has the same dependence on the registry.
- **The manager itself is downloaded from the registry by version**, and its tarball integrity is not recorded by the tools. Mitigation for a registered round: record `npm view <pkg>@<pin> dist.integrity` in the environment record, or vendor the tarball.
- **Install-time code outside lifecycle scripts.** `--ignore-scripts` does not disable a project's `.pnpmfile.cjs` hooks (pnpm), or the plugins listed in `.yarnrc.yml` (berry), which are committed JavaScript and run during the install. `YARN_IGNORE_PATH` stops only `yarnPath`. The files are covered by the clone's tree hash, but they do execute. The npm path has no equivalent. A round that adopts C5 v2 should either exclude a candidate that has a `.pnpmfile.cjs` or a non-empty `plugins:` (a mechanical C5 v2 condition, §4) or accept and declare the risk.
- **Project configuration still applies.** `.npmrc` (registry, `node-linker`, `public-hoist-pattern`), `pnpm-workspace.yaml` and `.yarnrc.yml` are read by the manager. They are in the tree hash, so they are fixed, but they can differ from what the maintainers intended. Only the settings in §1.3 are overridden.
- **Platform-dependent optional dependencies.** A lock lists optional packages for all platforms; the installed subset depends on the host OS and CPU. The same holds for npm.
- **Node version.** The Node version of the host is not part of the policy (as for npm); it belongs in the environment record.
- **`file:` / git dependencies.** yarn classic writes a machine-specific cache path into the lock for a `file:` dependency of a `file:` dependency, so such a lock is not reproducible. The fixture avoids it (one level of `file:`); a real candidate with it fails at the lock hash on another machine or at `--frozen-lockfile`.
- **Preparation steps are untested on pnpm.** `prisma-generate` calls `node_modules/prisma/build/index.js` (works only if `prisma` is a direct dependency, whose top-level link exists in pnpm) and `monorepo-context` mirrors the root `node_modules` as absolute links (a link to a link in the pnpm layout). Neither was exercised.
- **Proxy / CA variables.** `fetch-corpus`'s child-environment allow-list (`PATH`, `HOME`, `TMPDIR`, `npm_config_cache`) is unchanged, so on a host behind a TLS-intercepting proxy `npm exec` fails with `SELF_SIGNED_CERT_IN_CHAIN`, exactly like `npm ci` would. Setting the standard `npm_config_cafile` / proxy variables requires extending that list, which this branch did not do for the frozen npm path.

## 4. How a future registered round could adopt C5 v2

Principle (BR-U5b-68, ADR-027 item 4): the decision is dated and registered **before** the candidate list is regenerated, and the criteria are not relaxed after the list is seen. The 18 names above are already known, so the next round must disclose that, as ADR-027 did for its own extension.

1. **Dated ADR.** One decision: C5 v2 = "a tracked root lock file that the tools install reproducibly: `package-lock.json` (unchanged, wins if present), else exactly one of `pnpm-lock.yaml` or `yarn.lock` of a supported format". Exclusion reasons: `no-lock-file` (was `no-package-lock`), `ambiguous-lock`, `unsupported-lock-format`. State the disclosure (§0), and decide explicitly:
   - whether a candidate with `.pnpmfile.cjs` or berry `plugins:` is excluded (§2.3);
   - what happens when the draw selects a candidate whose install fails: recommended, no replacement from outside the draw order; the failure is recorded and the next in the seeded order is taken, which must be written down before the draw. (The npm path never needed this because `npm ci` failures were rare; do not assume it for the new managers.)
2. **Criteria document.** Amend `Docs/corpus-criteria.md` (registered): C5 text and a machine-block field (for example `lockfiles: 2` in `extension`). That is a registered artefact, so it needs a prereg version bump (`register-prereg-cli --reason …`). `parseCriteria` must accept the field (`scripts/lib/corpus.ts`, unregistered).
3. **Wire the selector.** In `select-corpus.ts`, when `lockfiles >= 2`: `exclusionReason` uses `c5v2Reason(candidate)` instead of `hasPackageLock !== true`; `resolveAddedEntry` reads the lock with `detectLockKind` and fills `tsc: project` from `lockTypescriptVersion(kind, …)` (npm keeps `lockTypescriptVersion` of `select-corpus.ts`) and `install` from `installForLock(kind, lockText, sha256)`. The pieces exist and are tested; only the call sites and the `gh` fetch of `pnpm-lock.yaml` / `yarn.lock` at the recorded commit are missing. The candidate record already has `hasPnpmLock` / `hasYarnLock`, so `candidates.json` needs no new field to be selectable; `searchCandidates` needs none.
4. **Dry run before registration.** For each candidate that would enter `corpus/corpus.json`: `fetch-corpus --check`, then a full `fetch-corpus` and `prepare-bases` on the experiment host, including the type-check of a copy (`u5a-base-measure`). Register `corpus.json` only with entries whose install passed. Record the manager pins and the Node/npm versions in the environment record (`record-env`).
5. **Registry entries.** Add the new tool files (`scripts/lib/lockfiles.ts`, `lockfile-readers.ts`, `pnpm-links.ts`) and the fixtures' locks to `REGISTERED_ARTEFACTS` in the same bump, so the install behaviour of the round is hash-pinned like `generate-e7-specs.ts` is. Adding to the list is allowed by the registry comment ("a registration made before the addition stays valid").
6. **Host.** The experiment host needs `npm` and registry access on the fetch day (or a populated `npm_config_cache`), nothing else: no global pnpm/yarn, no corepack. Give the child environment the proxy/CA variables it needs (§2.3).
7. **Scope.** Adopt it for the new round only. The three round-1 and the six E7-x entries stay as registered with their `npm-ci-ignore-scripts` hashes; no existing hash changes.
