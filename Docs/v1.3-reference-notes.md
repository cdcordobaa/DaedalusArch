# v1.3 reference projects and validation runner (FR-V3, FR-V5 skeleton)

Branch `v1.3-reference`, cut from `origin/v1.3-hexagonal`. Draft. Unit U-C2 of the v1.3 cycle (`aidlc-docs/inception/requirements/v1.3-validity-requirements.md` on `v1.2e`). DDD is a separate unit and is not here.

**Status in one paragraph.** Four greenfield reference projects (Clean Architecture, Layered, NestJS, Hexagonal), 27 to 30 source files each, compile with the repository's TypeScript. Each has a hand-written expected graph (layer of every file, every internal import edge), 9 to 11 violating variants with one planted defect each, 3 near-misses and a clean variant: 56 variants, 40 of them violations. Every expected finding was written from the style definition and the rule's documented intent, and committed (`64a93475`) before any part of the tool was run on them. The FR-V5 runner (`scripts/v1.3/validate-reference.ts`) materialises every variant, can run the firewall on it, and compares the result with the manifest per style and per rule. **The live run against Neo4j has not been done** (no Neo4j in the cloud environment); it is the first thing to do on the local machine (§7). The only tool output seen so far is the extractor and layer annotator on the four clean projects: 100 % of edges and layers agree with the hand-written graphs (§6.2).

## 2. Design decisions

1. **Compiles without a network install.** Framework packages (`typeorm`, `express`, `@nestjs/common`, `@nestjs/core`) are vendored as ambient `declare module` blocks in `types/vendor.d.ts`, not through tsconfig `paths` as the `antipattern-nest` fixture on `v1.3-judge-antipatterns` does. Reason: with `paths` the specifier resolves to a project file, so the extractor would see a file edge instead of a `Package` node and FF-P01 could not fire for a harness reason. With ambient modules the import stays a bare specifier. Checked: the extractor turns `typeorm`, `express` and `@nestjs/common` in the variants into `Package` targets (§6.2). `*.d.ts` files are excluded by the extractor's defaults, so `types/` adds no File node.
2. **The spec is the preset, unchanged.** Each project uses its preset's default directories, so `spec.yaml` is a verbatim copy with a header. A preset change requires re-copying and re-checking the layers and manifests.
3. **Compared rules.** `reference.json` lists the rules the runner scores (`scopeRules`): the structural and pattern rules that apply to the style (template applicability, `src/fitness-compiler/template-applicability.ts`, and the hexagonal library). FR-V6 tiers do not exist yet, so a rule is a *blocking candidate* when its severity is `critical`; the majors FF-S04, FF-P04 and FF-P05 are compared but pooled separately. Coupling metrics, SOLID proxies, naming rules and the neuronal functions are out of scope: they are threshold proxies or conventions, and FR-V6 makes them advisory. The runner lists their rows as *unscored*.
4. **One defect, possibly several findings.** Each violating variant plants exactly one defect, but a defect can legitimately violate several rules (a domain field holding an infrastructure object is an outward import, FF-S01 and FF-S04, and held state, FF-P06). The manifest lists every rule the defect breaks, each with its reason; `plants` names the rule the variant was built for.
5. **Finding keys.** Rule id + project-relative file, plus the target when both sides carry one (dependency rules: the imported file; FF-P01: the package; FF-P06: the held class's file). For FF-S02 the file is the lexicographically smallest path of the cycle and the target the next file, as the template's canonical rotation returns it; Neo4j compares strings by code point (note `src/presentation/Router.ts` < `src/presentation/http/...` because `R` < `h`).
6. **Near-misses** are code that looks suspicious but is architecturally fine under the style. They expect no finding and test precision.
7. **Type-only imports** are ordinary edges in the expected graph (one edge per importing and imported file, whatever the import syntax). The extractor's `isTypeOnly` flag is not part of the ground truth.

## 3. Sources and style definitions

| Style | Project | Canonical source |
|---|---|---|
| Clean Architecture | library loans (books, members, loans, fines), 29 files | Martin, R. C. (2017). *Clean Architecture*. Prentice Hall: ch. 22 (Dependency Rule), ch. 11 (DIP), ch. 14 (ADP), ch. 26 (Main) |
| Layered | orders (catalogue, customers, orders, discounts), 27 files | Fowler, M. (2002). *Patterns of Enterprise Application Architecture*. Addison-Wesley: ch. 1 (Layering), Service Layer, Table Data Gateway, Money; closed layering after Buschmann et al. (1996), POSA 1, "Layers" |
| NestJS | workshop registrations (three feature modules plus `src/domain`), 29 files | NestJS documentation, docs.nestjs.com: Controllers, Providers, Modules, Exception filters, Guards; Custom providers (injection tokens, `useClass`). Layer order from `presets/nestjs.yaml` |
| Hexagonal | hotel room booking (driving and driven ports), 30 files | Cockburn, A. (2005). *Hexagonal architecture* (Ports and Adapters). Allowed-dependency graph from `presets/hexagonal.yaml` and `Docs/v1.3-hexagonal-notes.md` |

Each `reference.json` states the style definition the manifests were written from, in 6 or 7 sentences. Points worth an audit:

- **Clean**: the composition root (`infrastructure/main.ts`) is in the outer circle, per Martin's Main component. Controllers live in `infrastructure` because the preset has no presentation layer.
- **Layered**: persistence returns plain records and the business layer maps them (Table Data Gateway), so persistence never imports a business type. The business layer builds its own lower layer (`business/ServiceFactory.ts`), so presentation never names persistence, as closed layering requires. `src/main.ts` is outside every layer.
- **NestJS**: repositories are bound through injection tokens to interfaces in `src/domain`. That is a documented NestJS option (Custom providers), not the docs' default of injecting provider classes. It was chosen so that the preset's DIP rule (FF-P02, critical) and use-case-isolation (FF-P04) can be satisfied by idiomatic code; §5 records what this hides. `src/main.ts` is outside every layer.
- **Hexagonal**: driving ports in `application/ports/in`, driven ports in `application/ports/out`; inbound adapters depend on driving-port interfaces; the composition root is `config/container.ts`.

## 5. Written before any tool run: precedence rule, rule-definition questions and predicted defects

**Precedence.** When the style definition and a rule's documented intent disagree on a case, the manifest follows the style definition. The disagreement is listed here as a rule-definition question (RDQ), so a firing on it is read as a question about the rule, not as a fault in the project. Everything in this section was written before the tool ran, from reading the presets, `src/fitness-compiler/cypher-templates.ts` and `src/fitness-compiler/hexagonal-templates.ts`. The predictions are not part of any manifest, and no manifest will be changed to match them.

| Id | Style, variants | Question |
|---|---|---|
| RDQ-1 | Layered, every variant | FF-P06 binds business to the domain kind and persistence to infrastructure. `OrderService` and `CatalogService` take gateways through their constructors (`CONSTRUCTOR_INJECTS` business to persistence), the normal closed-layer dependency. **Predicted to fire on the clean variant and on every other variant**: at least 4 rows (OrderService x3, CatalogService x1, possibly once more per edge type if the constructor parameter properties also yield FLOWS_TO), and one more on `n02` for `SalesReportService`. The manifests expect none. Should FF-P06 be disabled for `layered`, or should its binding exclude the adjacent lower layer? |
| RDQ-2 | NestJS `v07` | FF-P04 `use-case-isolation` flags a service that injects a non-domain, non-application dependency. The nestjs preset places infrastructure *below* application and calls service-to-repository the normal flow, so a service that injects a repository class is not a layering defect in this style. `v07`'s defect is DIP (concrete instead of port), so FF-P04 is **not** expected there. The two rules disagree about the NestJS layer model. |
| RDQ-3 | NestJS `n03` | A service injecting a sibling service is standard NestJS (docs, Providers). FF-P02's literal intent ("inject interfaces, not concrete classes") covers it; DIP's purpose (policy should not depend on detail) does not, since the dependency is on the same level. **FF-P02 is predicted to fire** (3 of 4 constructor dependencies are interfaces, 0.75 < 0.85). Should FF-P02 count only dependencies outside the class's own layer? |

## 6. Anti-circularity protocol and what has been run

### 6.1 Protocol

1. Projects, patches, expected graphs and manifests were written first and committed together (`64a93475`), before the runner existed and before any part of the tool was run on them.
2. The expected graph was checked only against an independent regex scan of the `import ... from` statements, never against the extractor (the test does the same, §8).
3. After the commit, the tool may run. A disagreement is never fixed by editing a manifest or the expected graph. It is recorded in §6.2 or §6.3 as a tool-defect candidate (TDC) or a rule-definition question (RDQ), with the variant and the rows. A manifest may change only for a fault in the manifest itself (a typo or a wrong path), found by reading the code, recorded here with its reason, in a separate commit.

```bash
# live, on the local machine (capped Neo4j up, NFR-V2); one style at a time is fine
NEO4J_URI=bolt://localhost:7687 NEO4J_PASSWORD=... \
  npx tsx scripts/v1.3/validate-reference.ts --out results/v1.3-reference [--style hexagonal]

# recompute the report from saved raw outputs, without Neo4j
npx tsx scripts/v1.3/validate-reference.ts --from-raw results/v1.3-reference/raw --out results/v1.3-reference/replay
```

The live mode runs `bin/firewall.ts evaluate --symbolic-only --format json` through the existing CLI evaluator (`cliEvaluate` in `scripts/lib/freeze-gate-main.ts`, explicit child environment, only the Neo4j triple). It writes one raw file per variant (`raw/<style>/<variant>.json`), `report.json` and `report.md`. Without `NEO4J_URI` and `NEO4J_PASSWORD` it refuses with exit 2.

**Metrics** (per rule, pooled per style over blocking candidates and over all compared rules):

- TP: an expected finding matched by a tool row. FN: an expected finding with no row. FP: a tool row of a compared rule that matches no expected finding.
- `recall = TP / (TP + FN)`, `precision = TP / (TP + FP)`.
- `precisionDistinct` counts a false-positive row that also appears on the clean variant only once (on the clean variant), so one baseline false positive does not count 14 times.
- `plantedDetected`: violation variants whose planted rule was matched. `silentNonViolations`: clean and near-miss variants with no unexpected row.
- Exit target (requirements, link 3): blocking recall per style ≥ 0.90; blocking precision (correct) ≥ 0.90.

Every mismatch is listed with the manifest's reason (missed) or with `also on the clean variant` (unexpected).

## 9. Limits

- **The same AI wrote the projects, the patches and the manifests.** The anti-circularity protocol keeps the tool's output out of the manifests, but not the author's own blind spots: a wrong reading of a style would be consistent across code and manifest. **The author must audit them** (§10) before the numbers are used as evidence.
- **Small, regular code.** 27 to 30 files, relative imports only, in-memory adapters, no path aliases, no dynamic imports, one barrel (Layered `n03`). Graph fidelity here is a lower bound on difficulty; FR-V2 on the E1 cells and the pilot projects is the real test.
- **One project per style**, so per-style recall rests on 9 to 11 violating variants. Per-rule cells are 1 to 5 findings; report them as counts, not rates.
- **Vendored typings** cover only what the variants use. The NestJS project is not run; decorators and DI wiring are typed but not executed.
- **NestJS uses injection tokens** to fit the preset's DIP rule (§3). A docs-default NestJS app (provider classes injected directly) would show RDQ-3 throughout.
- **Blocking is provisional**: severity `critical` stands in for FR-V6's `tier: blocking`. When the tiers land, re-derive `blockingCandidate` in each `reference.json` from them.
- **No live run, no Neo4j**: no finding-level number exists yet. The hexagonal Cypher has not been run against Neo4j either (`Docs/v1.3-hexagonal-notes.md` §6), so the Hexagonal live run is also that library's first golden-style check.
- **Frozen instrument untouched**: only new files under `tests/fixtures/v1.3-reference/`, `scripts/v1.3/`, `tests/unit/scripts/v1.3/` and this document. No preset, template, registered artefact or v1.2E file is modified.

## 10. Audit checklist for the author

1. For each style, read `reference.json` → `styleDefinition` against the cited source. Disagree with a sentence → the affected manifests change, in a commit that says so, before the first live run.
2. For each violating variant, read `variant.patch` and confirm it plants exactly one defect and that every expected finding is right (rule, file, target, reason). The tables in §4 are generated from the manifests.
3. For each near-miss, confirm the code is architecturally fine under the style.
4. Decide RDQ-1 to RDQ-3 (or defer them to the v1.3 scoring ADR), without editing the manifests to match the tool.
5. Spot-check `expected-graph.json` for one style by hand (the test checks it against a regex scan, which shares the author's reading of the import syntax but not the extractor's).
