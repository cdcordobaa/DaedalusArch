**Integration — the judge process**

## Question 1
How is the judge child process isolated from the author's own Claude Code setup?

Context: the design flags (`component-methods.md:1303-1306`) do not stop user settings, hooks, plugins, MCP servers, slash commands or the user `CLAUDE.md` from loading. They vary by machine and can inject text into the judge's context, which breaks reproducibility and the "judge under the author's subscription, nothing else" provenance claim. A `stream-json` init event lists tools, MCP servers, model and API-key source, but not `CLAUDE.md` content or hook-injected text, so a flag-only setup has no detector for those two leaks.

A) (Recommended) **Dedicated judge config dir as the primary isolation, with all flags on top.** `CLAUDE_CONFIG_DIR = <judgeConfigDir>` (default `~/.firewall/judge-claude-config`, outside every repo), logged in once with the author's subscription and holding no `CLAUDE.md`, hooks, plugins, agents, commands, output styles or settings beyond what the login writes; `CLAUDE_CONFIG_DIR` is added to the env allow-list. Argv: `-p`, `--model`, `--effort` (always explicit), `--output-format json`, `--json-schema <verdict schema>`, `--system-prompt <fixed judge persona>`, `--setting-sources project` with `cwd = neutralCwd` (a fresh empty temp directory per run, whose ancestors are checked to hold no `CLAUDE.md`), `--strict-mcp-config`, `--disable-slash-commands`, `--no-session-persistence`, `--tools ""` unless the Part 2 probe shows it disables structured output, no `--fallback-model`. `--exclude-dynamic-system-prompt-sections` is **not** passed (inert with `--system-prompt`, CLI 2.1.293 help). Env allow-list `PATH, HOME, USER, LOGNAME, TMPDIR, LANG, LC_ALL, __CF_USER_TEXT_ENCODING, CLAUDE_CONFIG_DIR` only (no `CLAUDECODE`, no other `CLAUDE_CODE_*`, no `ANTHROPIC_*`). Checks: (i) before each run, a listing of `judgeConfigDir` against a frozen entry allow-list (the login's own files, fixed by the Part 2 probe); any other entry fails closed; (ii) once per run, a `stream-json --verbose` init probe whose pass condition is frozen after the Part 2 probe: `tools ⊆ {structured-output tool}`, `mcp_servers = []`, model = requested under the Question 10 rule, `apiKeySource = none`; (iii) a canary test (Part 2 and Build and Test): a throwaway config dir holding a canary user `CLAUDE.md` and a canary `UserPromptSubmit` hook, plus a canary `CLAUDE.md` in an ancestor of a test cwd, each instructing the model to emit a token; the token must not appear in judge output under the judge argv and a clean dir. The probe result and a hash of the config-dir listing are stored in run provenance. If the Part 2 probe shows the subscription login cannot be used from a dedicated config dir, U4 code generation stops and the author is asked (conditional escalation, Section 9). **(design amendment: flag list, env allow-list, provenance fields)**
B) Design flags plus `--setting-sources project`, neutral cwd, MCP/slash-command flags and a `stream-json` probe, with no dedicated config dir (the previous answer; its `CLAUDE.md`/hook check has no detector).
C) Design flags only.
D) `--bare` plus `CLAUDE_CODE_OAUTH_TOKEN` in the child env.
E) Other (please describe after [Answer]: tag below)

[Answer]: A — criterion (affects results: judge context must be identical across machines and runs, and provenance must be defensible; isolation then holds by construction and is checkable by a directory listing plus the canary). Changed from the previous "flags first, config dir as fallback", because the flags-only leak check could not detect `CLAUDE.md` or hook text. D rejected (puts a token in the environment, and `--bare` skips the keychain).

## Question 2
In what format does the judge return its verdict, and how strictly is it parsed?

Context: a parse failure makes a run invalid; too few valid runs makes a unit invalid (Question 5). Silent defaults (confidence 0.5, file `'unknown'`) produce unmatchable violations and fake confidence.

A) (Recommended) CLI provider passes `--json-schema <verdict schema>`; Gemini uses its `responseSchema`; the text `result` is parsed as fallback when the probe shows no structured field. With every option: a missing confidence makes the run invalid (`MISSING_CONFIDENCE`, no 0.5 default). **Verdict consistency**: violations are counted only from runs with `pass = false`; a `pass = true` run's violations are ignored and counted in a `VERDICT_INCONSISTENT` warning; a `pass = false` run with no violations is a valid fail with no located violation. **Path normalisation** before the membership check: convert `\` to `/`, strip a leading `./`, resolve against `projectRoot`, reject anything outside it, express as root-relative POSIX; a violation whose normalised `filePath` is not one of the unit's files is dropped and counted in a warning (no `'unknown'`; basenames are not guessed). Both rules frozen in `business-rules.md`.
B) JSON requested in the prompt only, parsed by `parseVerdict`.
C) B plus one re-ask on parse failure.
D) Other (please describe after [Answer]: tag below)

[Answer]: A — criterion (affects results: parse failures and inconsistent verdicts turn into invalid runs or spurious violations, and unnormalised paths become unmatchable FP/FN in SO4); envelope location fixed by the Part 2 probe.

**Data flow — cassettes**

## Question 3
What is the cassette key, and what do `record` and `replay` mean?

Context: the design key `functionId/unitId/runIndex` (`component-methods.md:1216-1219`) collides across fixtures that share paths (`src/domain/x.ts`), and the design is internally inconsistent: `CassetteLLMProvider` takes a per-call `{functionId, unitId}` in its constructor (`:1226`) while the factory wraps the provider once per run (`:1257`). A key over the prompt body alone misses everything sent outside it (persona, schema, effort, flags); a per-hash call ordinal shifts when a retry occurs. Subscription budget is the highest schedule risk (Section 8).

A) (Recommended) **Key** = `sha256(canonicalJSON(request))` + `repetition` + `runIndex`, where `request = {prompt, systemPrompt, schema, provider, model, effort, maxTokens, argvFlags}` (`argvFlags` = the sorted flag names and non-content values of the argv, so a flag-set change is a miss). `runIndex` is passed explicitly through the existing port `evaluate(prompt, options, runIndex?)` (`component-methods.md:1227`); no call ordinal. `functionId`, `unitId`, project id and prompt hash are stored as entry metadata, not key parts (the constructor context is removed). **Retries** happen inside the decorator under the same key; the entry stores the attempt count. **Recorded outcomes**: every completed call sequence is recorded with its final outcome, valid or invalid (`PARSE_FAILURE`, `MISSING_CONFIDENCE`, `MODEL_MISMATCH`, `TIMEOUT` after retry, `BAD_ENVELOPE` after retry, `LLM_CLI_EXIT` after retry, not a usage-limit or auth exit), as the design's `parsedVerdict: null` entries already allow (`:1214`). Calls stopped by a usage limit, an auth failure or `LLM_CLI_NOT_FOUND` are **not** recorded and stay unissued (Questions 5, 15). **`record`** = reuse any recorded final outcome, valid or invalid (an invalid outcome is never re-called, so there is no selection on output); call on a miss and write. **`replay`** = answer only from cassettes; a miss is `CASSETTE_MISS`. **Scrubbing determinism**: `parsedVerdict` is computed at record time from the unscrubbed response and then passed through the same deterministic `scrubDeep` as the response; replay uses the stored `parsedVerdict` and never re-parses. The request hash is taken before scrubbing and stored. `repetition` (CLI `--judge-repetition`, default 0) forces fresh samples for the reliability sub-study. `cliVersion` is stored; a mismatch is a warning, not a miss. **One cassette dir per experiment is mandatory**, shared by every baseline and all its seeded variants, so identical requests reuse the baseline judgement; this is declared as caching in the method chapter. **(design amendment: `cassetteKey`, `CassetteEntry.key/outcome/attempts`, constructor context removed, `--judge-repetition`)**
B) Design key, hit requires equal prompt hash, provider and model.
C) B with one cassette directory per project.
D) Other (please describe after [Answer]: tag below)

[Answer]: A — criterion (affects results: makes the E1/E7/golden call volume feasible inside subscription windows, lets interrupted runs resume without misaligned hits, never reuses a judgement made under a different persona, schema or effort, reproduces invalid runs on replay, and removes judge noise on unchanged units from differential scoring, AD-7). ## Question 4
How do unit verdicts combine into the function verdict, and what does the function contribute to its dimension's AVR?

Context: the scorer counts functions (Section 3); ADR-007 defines AVR as violated functions over functions in the dimension, and the current code already weights a failing neuronal function by `getConfidenceWeight` (unstable → 0.2). With one neural function per dimension, any-fail saturates on real projects as the unit count grows. The same saturation reappears through the weight if `flaggedUnstable` is set when any one unit is unstable, or if passing units' confidence enters the weight of a fail. FR-33 requires "a stated rule"; FR-32 keeps the function as the denominator unit. Per-file seeded faults reach SO4 through the violations list (Question 8), whatever the function verdict.

A) (Recommended) Function verdict `fail` when strictly more than half of the valid units fail; otherwise `warning` when at least one valid unit fails or is `warning`; otherwise `pass`. **Confidence and instability are taken from the units that carry the verdict**: for `fail`, confidence = mean over the failing units of each unit's mean confidence over its runs that voted fail, and `flaggedUnstable` = strictly more than half of the failing units are unstable; for `pass`, the same over passing units; for `warning`, over all valid units (display only). A unit is unstable when the population standard deviation of confidence over its valid runs exceeds `unstableThreshold = 0.15`. AVR contribution unchanged (ADR-007, `getConfidenceWeight` on `fail` only, thresholds 0.85/0.60, weights 1.0/0.7/0.3, unstable 0.2), so no U3 change beyond FR-32; all of these values are frozen in Section 5.2. A unit test shows the weight of a `fail` is unchanged when passing units are added. Violations of every failing unit are listed whatever the function verdict. The fail share (`failingUnits / validUnits`) is derivable from the persisted `unitResults` and reported by U5b as a secondary SO3/SO5 measure, not as AVR. The 0.5 threshold is frozen before the first run; Build and Test reports any-fail and share variants as a sensitivity check (threats to validity), recomputed offline by FR-26 from persisted unit results (Section 6).
B) Confidence-weighted share of failing units as the function's AVR contribution (amends ADR-007's AVR definition and U3's `computeAVR`).
C) Any-fail; contribution as today.
D) Other (please describe after [Answer]: tag below)

[Answer]: A — criterion (affects results: the neural AVR, verdict and weight must not saturate with the unit cap or depend on the number of passing units, and must stay comparable with symbolic AVR as ADR-007 defines it; seeded per-file faults are still measured through violations). B is not taken under the standing approval because it would amend ADR-007; it remains a sensitivity variant.

## Question 5

A) (Recommended) Per unit: majority of valid runs (3 by default); a 1-1 split on 2 valid runs gives `warning`; fewer than 2 valid runs makes the unit invalid (counted, `INSUFFICIENT_VALID_RUNS` warning). **Run completeness**: a run is `complete` only when every selected (unit, run) call has a final outcome (Question 3). The function is a `FunctionFailure` only when fewer than half of the selected units are valid. Each result records `unitsSelected`, `unitsCapped` and `unitsInvalidByCause` (bundled C10 patch, Section 1.3).
B) Any invalid unit makes the whole function a `FunctionFailure`.
C) `FunctionFailure` only when no unit is valid.
D) Other (please describe after [Answer]: tag below)

[Answer]: A — criterion (affects results: under FR-36 a single flaky call must not reject a whole project run, a mostly-failed judgement must not be reported as a score, and a run cut off by quota must never be scored on a different unit set than its baseline, AD-7).

### 5.3 Defaults and amendments

- **Prompt determinism**: prompts contain root-relative paths only, sorted excerpt nodes and edges, no timestamps, no absolute `projectRoot`; the request hash is taken before cassette scrubbing and stored separately.
- **Router**: in symbolic-only mode `filterByMode` drops the neural half of hybrid pairs explicitly, and the router never dereferences an absent provider (latent bug, `router.ts:101`).
- **Provenance**: `judgeProvenanceOf` built once per run; in `record` mode `cliVersion` comes from `claude --version` and the probe result and config-dir listing hash are added; in `replay` mode all provenance is read from cassettes and the run manifest and nothing is spawned (Question 16).
- **Reliability sub-study**: within-run and between-repetition agreement is computed by U5b from committed cassettes, not from the `icc` field (left 0 and documented).
- **Design amendments for the clarifications file**: C14 flag list, env allow-list and provenance fields (Q1); canonical-request `cassetteKey`, `CassetteEntry.key/outcome/attempts`, constructor context removed, recorded invalid outcomes (Q3); new CLI option `--judge-repetition` (Q3, added to C9 options at `component-methods.md:1494-1496`); neural id via `computeViolationId` (Q8); `INTENT_VIOLATION` comment (Q11); `NeuronalFunctionResult` coverage and invalidity fields in the bundled C10 patch (Q5, Q6, Q7, Q17); `ClaudeCliEnvelope` gains the model-usage field fixed by the probe (Q10); FR-33 "stated rule" named as Q4 A (majority of valid units, `warning` below majority) with the Q6/Q17 selection rule.
