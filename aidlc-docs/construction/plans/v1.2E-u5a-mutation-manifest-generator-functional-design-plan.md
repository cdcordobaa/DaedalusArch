## Question 1
**Type-check gate for mutants.** FR-24 says "the mutated project must type-check". Three of five corpus bases do not type-check today under the repo tsc (Fact 3); none was measured with its own tsc.

A) (Recommended) Every base is **prepared to zero errors** before seeding. The tsc binary and version are **pinned per base** in the U5b `CorpusEntry` (`tscPath`, `tscVersion`; fixtures use the repo's pinned tsc) and never chosen at runtime. The preparation is the recorded `CorpusEntry` overlays and install policy (dev-nest `npm-ci-ignore-scripts`, realworld `src/config.ts` overlay from `config.ts.example`). **Freeze gate**: before the catalogue is frozen, each prepared base is type-checked with its pinned tsc and the error counts are committed under `Docs/DiagnosticRuns/u5a-base-typecheck.*` (as ADR-016 h does for U2). A base that cannot reach zero is declared excluded from seeding before any seed is placed. The mutant gate is then absolute (zero errors); as a guard the error set (code, file, message, after the `lineShifts` remap) is also compared with the base. Each row records the tsc version, base and mutant error counts.
B) "No new errors relative to the base" on unprepared bases.
C) Absolute gate on unprepared bases (excludes three of five corpus projects).
D) Other (please describe after [Answer]: tag below)

[Answer]: A (revised) (criterion: meets "must type-check" literally on every seeded base; pinning and measuring the tsc per base before freezing removes a per-project runtime choice and makes the base set fixed before seeding; B would reword FR-24 and let base errors mask a broken mutant, C loses three recall sites, risk R1)

## Question 2
**Framework packages for framework-leak mutants** (Facts 1, 2).

A) (Recommended) Stub packages (`node_modules/<pkg>/package.json` + `index.d.ts` declaring only the imported symbols) are written as part of **base preparation**, i.e. into both the baseline copy and the mutant copy, outside `src/`, **only when module resolution of that specifier from the importing file fails** (TypeScript module resolution with the base's tsconfig). A stub never overwrites or shadows an existing package directory anywhere on the resolution path (real `@nestjs/*`, `@prisma/*` in ghostfolio's monorepo-root `node_modules` or dev-nest after `npm ci` stay untouched; unit test). Each stub's resolved location is recorded in the row (`provisionedStubs[]: { specifier, path }`) and its files are part of `baseTreeSha`. The extractor never parses them; U2's installed-package check (ADR-015 item 7) classifies them as Package in both reports, so the differential scorer sees no spurious import-classification change. variant-b/c receive the same stubs for their existing imports.
B) Ambient `declare module` file under `src/` (becomes a File node; can trigger FF-C04).
C) Drop the framework-leak operator.
D) Stubs in the mutant copy only.
E) Other (please describe after [Answer]: tag below)

[Answer]: A (revised) (criterion: framework leakage is the most relevant LLM failure for SO5 and FF-P01 needs a seed; stubbing only on failed resolution keeps real typings on installed bases so the gate tests real code; B changes the measured graph, D creates baseline/seed diffs that are not the seed)

## Question 4
**How the 80–120 instances are reached, and data splits.** Fact 8: under their own specs, four of five corpus projects have no domain file, so the four domain-site operators (MO-S01, MO-P01, MO-DF01, MO-X01) have no site there; the plan's original "5 × 8 × 2 = 80" is not reachable (about 40 at most), and the generated-project top-up depends on running E1, which R §5 puts out of this cycle (E2).

A) (Recommended) Held-out split = corpus; dev split = fixtures (the correct-reference applications serve the FR-24 acceptance and are never pooled with corpus figures); every row carries `split: 'dev' | 'held-out' | 'probe'`. The instance count is **decided from a site-feasibility table before any seed is placed and before any detector runs on a seeded copy**:
   1. **Domain mapping route (provisional, Escalation E5)**: the corpus specs gain one uniform, scripted domain-layer rule (`**/domain/**` and `**/*.entity.ts` added to the domain layer), committed as its own change under ADR-015 item 4 and before the FR-18 re-baseline, so it is one attributable cause for every corpus figure. No per-project tuning.
   2. **Site-feasibility table**: `findSites` + preconditions on every prepared base for every golden operator (no RNG, no detector), committed under `Docs/DiagnosticRuns/u5a-site-feasibility.*`. Measured upper bounds after route 1 (Fact 8): domain operators on 4 projects (dev-nest has no spec and no domain files), non-domain operators on 4–5.
   3. **Pre-registered `sitesPerOperator` rule**: k = the smallest value in {2, 3} for which the table's feasible total reaches 80; if k = 3 reaches more than 120, a seeded subsample (derived seed, Question 10) cuts to 120. k is written into `Docs/operator-catalogue.md` and dated at the freeze. Results are reported clustered by project.
   4. If k = 3 does not reach 80, no further lever is used: the shortfall goes to the author under E5 (route b: generated bases this cycle, tied to E2; route c: restate the SO4 n). `sitesPerOperator` never absorbs a shortfall silently.
   Generated E1 projects (`baseKind: generated`) remain a top-up only if E2 brings E1 into this cycle.
B) Pool fixtures and corpus.
C) Generated projects only.
D) Other (please describe after [Answer]: tag below)

[Answer]: A (revised) (criterion: the original arithmetic could not produce the SO4 floor; a uniform pre-registered domain mapping plus a feasibility-driven, pre-dated k is the only route that can reach 80 within this cycle without results-dependent choices; ADR-015 item 1 keeps fixtures as the dev set, so B breaks a pre-registered rule; C ties SO4 to the SO5 schedule. Route 1 changes held-out specs beyond ADR-015 item 4, so it is escalated as E5 with this as the provisional default)

## Question 5
**Shape of `expected`.** Function ids depend on the style (BR-U1-18: FF-S03 runs for `layered` only; several pattern templates are disabled for `layered`), the reported file often is not the edited file (cycle canonicalisation; FR-12 `target`/`discriminator`), and some side effects depend on the site, not the operator (Fact 9).

A) (Recommended) **(design amendment)** The operator declares `expectedTemplates` (template names) with, per template, an expected location rule (`filePath`, optional `target`, optional `discriminator`, and a line rule) and optional `expectedEdges` (type, source, target). `applyMutation` resolves `expected.functionIds` from the project's spec via `parseSpec` and the applicability table, recording disabled matches as `expected.disabledFunctionIds` with the reason; the spec used is recorded (`specPath`, `specSha256`, Question 9). `expected.collateral` lists side-effect firings with their keys, in two parts: **operator collateral** declared in the catalogue, and **site collateral** computed per site from the base import graph with ts-morph, never from the detector (Question 10): a new import cycle → FF-S02 with its canonical key; a domain file gaining its first non-domain neighbour → `domain-stability` row; a created layered file without a test sibling → `test-file-pairing` row on that file. Project-wide metric rows (`abstraction-ratio` and any other row without a file key) are keyed by `functionId` only (hand-off to U3/U5b). The scorer key (U5bP Q2: `functionId, filePath, target, discriminator`) is computed from the declared location. Negative twins keep `{ negative: true }` plus `twinOf`, and carry their own site collateral.
