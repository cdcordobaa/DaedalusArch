## Question 1
**What is the "one fixture" for the hand-computed acceptance?** The five fixtures are not mutations of correct-reference (Fact 6), and correct-reference has baseline violations, so the differential path (D7) can only be exercised on a real mutation.

A) (Recommended) A copy of `fixtures/correct-reference` mutated by U5a operators: three single-seed copies (one structural, one topological, one data-flow) plus one negative twin, each scored against the unmutated correct-reference report; the expected `GoldenScore` (every cell, including `preExistingIgnored`, declared collateral, an undeclared new violation counted FP, twin specificity and the FLOWS_TO edge check) is computed by hand in `tests/fixtures/u5b/hand-computed/EXPECTED.md` and committed as canonical JSON before the scorer code. Exercises baseline subtraction, `lineShifts` and twins. The five fixtures stay the development set (ADR-015 item 1).
B) Convert `variant-a` `MANIFEST.md` to JSON and score against correct-reference as baseline (wholesale file differences; manifest row 1 is not a violation).
C) Absolute mode with an empty baseline report.
D) Other (please describe after [Answer]: tag below)

[Answer]: A (criterion: B and C test paths the thesis never uses; A tests the D7 path every SO4 number goes through)

## Question 2
**What counts as a detection, and how do multiple detections count?** CM:1634-1638 leaves `lineTolerance` and `multiDetection` open; R:107 requires the rule to be stated.

A) (Recommended) Instance-level **count-once**, with collateral bound to the manifest.
   - **Key**: new violations = multiset difference of `baselineMatchKey = (functionId, filePath, target ?? '', discriminator)` between seeded and baseline report. The key is serialised as a JSON-encoded array `[functionId, filePath, target ?? "", [...discriminator]]` (no separator or escaping rule needed). `functionId` is always present (Fact 12).
   - **Detection**: a seed is TP if at least one new violation from one of its `expected.functionIds` matches its site key; `line`, after the `lineShifts` remap, is confirmatory with `lineTolerance = 0`, and a mismatch is reported, not counted against.
   - **Collateral**: only new violations from functions listed in the row's `expected.collateral` (U5aP Q5, Q7; e.g. MO-DF01 → `dependency-direction`, `no-domain-outward-dep`) are neutral (reported per function, neither TP nor FP). **Every other new violation in a seeded copy is FP-strict** and enters labeller population P1 (Question 5).
   - **FP modes**: FP-strict violations labelled `unseeded-TP` are removed to give **FP-labelled**. Both precisions are reported, FP-labelled as the headline with FP-strict alongside.
   - **Per-function table**: each expected and applicable function that fires on the seed gets TP; each expected and applicable function that does not fire gets **FN** in its own row (so per-function recall is defined and not inflated, e.g. MO-S01's two functions). Instance, dimension, tag and overall tables count each seed once.
   - **Dimension and tag**: a seed's dimension is `expected.dimension`. Its tags are the set of tags of its expected functions; the seed is counted once in each tag's table.
   - **Canonical serialisation** of `GoldenScore` (exit criterion 1): maps as arrays of `[key, value]` sorted by key, floats written with fixed formatting (`toFixed(6)` on stored ratios), keys as JSON-encoded tuples; implemented once in `scripts/lib/canonical-json.ts`.
B) Count-per-function at every level (inflates TP when 2-3 functions see one seed).
C) Line-strict matching (breaks under the FR-10 merge where `line = min(lines)`).
D) Other (please describe after [Answer]: tag below)

[Answer]: A (criterion: this rule determines every P/R/F1 figure; B inflates recall, C produces false FN; binding collateral to the pre-registered manifest removes a researcher choice that would raise precision by construction)

## Question 3
**Edge cases that would otherwise depress recall or precision by construction.** No rule covers: (i) a seed whose expected function is disabled for the style or excluded as cannot-fire (BR-U1-19, BR-U1-39); (ii) metric functions, where a seed on an already-violating file raises a value without a new key; (iii) a seed merged into an existing IMPORTS pair (FR-10), changing `lines` but not the key; (iv) negative twins; (v) metric templates whose key carries a value (Fact 11).

A) (Recommended) Pre-register five rules in `Docs/matching-rule.md`, applied in this order:
   - (i) **not-applicable**: if every expected function is disabled, excluded or absent from `functionExecution.executed`, the seed leaves the recall denominator and is counted and declared per function. Within a seed, each expected function that is not applicable is dropped from that seed's per-function rows.
   - (iii) **merged pairs / site-invalid** (applied first among (ii)-(iii)): U5a rejects sites whose source/target pair already has an edge (precondition); the scorer flags any seed whose site key pre-exists in the baseline as `site-invalid` and excludes it, counted. **Exception**: for seeds whose expected functions are metric templates, (ii) applies instead.
   - (ii) **metric seeds**: U5a rejects sites already in violation for the targeted metric (precondition, U5aP Q10); the scorer additionally treats a matched pre-existing key whose evidence value crosses the threshold between baseline and seeded report as detected.
   - (iv) **twins**: a twin may declare `expected.collateral` (e.g. a fan-out crossing from MO-C04n's new import); any undeclared new violation on a twin copy is FP. Twin FPs enter **specificity** (= twins with no undeclared new violation / twins) and a separate **"precision incl. twins"** column; they are not in the headline precision denominator. No TN is counted elsewhere.
   - (v) **stable metric keys**: entry conditions on U3 (Section 7.1): (a) project-level metrics map a stable `filePath` (`'<project>'`) and value columns go to `evidence`, never into `discriminator`; (b) the FR-14 metric row filters (`dependency-inversion`, `domain-stability`, `abstraction-ratio` return violating rows only) land before the schema freeze. Unless both have landed, FF-C06, FF-P02 and FF-C01 are marked "excluded from differential FP accounting" (declared, counted). A scorer unit test shows that a ratio change alone produces no new key.
B) Rules (i) and (iv) only; metric and merged-pair seeds count as FN.
C) Leave all to U5a site selection, no scorer rule.
D) Other (please describe after [Answer]: tag below)

[Answer]: A (criterion: without (i)-(iii) recall is depressed by instrument design, not by detection; without (v) a value-bearing key turns every pre-existing metric violation into a new FP under D7; U5a preconditions and U3 key conditions are hand-offs, Section 7.1)

## Question 5
**Which violations and judge units does the labeller see (FR-27 (a) and (b)), and how many?** Corpus baselines (E7) and generated projects (E1) can carry thousands of violations (ghostfolio); labelling all is costly, labelling an arbitrary subset biases precision; FR-27 (b) needs a fixed judge-unit sample.

A) (Recommended) Four populations plus missed seeds, each pre-registered in `Docs/analysis-plan.md`:
   - (P1) all FP-strict violations from seeded runs, seeded copies and twins (Question 2, 3 (iv)), labelled exhaustively;
   - (P2) violations in unseeded corpus baseline reports, sampled per (project, function) stratum with a cap of 20 and a seeded RNG, inclusion probability recorded so precision on real code is estimated with stratum weights;
   - (P3) violations in E1 generated projects, same rule per (cell, function);
   - (P4) **judge units**: all units the judge evaluated on a pre-registered subset (run index 0 of every valid E1 cell, plus the five fixtures in full mode), sampled per (cell, dimension) with a cap of 10 and recorded inclusion probabilities; this is the FR-27 (b) population for judge-vs-panel agreement;
   - missed seeds not resolved by the mechanical FN rules (Question 8), labelled exhaustively as kind `missed-seed`.
   - **Budget**: a global labelling budget (items × 2 runs) is pre-registered; after P1 and missed seeds, remaining capacity is allocated to P2-P4 proportionally to population size by lowering caps uniformly. `llm-label --estimate` prints the call count from the plan before any live call and refuses when it exceeds the budget.
   All sampled items and weights are stored; `aggregate.ts` reports weighted precision and weighted judge-vs-panel agreement with CIs.
B) Label all violations everywhere (cost unbounded on ghostfolio).
C) P1 only (no precision on real code; SO4 qualitative FP analysis then rests on seeds alone).
D) Other (please describe after [Answer]: tag below)

[Answer]: A (criterion: SO4's qualitative FP/FN analysis needs labelled real-code violations, SO3's neural claim needs a fixed judge-unit sample, and a pre-registered budget keeps the final-phase Gemini cost bounded and checkable)

**C15.6 Labeller (FR-27)**

## Question 6
**How does run 2 differ from run 1?** At temperature 0 two identical calls measure only provider nondeterminism, so run-vs-run agreement and the `uncertain` rate would be near-vacuous.

A) (Recommended) Same pinned model and temperature 0 in both runs; run 2 presents items in a seeded shuffled order and permutes the order of the label options (and of the root-cause list) in the prompt, with the permutation seed stored. `uncertain` then means "label sensitive to framing". Both runs are replayable from cassettes; each cassette exchange stores the options actually sent (FR-31 `usedOptions`) and the permutation.
