# U1 Spec and Compiler — Business Rules (v1.2E)

> **Unit**: U1 · **Date**: 2026-10-07 · **Base**: `v1.2e` at `ee32a1f`
> **Format**: each rule has an id `BR-U1-nn`, the FR / ADR-015 item / plan question it implements, and an **acceptance check** that a code-generation step can test. "Q" is a question of `v1.2E-u1-spec-compiler-functional-design-plan.md`; "item" is an ADR-015 decision item.
> **Runtime rule ids**: `BR-SPEC-10` is the only rule id that appears in program output; the `BR-U1-nn` ids are design ids.
> **Process gates**: an acceptance cell starting with **Process gate** is checked outside Code Generation (PR review, Build and Test or thesis writing). Each such cell also names an automatable part that a code-generation step implements.
> Flows and exact Cypher are in `business-logic-model.md`; types and schema deltas are in `domain-entities.md`.
> **Settlements**: ADR-016 (2026-10-08) closes OI-4, OI-5, OI-6, OI-8, OI-9 and OI-11 (`business-logic-model.md` §9.1); the record is `aidlc-docs/construction/plans/v1.2E-lane2-functional-design-clarifications.md`.

(R2) *degree* is a node's number of IMPORTS edges. A *count heuristic* is a count of class or interface members, injections or declarations, used as a proxy for a design principle. It is justified as conservative: a check that relies on a heuristic is never counted towards the "structural and topological rules" claim.
