# v1.1 Units of Work — Architectonic Firewall

4 units, bottom-up dependency order. U0 builds in main, U1 and U2 run in parallel worktrees, U3 integrates last.

---

## U0: Shared Extensions (Foundation)

**Track**: Main (pre-worktree)
**Build order**: First — all other units depend on this
**Worktree**: None — built in `main` before worktrees are created

**Components**:
- C10 (Shared Domain) — new types: `ActionableViolation`, `BaselineSnapshot`, `BaselineResult`, `BaselineEntry`, `ValidationReport`, `SpecOverrides`, `FFOverride`, `GeminiConfig`, `NullLLMProvider`, `DisabledFunction`
- C3 (Spec Parser) — `exclude_paths` parsing, `enabled` field parsing, `validateSpec()` method
- C4 (Fitness Compiler) — `filterEnabled()`, `injectExcludePaths()`, `globToRegex()`

**Responsibilities**:
- Extend shared domain types for v1.1 features
- Add exclude_paths and enabled support to spec parser and compiler
- Add spec validation logic
- Ensure all existing 312 tests still pass (backward compatibility)

**Functional Design**: EXECUTE — new parsing logic, glob-to-regex conversion, validation rules

**Estimated scope**: ~15 files modified/new, ~40 new tests

---

## U1: Track A — Spec Generation & Baseline

**Track**: A (`track-a/spec-generation` worktree)
**Build order**: After U0 — depends on shared extensions
**Worktree**: `../DaedalusArch-TrackA`

**Components**:
- C3 (Spec Parser) — `loadPreset()`, `mergeSpecs()`, `listPresets()`
- C12 (Baseline Manager) — full new component
- C9 (CLI) — `firewall validate` command, `firewall baseline` command, `--baseline` flag on evaluate
- S1 (Pipeline) — `ValidateSpecCommand`, `CreateBaselineCommand`, `CompareBaselineCommand`, new pipeline configs
- Skill — `.claude/commands/firewall-init.md` prompt file
- Presets — `presets/clean-architecture.yaml`, `presets/nestjs.yaml`

**Responsibilities**:
- Preset template library with 2 architecture styles
- Preset loading and merging with project overrides
- Baseline snapshot creation, loading, comparison
- CLI commands for validate and baseline
- Baseline comparison in evaluate pipeline
- Claude Code skill prompt for end-to-end init flow

**Functional Design**: EXECUTE — preset selection logic, baseline key generation, baseline comparison algorithm, pipeline wiring

**Estimated scope**: ~25 files new, ~60 new tests

---

## U2: Track B — Demo Dashboard

**Track**: B (`track-b/demo-dashboard` worktree)
**Build order**: After U0 — depends on shared extensions (ActionableViolation type)
**Worktree**: `../DaedalusArch-TrackB`

**Components**:
- C8 (Scoring Engine) — `formatActionableViolation()`, `applyBaseline()`, extended report output
- C13 (Report Generator) — full new component
- C9 (CLI) — `firewall report` command
- S1 (Pipeline) — `GenerateReportCommand`, report pipeline config

**Responsibilities**:
- Actionable violation message formatting (What/Where/Why/Fix)
- HTML report generator with embedded data
- Cytoscape.js graph data builder (nodes by layer, edges by dependency, violations in red)
- Dashboard sections: header, AHS gauge, architecture graph, fitness cards, violations explorer, baseline split, summary stats
- HTML template with Tailwind CSS + Cytoscape.js + vanilla JS
- `firewall report` CLI command

**Functional Design**: EXECUTE — actionable message generation rules, graph data transformation, HTML template structure

**Estimated scope**: ~20 files new, ~30 new tests + visual verification

---

## U3: Gemini Integration

**Track**: Shared (back in main, post-merge)
**Build order**: Last — independent of U1/U2, integrates after merge
**Worktree**: None — built in `main` after both tracks merge

**Components**:
- C7 (LLM Critic) — `GeminiProvider`, `NullLLMProvider`, `LLMProviderFactory` extension
- C10 (Shared Domain) — `GeminiConfig` type (if not already in U0)

**Responsibilities**:
- Implement GeminiProvider using Google AI SDK
- NullLLMProvider for graceful degradation (no API key → symbolic-only)
- Factory pattern extension for provider selection
- Model configuration (env var > spec > default)
- Integration test with real Gemini API (optional, requires key)

**Functional Design**: SKIP — straightforward interface implementation, no complex business logic

**Estimated scope**: ~5 files new, ~15 new tests (mocked + optional integration)
