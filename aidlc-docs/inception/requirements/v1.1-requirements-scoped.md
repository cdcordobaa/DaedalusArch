# v1.1 Requirements — Architectonic Firewall (Demo-Scoped)

## Context

v1.0 delivered a working symbolic evaluation pipeline (8 units, 312 tests, 84 source files). v1.1 makes the tool **demoable on real brownfield repos** by adding two capabilities: (1) agent-assisted spec generation so users don't write YAML by hand, and (2) an interactive HTML dashboard that visualizes results for product demos.

## Vision

A developer opens Claude Code in any TypeScript project and runs the architectonic firewall skill. Claude reads the codebase structure, classifies the architecture, generates a tailored spec with sensible defaults, and produces an interactive HTML report showing violations, fitness function scores, and an architecture graph — all in under 2 minutes.

## Scope Decision

From the original 14 v1.1 FRs, this release includes 10 FRs across two parallel implementation tracks plus shared infrastructure. Deferred: FR-05 (inline suppression), FR-08 (ADR-to-spec), FR-10 (language abstraction), FR-11 (React/JSX), FR-12 (in-memory graph).

## Track A — Spec Generation (Claude Code Skill)

### FR-V1.1-01: Claude Code Skill for Spec Generation
**Priority**: Must | **Track**: A

A Claude Code skill (`.claude/commands/firewall-init.md`) that orchestrates spec generation for a target project. Claude Code itself acts as the LLM — no external API call needed for classification.

**Skill workflow**:
1. Read project structure (folder tree, package.json, tsconfig, framework markers)
2. Run APG extraction on the target project (calls existing v1.0 pipeline)
3. Mine APG signals via Cypher queries (directory patterns, dependency matrix, naming conventions, DI ratio)
4. Classify architecture style using structural signals (~300 tokens of facts, not raw code)
5. Map detected folders to layers
6. Select preset template based on classification
7. Apply project-specific overrides (exclude paths, threshold calibration)
8. Generate `firewall.spec.yaml` in project root
9. Run first evaluation with generated spec
10. Present results for user approval/modification

**Outputs**: Generated `firewall.spec.yaml`, first evaluation results

**Integration surface**: Claude Code skill only (`.claude/commands/`). No standalone CLI `init` command for this release.

### FR-V1.1-03: Exclude Paths in Cypher Queries
**Priority**: Must | **Track**: A

Wire `exclude_paths` from spec YAML into Cypher `WHERE NOT` clauses.

```yaml
- id: FF-C02
  name: module-fan-out
  threshold: 10
  exclude_paths:
    - "src/pipeline/pipeline-factory.ts"
    - "src/cli/**"
```

The fitness compiler injects path exclusion predicates into every Cypher template that supports it. Glob patterns converted to regex for Cypher matching.

### FR-V1.1-06: Framework Presets
**Priority**: Must | **Track**: A

Two built-in presets for the demo:

| Preset | Layers | Key Rules |
|--------|--------|-----------|
| `clean-architecture` | domain, application, infrastructure | Dependency direction, DI enforcement, layer isolation, no layer skip |
| `nestjs` | domain, application, infrastructure, presentation | Module boundaries, decorator conventions, DI patterns, controller isolation |

Each preset is a YAML template in a `presets/` directory containing:
- Layer definitions with directory mappings
- Canonical fitness functions (Tier 1 — definitional for the style)
- Default thresholds calibrated from empirical data (spike repos)
- Default exclude paths (`node_modules/`, `dist/`, `*.spec.ts`)

The skill selects the appropriate preset based on framework detection (presence of `@nestjs/core` in package.json → nestjs preset, otherwise → clean-architecture).

### FR-V1.1-14: Spec Validation and Linting
**Priority**: Must | **Track**: A

Validate AoC YAML spec before running the pipeline. Invoked automatically by the skill after spec generation, and available as `firewall validate`.

```bash
firewall validate --spec firewall.spec.yaml
```

Checks:
- Layer directories exist in the target project
- Fitness function IDs are unique
- Referenced Cypher templates exist
- Threshold values are in valid ranges
- `exclude_paths` patterns are valid globs
- `enabled` field is boolean when present

## Track B — Interactive Demo Dashboard

### FR-V1.1-07: Actionable Violation Messages
**Priority**: Must | **Track**: B

Violations must include four components:
- **What**: specific rule violated (ID + name + dimension)
- **Where**: file path + line number
- **Why**: human-readable explanation of the rule and how it was violated
- **Fix**: suggested action to resolve

```
[major] FF-C02 — Fan-out exceeded (12 > 10)
  File: src/pipeline/pipeline-factory.ts:64
  Why:  This file imports from 12 different modules, exceeding the max_fan_out threshold.
  Fix:  Consider extracting a service factory or using a DI container to reduce direct imports.
```

This format is used in both CLI output and the HTML dashboard.

### FR-V1.1-15: Interactive HTML Report Generator (NEW)
**Priority**: Must | **Track**: B

New CLI command that generates a self-contained HTML dashboard from evaluation results.

```bash
firewall report --spec firewall.spec.yaml --project . -o report.html
```

**Dashboard sections**:

1. **Header** — Product name ("Architectonic Firewall"), project name, evaluation timestamp, spec version
2. **AHS Score** — Headline metric with gauge visualization + breakdown by dimension (structural, coupling, dependency-direction, convention, etc.)
3. **Architecture Map** — Cytoscape.js graph with dagre hierarchical layout: nodes = components colored by layer, edges = dependencies, violation edges highlighted in red
4. **Fitness Function Cards** — Grid of all evaluated functions: name, dimension, pass/fail badge, score vs threshold, severity level
5. **Violations Explorer** — Filterable/sortable table with columns: file, rule ID, rule name, severity, dimension, description, suggested fix. Filters: by severity, by dimension, by layer, by baseline status
6. **Baseline vs New** — Visual split showing inherited violations (in baseline, don't block CI) vs newly introduced violations (block CI)
7. **Summary Stats** — Total files analyzed, total components, layers detected, compliance percentage, symbolic vs neuronal evaluation status

**Technical constraints**:
- Single self-contained HTML file — no build step, no dev server required
- Dependencies via CDN: Tailwind CSS, Cytoscape.js, dagre layout plugin
- Evaluation data embedded as inline JSON (injected by the generator at build time)
- Vanilla JavaScript — no framework
- Must render correctly when opened directly via `open report.html`

**Data source**: Consumes the same JSON output shape produced by the existing v1.0 `report-formatter.ts`, extended with actionable message fields from FR-V1.1-07.

## Shared Infrastructure

### FR-V1.1-04: Rule Enable/Disable Mechanism
**Priority**: Must | **Track**: Shared

Allow disabling specific fitness functions in the spec:

```yaml
- id: FF-S03
  name: no-layer-skip
  enabled: false
  reason: "3-layer architecture — all cross-layer imports are adjacent"
```

The fitness compiler skips functions with `enabled: false`. The dashboard shows disabled functions as grayed-out cards. Default: `enabled: true` (backward compatible).

### FR-V1.1-09: Incremental Rule Adoption (Baseline)
**Priority**: Must | **Track**: Shared

Baseline mechanism for brownfield adoption:

```bash
# After first evaluation, snapshot current violations as baseline
firewall baseline --spec firewall.spec.yaml --project .

# Subsequent evaluations compare against baseline
firewall evaluate --spec firewall.spec.yaml --project . --baseline baseline.json
```

- Existing violations go into `baseline_violations.json`
- Baselined violations appear in reports but don't fail CI
- Only NEW violations (not in baseline) fail CI
- Dashboard shows baseline vs new split (FR-V1.1-15 section 6)
- The skill auto-generates baseline after first evaluation

### FR-V1.1-13: GeminiProvider for Neuronal Evaluation
**Priority**: Must | **Track**: Shared

Implement `GeminiProvider` replacing `MockLLMProvider` for the neuronal evaluation path:

```typescript
class GeminiProvider implements LLMProvider {
  constructor(config: { apiKey: string; model?: string })
  evaluate(prompt: string, options: LLMOptions): Promise<DomainResult<LLMResponse>>
}
```

- Uses Google AI SDK (`@google/generative-ai`)
- Required for semantic/intent fitness function dimensions
- Neuronal evaluation results displayed in dashboard alongside symbolic results
- Spec generation (FR-01) does NOT use this — Claude Code handles classification natively
- Falls back gracefully when no API key configured (symbolic-only mode)

## Non-Functional Requirements

### NFR-V1.1-01: Neo4j as Graph Database
Neo4j is the graph database for all evaluation. Docker + Neo4j is an accepted prerequisite. No in-memory alternative in this release.

### NFR-V1.1-02: First-Evaluation Under 2 Minutes
From skill invocation to first interactive HTML report: under 2 minutes on a project with up to 500 files (excluding Neo4j startup).

### NFR-V1.1-03: Signal-to-Noise Ratio
After spec generation, the first evaluation should produce < 20 violations on a well-structured project, with > 80% being genuine issues.

### NFR-V1.1-04: Backward Compatibility
v1.0 specs (`specs/clean-arch.yaml`) must continue to work unchanged. New fields (`enabled`, `exclude_paths`, `baseline`) are additive and optional.

### NFR-V1.1-05: Real Repo Validation
The implementation must be validated against at least one real open-source TypeScript repo (selected via research) in addition to v1.0 test fixtures.

## Architecture Decisions for v1.1

### AD-01: Spec Generation via Claude Code Skill, Not Coded LLM Call
Rationale: The skill leverages Claude Code's native intelligence for architecture classification. No external LLM API call is needed for init — the agent IS the LLM. This eliminates an entire integration surface (prompt engineering, API key management, response parsing) from the codebase.

### AD-02: Rule Catalog Separate from Presets
Rationale: v1.0 conflated templates with the rule catalog. v1.1 separates:
- **Rule catalog**: all possible fitness functions with metadata (dimension, severity, params)
- **Presets**: curated subsets for specific architecture styles (clean-arch, nestjs)
- **Spec**: project-specific selection + overrides + exclusions

### AD-03: Exclude Paths via Cypher Parameter Injection
Rationale: `WHERE NOT` clauses injected into Cypher templates. The fitness compiler reads `exclude_paths` and converts globs to regex for Cypher path filtering.

### AD-04: Gemini for Neuronal Path Only
Rationale: Neuronal evaluation (semantic fitness functions) requires a real LLM provider. Gemini via Google AI SDK is the chosen provider. Init classification is handled by Claude Code natively. This separates concerns: agent-assisted setup (Claude Code) vs programmatic evaluation (Gemini).

### AD-05: Embedded HTML Report
Rationale: Single self-contained HTML file with embedded JSON data. No server needed, no CORS issues, shareable via email/Slack. Cytoscape.js with dagre layout for architectural graph visualization — purpose-built for directed graph analysis with hierarchical layer rendering.

### AD-06: Option C Parallel Construction
Rationale: Inception through Units Generation runs in main (single state, single audit). At code generation, two worktrees split from main — one per track. Both merge back to main for a shared Build & Test phase. This follows the AI-DLC framework's single-state model while enabling parallel coding.

| FR | What | Why Deferred |
|----|------|-------------|
