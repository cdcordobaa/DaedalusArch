# v1.1 Requirements — Project-Agnostic Architectural Firewall

## Context

v1.0 delivered a working symbolic evaluation pipeline (8 units, 312 tests, 84 source files). Self-evaluation on DaedalusArch's own codebase exposed critical developer experience gaps that prevent real-world adoption. v1.1 transforms the tool from "works for one architecture style with manual YAML authoring" to "any TypeScript project can get value in under 5 minutes via agent-assisted setup."

## Vision

A coding agent (Claude, Cursor, Gemini, Copilot) uses a **skill/tool** to:
1. Scan a target project's codebase
2. Detect architecture style, folder structure, framework
3. Generate a tailored AoC YAML spec with appropriate rules
4. Map existing ADRs to fitness functions automatically
5. Run the first evaluation and present actionable results

The human approves/tunes the generated spec. Subsequent evaluations run automatically in CI.

## Functional Requirements

### FR-V1.1-01: Agent Skill / MCP Tool for Spec Generation
**Priority**: Must

An LLM-callable tool/skill that agents can invoke to set up DaedalusArch for a project.

**Inputs**: project path, optional ADR directory, optional hints ("this is a NestJS app")
**Process**:
1. Scan project structure (folder tree, package.json, tsconfig, framework markers)
2. Detect architecture style (layered, modular, hexagonal, framework-specific)
3. Detect framework (NestJS, Next.js, Express, plain TS, React/Vite, monorepo)
4. Map detected folders to layers
5. Select applicable fitness functions from a rule catalog
6. Parse ADRs if present → generate additional fitness functions
7. Generate AoC YAML spec with sensible defaults and exclusions
8. Present spec to user for approval/modification

**Outputs**: Generated `firewall.spec.yaml` in project root

**Agent integration surfaces**:
- Claude Code: MCP tool or slash command (`/firewall-init`)
- Cursor: custom tool definition
- Generic: CLI command (`firewall init`) with interactive prompts

### FR-V1.1-02: `firewall init` CLI Command
**Priority**: Must

Interactive CLI command that guides spec creation without requiring an agent.

```
firewall init [--project <path>]
  → Detects: TypeScript, React, NestJS, Next.js, Express, plain
  → Shows: detected layers, folder mapping
  → Asks: "Is this correct? [Y/n]"
  → Generates: firewall.spec.yaml
  → Runs: first evaluation with generated spec
```

### FR-V1.1-03: Exclude Paths in Cypher Queries
**Priority**: Must

Wire `exclude_paths` from spec YAML into Cypher `WHERE NOT` clauses.

```yaml
- id: FF-C02
  name: module-fan-out
  threshold: 10
  exclude_paths:
    - "src/pipeline/pipeline-factory.ts"
    - "src/cli/**"
```

The fitness compiler must inject path exclusion predicates into every Cypher template that supports it.

### FR-V1.1-04: Rule Enable/Disable Mechanism
**Priority**: Must

Allow disabling specific fitness functions in the spec:

```yaml
- id: FF-S03
  name: no-layer-skip
  enabled: false          # ← new field
  reason: "3-layer architecture — all cross-layer imports are adjacent"
```

Template-injected functions can be disabled by overriding with `enabled: false`.

### FR-V1.1-05: Per-Violation Inline Suppression
**Priority**: Should

Allow suppressing specific violations in source code:

```typescript
// firewall-ignore FF-C02: composition root, high fan-out by design
import { Neo4jRepository } from '../neo4j-ingestion/index.js';
```

The APG extractor reads these comments and the evaluation engine skips violations on annotated files/lines.

### FR-V1.1-06: Framework Presets
**Priority**: Must

Built-in presets that auto-configure layer mappings and rules:

| Preset | Layers | Key Rules |
|--------|--------|-----------|
| `plain-ts` | domain, application, infrastructure | Standard clean-arch rules |
| `nestjs` | domain, application, infrastructure, presentation | Module boundaries, decorator conventions, DI patterns |
| `nextjs` | pages/app, components, lib, api | Client/server boundary, API route isolation, component purity |
| `express` | routes, controllers, services, models | Route-controller-service pattern, middleware isolation |
| `react-vite` | components, hooks, services, store, utils | Component purity, hook rules, no side effects in render |
| `monorepo` | packages/* | Cross-package dependency rules, shared package stability |

Each preset is a YAML template in a `presets/` directory. `firewall init` uses detection to select the right one.

### FR-V1.1-07: Actionable Violation Messages
**Priority**: Must

Violations must include:
- **What**: specific rule violated
- **Where**: file path + line number (not just file)
- **Why**: human-readable explanation
- **Fix**: suggested action

```
[major] FF-C02 — Fan-out exceeded (12 > 10)
  File: src/pipeline/pipeline-factory.ts:64
  Why:  This file imports from 12 different modules, exceeding the max_fan_out threshold.
  Fix:  Consider extracting a service factory or using a DI container to reduce direct imports.
  Suppress: Add "// firewall-ignore FF-C02" above the import block
```

### FR-V1.1-08: ADR-to-Spec Mapping Pipeline
**Priority**: Must

Automated pipeline that:
1. Detects ADR files in project (docs/, adr/, .adr/, decisions/)
2. Parses ADR content (MADR, Nygard, Y-Statement formats — already implemented in v1.0)
3. Uses LLM to extract architectural constraints from ADR prose
4. Generates fitness functions from extracted constraints
5. Adds generated functions to the spec with `source: adr` tag and `adr_ref` linking

Example: ADR says "We chose PostgreSQL over MongoDB for ACID compliance" → generates rule: "No MongoDB driver imports allowed in the codebase."

### FR-V1.1-09: Incremental Rule Adoption
**Priority**: Should

Allow running a subset of rules, not the full spec:

```bash
# Only structural rules
firewall evaluate --project . --spec firewall.spec.yaml --dimensions structural

# Only specific rules
firewall evaluate --project . --spec firewall.spec.yaml --rules FF-S01,FF-S02,FF-C02

# Severity filter
firewall evaluate --project . --spec firewall.spec.yaml --min-severity major
```

### FR-V1.1-10: Language-Agnostic APG Abstraction
**Priority**: Should (future-proofing, TS-only implementation for now)

Refactor the APG extractor interface to support multiple languages:

```typescript
interface APGExtractor {
  readonly language: string;
  readonly fileExtensions: string[];
  canExtract(projectPath: string): Promise<boolean>;
  extract(projectPath: string, options?: ExtractorOptions): Promise<DomainResult<APGResult>>;
}
```

Current `ts-morph` extractor becomes `TypeScriptExtractor implements APGExtractor`. Future extractors: `PythonExtractor`, `JavaExtractor`, `GoExtractor`.

The APG schema (nodes, edges) is already language-agnostic — the same graph structure works for any language.

### FR-V1.1-11: React/JSX/TSX Support
**Priority**: Must

Extend the TypeScript APG extractor to handle React patterns:
- Component detection (function components, class components)
- Hook extraction (custom hooks, built-in hooks)
- Props type extraction
- JSX/TSX file parsing
- Client/server component boundaries (Next.js `'use client'` / `'use server'`)
- Re-export barrel detection in component libraries

### FR-V1.1-12: In-Memory Graph Option
**Priority**: Should

Provide an alternative to Neo4j for simple/local analysis:

```bash
# Default: uses in-memory graph (no Docker needed)
firewall evaluate --project . --spec firewall.spec.yaml

# Explicit Neo4j (for large projects or persistent snapshots)
firewall evaluate --project . --spec firewall.spec.yaml --neo4j-uri bolt://localhost:7687
```

An in-memory adjacency list implementation of `GraphRepository` that executes a subset of Cypher-like queries without Neo4j. Covers the 80% use case (basic structural/coupling analysis) without infrastructure.

### FR-V1.1-13: Real LLM Providers
**Priority**: Must

Implement `ClaudeProvider` and `OpenAIProvider` replacing `MockLLMProvider`:

```typescript
class ClaudeProvider implements LLMProvider {
  constructor(config: { apiKey: string; model?: string })
  evaluate(prompt: string, options: LLMOptions): Promise<DomainResult<LLMResponse>>
}
```

Required for:
- Neuronal evaluation mode (semantic/intent dimensions)
- Agent skill spec generation (FR-V1.1-01)
- ADR-to-spec mapping (FR-V1.1-08)

### FR-V1.1-14: Spec Validation and Linting
**Priority**: Should

Validate the AoC YAML spec before running the pipeline:

```bash
firewall validate --spec firewall.spec.yaml
```

Checks:
- Layer directories exist in the project
- Fitness function IDs are unique
- Referenced Cypher templates exist
- Threshold values are in valid ranges
- `exclude_paths` patterns are valid globs
- ADR references resolve to existing files

## Non-Functional Requirements

### NFR-V1.1-01: Zero-Infrastructure Default
The default evaluation mode must not require Docker or Neo4j. In-memory graph for projects under 500 files.

### NFR-V1.1-02: First-Evaluation Under 2 Minutes
From `npm install daedalus-arch` to first useful evaluation result: under 2 minutes including `firewall init`.

### NFR-V1.1-03: Signal-to-Noise Ratio
After `firewall init`, the first evaluation should produce < 20 violations on a typical well-structured project, with > 80% being genuine issues (not false positives).

### NFR-V1.1-04: Agent Skill Response Time
The MCP tool / agent skill must respond within 30 seconds for spec generation on projects up to 1000 files.

### NFR-V1.1-05: Backward Compatibility
v1.0 specs (`specs/clean-arch.yaml`) must continue to work unchanged. New features are additive.

## Architecture Decisions for v1.1

### AD-01: Spec Generation via LLM, Not Heuristics
Rationale: Rule-based detection (regex on folder names) is fragile. An LLM reading the codebase can understand architectural intent, not just folder patterns. The agent skill sends project structure + sample files to the LLM and gets back a spec draft.

### AD-02: Rule Catalog Separate from Templates
Rationale: v1.0 conflated templates (clean-arch) with the rule catalog. v1.1 separates them:
- **Rule catalog**: all possible fitness functions with metadata (dimension, default severity, required params)
- **Presets**: curated subsets of the catalog for specific architecture styles
- **Spec**: project-specific selection + overrides + exclusions

### AD-03: Exclude Paths via Cypher Parameter Injection
Rationale: Adding `WHERE NOT` clauses to every Cypher template. The fitness compiler reads `exclude_paths` from the spec and injects glob-to-regex path filters as Cypher parameters.

### AD-04: In-Memory Graph as Default
Rationale: Neo4j is powerful but overkill for most dev-time analysis. An in-memory graph with simple path queries covers structural, coupling, and convention dimensions. Neo4j becomes opt-in for advanced features (snapshots, drift, complex APOC queries).

### AD-05: Language Abstraction at APG Layer
Rationale: The APG schema (File, Class, Interface, Method, Function + IMPORTS, IMPLEMENTS, etc.) is universal. Only the extractor is language-specific. Adding a new language = adding a new extractor, everything else works unchanged.
