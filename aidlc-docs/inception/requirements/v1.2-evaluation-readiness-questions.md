## Question 5 — `Package` node identity for scoped and subpath specifiers
Specifiers seen in the corpus include `@nestjs/common`, `@nestjs/common/http`, `express`, `@prisma/client`, `rxjs/operators`, `node:fs`, `./relative` (not a package). `forbidden_imports` lists today contain `@nestjs/*`, `typeorm`, `express`, `prisma`, `@prisma/*`, `sequelize`.

A) **One node per package root** (`@scope/name` or `name`), with the subpath kept on the edge as part of `specifier`. `@nestjs/common/http` → Package `@nestjs/common`, edge `specifier: "@nestjs/common/http"`. Node built-ins (`node:fs`, `fs`) become Package nodes with `scope: "node"`. Matching for `forbidden_imports`: exact name, or glob on `scope/*`. Recommended: matches how `package.json` names dependencies.
B) **One node per full specifier** (`@nestjs/common` and `@nestjs/common/http` are different nodes). Finer, but inflates fan-out and makes the Package list noisy.
C) **One node per scope for scoped packages** (`@nestjs`), one per name otherwise. Coarse; loses the ability to forbid `@nestjs/typeorm` while allowing `@nestjs/common`.

## Question 7 — Severity of the new bound-parameter validation rule
Stage-2 rules are fatal only in strict mode, which no caller enables. A declaration whose template requires a parameter the document does not supply currently compiles and fails at Neo4j (R-4.13).

A) **Always fatal**, independent of strict mode: an unbound required parameter is a compile defect, not a style warning. The spec fails to parse with `BR-SPEC-10` and the offending function and parameter named. Recommended.
B) **Follow strict mode** like the other stage-2 rules, and turn strict mode on by default in the CLI (`--no-strict` to relax). Consistent, but changes the behaviour of every existing rule at once.
C) **Warning plus auto-disable**: compile proceeds, the function is disabled with reason `unbound parameter`, counted under `droppedFunctions`, and the score excludes it. Never blocks, always visible.
