**Date**: 2026-10-14. **Depth**: comprehensive (the cycle's output decides whether the thesis tool can be trusted).
**Answers**: `v1.3-validity-questions.md`. Every answer is an AI default chosen under the author's delegation.

| Item | Value |

## Methodology frame (METH-V1)

- **Study 1** = v1.2E. It stays frozen, and `--check-prereg` must keep passing on the `v1.2e` branch.
- **v1.3** = development. It may tune on all Study 1 data, and every tuning decision is logged as an ADR.
- **Study 2** = pre-registered before it runs, on fresh projects and tasks that v1.3 never touched. It is out of scope for this cycle except its design.

## Functional requirements

| ID | Requirement |
|---|---|
| FR-V1 | **Integrate the drafts** #69 (dynamic imports, NestJS module wiring), #74 (MCP loop, with #55 underneath it), #76 (hexagonal) and #79 (judge anti-pattern operators) into one `v1.3` branch cut from `v1.2e`. All tests green. The new extractor options are on by default in v1.3. |
| FR-V2 | **Graph fidelity harness (link 1).** For any TypeScript project it computes, per run: (a) import-edge precision and recall against a reference (dependency-cruiser plus the TypeScript compiler's module resolution); (b) file-to-layer accuracy against an expected layer map, where one exists; (c) a list of every disagreement, with the reason class (alias, dynamic, type-only, re-export, out-of-root, bug). |
| FR-V3 | **Reference projects per style** (clean, layered, NestJS, hexagonal, DDD). Each has a clean variant and violating variants, a hand-written `expected-graph` (layer map and key edges) and an `expected-findings.json` manifest (rule, file, reason). They are small (about 15 to 40 files) and compile. |
| FR-V4 | **DDD library.** Tactical rules: aggregate boundaries (outside code refers only to the aggregate root), repositories only for aggregate roots, immutable value objects, a framework-free domain, domain events raised in the domain. Strategic rules: bounded contexts as modules, no imports across contexts except through a declared public API or anti-corruption layer. It has a preset, templates outside the frozen registry, fixtures and tests. |
| FR-V5 | **End-to-end validation runner.** Runs the tool on every reference project and compares the findings with the manifest. Reports per-style and per-rule recall and precision, with every mismatch explained. |
| FR-V6 | **Rule tiers.** A formal `tier: blocking or advisory` field. Only blocking rules can fail the verdict. Advisory rules are reported, and they are weighted out of the AHS, or into a separate score. FF-CV05 test pairing and the threshold proxies become advisory. The change is documented as a v1.3 scoring ADR, and Study 1 scoring is unchanged. |
| FR-V7 | **Labelling of findings in two parts.** Each sampled finding gets a label for *correct* (the condition holds in the code) and one for *meaningful* (an architect would want it fixed). The Gemini API labeller runs with tools off. The author audits a random sample. Precision is reported per rule. Sources: the existing E1 cells (development data) and the pilot generations. |
| FR-V8 | **Judge filter-and-explain step.** The judge reviews each symbolic finding and confirms or dismisses it, with a reason. We measure how much precision it adds and how much recall it costs on the reference projects and on the labelled sample. |
| FR-V9 | **Judge detection.** Run the #79 anti-pattern operators on the reference projects and the pilot generations, and report the judge's catch rate per operator. |
| FR-V10 | **Spec-influence pilot (exploratory).** For each style (hexagonal, DDD, clean), generate a small set of projects from a full AaC spec and from minimal prose, using 1 or 2 models and a few tasks. Run the tool, label a sample, and describe which patterns the spec induces and where the tool or the rules fail. This is not pre-registered; it is used only to find defects and to design Study 2. |
| FR-V11 | **Validation report.** Every link, every target, met or missed, with evidence paths. It is the exit gate of this cycle. |
| FR-V12 | **Study 2 design outline**: hypotheses, arms (including the MCP firewall-in-the-loop with multi-step feature tasks), fresh data, and a pre-registration draft. |

## Exit targets (provisional; your director may adjust them)

| Link | Metric | Target |
|---|---|---|
| 1 | Import-edge precision and recall against the reference, on reference and pilot projects | ≥ 0.95 each; every disagreement classified |
| 1 | File-to-layer accuracy on reference projects | ≥ 0.95 |
| 3 | Seeded or manifest recall per style (blocking rules) | ≥ 0.90 |
| 3+4 | Precision of blocking rules, *correct* label | ≥ 0.90 |
| 4 | Precision of blocking rules, *meaningful* label | reported; target set after the first round |
| Judge | Catch rate on anti-pattern seeds | ≥ 0.80 (reported per operator) |
| Judge filter | Precision gain at recall loss ≤ 0.05 | reported |

A missed target is either fixed or waived in writing in the validation report, with the reason.

## Non-functional requirements

- **NFR-V1, frozen instrument.** No registered v1.2E artefact changes on `v1.2e`. v1.3 lives on its own branch, and new templates live outside `CYPHER_TEMPLATES`.
- **NFR-V2, machine load.** At most 2 local build lanes plus 1 reviewer. One capped Neo4j. `jest --maxWorkers=2`. Work that doesn't need Neo4j goes to cloud routines.
- **NFR-V3, determinism.** Symbolic results are reproducible byte for byte. LLM calls are recorded as cassettes.
- **NFR-V4, cost.** Generation and labelling use the subscription, the cloud credit or the Gemini key. Gemini spend is reported. There is no single paid run above the pilot sizes in FR-V10 without escalation.
- **NFR-V5, security baseline** enforced, as in v1.2E: secrets only from `.env`, never printed, and the judge, labeller and generator isolation is kept.
- **NFR-V6, speed.** The first evidence comes quickly: FR-V2 on the existing E1 cells is the first result.

## Revision 2 (2026-10-15, author decision): no pre-registration until the tool is shown fit

The author said: "i dont want preregistrations until we make sure the tool is good enough to actually detect what we are trying to find out".
- FR-V12 is reduced to an **informal Study 2 outline only**. No pre-registration document, no prereg bump and no registration of any v1.3 artefact happen in this cycle.
- **Fitness gate before any pre-registration:** the sealed hold-out validation meets the exit targets, or the author accepts written waivers, and the author explicitly says the tool is good enough.
- The safeguards that are not pre-registration stay: the sealed hold-out set, blind manifests, a priori tiers and the sealed Study 2 task hash. They keep the development measurements honest, and they cost nothing later.
