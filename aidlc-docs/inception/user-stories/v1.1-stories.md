## Epic: E-INIT — Agent-Assisted Spec Generation

### S-INIT-01: Skill-Driven Spec Generation
**As** ARCH, **I want** to run a Claude Code skill on any TypeScript project that scans the codebase, classifies the architecture, and generates a tailored `firewall.spec.yaml`, **so that** I can set up architectural governance without writing YAML by hand.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given a TypeScript project with a src/ directory and package.json
When I invoke the firewall-init skill in Claude Code
Then the skill scans the project structure
And classifies the architecture style (clean-architecture or nestjs)
And maps directories to architectural layers
And generates a firewall.spec.yaml in the project root
And presents the generated spec for my approval
```

**Personas**: ARCH, DEV
**FRs**: FR-01

---

### S-INIT-02: Framework Detection and Preset Selection
**As** DEV, **I want** the skill to automatically detect whether my project uses NestJS or plain TypeScript and apply the correct preset, **so that** the generated spec matches my framework's conventions without manual configuration.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given a project with @nestjs/core in package.json dependencies
When the skill runs framework detection
Then it selects the nestjs preset
And the generated spec includes NestJS-specific layer mappings (domain, application, infrastructure, presentation)
And includes NestJS-specific fitness functions (module boundaries, controller isolation)

Given a project without any framework markers
When the skill runs framework detection
Then it selects the clean-architecture preset
And the generated spec includes standard layers (domain, application, infrastructure)
```

**Personas**: DEV, ARCH
**FRs**: FR-06

---

### S-INIT-03: Preset Template Library
**As** ARCH, **I want** presets stored as YAML templates in a `presets/` directory with canonical fitness functions, default thresholds, and standard exclude paths, **so that** I can review, customize, and contribute new presets.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given the presets/ directory
When I list available presets
Then I find clean-architecture.yaml and nestjs.yaml
And each preset contains: layer definitions, fitness function list, default thresholds, default exclude_paths

Given a preset template
When the skill applies it to a project
Then layer directory mappings are parameterized from the project's actual folder structure
And thresholds use empirically calibrated defaults from spike data
```

**Personas**: ARCH
**FRs**: FR-06

---

### S-INIT-04: Exclude Paths in Fitness Functions
**As** DEV, **I want** to specify `exclude_paths` per fitness function in the spec so that known exceptions (composition roots, test files, generated code) don't trigger false positive violations, **so that** I trust the evaluation output.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given a spec with exclude_paths on FF-C02 containing "src/pipeline/pipeline-factory.ts"
When the fitness compiler generates Cypher for FF-C02
Then the Cypher includes a WHERE NOT clause filtering out the excluded path
And the evaluation does not report violations for that file under FF-C02

Given a spec with glob pattern "src/cli/**" in exclude_paths
When the fitness compiler processes the glob
Then all files under src/cli/ are excluded from that fitness function's evaluation
```

**Personas**: DEV, ARCH
**FRs**: FR-03

---

### S-INIT-05: Rule Enable/Disable
**As** ARCH, **I want** to disable specific fitness functions in the spec with `enabled: false` and an optional reason, **so that** I can ship a preset with all rules defined but selectively activate them for the project.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given a spec where FF-S03 has enabled: false
When the fitness compiler processes the spec
Then FF-S03 is skipped during evaluation
And the evaluation report lists FF-S03 as "disabled" with its reason

Given a spec where a fitness function has no enabled field
When the fitness compiler processes it
Then it defaults to enabled: true (backward compatible with v1.0 specs)
```

**Personas**: ARCH
**FRs**: FR-04

---

### S-INIT-06: Spec Validation
**As** DEV, **I want** to validate my `firewall.spec.yaml` before running an evaluation, **so that** I catch configuration errors early instead of getting cryptic pipeline failures.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given a spec referencing a layer directory that doesn't exist in the project
When I run firewall validate --spec firewall.spec.yaml
Then the validator reports "Layer directory 'src/domain/' not found" as an error

Given a spec with duplicate fitness function IDs
When validation runs
Then it reports "Duplicate fitness function ID: FF-C02" as an error

Given a spec with an invalid exclude_paths glob pattern
When validation runs
Then it reports the invalid pattern with a clear error message

Given a valid spec with no issues
When validation runs
Then it reports "Spec valid: 12 fitness functions, 3 layers, 0 errors"
```

**Personas**: DEV, ARCH
**FRs**: FR-14

---

### S-INIT-07: Baseline Snapshot Creation
**As** DEV, **I want** to snapshot existing violations after the first evaluation so they become a baseline that doesn't block CI, **so that** I can adopt the firewall on a brownfield project without fixing everything first.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given a first evaluation that finds 15 violations
When I run firewall baseline --spec firewall.spec.yaml --project .
Then a baseline_violations.json is created containing all 15 violations
And each violation is keyed by rule ID + file path + violation signature

Given a baseline exists and a subsequent evaluation finds 17 violations
When the evaluation runs with --baseline baseline.json
Then 15 violations are marked as "baseline" (informational, don't fail CI)
And 2 violations are marked as "new" (fail CI)
```

**Personas**: DEV, LEAD
**FRs**: FR-09

---

### S-INIT-08: Baseline Integration in Skill Flow
**As** ARCH, **I want** the Claude Code skill to automatically create a baseline after the first evaluation during init, **so that** the brownfield adoption flow is seamless — no extra manual step.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given the skill has generated a spec and run the first evaluation
When the evaluation completes with violations
Then the skill automatically creates baseline_violations.json
And reports: "Baseline created with N existing violations. Future new violations will block CI."
And asks if the user wants to review or adjust the baseline
```

**Personas**: ARCH, DEV
**FRs**: FR-01, FR-09

---

### S-INIT-09: First Evaluation in Skill Flow
**As** DEV, **I want** the skill to run the first evaluation immediately after generating the spec, **so that** I see results without running a separate command.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given the skill has generated and validated a firewall.spec.yaml
When the user approves the spec
Then the skill runs firewall evaluate --spec firewall.spec.yaml --project . --format json
And presents the evaluation results (AHS score, violation count, top violations)
And offers to generate an HTML report (FR-15)
```

**Personas**: DEV, ARCH
**FRs**: FR-01

---

### S-INIT-10: APG Mining Queries
**As** ARCH, **I want** the skill to mine the APG using targeted Cypher queries that extract structural signals (directory patterns, dependency matrix, naming conventions, DI ratio), **so that** classification is based on graph facts, not raw code.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given an APG has been built from a TypeScript project
When the skill executes mining queries
Then it produces a structured summary containing:
  - Directory-to-layer naming signals
  - Dependency matrix (layer-to-layer import counts)
  - Naming pattern counts (I*Repository, *UseCase, *Controller)
  - Constructor injection ratio
  - Anomalies (cases breaking majority patterns)
And the summary is under 500 tokens of structured facts
```

**Personas**: ARCH
**FRs**: FR-01

## Epic: E-DASH — Interactive Demo Dashboard

### S-DASH-01: Dashboard Layout and Header
**As** ARCH (demo presenter), **I want** an interactive HTML report with a professional header showing the product name, project name, evaluation timestamp, and spec version, **so that** the dashboard is presentable to stakeholders.

**Acceptance Criteria (Checklist)**:
- [ ] HTML file opens directly in browser via `open report.html` (no server needed)
- [ ] Header displays: "Architectonic Firewall" product name, target project name, evaluation date/time, spec file name
- [ ] Page uses Tailwind CSS for clean, professional styling
- [ ] All data is embedded as inline JSON (self-contained, no external fetch)
- [ ] Page is responsive (works on projector/large screens for demos)

**Personas**: ARCH
**FRs**: FR-15

---

### S-DASH-02: Data Visualizations (AHS Score, Architecture Graph, Fitness Cards)
**As** ARCH (demo presenter), **I want** the dashboard to show an AHS score gauge with dimension breakdown, a Cytoscape.js architecture graph with layer-colored nodes and violation-highlighted edges, and a grid of fitness function cards showing pass/fail status, **so that** I can visually walk through the architectural health of a project.

**Acceptance Criteria (Checklist)**:
- [ ] AHS score displayed as a large number with gauge/progress visualization
- [ ] Dimension breakdown shows individual scores (structural, coupling, dependency-direction, convention, etc.)
- [ ] Architecture graph renders using Cytoscape.js with dagre hierarchical layout
- [ ] Graph nodes are colored by architectural layer (domain = green, application = blue, infrastructure = orange, etc.)
- [ ] Graph edges show dependencies; violation edges are highlighted in red
- [ ] Nodes are clickable (shows component details on click)
- [ ] Fitness function cards show: name, dimension, pass/fail badge, score vs threshold, severity
- [ ] Cards are visually grouped by dimension

**Personas**: ARCH, LEAD
**FRs**: FR-15

---

### S-DASH-03: Interactive Features (Violations Explorer, Filtering, Baseline Split)
**As** DEV, **I want** the dashboard to have a filterable violations table and a baseline-vs-new split view, **so that** I can find the violations I need to fix and understand which are pre-existing vs newly introduced.

**Acceptance Criteria (Checklist)**:
- [ ] Violations table displays: file path, rule ID, rule name, severity, dimension, human-readable description, suggested fix
- [ ] Table is sortable by any column (click column header)
- [ ] Filters available: by severity (critical/major/minor/info), by dimension, by layer, by baseline status
- [ ] Baseline vs New section shows clear visual split (e.g., two panels or toggle)
- [ ] Baseline violations styled differently (muted/grayed) from new violations (bold/red)
- [ ] Summary stats shown: total files, total components, layers detected, compliance %, evaluation mode (symbolic/neuronal/hybrid)
- [ ] Violation messages include What/Where/Why/Fix per FR-07 format

**Personas**: DEV, ARCH, LEAD
**FRs**: FR-07, FR-15

---

### S-DASH-04: Report Generator CLI Command
**As** DEV, **I want** a `firewall report` CLI command that takes evaluation results and produces a self-contained HTML file, **so that** I can generate reports without the skill.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given evaluation results in JSON format
When I run firewall report --spec firewall.spec.yaml --project . -o report.html
Then a single self-contained HTML file is created at report.html
And the file embeds the evaluation JSON as inline data
And the file includes Tailwind CSS and Cytoscape.js via CDN references
And the file renders correctly when opened with a browser

Given evaluation results with a baseline
When I generate a report with --baseline baseline.json
Then the report includes the baseline-vs-new split view
And baseline violations are marked accordingly
```

**Personas**: DEV, ARCH
**FRs**: FR-15

---

### S-DASH-05: Actionable Violation Message Format
**As** DEV, **I want** every violation to include What (rule ID + name), Where (file + line number), Why (human-readable explanation), and Fix (suggested action), **so that** I know exactly what to do without reading documentation.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given an evaluation that detects a dependency-direction violation
When the violation is reported (CLI or dashboard)
Then the message includes:
  - What: "[major] FF-S01 — dependency-direction"
  - Where: "src/domain/UserService.ts:42"
  - Why: "Domain layer file imports from infrastructure layer, violating dependency direction rule"
  - Fix: "Move the infrastructure dependency behind an interface in the domain layer"

Given a violation with exclude_paths available
When the message is formatted
Then the Fix section also suggests: "Or add this path to exclude_paths for FF-S01"
```

**Personas**: DEV
**FRs**: FR-07

## Epic: E-LLM — Neuronal Evaluation Provider

### S-LLM-01: GeminiProvider Implementation
**As** ARCH, **I want** a `GeminiProvider` that implements the existing `LLMProvider` interface using the Google AI SDK, **so that** the neuronal evaluation path uses a real LLM instead of the mock.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given a valid GEMINI_API_KEY environment variable
When the pipeline initializes with provider: "gemini"
Then a GeminiProvider is instantiated with the API key
And it implements evaluate(), returning DomainResult<LLMResponse>
And it passes the same interface contract as MockLLMProvider

Given no GEMINI_API_KEY is set
When the pipeline initializes
Then it falls back to symbolic-only mode
And logs a warning: "No Gemini API key configured. Running symbolic-only evaluation."
```

**Personas**: ARCH, LEAD
**FRs**: FR-13

---

### S-LLM-02: Neuronal Results in Dashboard
**As** ARCH (demo presenter), **I want** the dashboard to display neuronal evaluation results alongside symbolic results, **so that** I can demonstrate the dual-path evaluation capability.

**Acceptance Criteria (Checklist)**:
- [ ] Fitness function cards show evaluation mode badge: "symbolic", "neuronal", or "hybrid"
- [ ] Neuronal fitness functions display the LLM's reasoning/judgment alongside the score
- [ ] Dashboard summary stats include: X symbolic functions, Y neuronal functions evaluated
- [ ] When neuronal evaluation was skipped (no API key), dashboard shows "Symbolic only — configure Gemini for neuronal evaluation"

**Personas**: ARCH, LEAD
**FRs**: FR-13, FR-15

---

### S-LLM-03: Gemini Model Configuration
**As** ARCH, **I want** to configure the Gemini model and parameters in the spec or environment, **so that** I can control cost and quality of neuronal evaluation.

**Acceptance Criteria (Gherkin)**:
```gherkin
Given a spec with llm_config.model: "gemini-2.0-flash"
When the GeminiProvider initializes
Then it uses the specified model for all neuronal evaluations

Given no model specified in spec or environment
When the GeminiProvider initializes
Then it defaults to "gemini-2.0-flash" (fast, cost-effective default)

Given a GEMINI_MODEL environment variable is set
When the provider initializes
Then the env var takes precedence over spec config
```

**Personas**: ARCH
**FRs**: FR-13
