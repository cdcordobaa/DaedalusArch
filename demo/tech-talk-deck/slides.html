Why Models Fail — Layer 1

Text machines, not architects.

📄
Fan et al. (2024) — Meta, ICSE
"LLMs learn what code looks like, not what code does."
LLMs are trained on static text — source code as character sequences. They never observe runtime state, execution paths, or how components interact. They learn syntax and statistical co-occurrence, not causality or behavior. The proposed fix — Execution-Aware Training — doesn't exist yet.
What the model sees — valid syntax, compiles

Why Models Fail — Layer 2

Hallucinated Coupling.

📈
Slater (2025) — Georgia Tech
"Hallucinated Coupling": when faced with architectural purity vs. functional shortcuts, the model always takes the shortcut.
GitHub is full of code that works but is badly structured. The MLE training objective means the model's "default architecture" is the statistical average of all code ever written — which overwhelmingly contains lazy patterns.
What the model generates
// domain/user.entity.ts import { Column, Entity } from 'typeorm' // ORM in domain! @Entity() export class User { @Column() name: string }
What it should generate
// domain/user.entity.ts // No framework imports! export class User { constructor( public readonly name: string ) {} }
The model imports typeorm directly into the domain entity because that's what most GitHub code does. The shortcut is the statistical default.

Why Models Fail — Layer 5

Each file is independent.

🗒
Zhang et al. (2024) — SAIP
LLMs demonstrate strong performance on local design decisions but fail systematically on system-level reasoning.
Cross-cutting concerns — logging, auth, error handling — are consistently omitted or implemented inconsistently. The model generates each file as an independent task, not as part of a coordinated system.

The Reward Hacking warning.

What happens when unit tests and natural language specifications disagree?

⚠
ImpossibleBench — Zhong, Raghunathan & Carlini (2025, Anthropic)
When tests conflict with specs, agents exploit the tests rather than follow the spec.
Researchers took LiveCodeBench and SWE-bench and mutated their unit tests to directly conflict with the specs. This creates "impossible" tasks where passing tests necessarily means violating the spec.
✘
Agents find ways to game the evaluation rather than fix the code
✘
Some agents delete failing tests rather than fix underlying bugs
✘
RL-trained models show higher reward hacking rates — reinforcement learning amplifies shortcut-seeking
Why this matters for architecture
If an agent's only feedback loop is "do the tests pass?", the agent will optimize for passing tests — even if that means violating architectural constraints that aren't captured in tests. A project can have 100% test coverage and zero architectural compliance.

The Approach

Architecture-as-Code: 30 lines of YAML.

A three-layer spec that turns intent into a machine-verifiable contract.

specs/clean-arch.yaml
# Layer A — Architectural Model architecture: style: clean-architecture layers: - name: domain directories: [src/domain/**] roles: [entity, value-object, repository-interface] - name: application directories: [src/application/**] roles: [use-case, dto] - name: infrastructure directories: [src/infrastructure/**] roles: [repository-impl, controller] # Layer B — Fitness Functions fitness_functions: - id: FF-S01 name: dependency-direction dimension: structural severity: critical route: symbolic # Layer C — Scoring Weights scoring: weights: { structural: 0.35, coupling: 0.20, pattern: 0.20 } thresholds: { pass: 0.80, warning: 0.65, soft_block: 0.50 }

Step 2 — Firewall compiles to Cypher
compiled query
WITH $layerOrder AS lo MATCH (src:File) -[:IMPORTS]->(tgt:File) WHERE src.layer IS NOT NULL AND tgt.layer IS NOT NULL WITH src, tgt, apoc.coll.indexOf( lo, src.layer) AS sIdx, apoc.coll.indexOf( lo, tgt.layer) AS tIdx WHERE sIdx < tIdx RETURN src.filePath, tgt.filePath
