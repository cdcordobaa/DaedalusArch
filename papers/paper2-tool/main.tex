\begin{abstract}
Architecture conformance checkers for TypeScript mostly express one kind of rule: a path pattern may not import
another path pattern. We present \tool{}, an architectural firewall that compiles a declarative
Architecture-as-Code (AaC) specification into Cypher fitness functions over an Architectural Property Graph (APG).
Besides module imports, the APG records constructor injection, barrel re-exports, inheritance, interface
implementation and calls, so one specification can state dependency direction together with dependency inversion,
repository and use-case patterns, domain-state purity, coupling metrics, SOLID proxies and conventions: 25
symbolic functions and 2 rubric-driven functions per style library. An isolated large-language-model (LLM) judge
assesses semantic intent and module integrity on a capped sample of units; all functions feed a seven-dimension
health score and a four-band verdict. The evaluation was pre-registered and every aggregate table is regenerated by
script. On 73 seeded violations at held-out sites in seven open-source projects, the symbolic path reaches recall
0.918 [0.818, 1.000]; all six misses are dynamic \texttt{import()} calls that the extractor does not model. After
two scorer defects were corrected (post hoc), no seeded finding is a false positive (precision 1.000); in the
post-hoc labelled reading, which keeps the registered matching rule and lets an LLM labeller judge the 13 findings
that the defects produced, precision is 0.957 [0.893, 1.000] and F1 0.937 [0.878, 0.986]. Precision on unseeded
real findings is much less certain: 0.328 to 0.789 depending on how uncertain labels are treated. On nine real
projects the judge marks 73 of 331 units as failing, yet under the registered aggregation and its 0.08 weight bound
it changes no verdict; replacing the judge model on 100 recorded units leaves every verdict unchanged
(agreement 0.94, $\kappa = 0.766$). On the rules both tools can express, \tool{} detects what \dc{} detects once a
translation defect is corrected; the contribution is the breadth of the rule language, the graph, the score and the
reproducible evaluation, not better layer detection. An exploratory pilot of a coding agent asked to review the
same trees against the same specification finds the clear-cut seeds but reproduces about a quarter of the
firewall's findings, varies between runs and costs minutes and credits per review. An internal audit regenerated
310 committed result files byte for byte, before the post-hoc corrections behind the SO4 tables reported here.
A v1.3 revision, measured only on a development set so far, adds a priori blocking and advisory tiers, fixes eleven
defects that the new measurements exposed, and reports graph fidelity as agreement with the TypeScript compiler
(Jaccard 0.988 on 72 generated projects, 0.913 on seven real ones, every disagreement explained); an independent
checker finds 0 incorrect findings among 2668 checkable ones, and a generic graph extension expresses 25 of 27
designer-planted architectural facts that the earlier graph cannot express at all (0 of 27). Rules remain Cypher
text; an in-process interpreter runs the same text and matches Neo4j on 65,254 real-graph statements and on 836,000
fuzzed statements with no mismatch. On rules that dependency-cruiser, eslint-plugin-boundaries and ArchUnitTS can
express, agreement is $\kappa = 1.000$ on the reference set and 0.913 to 1.000 on 29 open-source projects, with no
disagreement traced to our tool. On 15 human-written projects all 283 blocking findings are correct, and a negative
control rejects all 500 falsified ones. Verdicts are invariant in 637 of 655 semantics-preserving transformations.
We also report the limits: the development sets detect only 33\% of rule mutants, and two exploratory searches for
external validity (developer fixes and known groups) found no robust signal. A sealed hold-out run and human labels
are still pending.

\section{Introduction}\label{sec:intro}

Architecture erosion, the gradual divergence of an implemented system from its intended architecture, is a
long-standing concern \citeneeded{desilva2012erosion,rosik2011drift}. The usual remedy is static conformance checking:
an architect states the intended structure and a tool reports the code that departs from it
\citeneeded{murphy1995reflexion,knodel2007comparison,passos2010static}. In the TypeScript ecosystem the most widely
used checker of this kind is \dc{} \citeneeded{depcruise}, whose \texttt{forbidden} rules are regular expressions over
the source and target paths of module dependencies. Path rules capture layer direction, cycles and forbidden packages
well. They cannot state that an application service should depend on abstractions rather than concrete classes,
that a repository should implement a domain interface, or that a domain class should not hold infrastructure state
through an injected constructor parameter. These properties need symbol kinds, class roles and edges other than
\texttt{import}.

Two recent trends make the gap more pressing. Coding agents now produce large amounts of code from natural-language
requests, and spec-driven development proposes that a written specification, not a prompt history, should govern what
they produce \citeneeded{speckit2025,kiro2025}. A specification of architecture that a machine can check, and that
can be run on a change before it lands, fits that workflow: it is meant to act as a firewall rather than as a report
read weeks later. This paper evaluates the checker on existing code; it does not evaluate the gate inside an
agentic workflow, which is the subject of a separate study.
At the same time, some architectural properties (does this file carry responsibilities of a different layer? is an
invariant duplicated across a module?) resist a purely structural statement, which invites an LLM judge
\citeneeded{zheng2023judging}, with the known risks of non-determinism and bias
\citeneeded{wang2023fair,panickssery2024self}.

This paper presents \tool{}, a command-line architectural firewall for TypeScript, and an evaluation designed to be
checked by others. We make the following contributions:
\begin{enumerate}
  \item \textbf{A declarative AaC specification compiled to Cypher fitness functions} over a purpose-built APG with
        6 node labels and 9 relationship types, including \edge{CONSTRUCTOR\_INJECTS} and \edge{RE\_EXPORTS}
        (Section~\ref{sec:approach}). On our real projects constructor injection is common and barrel re-exports
        are rare (Section~\ref{sec:rq1}). % src: Docs/ADR.md, ADR-005 amendment (2026-10-08); results/apg-ablation/so2/graph_coverage.csv (edges_re_exports 5, 0, 2, 0; edges_constructor_injects 5, 309, 23, 23 on realworld, ghostfolio, truthy, dry-run)
  \item \textbf{A broader rule catalogue} than path-based checkers: 27 functions per style library (25 symbolic, 2
        neural) across structural, pattern, coupling, SOLID and convention dimensions, of which a rule-by-rule
        translation to \dc{} can express 6. % src: results/pre-tag/so1-metrics-53cfaed4a313.json (libraries: declared 27, withTemplate 27); src/fitness-compiler/cypher-templates.ts (25 symbolic templates); results/tool-comparison/depcruise/translation.json and ADR-030 item 2 (translated: FF-S01, S02, S03, S04, P01, C04)
  \item \textbf{An isolated LLM judge} for semantic intent and module integrity, run with no tools, a frozen rubric,
        an allow-listed configuration and recorded cassettes, and bounded in its effect on the score.
  \item \textbf{A health score and a verdict} (pass, warning, soft-block, hard-block) that aggregate symbolic and
        neural results across seven dimensions.
  \item \textbf{A pre-registered, reproducible evaluation}: seeded detection at held-out sites with twins, labelled
        real-code precision, the judge's effect on nine real projects and its robustness to the judge model, an APG
        ablation, a comparison with \dc{}, five real fix commits and an exploratory plain LLM-review baseline. An
        internal audit regenerated 310 committed result files byte for byte; it predates the post-hoc corrections
        of the SO4 tables (Section~\ref{sec:impl}).
        % src: Docs/DiagnosticRuns/reproduction-audit-2026-10-10.md, "Verdict counts (files)"; ADR-033, ADR-036, ADR-038 in Docs/ADR.md
  \item \textbf{A v1.3 revision with development-set evidence} (Section~\ref{sec:v13}): a priori rule tiers, graph
        fidelity reported as agreement with two other extractors, an independent correctness checker, an opt-in
        graph extension (APG v2) for facts no import graph holds, and eleven defects found and fixed with their
        effects attributed. All v1.3 figures are development-set figures; the hold-out run is pending.
  \item \textbf{Evidence about the evidence} (Sections~\ref{sec:v13-interp} to~\ref{sec:v13-null}): differential
        testing of a second Cypher engine against Neo4j, convergent agreement with three independent checkers,
        correctness on human-written code with a negative control, metamorphic invariance, a mutation analysis
        that measures how much the test oracle can detect, a replication package checked number by number, and
        two null results reported as such.
\end{enumerate}

We state the positioning plainly. On the rules both tools can express, \tool{} does not detect more than \dc{}:
the apparent advantage in our registered comparison disappears once a translation defect that favoured our tool is
corrected (Section~\ref{sec:rq5}). The contribution lies elsewhere: in what can be specified, how it is compiled and
scored, and how the claims about it are made checkable. The evidence that the broader rules are \emph{accurate} is
thinner than the evidence that they can be stated: seeds cover 4 of the 19 functions that \dc{} cannot express, and
real-code precision rests on 24 labelled findings (Sections~\ref{sec:rq2} and~\ref{sec:rq3}).

\section{Background and Related Work}\label{sec:related}

\paragraph{Architecture conformance checking.}
Reflexion models compare a hypothesised high-level model with a source model extracted from code and classify each
dependency as convergent, divergent or absent \citeneeded{murphy1995reflexion}; hierarchical variants scale the idea
\citeneeded{koschke2003hierarchical}. Comparative studies distinguish reflexion models, dependency rules and
component access rules \citeneeded{knodel2007comparison,passos2010static}. Dependency constraint languages such as
DCL state allowed and forbidden relations between modules of an object-oriented system, including relations other
than import, such as creation and inheritance \citeneeded{terra2009dcl}. ArchUnit expresses architecture rules for Java
as unit tests in a fluent Java API \citeneeded{archunit}. jQAssistant scans artefacts into a Neo4j graph and lets
users write constraints as Cypher queries \citeneeded{jqassistant}, which is the closest precedent for our compilation
target. Sonar's platform includes architecture and design rules \citeneeded{sonarqube}. For TypeScript, \dc{}
\citeneeded{depcruise} and eslint-plugin-boundaries \citeneeded{eslintboundaries} check path-pattern dependency rules.
\tool{} differs from these in three ways: the rules are not written as queries or code but declared in a
specification and compiled from templates; the graph carries TypeScript-specific edges (constructor injection,
per-name barrel re-exports, type-only flags); and results are aggregated into a score and verdict meant to gate a
change.

\paragraph{Fitness functions and architecture as code.}
Ford et al.\ define an architectural fitness function as an objective integrity assessment of some architectural
characteristic, and argue for running such functions continuously \citeneeded{ford2017evolutionary,ford2022evolutionary2}.
The clean-architecture rules of our presets follow Martin \citeneeded{martin2017clean}. We treat the AaC
specification as the single source from which fitness functions are generated, so that adding a style or adjusting
a threshold is a specification change, not a code change.

\paragraph{Code graphs for analysis and agents.}
Code property graphs merge syntax, control flow and data flow into one graph for vulnerability discovery
\citeneeded{yamaguchi2014cpg}. Recent work gives LLM agents a code graph to navigate: CodexGraph exposes a graph
database of a repository to an agent through queries \citeneeded{liu2024codexgraph}, and RepoGraph builds a
repository-level graph to retrieve context for software engineering tasks \citeneeded{ouyang2024repograph}. Our APG
is deliberately smaller than a code property graph: it keeps only what the fitness functions need, and the judge
reads a graph excerpt around each unit rather than the whole repository.

\paragraph{LLM as a judge.}
Using a strong LLM to grade outputs agrees reasonably with human preference in open-ended tasks, but is sensitive to
position, verbosity and self-preference \citeneeded{zheng2023judging,wang2023fair,panickssery2024self}. Neuro-symbolic
systems combine learned and symbolic components so that each covers the other's weaknesses
\citeneeded{garcez2023neurosymbolic}. In \tool{} the symbolic path is primary and deterministic; the judge covers
two properties the symbolic path cannot state, its weight is bounded, and its calls are recorded for replay.

\paragraph{Spec-driven development and pre-registration.}
Spec-driven development tools let a written specification drive agentic code generation
\citeneeded{speckit2025,kiro2025}. We know of no peer-reviewed evaluation of such tools at the architectural level.
Pre-registration, fixing hypotheses and analyses before data are seen, is established in other empirical sciences
\citeneeded{nosek2018prereg} and rare in tool papers; we use it to separate registered from post-hoc results.

\subsection{The AaC specification}\label{sec:spec}

A specification has three layers (ADR-004): an architectural model (style, ordered layers, directory globs and file
patterns per layer, roles), a list of fitness functions with dimension, severity, optional thresholds and exclusions,
and a scoring section with dimension weights and verdict thresholds. Listing~\ref{lst:spec} abbreviates the NestJS
preset. Three style libraries are shipped (clean architecture, layered, NestJS); each declares the same 27 function
identifiers, and every declared function has a Cypher template or a rubric. % src: results/pre-tag/so1-metrics-53cfaed4a313.json ("libraries": share 1 for all three styles)
A function whose template does not apply to the style or to the declared layer kinds is disabled with a recorded
reason rather than silently dropped.

\begin{lstlisting}[style=yaml,caption={Abbreviated NestJS preset (\texttt{presets/nestjs.yaml}).},label={lst:spec},float=t]

      directories: [src/domain/**, src/core/**, src/entities/**]

\subsection{The Architectural Property Graph}\label{sec:apg}

The extractor uses ts-morph over the project's own \texttt{tsconfig}. The APG has six node labels (File, Class,
Interface, Method, Function, Package) and nine relationship types (Table~\ref{tab:apg}).
% src: Docs/ADR.md, ADR-005 amendment; src/shared/types/enums.ts (NODE_TYPES, EDGE_TYPES)
Three choices matter for TypeScript. \edge{IMPORTS} edges are merged per file pair and carry the specifiers, lines,
imported names and a type-only flag; external modules end at a Package node named by its specifier, so package rules
never depend on how a package resolves on disk. \edge{RE\_EXPORTS} resolves barrel files per exported name, and the
dependency and cycle queries traverse \edge{IMPORTS|RE\_EXPORTS}, so a dependency routed through an
\texttt{index.ts} is not lost; coupling metrics stay on \edge{IMPORTS} only. \edge{CONSTRUCTOR\_INJECTS} records
the resolved type of each constructor parameter, which is how collaborators arrive in NestJS and Angular code.
Layers and roles are annotated on nodes at ingestion from the specification's globs.

\subsection{Compilation to fitness functions}\label{sec:compile}

Each symbolic function is a parameterised Cypher \citeneeded{francis2018cypher} template (ADR-006); the compiler binds parameters from the
specification (layer order, layer names by kind, thresholds, forbidden packages), injects \texttt{exclude\_paths} at a
marked anchor, checks that every required parameter is bound, and disables a function whose template does not apply.
Every query is ordered, so the same graph gives the same rows. Listing~\ref{lst:cypher} shows two templates. The
first is an ordinary direction rule over imports and re-exports. The second, domain-state purity, has no
path-pattern equivalent: it reads injected constructor parameters and field stores.

\begin{lstlisting}[style=cypher,caption={Two compiled templates (abridged from \texttt{src/fitness-compiler/cypher-templates.ts}).},label={lst:cypher},float=t]
// FF-S01 dependency-direction
MATCH (src:File)-[i:IMPORTS|RE_EXPORTS]->(tgt:File)
WHERE src.layer IS NOT NULL AND tgt.layer IS NOT NULL AND src.layer <> tgt.layer
WITH src, tgt, i, apoc.coll.indexOf($layerOrder, src.layer) AS s,
                  apoc.coll.indexOf($layerOrder, tgt.layer) AS t
WHERE s >= 0 AND t >= 0 AND s < t /*EXCLUDE:src*/
RETURN src.filePath AS source, tgt.filePath AS target, type(i) AS relType, i.line AS line

// FF-P06 domain-state-purity
MATCH (c:Class)-[e:FLOWS_TO|CONSTRUCTOR_INJECTS]->(t)
WHERE c.layer = $domainLayer AND t.layer = $infraLayer AND (t:Class OR t:Interface) /*EXCLUDE:c*/
RETURN c.filePath AS filePath, c.name AS class, t.name AS targetName, type(e) AS relType
\end{lstlisting}

Each result row becomes a violation with a stable key (function, file, target, discriminator), a message and
evidence columns. The key excludes line numbers, which makes baseline comparison robust to unrelated edits.

\subsection{The isolated judge}\label{sec:judge}

Two functions are neural: \ff{FF-N01} (architectural integrity) and \ff{FF-N02} (intent alignment). Each carries a
rule, a pass and fail rubric and an evidence requirement in the specification (Listing~\ref{lst:spec}). A selector
draws judge units (files, classes or modules) round-robin across layers up to a cap of 20 units per function and
project; the context assembler gives the judge the unit's source and an excerpt of the APG around it.
% src: Docs/judge-preregistration.md (degradation ladder: "E7 unitCap 20"); src/llm-critic/judge-unit-selector.ts; src/llm-critic/judge-graph.ts
The judge is a pinned Claude model (\texttt{claude-opus-5-5}) invoked through the Claude Code CLI at a pinned
version, with effort fixed before the first measured run. % src: Docs/judge-preregistration.md, "Instrument" table (model claude-opus-5-5, effort high, PINNED_CLI_VERSION 2.1.294)
\todo{decide whether to name the labeller model identifier in the text; it is recorded in the labels ledger.}
Isolation is enforced, not assumed: a dedicated configuration directory with an allow-list, a frozen argument vector
with all tools disabled, structured output only, a per-run probe that the resolved model equals the pinned one, and
auto-update disabled (ADR-018). The rubric text is frozen and its hash is asserted by a unit test. Each unit is judged
three times and decided by majority. Every call is recorded in a cassette, so any judged run can be replayed with no
model call. A function fails under the registered rule \texttt{majority-of-valid-units-v1} when strictly more than
half of its valid units fail. % src: Docs/analysis-plan.md §12.1
In full mode, the router runs all symbolic queries first; the judge never overrides a symbolic result.

\subsection{Scoring and verdict}\label{sec:scoring}

For each dimension $d$, the Architectural Violation Ratio $\mathrm{AVR}_d$ is the confidence-weighted share of its
executed functions that fail; disabled functions leave the denominator. The Architectural Health Score is
\begin{equation}
  \mathrm{AHS} = \sum_d w_d \, (1 - \mathrm{AVR}_d), \qquad \textstyle\sum_d w_d = 1,
\end{equation}
with weights renormalised over executed dimensions (ADR-007). $\mathrm{AHS}_{\mathrm{det}}$ uses the five symbolic
dimensions; $\mathrm{AHS}_{\mathrm{comb}}$ adds the semantic and integrity dimensions with the full-mode weights.
The verdict is pass at $\geq 0.80$, warning at $\geq 0.65$, soft-block at $\geq 0.50$ and hard-block below.
% src: presets/nestjs.yaml (scoring.thresholds, full_mode_weights)
In every registered specification the two judge dimensions weigh $W_n = 0.08$ in total, so the judge's verdicts can
lower $\mathrm{AHS}_{\mathrm{comb}}$ by at most 0.08 relative to its judge-blind value (the same score with both
judge dimensions clean) and cannot raise it above that value.
% src: Docs/ADR.md, ADR-028 "Review fixes (2026-10-10, prereg v15)"
The judge-blind value itself is not the rules-only score: adding two dimensions that do not fail raises the score
above $\mathrm{AHS}_{\mathrm{det}}$ (a dilution effect). This bound and this dilution are design decisions with
consequences that Section~\ref{sec:rq4} measures. The verdict thresholds and dimension weights are the presets'
defaults; they have not been calibrated against architects' judgements.

\section{Implementation and Reproducibility}\label{sec:impl}

\tool{} is written in TypeScript (Node.js), with ts-morph for extraction and Neo4j with APOC for the graph; each
evaluation builds a fresh graph (ADR-010). The source has about 22\,000 lines in \texttt{src/}, organised into the
modules of Figure~\ref{fig:pipeline} (spec parser, APG extractor, ingestion, fitness compiler, evaluation engine,
router, LLM critic, scoring engine, report). % src: derived, `find src -name '*.ts' | xargs cat | wc -l` at v1.2e (8fbe079e) gives 22 433 lines (count it again before submission)
The command-line interface supports symbolic-only, neural-only and full modes; reports validate against a JSON
schema.

Reproducibility rests on five mechanisms.
(i) \emph{Pre-registration with a hash gate}: a registry (\texttt{corpus/prereg.json}) lists the registered
artefacts (analysis plan, matching rule, threats register, plans, specifications, translator) with their hashes; every
experiment plan is checked against it before a run, and every run record stores the version it ran under.
(ii) \emph{Run records}: each run stores the tool commit, the environment fingerprint, the specification hash and the
cassette mode.
(iii) \emph{Cassettes}: judge and labeller calls are recorded and replayed; replay mode uses a provider that rejects
every live call.
(iv) \emph{Scripted aggregation}: every committed table is written by a script from run records, reports, labels and
cassettes, never by hand.
(v) \emph{Explicit post-hoc labelling}: every change after results were seen has a dated ADR marked POST-HOC, and
the earlier result is kept beside the new one.

\section{Evaluation Design}\label{sec:design}

\subsection{Research questions}

\begin{description}
  \item[RQ1] \emph{Coverage and latency.} What does the specification compile to on real projects, how long does an
        evaluation take, and what do the non-import edges contribute?
  \item[RQ2] \emph{Seeded detection.} How well does the symbolic path detect violations seeded into held-out projects?
  \item[RQ3] \emph{Real-code precision.} What share of findings on unseeded real code are true violations?
  \item[RQ4] \emph{Judge contribution.} What does the judge find on real projects, and does it change scores or verdicts?
  \item[RQ5] \emph{Comparison.} How does \tool{} compare with \dc{} on the rules both can express, and on real fixes?
\end{description}

\subsection{Seeding}

Ground truth is produced by mutation operators applied to copies of each project (ADR-008), in the spirit of
mutation testing \citeneeded{jia2011mutation}. The frozen operator catalogue covers import direction (MO-S01),
layer skip (MO-S03), forbidden packages (MO-P01), orphan files (MO-C04), SRP and ISP thresholds (MO-SO01, MO-SO02),
class renames that break naming (MO-CV02), domain fields holding infrastructure objects (MO-DF01), and dynamic
\texttt{import()} of an infrastructure module (MO-X01), which is declared outside the extractor's coverage before
any run. % src: Docs/operator-catalogue.md, operator table
Every operator has a \emph{twin}: a near-identical edit that should not raise a violation (for example, an
infrastructure file importing the same package). Each operator is applied at $k = 2$ sites per project; a copy must
type-check, and copies that fail preconditions are rejected and counted. The registered held-out total is 85 golden
seeds; 73 are scored after rejections and two not-applicable rows, below the registered floor of 80.
% src: results/so4-heldout/agg/golden_instances.csv (n_registered 85, n_scored 73, floor 80, shortfall 7)
Two judge-probe operators (MO-X02, MO-X03) produced no scored instance because they found no site: on six projects
there was no candidate site at all, and on nestjslatam every candidate was refused by the operator's
\texttt{not-removable-guard} precondition. No seeded copy was produced, so the judge has no seeded ground truth.
% src: results/so4-heldout/agg/seed_coverage.csv (MO-X02 and MO-X03: 7 rows each, stage mutate, reason no-site; candidates 0 on six projects; nestjslatam__ddd candidates 112 and 7, all not-removable-guard)

\subsection{Matching}

Scoring is differential (\texttt{Docs/matching-rule.md}). The new violations of a seeded copy are the multiset
difference of violation keys between the copy and its unseeded base (MAT-03). A seed is a true positive when a new
violation of one of its expected functions has an expected key (MAT-04); each seed counts once (MAT-05). New
violations that are neither detections nor declared collateral are strict false positives (MAT-09); a labeller may
reclassify them as true violations that the seed exposed, giving FP-labelled (MAT-10). A twin that raises any new
undeclared violation has fired (MAT-17). Lines never enter the key (MAT-02).

\subsection{Metrics and intervals}

Precision, recall and F1 follow MAT-11. Because the two copies of one operator on one base are not independent, the
interval unit is the (project, operator) cell: with ten or more cells, a percentile bootstrap over cells (10\,000
resamples) is primary; a Wilson \citeneeded{wilson1927} or Clopper-Pearson \citeneeded{clopper1934} interval on
instances is reported only as the ``if independent'' bound. % src: Docs/analysis-plan.md §5
When every cell is perfect the bootstrap degenerates to a zero-width interval; we then quote the Clopper-Pearson
bound instead (ADR-033). Baseline precision on real code is a Horvitz-Thompson ratio \citeneeded{horvitz1952} over a
stratified sample with Wilson intervals on the Kish effective size \citeneeded{kish1965}. Labels come from an LLM
labeller of a different model family from the judge (a Gemini model through a separate CLI), run twice per item.
Unlike the judge's CLI, the labeller's CLI (agy 1.3.2) cannot deny its web-search tool; a post-hoc check found that
no recorded labeller call completed a tool step, and calls that do are treated as invalid (ADR-034).
% src: git log, commit 56e77f66 message ("live agy labeller cassettes ... agy 1.3.2"); Docs/labeller-route.md; Docs/ADR.md ADR-034 (title: "agy 1.3.2 cannot deny search_web, so any call that completes a tool step is invalid"; item 6)

\paragraph{Limitation: FLOWS\_TO.}
The \edge{FLOWS\_TO} edge, intended to capture a domain class holding infrastructure state through a field, is empty
on every real project. Its definition is narrow (a field initialised with \texttt{new T()} or assigned outside the
constructor), and in dependency-injected code collaborators arrive through the constructor instead. The measured
field stores were 2 (realworld), 23 (ghostfolio), 3 (truthy) and 3 (dry-run); every one was skipped because its
target was not an extracted class or was a union type, so no edge resulted. % src: results/apg-ablation/so2/flows_to_stores.csv
On the fixtures the extractor produces exactly the predicted edges. We therefore report data flow as bounded to
field-store patterns, validated on fixtures and near-empty on DI-style code (ADR-023); domain-state purity on real
code rests on \edge{CONSTRUCTOR\_INJECTS} and \edge{IMPORTS}, not on \edge{FLOWS\_TO}.

\subsection{Robustness of the judge to its model}\label{sec:robust}

One threat to any LLM judge is that its verdicts reflect the particular model rather than the rubric and the code.
A separate check, registered before any call (ADR-038), replayed 100 recorded judge units through the same pinned
route with only the model changed, from the frozen \texttt{claude-opus-5-5} to \texttt{claude-sonnet-5-5}. The
units were drawn by a registered seed from four strata (E7 and E1, by judge function), 25 each, in 41 reports; each
unit was judged three times as before, 300 calls in all, with no invalid run.
% src: Docs/ADR.md ADR-038 Decision items 1-3; results/judge-robustness/summary.json (units 100, calls 300, invalidRuns 0, reportsAffected 41)
The two models agreed on 94 of the 100 unit verdicts (agreement 0.94, Wilson [0.875, 0.972]; Cohen's
$\kappa = 0.766$ [0.565, 0.926]; Gwet's AC1 0.931). The point estimate of $\kappa$ clears the pre-declared floor of
0.60, which the registration reads as ``the unit verdicts are robust to the judge model''.
% src: results/judge-robustness/agreement.csv (row all, primary: agreement 0.940000, ci 0.875232-0.972214, kappa 0.766355, kappa ci 0.565170-0.925651, ac1 0.931232); results/judge-robustness/summary.json (interpretation "model-robust (kappa >= 0.60)", kappaFloor 0.6)
All six disagreements go one way: Opus failed the unit and Sonnet passed it, so Opus failed 18 units and Sonnet
12; the frozen judge is slightly stricter, although the two fail rates' intervals overlap. Agreement was perfect on
the E1 strata and lower on E7 intent alignment ($\kappa = 0.43$ on 25 units). Substituting the Sonnet votes into the
41 reports changed no function verdict and no project or cell verdict, under the registered rule and under the
any-fail rule.
% src: results/judge-robustness/transition.csv (opus fail -> sonnet pass 6; pass -> fail 0); results/judge-robustness/fail-rates.csv (opus 18/100 [0.117, 0.267], sonnet 12/100 [0.070, 0.198]); results/judge-robustness/agreement.csv (E1 rows 1.000; E7:FF-N02 kappa 0.431818); results/judge-robustness/summary.json (functionVerdictChanges 0, registeredVerdictChanges 0, anyFailVerdictChanges 0)
This is a reliability result, not a validity one: two models of the same vendor agreeing does not show that either
is right, and with about 18\% failing units $\kappa$ is unstable, which is why AC1 is reported beside it. It does
answer the narrower question of whether the judge's (null) effect on verdicts is an accident of the model chosen.

\subsection{Why not just ask an LLM? An exploratory pilot}\label{sec:llmreview}

A reader may ask why a firewall is needed when a coding agent can simply be asked to review the code against the
architecture. A small pilot, registered before any review call and labelled \emph{exploratory} throughout (no
hypothesis test, no claim beyond its trees), gives a first answer (ADR-036). A confined Codex CLI agent
(\texttt{gpt-5.6-terra}, reasoning effort medium, read-only sandbox, no network) received the project's
specification rendered as prose, one sentence per listed rule, and returned the violations it found as
(rule, file, reason) records. The trees were five seeded copies (one each of MO-S01, MO-P01, MO-C04, MO-SO01 and
MO-CV02, on five bases, drawn by a registered seed), their five unseeded baselines, and the before and after trees
of two real fix pairs (p4 and p5). The answers were scored with the same differential keys as RQ2 and RQ5.
% src: Docs/ADR.md ADR-036 Decision items 1-3, 6, 7; Docs/DiagnosticRuns/llm-review-pilot-2026-10-11.md header
A registered credit budget stopped the run early: 25 of the 42 planned reviews ran (one run of every tree, a second
run of 11 trees).
% src: Docs/DiagnosticRuns/llm-review-pilot-2026-10-11.md "Execution and the budget stop" (25 of 42 valid; budget stop 150 credits)

\paragraph{Seeds.} The agent detected the seed in 9 of the 10 seed-runs (Wilson [0.60, 0.98] if the runs were
independent, which they are not), and every one of the five seeds in at least one run; \tool{} matched all five in
SO4. % src: Docs/DiagnosticRuns/llm-review-pilot-2026-10-11.md "Seeds" (9/10 = 0.90, Wilson 0.60-0.98 "if independent"; firewall matched 5/5); results/llm-review/seeds.csv, results/llm-review/recall.csv
On five clear-cut seeds, then, a plain LLM review does about as well as the firewall.

\paragraph{Consistency.} Over the 11 trees with two runs, the mean pairwise Jaccard similarity of the two runs'
(rule, file) sets was 0.727. On the ten small seeded and baseline trees it was 0.799 (range 0.54 to 0.94); on the
largest tree (p4 before the fix, 726 files) it was 0: the two runs listed 28 and 2 findings with none in common.
% src: Docs/DiagnosticRuns/llm-review-pilot-2026-10-11.md "Consistency" (0.727 over 11 trees; 0.799, range 0.54-0.94; p4-before 0.000; 28 and 2 findings); results/llm-review/consistency.csv (the summary.json mean 0.571 is a declared scorer defect that averages one-run trees as 0)
The agent flagged both real fixes in their single run pair, but on p4 an unchanged tree reviewed twice also
``resolves'' a finding in one of two run pairs, so one run cannot tell a fix from run-to-run variation.

\subsection{What v1.3 changes}\label{sec:v13-changes}

\begin{itemize}
  \item \textbf{A priori rule tiers.} Before any v1.3 labelling or precision measurement, each rule was assigned to a
        \emph{blocking} tier (a defining constraint of the style, checked as a structural fact) or an
        \emph{advisory} tier (metric thresholds, principle proxies, conventions, guidelines). Only blocking rules can
        fail a v1.3 verdict, and the judge functions are reported but do not block. v1.3 scores are therefore not
        comparable with the v1.2E scores above. % src: Docs/v1.3/rule-tiers.md ("Committed 2026-10-14, before any v1.3 labelling"; Principle; "Consequence")

        to the declaring file, and each template reads a declared \emph{edge view} chosen before re-measurement;

\subsection{One rule text, two engines}\label{sec:v13-interp}

% Provenance for the subsections from sec:v13-interp to sec:v13-null: paths without a branch prefix are on origin/v1.3. A path written
% "git show <sha>:<path>" is on the head branch of a pull request that is not merged into v1.3 (pinned to the branch
% tip on 2026-10-16; see the header note); the PR number is given. Reports from #190, #168, #185 and #215, which have since
% merged, are cited by their v1.3 paths. Figures marked \explor{} come from human-written

% estimates either.
A rule in \tool{} is its Cypher text, and v1.3 keeps it that way: an in-process, read-only Cypher interpreter runs
the same compiled string that Neo4j would receive, so the tool can run without a database server and no rule is
rewritten in TypeScript. Neo4j stays the reference engine for every reported number.

\subsection{How strong is the test oracle? Rule mutation}\label{sec:v13-mutation}

The figures above test the tool against the reference set. We also asked the reverse question: if a rule's Cypher

operators applied in memory to the 22 scored rules give 290 mutants, of which 273 can be measured on the
interpreter. The two development sets detect a change in an expected finding for 90 of the 273 (33\%), or 130
(48\%) when changes that only add or remove false positives on clean and near-miss cases are counted.

\section{Discussion}\label{sec:discussion}

\paragraph{Where the value lies.}
On import rules, a mature path checker already does the job, faster and with dynamic imports covered. The value of
compiling a specification to graph queries lies in the rules beyond imports: a single specification states layer
direction, inversion, roles, purity, metrics and conventions, and the graph carries the TypeScript facts those rules
need (injection, barrels, type-only imports). For an agentic workflow, the specification could also give the agent
and the checker one shared description of the architecture, and the verdict a gate that can block a change; we have
not evaluated that use here. The price of this breadth is a specification: the corpus specifications have a median
of 299 content lines, against one line per rule for a path checker. % src: results/pre-tag/so1-metrics-53cfaed4a313.json (contentLines median 299)

\paragraph{Why not just ask an LLM?}
The exploratory pilot of Section~\ref{sec:llmreview} suggests that a coding agent given the same specification in
prose finds clear-cut seeded violations about as often as the firewall, but it lists about a quarter of the
firewall's findings, its answers on a large tree change between runs, and each review costs minutes and credits.
These are the properties a gate needs most: the same answer for the same code, coverage of every mapped file, and a
cost low enough to run on every change. The two are not exclusive; the firewall's judge is itself an LLM, confined
to a sample of units and bounded in weight.

\paragraph{Breadth costs precision.}
The broad rules are where real-code precision is least known. In our labelled sample the weakest rule is test
pairing (\ff{FF-CV05}), which holds about half of the sampling weight and is the largest single source of false or
uncertain labels, while the few dependency-inversion items were all labelled true. The baseline precision range
(0.33 to 0.79) reflects this concentration as much as the breadth itself. A firewall that blocks on such findings
would frustrate users; the score's per-dimension weights and the four-band verdict exist to absorb noise, but the
thresholds and weights are uncalibrated defaults and we have not validated that the bands match an architect's
judgement. Seven of the nine real projects are soft- or hard-blocked and none passes, which a team adopting the
gate would have to accept or tune. % src: results/e7-corpus/agg-proportional/ahs_by_aggregation.csv (verdict_registered: 1 warning, 3 soft-block, 5 hard-block, 0 pass)

\paragraph{The judge.}
Under the registered weight the judge cannot change a verdict, and its unit verdicts barely depend on which of two
models runs it. Neither fact says the verdicts are right. Two readings are possible. Either the judge's role is
diagnostic (explaining and expanding symbolic findings), in which case the weight bound is appropriate; or it should
be able to block on semantic grounds, in which case its weight must rise, and only after its verdicts have been
validated against human labels. We registered the second reading as a sensitivity analysis for the next experiment
rather than adopting it, and the dilution effect it exposes (Section~\ref{sec:rq4}) must be fixed first.

\paragraph{Pre-registration in a tool paper.}
Pre-registration did not prevent post-hoc changes; it made them visible. Every number above that was produced after
seeing an earlier result sits beside that earlier result. The reproduction audit then caught a table that mixed two
rule versions, which a reader could not have detected from the paper alone.

\paragraph{Lessons for tool builders.}
(1) A translation-based comparison is fairer than hand-written baselines, but the translator is itself a source of
error, in our case one that favoured our own tool. (2) Seeded twins catch scorer defects as well as detector
defects. (3) Narrow edge definitions validated on fixtures may be empty on real code; measure the edge counts on real
projects before relying on them.

\section{Threats to Validity}\label{sec:threats}

\paragraph{Circularity.}
The rules, the mutation operators, the expected keys and the matching rule were written by the same team. Seeded
recall therefore measures whether the tool detects the constructs its authors anticipated, not real violations. We
mitigate this with held-out projects, twins, a tier of projects unseen during development, labelled real findings
(RQ3), an external tool on the same seeds (RQ5) and real fix commits, but the real-code evidence is small (24 labelled
findings, five fix pairs).

\paragraph{A NestJS-heavy corpus.}
Most projects are NestJS back ends or follow its conventions; 52 of 73 scored seeds come from NestJS-style
specifications, and only one project (7 seeds) is evaluated with the layered specification style. By the corpus's
own style attribute two projects are layered (19 seeds): nestjs-active-record is recorded as layered in the corpus
but received a NestJS specification from the registered rule. % src: results/so4-heldout/agg/golden_instances.csv (spec_style rows: nestjs 52, clean-architecture 14, layered 7; corpus_style rows: layered 19, nestjs 40, clean-architecture 14)
Results may not transfer to front-end code, monorepos with many packages, or other frameworks. The latency gate
covers one project of 241 files, so latency on much larger code bases is not shown.

\paragraph{Single-model labeller.}
All labels come from one LLM labeller run twice; run-to-run agreement is a reliability check, not a validity check.
The planned author audit of the labels has not been done. The baseline precision, the FP-labelled reclassification of
10 strict false positives, and therefore the labelled precision of 0.957, all depend on this labeller.

\paragraph{Post-hoc changes.}
The corrected SO4 reading (matching rule 1.2.0 and the style guard), the labelled SO4 reading (ADR-033), the
instrument v2 role exemptions, the
proportional and judge-weighted readings on E7, the \texttt{dts} comparison variant and the alternative treatments of
uncertain labels were all decided after earlier results were seen. Each is dated in an ADR and reported beside the
registered result. The golden N of 73 is below the registered floor of 80.
% src: Docs/ADR.md, ADR-025, ADR-026, ADR-028, ADR-030 results, ADR-033

\paragraph{The judge weight bound.}
With $W_n = 0.08$, the judge cannot move any verdict whose judge-blind score is more than 0.08 above a threshold, and
under the registered aggregation it moved none. The finding ``the judge changed no verdict'' is thus largely a
consequence of the registered configuration, not a measured property of the judge's discrimination. The
judge-weighted reading shows that the conclusion reverses with a larger weight. The judge-robustness check
(Section~\ref{sec:robust}) uses one alternative model of the same vendor on a sample of 100 units.

\paragraph{Specification validity.}
The E7 specifications were generated mechanically, declared floor-motivated, and never reviewed by an architect;
at least one mapping places an application directory in the domain layer. Every layer-dependent result on E7
(direction, purity, and the judge's intent-alignment rubric, which reads the declared layer role) is measured
against a specification whose validity we have not assessed.

\paragraph{Extractor gaps on real code.}
Dynamic imports occur in two real projects, ghostfolio's aliased library imports are treated as external, layer
coverage is as low as 55\%, and the cycle query is capped at 100 rows (Section~\ref{sec:rq1}). Real-code recall is
bounded by these gaps, which the seeded recall does not show.

\paragraph{Sample composition and development exposure.}
One function (test pairing) carries about half of the RQ3 sampling weight, and three of the nine projects
contribute no labelled item. The four core projects were used to build the tool and also host the ablation, the
latency gate and most seeds; this is an internal-validity threat, not only a corpus property.

\paragraph{Labeller and audit.}
The labeller's CLI cannot deny its web-search tool; no recorded call used it, but the isolation claimed for the
judge does not hold for the labeller as configured (ADR-034). The reproduction audit is internal and predates the
corrections behind the labelled SO4 and baseline tables (Section~\ref{sec:impl}).

\paragraph{Model-family overlap.}
The judge and the alternative judge are Claude models. Where code, rubrics or specifications in the project were
written with the help of the same model family, self-preference \citeneeded{panickssery2024self} may bias the
judge's verdicts in either model.

\paragraph{Conclusion validity.}
We report three SO4 readings, three treatments of uncertain labels and four judge aggregations. Each alternative is
dated and shown beside the registered one, but we make no correction for the number of readings inspected, and the
labelled SO4 reading was designated after all three were seen.

\paragraph{The LLM-review pilot.}
The pilot uses one prompt written by the authors, one reviewer model, five seeds and two pairs with one or two runs
each, cost-motivated cuts (two large bases and the advisory rules left out), and trees whose firewall outcomes were
known before registration. % src: Docs/ADR.md ADR-036 Consequences (TV-111 one prompt, one model, author-written prose; TV-112 leakage channels; TV-113 tiny n, cost-motivated cuts, known firewall outcomes)

\paragraph{The v1.3 evidence is development evidence.}
Every v1.3 figure in Section~\ref{sec:v13} comes from cases that the v1.3 changes were made against or that were
known while they were made, including the reference projects, the E1 cells and the SO4 seeds. The reference
author-manifests were written with knowledge of the rules, the APG v2 cases were planted by the designer of the
enrichments, and the graph-fidelity disagreements have not been adjudicated by a human. Until the sealed hold-out
run and the human labels exist, these figures support only the claim that each change does what its stated reason
says on the development set. % src: Docs/DiagnosticRuns/v1.3-reference-after-fixes-2026-10-15.md (banner); Docs/DiagnosticRuns/apg2-ablation-2026-10-15.md ("Notes and limits"); Docs/DiagnosticRuns/v1.3-graph-fidelity-2026-10-14.md ("The human_verdict column is empty")

\paragraph{Strength of the oracle and of the external evidence.}
The rule-mutation analysis shows that the development sets detect a third of plausible rule faults, so agreement
with them is weaker evidence than the perfect scores suggest. Convergent agreement cannot reveal a fault that all
four tools share, and it covers only the rules the other tools can express. The external projects are human-written,
but their selection and specifications come from one Claude-family author, and verdict-level results change with
the specification author. The developer-fix and known-groups studies were designed to provide external signals and
did not; we have no evidence yet that the blocking findings predict what maintainers or architects would change.

\paragraph{Other threats.}
We follow the usual construct, internal and external validity categories \citeneeded{wohlin2012experimentation}; the
full register is \texttt{Docs/threats-to-validity.md}.
The judge model and CLI are pinned, but replay reproduces recorded calls rather than the model's behaviour later.
Runtimes come from a shared machine. Four groups of inputs (corpus clones, seeded copies and their manifest, prepared
bases) live outside the repository; their hashes are now recorded but they are not distributed with it.

reported here; without it, the paper evaluates a conformance checker, not the agentic gate that motivates it.

\section{Conclusion}\label{sec:conclusion}

\tool{} compiles a declarative architecture specification into Cypher fitness functions over a TypeScript
architecture graph with constructor-injection and re-export edges, adds an isolated and bounded LLM judge, and
aggregates everything into a health score and a verdict. On the import rules that a path-based checker can express it
performs on par with \dc{}, not better. Its contribution is the breadth of what can be specified and checked, the
graph that makes those checks possible, and an evaluation whose numbers can be regenerated: seeded recall 0.918 with
all misses outside coverage and no false positive once two scorer defects are corrected (labelled F1 0.937), a
real-code precision between 0.33 and 0.79 that is dominated by one test-pairing rule, and a judge whose registered
effect on verdicts is nil and whose unit verdicts are robust to swapping its model. Whether the broader rules are
accurate and useful is the open question: most of them have no seeded ground truth and few labelled findings. An
exploratory pilot suggests that simply asking a coding agent is no substitute for a deterministic gate. Future
work: seed the untested rules, model dynamic imports, widen \edge{FLOWS\_TO}, remove the score's dilution effect,
validate the judge against human labels, audit the labels, and extend the corpus beyond NestJS.
The v1.3 revision addresses several of these on a development set: dynamic imports are modelled, eleven defects
were fixed with their effects attributed, graph fidelity is reported as agreement with the compiler, and no
checkable finding was incorrect. Later v1.3 work adds evidence of a different kind: a second Cypher engine
that agrees with Neo4j on every compared statement, agreement with three independent checkers on the rules they
share, correct blocking findings on human-written code, and verdicts that survive semantics-preserving
transformations. It also adds evidence against over-reading these results: the test oracle misses most mutants that
loosen a rule, and two searches for external validity were null. Its validity rests on the sealed hold-out run, the
human labels and the generation-loop study (Study 2), none of which has been run.
